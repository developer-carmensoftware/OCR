## `16:20` Fix: `GET /admin/alerts` returned a `total` capped at the pagination `limit`

Found while explaining what the Overview page's "Open Alerts" KPI reads from.
`Overview.tsx` calls `fetchAlerts({ status: 'open', limit: 1 })`; the backend computed
`"total": len(rows)` from the SQL result **after** `.limit(1)` was applied — so `total`
could only ever be `0` or `1`, never the real number of open alerts. Same latent bug in
`AnomaliesPage.tsx`'s `limit: 100` call, just far less likely to be hit in practice.

`routers/admin/monitoring.py`'s `list_alerts`: filters extracted into `_apply_filters()`,
run once as a real `SELECT count(*)...` (no `LIMIT`) for `total`, and once as the
existing paginated `SELECT * ... LIMIT :limit` for `data`.

**Verified the actual bug, not just the fix**: inserted 3 temporary open alerts into the
dev DB, hit `GET /admin/alerts?status=open&limit=1` — confirmed `"total": 3` with `data`
still correctly capped at 1 row (would have read `"total": 1` on the old code). Deleted
the test rows immediately after (DB confirmed back to 0 alerts). `ruff check`,
`ruff format --check` clean.

## `17:00` Scalability remediation — "will a page hang for minutes as data grows?"

User asked to check the system was actually ready for large usage-data volume, worried
about a page hanging for minutes. Audited backend query/index/pool behavior and frontend
fetch/render patterns directly (not guesswork) before writing a plan. The real finding
wasn't "one slow page" — it was that **nothing could ever time out**, so a bad query
degrades from slow to hung, and a pool of only 10 DB connections (shared by the whole
app, OCR extraction included) means a few concurrent hangs can stall everything, not just
admin. Four phases, all built and verified against the real dev DB, not just unit-tested.

### Phase 0 — safety net

- `app/database.py`: added a hard 30s `statement_timeout`. **Took two attempts to get
  right, both proven empirically, not assumed**: `connect_args={"server_settings": ...}`
  (the "textbook" asyncpg way) was silently dropped by Supabase's Supavisor pooler — a
  known pgbouncer-family limitation. A `PoolEvents.connect` listener issuing a real `SET`
  query worked once, but Supavisor turned out to reset session GUCs on a *reused* pooled
  connection between logical sessions too (same physical connection, same TCP socket —
  the `SET` still didn't survive). Final fix: re-apply `SET statement_timeout` on every
  `PoolEvents.checkout`, not just `connect`. Proved it actually enforces, not just
  displays correctly: ran `SELECT pg_sleep(35)` and confirmed Postgres killed it at 31.1s.
- `lib/api/client.ts` / `adminClient.ts`: `createApiClient` now accepts a `timeoutMs`
  that's applied automatically unless the caller already manages its own `AbortSignal`
  (OCR extraction's existing per-call `fetchTimeout()` usage is untouched) — `adminFetch`
  set to 30s, matching the backend, so client and server give up together.

### Phase 1 — bound the two genuinely unbounded queries

- `GET /admin/quotas/overview`: added `limit` (le=500, matching `tenants.py`'s
  convention) and a 92-day max date-range guard (→ 400 `ValidationError`) on the
  per-tenant-per-module usage aggregate, which had neither before.
- `GET /admin/usage-summary`: same 92-day guard — this endpoint returns one row per
  date×tenant×module with *no* row limit at all; date-range width is the only lever
  that bounds it short of adding real pagination (out of scope for this pass).
- Along the way, found `GET /admin/tenants`'s `"total"` had the **exact same bug**
  already fixed once today on `/admin/alerts` — `len(rows)` computed *after* `.limit()`,
  so a caller could never actually detect truncation. Fixed the same way (separate
  `count(*)` query), then wired `TenantsPage.tsx` and `LLMLogsPage.tsx` (via the
  existing `has_more` field `get_llm_usage` already returned but discarded) to show an
  inline "Showing N of M — narrow the filter" note when truncated.
- Verified live: oversized ranges 400 on both endpoints with a clear message (and the
  frontend now actually surfaces it — `fetchUsageSummary`/`fetchQuotaOverview` were
  discarding the `detail` field entirely); normal ranges unaffected; `limit=2` on
  `/admin/tenants` correctly returns `total: 4, data.length: 2` against the real 4-tenant
  dev DB.

### Phase 2 — missing indexes + anomaly_alerts retention

- `ocr_tasks` (never purged — 5-year legal retention) had 5 single-column indexes and
  none covering the actual `WHERE created_at range AND deleted_at IS NULL GROUP BY
  module_id, tenant_id, DATE(created_at)` pattern 3 admin endpoints use. Added a partial
  composite index (`OCRTask.__table_args__` + matching migration).
- `anomaly_alerts.resolved_at` had no index at all, and the table now grows daily with
  no retention job since this week's new anomaly-detection cron started writing to it.
  Added a partial index on `created_at WHERE resolved_at IS NULL`, plus a 90-day retention
  job for *resolved* alerts (shorter than the other log tables' 12 months — alerts are
  actionable-in-the-moment, not a compliance record) — a `fn_purge_resolved_alerts()` SQL
  function + `cron.schedule`, mirroring the existing Class-A job pattern exactly
  (`20260615000004_cron_jobs.sql`).
- New migration: `supabase/migrations/20260708170000_scalability_indexes_and_alert_retention.sql`.
  **Not yet applied** (`supabase db push`) — this touches the shared remote DB schema,
  left for explicit go-ahead rather than pushed silently.

### Phase 3 — frontend debounce

- `DateRangePicker.tsx`: local state gives instant input feedback, the parent's
  `onChange` (which drives a fetch in every consumer) is debounced 300ms.
- `PerformancePage.tsx`'s free-text `minMs` filter: same 300ms debounce, mirroring the
  one existing debounce precedent already in this codebase (`ArCustomerProfiles.tsx`'s
  search box) — previously fired one full request per keystroke.
