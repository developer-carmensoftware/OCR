# 2026-08-18

## Uncommitted / in progress

`09:30` **Email-automation notifications now say something and open something.**
`document_posted` / `document_failed` have been written to `user_notifications` since the
pipeline shipped, but the bell was never taught about them: the checklist in
`MEMORY.md` (`TYPE_META` + switch case + en/th keys) was skipped, so a row rendered the
literal string `document_posted` under a generic grey bell, and clicking it navigated to
`#/pricing/orders` — the credit-order history, an unrelated page it landed on only because
`order_id` is `null` for email documents.

  (display name via `OCR_BANK_MAP`), doc no., JV no. (posted only) and the processed
  timestamp, plus a translated `reason_code` and the verbatim pipeline/Carmen error for
  support. There is no tenant-facing email-document page to navigate to — the admin list at

  Escape handling, portal, framer-motion entrance and reduced-motion path already tested there.
- `components/common/NotificationBell.tsx` — `TYPE_META` entries (`FileCheck2`/success,
  `FileWarning`/error; file-shaped so they don't read as the circle-shaped order rows),
  `notifText` cases, and a `document_*` branch in `handleItem` that opens the dialog rather
  than setting the hash. Mark-read behaviour is unchanged.
- `lib/api/notifications.ts` — `document_posted` / `document_failed` added to the type union
  (it had 4 members while the backend wrote 6).
- `i18n/dict.ts` — `notif.docPosted/docFailed`, the `notif.detail.*` labels, and the
  `notif.reason.*` sentences for the five codes the pipeline actually raises

- `styles/components/notification-bell.css` — `.notif-detail*` readout (label/value grid,
  mono values, scrolling raw-error block) and a 2-line clamp on `.notif-bell__text`, since an

`09:50` **Two gaps found on review of the above.**

- **The filename showed as "—" on every existing notification.** The payload only started
  carrying `attachment` an hour earlier, so all 8 live rows predated it. Migration
  `20260818000000_backfill_notification_attachment.sql` puts the name back by joining
  `payload->>'document_id'` to `email_documents.attachment` — applied to prod: 4 of 8 rows
  recovered, the other 4 have no ledger row left (a BU reset deleted them) and keep the "—".
  One-shot; `_finish` writes the key from now on and the table purges at 30 days.
- **A posted document now offers "Open JV in Carmen".** `jv_no` in the payload is Carmen's
  own JV id (the post's `InternalMessage`, e.g. `982`), the same value
  `hooks/credit-card/useOcrSubmission.ts` hands to `/glJv/{id}/show`, so the link is
  `getCarmenUrl()` and nothing new. Rendered as an `<a target="_blank">` in the dialog body,
  **not** through CustomModal's `onCancel` slot: that slot is what Escape fires, so wiring
  it here would make dismissing the dialog open a Carmen tab.

`10:05` **The teal button was broken in dark mode, and not only the new one.**
Measured, not eyeballed (WCAG ratios from the OKLCH values in `base.css`):

- `.btn-success` is `color: white` on `var(--emerald)`. Light theme's emerald is a dark
  green (L 0.62); **dark theme's is a light teal (L 0.72), so white lands at 2.37:1** —
  below the 3:1 large-text floor, let alone 4.5:1. Now ink (`oklch(0.18 0.01 188.43)`) on
  the same fill: **7.91:1**, hover **6.05:1**. Specificity alone beats the base rule and its
  hover, so no `!important`.
- **`--emerald-mid` was never defined for dark**, so every use fell through to the light
  theme's `oklch(0.88 0.05 145)` — a pale mint, wrong hue (145 vs 188) and far too bright.
  It is `.btn-success`'s border *and its hover fill*, so hovering turned the button pale
  green with white text at **1.41:1**. Also fixes the halo on `.status-badge.success` and
  `.modal-icon.success`. Now `oklch(0.4 0.06 188.43)`, matching `--teal-mid`.

Rest of the dialog measured clean in dark: labels 4.70:1, values 12.69:1, message 8.54:1,
raw-error block 7.99:1, success icon 6.49:1, error icon 4.85:1.

**Not fixed, pre-existing and app-wide:** `.btn-primary` in dark is white on `--primary`
at **3.23:1**, and `.btn-success` in *light* is white on emerald at **3.43:1**. Both fail AA
for body-size text. Fixing either means moving a shared token that every screen uses — a
design-system decision, not a bug this change introduced.
