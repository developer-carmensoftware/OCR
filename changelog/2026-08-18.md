`11:00` **Switching Email Automation off destroyed the mail that arrived while it was off.**
Started as a suspicion that the poll ignores the enable toggles — it does not. `resolve_by_tag()`
carried `WHERE enabled IS TRUE` and `match_rules()` filters `is_active` as its first line, both
ahead of `consume_document()` and the LLM call, both covered by tests. What was actually wrong
sits one step earlier: `_fetch_unseen()` marks the whole batch `\Seen` on the way in, *before*
anyone knows who a message belongs to. A switched-off BU then fell out as `unrouted` — no
`email_documents` row, no notification, and the mail permanently read. Turn the feature back on
and nothing arrives; every statement from the off-period is gone with no way to re-run it. The
out-of-credits path has handed mail back via `_unmark_seen()` since day one; being switched off
is the same kind of temporary, and was not treated that way.

### Backend

- `services/email_ingest_service.py` — `_process_message()` now answers `retry_later` (the
  existing hand-back path) for the three reversible states: `enabled = false`, no active package,
  and — via `_HOLD = (InsufficientCredits, ModuleDisabled)` — the module being switched off for
  that tenant. The tag also goes into `exhausted`, so the rest of that BU's mail in the same batch
  costs nothing. Only an unknown tag or a missing tenant row is still dropped as `unrouted`: there
  is nobody to hold mail for.
- **`ModuleDisabled` used to be filed as `unreadable_document`** — a red row and a
  `document_failed` in the customer's bell for a module *we* switched off, pointing whoever
  debugged it at a PDF that was fine.
- `services/email_settings_service.py` — `resolve_by_tag()` no longer filters on `enabled`. It
  answers identity; the caller decides permission. One `None` cannot mean both "no such tag"
  (drop it) and "known tag, paused" (keep it).
- **Two bounds, because held mail stays unseen and would otherwise pile up for ever**
  (`imap_batch_size` is 10, and SEARCH answers oldest-UID-first, so one switched-off BU whose bank
  mails daily would have filled every batch within ten days and silently starved every other
  tenant):
  - `_fetch_unseen()` takes the **newest** matching UIDs (`[-limit:]`), so a backlog can only ever
    use capacity nothing newer wants.
  - `SEARCH … SINCE` floor from the new `IMAP_HOLD_DAYS` (default 14) — the retry window. Past it
    a held message drops out of every poll and simply stays in the mailbox. `_fetch_confirmations()`
    got both for the same reason: a confirmation for a tag nobody is waiting on is never marked
    seen either, and five of those would pin the sweep to stale mail permanently.
  - Ceiling, stated in the code: a poller outage longer than `IMAP_HOLD_DAYS` ages out real mail
    too. `#/admin/email` cron health is what catches that.
- `run_ingest()` summary carries `retry_later` in its initial shape, not only when it happens.

`11:40` **A load test for the thing that actually costs money: many BUs, one mailbox, one
poll.** `scripts/email_multibu_loadtest.py` (new, no production code touched). The existing
load report measures `POST /credit-card/extract` over HTTP, which never touches routing, the
ledger, credits or posting; nothing measured the email pipeline, and nothing had ever run a
batch with several BUs' documents interleaved in it.

Two questions it answers:

- **Does a mixed batch stay attributed to the right BU?** `_process_attachment` sets
  `current_tenant_id` and `current_carmen_uri` as ContextVars per attachment. A leak means a
  credit charged to one company and a JV posted into another's books — the one failure
  unattended posting cannot undo. Messages are interleaved BU1,BU2,BU3,BU1,… on purpose, and
  every assertion reads `email_documents` / `ocr_tasks` / `credit_cards` / `llm_usage_logs`
  back out of the database and compares against the tag on the envelope, never against what
  `run_ingest` returned. The captured JV payloads are checked to carry their own BU's host.
- **Does one poll finish before the next tick?** Attachments are serial and `_poll_lock`
  skips an overlapping poll, so "many BUs at once" is one queue. The script reports per
  document p50/p95, whole-poll wall clock, and the documents that fit in the 10-minute cron.

Also reports tokens and USD from `llm_usage_logs` split by `call_type` — `extract` is the
vision call every document makes, `suggest` is the GL fill a BU only pays for until
`fill_missing_mappings` has learned its payment types.

Modes: `batch` (the matrix, `--gates` adds the duplicate and tax-ID cases), `concurrent`
(`_process_attachment` under `asyncio.gather` at C=1/2/4/8 — a shape we do not ship, run to
find the ceiling and to prove the ContextVars survive parallelism before anyone parallelises
the poll), `overlap` (a second `run_ingest` mid-flight must answer `busy` and charge nothing
twice), `cleanup`.

**Carmen is a dry run.** `post_gljv`, `post_input_tax`, `get_tax_profiles`, `get_account_codes`
and `get_departments` are patched on `email_ingest_service` — the names it imported them
under, not on `carmen_service`, which would leave this module bound to the originals. No HTTP
request for Carmen leaves the process. The LLM, `consume_document`/`refund_document`, the
ledger and every DB write are real, because those are what is being measured.

`es.foreign_tax_id` is patched to None **for the matrix only**: a real bank document prints a
real customer's TIN, which is very likely already registered to the dev BU, and every document
would park as `tax_id_mismatch` before the happy path ran once. The gate keeps its own
unpatched case under `--gates`.

Safety: refuses to start if `DATABASE_URL` names the production project; appends to a
`LoadTest` folder it creates rather than `AR Agent`, which the deployed cron is polling;
scratch tenants (`loadtest-%.local`, the pattern `load_test_v2.py --mode cleanup` already
knows) and every row they own are deleted in a `finally` — after the numbers are printed.
`--dry-check` swaps **both** LLM calls for canned answers so the harness can be proven before
any money is spent.

`13:00` **Five more ways a customer's mail was lost, all in the ingest path.** A review
after the hold-unread change above. Same root every time: `_fetch_unseen()` marks the whole
batch `\Seen` *before* anyone knows who a message belongs to, so every path that then
declines to write a ledger row throws the message away permanently. Three of the five
destroyed a document silently — no row, no notification, no log anyone would go looking for,
and no retry anywhere in this feature to save it.

### Backend — `services/email_ingest_service.py`

- **F1 · The IMAP calls spoke sequence numbers, not UIDs.** `box.search`/`fetch`/`store`
  are per-session and shift down on any expunge; the variable was named `uid` throughout,
  which is what hid it. `_fetch_unseen` flagging inside its own connection was fine —
  `_set_seen` was not: it opens a **new** connection minutes later, so `_unmark_seen`
  (hold-and-retry) and `_mark_seen` (confirmation sweep) both stored by numbers captured in
  a previous session. Anyone deleting a message from the `AR Agent` label mid-poll meant the
  held mail stayed `\Seen` (lost) while an unrelated message was silently marked unread. Now
  `box.uid("SEARCH"/"FETCH"/"STORE", …)` in all three functions, via a new `_uid_search()`.
  UIDs are stable for the life of the mailbox, which is what this code always assumed.
  **Measured on the live `AR Agent` folder, read-only, 13:20:** it is already off by one —
  `UID SEARCH ALL` answers `2…16` where `SEARCH ALL` answers `1…15`. So the newest message
  is UID 16 / sequence 15, and the old `_set_seen` storing "16" in a fresh connection
  addressed a sequence number that does not exist (`FETCH 16` → nothing). Every hand-back
  on this mailbox was already hitting the wrong message or none at all.
- **F2 · A crash mid-poll lost every message after the failing one.** One DB blip on message
  3 of 10 left 4–10 `\Seen`, unprocessed, and — never having reached `_claim` — recorded
  nowhere at all. `run_ingest` now counts what it has attempted and hands the untouched tail
  back. The message that actually raised stays flagged **on purpose**: returning it would
  re-crash the next poll forever, and the FAILED `job_runs` row is its trail.
- **F3 · A mail whose attachments were all unsupported left no trace.** `_process_message`
  returned `skipped` on `not attachments` before the tag was even resolved, so an `.xlsx`, a
  `.rar` or a bank's `.zip` of CSVs produced nothing: mail read and gone, and `#/admin/email`
  had nothing to show the customer who asked where Tuesday's document went. This is the exact
  case the ledger table was created for — `20260803000000_email_automation.sql` names *"no
  attachment"* in its header. `_attachments()` now returns `(accepted, rejected)`; a message
  that carried a named part and had **every one** refused resolves its tag and writes one
  `skipped` / `unsupported_attachment` row per rejected name. A zip that yielded nothing
  readable is reported under its own name. A message naming **no file at all** stays a free
  silent skip — bank "your statement is ready" notices must not fill the ledger. Costs
  nothing: it exits far ahead of `consume_document`.
- **F4 · Two attachments with the same filename: the second was silently dropped.** `_claim`
  dedupes on `(tenant_id, message_id, attachment)`, so the second `report.pdf` violated the
  unique index and was filed "already handled" without being looked at. Not hypothetical —
  `_unzip` strips directories, so a bank's `2026/01/report.pdf` and `2026/02/report.pdf`
  arrive as two identical names in one message. New `_unique_names()` renames the second and
  later occurrences to `report (2).pdf`, applied across accepted **and** rejected names at
  once since they share that index. The suffix goes before the extension deliberately:
  `validate_magic_bytes()` and `match_rules()` both read the extension.
- **F5 · Mail past `IMAP_HOLD_DAYS` disappeared with no counter anywhere.** The bound added
  at `11:00` is right, but past the window a message drops out of every poll silently, so a
  poller outage longer than 14 days loses real mail with no symptom at all. `_fetch_unseen`
  now runs one extra `UID SEARCH` per poll — same terms minus `SINCE`, no FETCH, on the
  connection already open — and returns the difference as `beyond_window`. `SMALLER` is kept
  in both searches or an oversized *recent* message would be miscounted. `run_ingest` puts it
  in the summary and logs a WARNING; `_record_run` opens an `email_ingest_beyond_window`
  anomaly alert (WARN, tenant `system`), deduped while open, so a standing backlog raises one
  alert rather than one every ten minutes.
