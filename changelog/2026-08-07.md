## `10:15` Email Automation — our own settings screen, and Gmail's confirmation code

### Why

`CARMEN_INTEGRATION.md` §2 puts the settings screen on Carmen's side, so the API had no
client at all: the only way to exercise `PUT /settings` end to end was curl, and nobody
could see what the screen Carmen has to build actually looks like. And the Gmail
auto-forward setup still needed one of us on a call, because Google mails its
confirmation code **to the shared ingest mailbox** — the one place the customer cannot
open.

### Backend

- `_process_message` now catches mail from `forwarding-noreply@google.com` **before** the
  attachment check. That ordering is the whole fix: a confirmation mail carries no
  attachment, so it was being dropped on the first line of the function. The code is read
  out of the subject (`(#123456789)`), stored against the BU the envelope tag names, and
  returned by `GET /settings` — [`services/email_ingest_service.py`](../backend/app/services/email_ingest_service.py).
  Outcome is `skipped`, deliberately not `unrouted`: that counter alerts at five per poll
  and exists to catch real documents going nowhere.
- `gmail_confirm_code(sender, subject)` checks the **sender**, not just the pattern —
  `(#123456789)` is an unremarkable thing for a bank to put in a subject line, and a false
  positive would file a real invoice as a confirmation code.
- `es.record_gmail_code()` never raises: a poll carrying real invoices must not fail
  because a convenience write did — [`services/email_settings_service.py`](../backend/app/services/email_settings_service.py).
- `to_response()` gains `gmail_confirm: {code, at} | null`. Added there rather than in
  `build_settings_response` so `GET` and `PUT` cannot drift apart.
- Tests +8: `test_email_ingest_routing.py` (the pure matcher, incl. the display-name
  sender form and the bank-subject false positive) and `test_email_ingest_pipeline.py`
  (branch fires before the attachment check, no-tag case stays quiet, a bank document
  with `(#…)` in its subject still posts). Email suite green.

### Frontend — `#/email-settings`

- New page, English only, reachable by URL and deliberately **not linked from Home** while
  it is a test surface — [`pages/EmailSettings.tsx`](../frontend/src/pages/EmailSettings.tsx).
  Three-step checklist (tax IDs → banks → forwarding address + Gmail code) ported from the
  `feat/email-flow` branch's `SettingsView`, reworked onto the current contract; the
  connection card on top carries host/BU, the enable toggle and the §2.6 posting
  credential.
- It calls `/api/v1/carmen/*` **the way Carmen does** — the user's raw Carmen token in
  `Authorization` with no scheme, proven against their own Carmen on every request. That
  means the 401 / 502 / 429 / 409 paths are exercised, which the admin-JWT shortcut would
  have skipped entirely. The token is stashed from the SSO URL param
  ([`hooks/useCarmenSSO.ts`](../frontend/src/hooks/useCarmenSSO.ts)) and cleared by
  `clearToken()` alongside the session JWT.
- [`lib/api/emailAutomation.ts`](../frontend/src/lib/api/emailAutomation.ts) is a plain
  `fetch`, **not** `apiFetch`, for a second reason beyond auth: `apiFetch` treats any 401
  as "our session died" and fires `ocr:unauthorized`, which wipes tenant storage. A 401
  here means *Carmen* rejected the token — different failure, different remedy, and §2.1
  asks for it to be rendered apart from a 502.
- [`hooks/email-settings/useEmailSettings.ts`](../frontend/src/hooks/email-settings/useEmailSettings.ts):
  no Save button and no dirty tracking. `PUT /settings` is a full replace that returns the
  same body `GET` does, so every mutation sends the complete state and swaps in the
  response — one call per change, which also matters because the settings endpoints are
  rate-limited to 20/min per IP.
- Bank options come from `GET /bank-codes`, never the frontend `BANKS` constant (§2.3 is
  explicit that a second hardcoded list is what that endpoint exists to prevent).

## `11:40` First live end-to-end email post — and two infra findings

### It works

BBL fee invoice forwarded to `boonyawat.asu+41645ee4@gmail.com` → poll → **JV 973 in
Carmen**, confirmed on their screen. `email_documents` = `posted`, no note (so
`_post_input_tax` succeeded too), `credit_cards.submitted_at` stamped, charged against the
subscription allowance (`docs_used 0 → 1`, no `credit_ledger` row — correct, the ledger
only records top-up spend). Two LLM calls, $0.000485: the vision extract plus
`_suggest_missing_mappings`, which AI-filled and **saved** `'002205903321' → GEN/1021009`.
That merchant number arrived as a payment-type label and is now deterministic for every
later document — worth a human look before the next one.

### Why nothing happened until someone asked

`job_runs` for `email-ingest` was **empty**. Nothing schedules the poll: the code says so
itself at `routers/email_automation.py:337`. Every part of the setup was already correct —
tag, sender, filename pattern, entitlement, token — so this looked like a broken pipeline
and was only ever a missing trigger.

`INTERNAL_JOB_TOKEN` is also **absent from `backend/.env`**, so
`POST /email-ingest/run` 401s (the dependency falls through to the admin-JWT branch). The
Vault side is fine — `vault.secrets['internal_job_token']` holds a real 64-char value, not
the placeholder. Only the `.env` copy is missing.

### Dev cron was calling the prod app (fixed)

`system_configs['app.base_url']` on the **dev** database held the **prod** Render URL, so
all three Class-B cron jobs on dev had been making HTTP calls into production:
`pricing-sync` (syncing prod's model pricing every 8h, on top of prod's own job),
`anomaly-detection` (writing `anomaly_alerts` rows into prod), and `keep-warm` (keeping
prod warm while dev cold-started). Repointed to `…-xntb.onrender.com` by hand — this key
is per-environment, which is why `20260615000004` seeds it as `""` rather than pinning it
in a migration.

Prod's own copy audited afterwards and it is correct (`…onrender.com`, set 2026-07-21);
its three Class-B jobs have been answering 200 every 10 minutes throughout. Nothing about
the dev misconfiguration broke prod — it only got called twice.

### Dev and prod shared one internal job token (rotated)

`vault.secrets['internal_job_token']` held the **same** 64-char value on both databases
(fingerprint `4db2e2fe`), so a leak of the dev secret would have opened prod's maintenance
endpoints — the five `admin/maintenance` routes plus both email-ingest ones. Dev has been
given its own (`61a37e3e`), overwriting rather than adding to both its Vault row and
`backend/.env`, so the old value now exists only on the prod side. Prod untouched.

`keep-warm` is unaffected either way — it is a bare `net.http_get` to `/api/v1/health`
with no `Authorization` header. Only `pricing-sync` and `anomaly-detection` present the
token, so those are the two that need the dev Render instance's env updated to match.

### Still not done

No cron for `email-ingest/run` or `email-ingest/health`. The shape is already written out
in the `check_token_health` docstring, including the 10-minute (not 5) reasoning and the
`value #>> '{}'` unwrap that `20260715010000` exists because of. Blocked on the deployed
dev backend having IMAP settings and `INTERNAL_JOB_TOKEN` in its own Render env — the
local `.env` is not what the cron will hit.

and the second trades a real guarantee — junk PDFs currently cost nothing — for one less
form field.
