### Backend

- `_process_message` now catches mail from `forwarding-noreply@google.com` **before** the
  attachment check. That ordering is the whole fix: a confirmation mail carries no
  attachment, so it was being dropped on the first line of the function. The code is read

- `es.record_gmail_code()` never raises: a poll carrying real invoices must not fail
  because a convenience write did — [`services/email_settings_service.py`](../backend/app/services/email_settings_service.py).
- `to_response()` gains `gmail_confirm: {code, at} | null`. Added there rather than in

  sender form and the bank-subject false positive) and `test_email_ingest_pipeline.py`

### Frontend — `#/email-settings`

- New page, English only, reachable by URL and deliberately **not linked from Home** while
  it is a test surface — [`pages/EmailSettings.tsx`](../frontend/src/pages/EmailSettings.tsx).
  Three-step checklist (tax IDs → banks → forwarding address + Gmail code) ported from the
  `feat/email-flow` branch's `SettingsView`, reworked onto the current contract; the
  connection card on top carries host/BU, the enable toggle and the §2.6 posting
  credential.
- It calls `/api/v1/carmen/*` **the way Carmen does** — the user's raw Carmen token in
  `Authorization` with no scheme, proven against their own Carmen on every request. That
  means the 401 / 502 / 429 / 409 paths are exercised, which the admin-JWT shortcut would
  have skipped entirely. The token is stashed from the SSO URL param
  ([`hooks/useCarmenSSO.ts`](../frontend/src/hooks/useCarmenSSO.ts)) and cleared by
  `clearToken()` alongside the session JWT.
- [`lib/api/emailAutomation.ts`](../frontend/src/lib/api/emailAutomation.ts) is a plain
  `fetch`, **not** `apiFetch`, for a second reason beyond auth: `apiFetch` treats any 401
  as "our session died" and fires `ocr:unauthorized`, which wipes tenant storage. A 401
  here means *Carmen* rejected the token — different failure, different remedy, and §2.1
  asks for it to be rendered apart from a 502.
- [`hooks/email-settings/useEmailSettings.ts`](../frontend/src/hooks/email-settings/useEmailSettings.ts):
  no Save button and no dirty tracking. `PUT /settings` is a full replace that returns the
  same body `GET` does, so every mutation sends the complete state and swaps in the
  response — one call per change, which also matters because the settings endpoints are
  rate-limited to 20/min per IP.
- Bank options come from `GET /bank-codes`, never the frontend `BANKS` constant (§2.3 is
  explicit that a second hardcoded list is what that endpoint exists to prevent).

## `15:20` Email Automation — `owner_emails`, an optional second layer before the LLM

`owner_emails` on `email_ingest_settings`: the BU's own addresses. **Empty is the default
and accepts anything** — the shape `filename_patterns` and `bank_sender_email` already
use. Non-empty means a message must carry one of them in `From`/`To`/`Cc`, or its
attachments are recorded `sender_not_allowed` and never scanned, at no cost.

### Why it is a layer and not the router

This started as "can we just route the BU by `To:`". That cannot work and the failure is
nasty: on an auto-forward `To:` is still the *customer's* address, so a `To:`-router
passes every hand-sent test and then drops every real auto-forward. `To:`/`From:`/`Cc`
are also written by whoever composed the message, unlike the `+tag`, which a mail server
had to actually deliver to. So the three signals now stack, each doing what it can prove:

```text
tag        → whose BU        envelope, server-enforced
owner_emails → may it spend  headers, free, optional, forgeable
tax ID     → whose document  after extract, the only one that sees the paper
```

- Gate lives in `_run_document` **before** `match_rules` — coarsest question first, so
  mail that is not this BU's at all is not filed under the narrower "your pattern was too
  tight" reason. `refund=False`: nothing was charged yet.
- `_fetch_unseen` now also carries `From`+`To`+`Cc` as one string (`people`). Matched as a
  case-insensitive substring, so `"Accounting" <a@b.com>` needs no parsing — the same way
  `bank_sender_email` is matched.
- **A list, not one address, and the UI says why.** The two arrival modes put the customer
  in different headers: auto-forward → `To:` (the mailbox), manual forward → `From:` (the
  employee). Registering only the mailbox silently refuses every hand-forward. That case
  is pinned in `test_sender_allowed` so it stays a deliberate behaviour rather than a bug
  someone "fixes" by matching more headers.
- Validation is loose on purpose (`_looks_like_email`: an `@`, a dotted domain, no
  spaces). A rejected address is one the customer cannot register at all; a wrong one only
  refuses their own mail, visibly, in their own document history. `422 invalid_email`.
- [`20260807010000_email_owner_emails.sql`](../supabase/migrations/20260807010000_email_owner_emails.sql)
  — `jsonb not null default '[]'`. **Applied to dev**, along with `20260807000000`, which
  the 10:15 entry above still calls pending — it is not.
- `CARMEN_API_SPEC.md` §1 + §2, `CARMEN_INTEGRATION.md` §2.3 and the `reason_code` list.
  Tests +11. Email suite green, 137 passed.

### A real credit-guard bypass, found by the harness's spend check

[`scripts/email_ingest_e2e.py`](../scripts/email_ingest_e2e.py) appends 20 fixtures into
`ocr-test` and asserts on the resulting `email_documents` rows — 17 free cases (no
attachment, bare/unknown/unpaid tag, the Google-confirm-code branch, both `owner_emails`
shapes, password/size/count limits, `Received … for` fallback, exact-dedupe) plus 3 paid
ones. Every reason code every ledger row's `status`, not just its `reason_code` — that
distinction is what caught the bug below; the first pass had all 20 reason codes right
while still charging a credit it should not have.

`P14` (a `.pdf` that is a GIF in disguise) landed `failed` with 22 `ocr_tasks` rows created
across a run that should have created zero. `ensure_pdf_openable`'s own docstring says it
exists to stop exactly this "*before the caller commits side effects (e.g. consuming a
document credit)*" — it didn't. `fitz.open(stream=b"GIF89a…", filetype="pdf")` does not
check the header when the type is forced; it returned a **one-page document**, and the
failure only surfaced inside extraction, after `consume_document()` and `create_task()`.
`validate_magic_bytes` didn't catch it either — GIF *is* a supported signature; it never
compares content against the claimed extension.

Fix, in [`pdf_utils.open_pdf`](../backend/app/utils/pdf_utils.py): reject anything without
a `%PDF` marker in the first 1KB before calling into PyMuPDF at all. Second half in
[`email_ingest_service._open_or_fail`](../backend/app/services/email_ingest_service.py):
catch the resulting `ExtractionError` as `_Skip("unreadable_document", refund=False)`
instead of letting it fall through to the generic handler, which files everything as
`failed` — a junk attachment must read as the free `skipped` it always was, not a red row
on Carmen's screen. Same guard, so **the interactive upload path had this hole too**.

Regressions: `test_bytes_with_no_pdf_header_are_refused` (GIF/PNG/plain-text bytes, all
missing `%PDF`) in `test_pdf_utils.py`; the harness itself is the ingest-side regression
test now that `Case.status` is asserted alongside `reason_code`.

- **`06-limits` needs 19 burns, not 20**, and needs to run as part of the whole collection

  `00-auth/wrong-carmen-token` already spends one call against the same 60s window before
  `06-limits` starts. Running `06-limits` alone needs 20. Re-running the **whole**
  collection twice inside 60 seconds trips it earlier than either count predicts — the
  window is doing its job, not malfunctioning; wait out the minute or restart the backend
  (resets the in-memory counters) before comparing two runs.
- `runtime.scripts` in this CLI's `.yml` format is an array of `{type, code}`, and its
  sandbox does not expose `require()` — a `preRequest` script looping with `axios` silently

  needs no scripting sandbox to behave correctly.

### Noted while looking, not acted on

  not treat it as one. Still no DKIM check: it would cover auto-forwards only.
