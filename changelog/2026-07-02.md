## Backend — fix double-VAT on tax invoice (accounting-critical)

`HH:MM` **fix(credits): tax invoice was double-VATed → Carmen AR received the wrong total** — the approve/decide flow issued the TAX_INVOICE by passing `order.amount_thb` (which is the **gross**, VAT-inclusive price the customer paid) into `issue_document`, whose contract is a **net** input that then gets VAT added on top. Net 490 → the tax invoice stored subtotal 524.30 / vat 36.70 / total **561.00** instead of 490 / 34.30 / **524.30** (`gross × 1.07`). `post_ar_entry` then forwarded the inflated total (and embedded it in the Description) to Carmen AR. The proforma was always correct (issued from net); this affected **every** tax invoice issued via approve.

- Fix ([admin/credits.py](backend/app/routers/admin/credits.py)): issue the tax invoice from the proforma's authoritative `subtotal` (net) so it reproduces the proforma exactly; fall back to `split_inclusive(order.amount_thb)` when no proforma. Added `split_inclusive` import.
- Regression guard ([test_admin_credits_api.py](backend/tests/integration/test_admin_credits_api.py)): `_proforma` fixture now carries subtotal/vat/total; the approve test asserts `issue_document` is called with the **net** (990), not the gross (1059.30).
- Data remediation ([scripts/fix_double_vat_tax_invoices.sql](scripts/fix_double_vat_tax_invoices.sql)): audit + correct already-issued double-VATed tax invoices from their proforma, plus a list of orders already posted to Carmen AR that finance must reverse/re-post (incl. `AI-202607-0005`). Carmen has no delete API from this app.
- **Ops**: needs `supabase db push` (applies `buyer_tel` column the ORM now references) + backend restart for this fix **and** the 3-line AR remark (Contact Name / Tel. / Email) to take effect — the observed single-line `Contact Name : -` was stale pre-edit code.
