# 2026-09-14

## Package change: stop blocking, start warning

`10:58` Two separate gates stopped a subscriber from changing plan mid-term, and both
decided for the customer how to spend their own money:

1. **Downgrade** — a tier with fewer docs than the active plan: `PlanCard`'s CTA was
   `disabled`, and `create_order` 409'd with "Downgrade is not supported."
2. **Annual lock** — an annual subscriber could not switch the billing toggle to monthly
   at all; same 409 behind it.

Both are gone. What replaces them is one confirmation at **slip upload** — the first step
where money actually turns on, since an order on its own is free to cancel.

### Backend

- `services/credit_service.py` — **deleted `purchase_block_reason()`**. With both rules
  relaxed it returned `None` on every path.
- `routers/credits.py` — deleted the guard block in `create_order`, which also removed the
  `active_subscription()` call and the `SELECT CreditPack` that fetched the current tier
  (two queries off the order-creation path). Both imports went with it.
- No schema, migration, or approve-path change: `activate_subscription()` already
  supersedes the active row unconditionally, and its docstring says so — *"keeps the unique
  index safe if the guard is ever relaxed."*
- `tests/unit/test_credit_service.py` — `TestPurchaseBlockReason` deleted.

### Frontend

- `constants/billing.ts` — new `planChangeLoss(packCode, packCredits, period, sub)` →
  `'quota' | 'period' | null`. One predicate, two call sites.
  - `'quota'` — the new tier allows fewer docs/month.
  - `'period'` — annual traded for monthly, **same tier**. Quota is unchanged, so a
    credits-only comparison misses it, yet the prepaid months are forfeited: the costlier
    of the two losses. Unlocking gate 2 without this branch would have left a money hole.
  - An upgrade resets the period too, but buys more quota — warning there is noise.
- `components/pricing/SlipUpload.tsx` — new optional `warning?: string`. Set ⇒ the Confirm
  button opens `CustomModal` (`type="warning"`, `confirmVariant="danger"`, `busy`) instead
  of uploading. **The guard lives in the shared component, not in the callers**:
  `PendingOrderBanner` reaches this button without passing through `CheckoutFlow`, so a
  per-caller guard would have shipped half-covered.
- `CheckoutFlow.tsx` / `PendingOrderBanner.tsx` — take `sub`, build the message. Both pages
  that render them (`Pricing.tsx`, `OrderHistory.tsx`) already held an `ActiveSubscription`
  from `getUsage()`, so this is prop-passing, no new fetch and no new server field.
- `PlanCard.tsx` — dropped `isDowngrade` from `disabled` only. The `Downgrade` CTA label and
  the `.plan-cta-tip` / `.sr-only` note stay; the note now says what switching costs.
- `Pricing.tsx` — deleted `annualLocked`, its effect, the monthly toggle's `disabled`/`title`
  and the grey note paragraph.
- `tutorial/screens.tsx` untouched — it passes no `sub`, so the fixture shows no warning.

### Copy (`i18n/dict.ts`, EN + TH)

- **Deleted** `plan.monthlyLockedNote` — its gate is gone.
- **Rewrote** `plan.downgradeNote`: "Downgrading is available when your current plan ends"
  became false the moment the CTA went live.
- **Added** `slip.changeTitle`, `slip.changeWarnQuota` (`{prev}` → `{next}` documents),
  `slip.changeWarnPeriod`.
- The wording is **"once this payment is approved"**, not "immediately". The plan actually
  changes when the *admin approves the slip*, not on upload — "immediately" would have the
  buyer reopen the page, still see the old quota, and report it as a bug.
- Per the agreed scope the warning states the quota numbers and **does not mention the
  top-up balance**, even though `tenant_credits` is in fact untouched by a plan change.

## `scripts/seed_browser_session.py` — drive the UI in a real browser

`11:45` Nothing in this repo could open the app in a browser, because the app is SSO-only
and `get_current_session` ([dependencies.py:125](../backend/app/auth/dependencies.py)) needs a
live `ocr_sessions` row, not just a validly signed JWT — the row is where the encrypted
Carmen token lives, so a hand-minted token gets 401 "Session not found or revoked". That is
the actual blocker to browser testing; the browser driver never was.

The script writes one session row and prints the `sessionStorage.setItem` snippet to paste
into DevTools. It **reuses `create_session_jwt` and `encrypt_carmen_token`** from
`app.auth.session` rather than re-implementing Fernet and the claim set — the two must agree
or the row decrypts to garbage at request time. Both imports are deferred into `main()` so
`--help` works without `app.config` validating the whole environment first.

- `--revoke` deactivates what it wrote, and a fresh run revokes its own older sessions first,
  so repeated use doesn't pile up live sessions. Rows are tagged by `carmen_user_id =
  'seed-browser-session'`, which is what scopes both.
- **The Carmen token it stores is a placeholder.** Read-only screens and the whole purchase
  flow work (checkout sends its own buyer block); anything that calls Carmen ERP does not —
  posting a JV, and `company-profile`, which falls through to an empty form. Documented in
  the script's own docstring so nobody mistakes it for a way to test posting.
- Checked by hand with `ruff check --config backend/pyproject.toml` and `ruff format --check`,
  since CI's ruff job only covers `app/` and `tests/`.

`12:05` The Carmen credential is read from **`CARMEN_AUTHORIZATION`** in `backend/.env`
(falling back to a placeholder, with a printed warning, when unset) — so Carmen-backed
screens work too, not just the Carmen-free ones. Store it **whole**: `carmen_service` sends
it verbatim (`"Authorization": carmen_token`, line 37 — no scheme bolted on), which is why
the value starts with `direct `. Stripping that prefix yields a session that 401s against
Carmen with nothing in the logs to explain it. The var is not in `.env.example` — it was
removed as dead in 2026-07-08 and survives as a hand-maintained local value.

### Verified against the running stack

`12:10` With `:8010` and `:3010` up, a seeded session was used to exercise the real API —
not mocks — on `dev.carmen4.com/carmencloud`, whose live plan is **`sub_starter`, 200
docs/month, 97 used**:

- `POST /credits/orders {"pack_code": "sub_lite"}` (100 docs, i.e. a genuine downgrade from
  200) returned **HTTP 200**, order `94d62a5a…`, proforma `AI-202609-0003`. That exact call
  returned 409 "Downgrade is not supported." before today.
- The live `GET /credits/orders` and `GET /auth/usage` payloads were fed verbatim into a
  throwaway render of `PendingOrderBanner`; the dialog came back containing
  **"from 200 to 100 documents"**. Real API shape → real component → real copy.
- The test order was then cancelled (`status: void`); zero open orders remain, and the
  subscription row was untouched.

**`--bu carmen` was asked for but cannot show this feature**: that tenant's
`/auth/usage` returns `subscription: null`, so `planChangeLoss` correctly returns null and
there is nothing to downgrade from. `carmencloud` is the only tenant in this database with
an active subscription, which is why the check ran there.

Paired with this, `playwright` was registered as an MCP server for this project
(`claude mcp add playwright npx @playwright/mcp@latest`, local config) so the agent can drive
the browser directly. Reports healthy; MCP tools only enter a session's registry at startup,
so it takes effect on the next Claude Code session.
