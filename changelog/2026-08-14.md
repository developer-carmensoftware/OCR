## Uncommitted / in progress

`12:00` **AP Invoice is charged per page, not per document.** `/api/v1/ap-invoice/extract`
consumed exactly one document per request no matter how many PDF pages went to the vision
LLM — a 5-page selection cost the tenant 1 while costing us 5 pages of tokens. A page is now
a document: select 2 pages → 2 documents. Bounded by `MAX_PAGES_PER_CALL` (5), so the most a
single scan can cost is 5. **Credit Card OCR is unchanged** (1 per file) — it has no page
selector and no UI that would show the user a price first.

### Backend

- `utils/pdf_utils.py` — `ensure_pdf_openable()` returns the page count (`int | None`)
  instead of discarding it. It already opened and counted the document; pricing the scan
  would otherwise mean opening it a second time. The credit-card and email-ingest callers
  ignore the return, unchanged.
- `utils/pages.py` — new `billable_pages(page_count, selected)`: non-PDF → 1; explicit
  selection → in-range indices capped at `MAX_SELECTED_PAGES`; no selection → whole PDF
  capped the same way. Floor of 1 keeps charge/refund symmetric when every selected index
  is out of range (the service rejects that a moment later and the router refunds). It
  lives beside `parse_selected_pages` because it has to mirror the page-resolution branches
  in `extract_ap_invoice_data()` — the two must move together.
- `routers/ap_invoice.py` — `consume_document(increment=pages)` /
  `refund_document(charged, increment=pages)`. Charge ordering unchanged: a locked or
  corrupt PDF and a disabled module still fail before anything is charged.
  Known ceiling, marked `ponytail:` — the whole N draws from one pool, so a tenant with 3
  subscription documents left who scans 5 pages pays 5 credits and strands the 3. Same
  behaviour the credit-card batch path has always had; split across pools only if reported.
- Tests — new `tests/unit/test_pages.py` (16 cases across `parse_selected_pages` +
  `billable_pages`; the parser had no test file at all before). `test_ap_invoice_router.py`
  gains `TestPerPageCharging`: 2-page selection → `increment=2`, no selection on a 3-page
  PDF → `increment=3`, 1-page PDF → `increment=1`, and a failed extraction refunds the 2 it
  charged. `_valid_pdf_bytes()` takes a page count now.

`12:30` **`ocr_tasks.charged_docs` — what a task actually cost.** Direct consequence of the
above: once a page is the unit, `COUNT(ocr_tasks)` stops meaning "documents consumed", and
nothing in the schema could answer "what did this task cost". A subscription-funded scan
writes **no per-scan row at all** (only `tenant_subscriptions.docs_used += N`), and a
credit-funded one writes `credit_ledger.ref` = the **filename**, not the task id — the charge
happens before `create_task`, so there is no id to reference. Every "documents" figure on the
admin dashboard was a task count and would have silently under-reported AP from today.

- `supabase/migrations/20260814000000_ocr_tasks_charged_docs.sql` — one column,
  `smallint not null default 1`. The default makes every historical row correct as it stands
  (they each cost exactly one), so there is no backfill and no data migration. **Not pushed**
  — `supabase db push` is yours to run.
- `models/business.py` + `task_service.create_task(charged_docs=1)` — callers pass what
  `consume_document()` actually took: `pages` for AP, `1` per file for credit card (router
  and email ingest), and **`0` when the charge failed open** (`consume_document` returns None
  on an infra error), so `SUM(charged_docs)` never claims a document that was not taken.
- `services/summary_service.py` — the daily rollup's document query is
  `COALESCE(SUM(charged_docs), 0)`, not `COUNT(*)`. This is what fills
  `daily_usage_summary.total_documents`, i.e. every historical number on `#/admin/usage`.
- `services/usage_analytics_service.py` — `doc_count` and `total_documents` sum the column.
  The two remaining `COUNT(OCRTask.id)` sites are left alone on purpose: the error-rate
  denominator and the engagement funnel's `tried` count **attempts**, and a failed 3-page
  scan is one failure, not three.
- `db/queries.sql` items 11 + 14 — `bu_ge_5_docs` and the weekly `docs`/`docs_per_bu` curve
  sum the column too, so the reference SQL still cross-checks the dashboard.
- Tests — `TestPerPageCharging` gains the task-cost pair (2-page selection → `charged_docs=2`;
  charge failed open → `0`). `test_summary_service.py` pins the rollup to
  `SUM(charged_docs)`: that query is raw SQL with no ORM to catch a rename, and it is the
  source of every historical usage figure.

Answering the question directly, once pushed:

```sql
-- what each task cost
SELECT id, module_id, original_filename, charged_docs, status FROM ocr_tasks
WHERE tenant_id = :tid ORDER BY created_at DESC LIMIT 50;
-- net documents consumed (failed tasks are refunded)
SELECT SUM(charged_docs) FROM ocr_tasks
WHERE tenant_id = :tid AND deleted_at IS NULL AND status <> 'failed';
```

## Purchase tutorial — a reusable guided-tour modal

`15:10` **A Tutorial button on Plans & Credits, opening a 10-step guided tour of buying a
package.** Narration from the standalone manual
`erp_carmen_manual_v2_6_ai_package_purchase_guide.html`, replaced mid-build by the approved Thai
copy supplied for this feature. The screens it narrates are not drawings of the app — they are the
app.

**Built as a kit, not a page.** More modules are getting tutorials, so the chrome — the camera,
the highlight, progress, navigation, keyboard, focus — lives once in `components/tutorial/` and a
module supplies only copy and figures. Adding the next one is three steps:

1. write the steps as `TutorialStepDefinition[]` in `content/tutorials/<module>.ts`
2. build the figures, marking anything a step points at with `<Spot id="…">`
3. render `<TutorialModal open onClose steps title />` from the page

### Frontend — the kit

- `components/tutorial/TutorialModal.tsx` — the shared shell. Native `<dialog>` + `showModal()`,
  so focus trapping, Escape, inertness of the page behind and top-layer painting are the
  platform's job (the same reason `AppHeader` uses the popover API). Narration pane beside the
  stage, stacking under 68.75rem. Arrow keys walk the tour, clickable pips jump, the last step
  swaps Next for Done and can carry a module-supplied call to action. Body scroll is locked
  exactly as `OrderDrawer` does it — a modal dialog makes the page inert but not unscrollable.
- `components/tutorial/useCamera.ts` — the framing maths (below).
- `components/tutorial/Spot.tsx` — `<Spot id>` marks whatever a step points at and reads the
  active step from context. Context, not a prop: a figure is a dozen components deep, and
  threading `spot` through all of them is the tax that stops people writing tutorials.
  `display: contents`, so wrapping something never changes the figure's own layout.
- `components/tutorial/types.ts` — `TutorialStepDefinition` is `{ spot?, icon } & Record<Lang,
  TutorialStepCopy>`, so the compiler asks for Thai, the same guarantee `dict.ts` gives. **No
  `spot` means an overview step.** A step may also set `canvasWidth` when its screen is not the
  1080px pricing page.
- `styles/components/tutorial.css` — app tokens throughout, no raw hex, light and dark.

### Frontend — the purchase tutorial

- `content/tutorials/purchase.ts` — the ten steps' copy, now the **approved Thai** supplied for
  this feature. It was written against seven steps, so each approved sentence sits on the step it
  describes and the added steps (three overviews, and splitting "read the invoice" from "print
  it") are written in the same voice. The source manual's own slips are gone: its Thai step-3
  heading read "ไร้สาระหมดอายุ" where the point is that credits never expire, and its step 7
  pointed at "ระบบจริง" through a hardcoded `https://app.carmen.blue/#/pricing`, which breaks dev
  and staging and means nothing now that the tour runs on top of the page it describes. The
  approved copy's `[ต้องยืนยันก่อนเผยแพร่]` flag on "ไม่มีวันหมดอายุ" is resolved rather than
  shipped: the claim already reaches customers as `pricing.topupSub2` ("Buy once, never expire")
  and `checkout.kindTopup`, and is stated in `docs/Billing_Purchase_Flow.md`.
- `components/pricing/tutorial/screens.tsx` — the five figures. They **mount the product**:
  `PlanCard`, `EnterpriseCard`, `PackList`, `StepWizard`, `ProformaDocument`, `SlipUpload` and
  `PendingOrderBanner`, all rendered from fixtures. Two things are rebuilt as static markup **on
  their real class names**, because the components cannot be mounted: `CheckoutFlow` fetches on
  mount and keeps its phase in `useCheckout` with no prop to preset it, and `AppHeader` renders
  `NotificationBell` whenever authenticated (a fetch, a 60s poll, a localStorage read) and opens
  its overflow menu into the top layer, above the dialog.
- `components/pricing/tutorial/fixtures.ts` — the made-up `CreditPack[]`, `BillingDocument`,

  instead of the tutorial quietly drawing something the product no longer looks like. The buyer is
  invented; the source manual's mock buyer was a real customer, down to the tax ID.
- `components/pricing/tutorial/PurchaseTutorial.tsx` — marries copy to figures and hands them to
  the modal. That is the whole module-specific surface.
- `pages/Pricing.tsx` — the button (between Plans|History and the language toggle, reusing
  `.btn .btn-sm .btn-outline`, inheriting the ⋯-popover collapse under 640px) and the modal,
  `lazy()` and mounted only while open.
- `i18n/dict.ts` — `nav.tutorial` + 9 `tutorial.*` chrome keys, EN + TH.

### Why the figures are the real components

The first cut drew the screens by hand in Tailwind, ported from the manual. It looked nothing like
the product, for three separate reasons, and the third is why the drawing approach was abandoned:

1. **Preflight is off here.** `styles/tailwind.css` imports `tailwindcss/theme` +
   `tailwindcss/utilities` and deliberately not preflight, so every `<h2>`, `<h3>`, `<p>` and
   `<ol>` in the ported markup carried UA default margins and the proforma's terms list carried a
   40px indent. That alone crowded every step.
2. **Viewport breakpoints inside a narrow stage.** A `lg:` breakpoint still matched, so a
   three-column grid held together inside a 700px pane and the cards became strips. The first fix
   for this — container queries — traded the squeeze for a subtler lie: the figure reflowed into a
   narrow-window arrangement while the reader's own window was showing three columns.
3. **A foreign design language.** Tailwind slate/blue, `font-black`, `rounded-2xl` against a
   product built on Carmen tokens, Inter/Sarabun and its own classes. Even laid out correctly, a
   redrawing keeps reading as a different product.

Mounting the real components deletes 1 and 3 outright and cannot drift. Nothing in the figure is
reachable: one `inert` on the canvas kills clicks, focus and keys for the whole subtree, which is
what stops `ProformaDocument`'s Print button, `SlipUpload`'s file picker and the banner's cancel
action from doing anything real. Chasing per-component `disabled` props would have missed most of
them.

### The stage is a camera, not a scroll pane

Scrolling a picture the reader cannot act on is friction, and it hides the thing being pointed at.
The stage does not scroll (`overflow: hidden`). Each figure is a page-sized picture laid out at its
real width — 1080px for the pricing page, 1480px for the credit-card module's `.app-container` —
and `useCamera.ts` frames it:

- a step with **no `spot` is an overview**: the whole page, fitted, nothing highlighted
- a step **with a `spot` zooms and pans** to it, capped at 1.6× so the target keeps its
  surroundings, clamped so the camera never shows past the page edge
- the move between the two is the transition the tour is made of

Every screen opens with an overview step before its details. `spot` also accepts a plain CSS
selector — the escape hatch for product markup a figure mounts rather than redraws, which is how
the print step points at `ProformaDocument`'s own `.pf-toolbar`.

`transform`, not `zoom`: transforms leave layout metrics alone, so `scrollHeight` still reports the
figure's true height in every engine, while `zoom`'s effect on `offsetHeight` vs
`getBoundingClientRect` differs between them.

### Motion, and the accessibility of it

A camera that zooms and pans across a full-bleed picture is exactly the large-field optical flow
that makes some people ill, and someone feeling ill will not go hunting through OS settings for
relief. So:

- **The default is gentle.** The camera moves on a 280ms ease-out tween, not a spring — a spring
  overshoots, and the settle at the end of a zoom is the worst of it. The narration and the figure
  crossfade with no slide or scale on either. Opening and closing fade with a scale small enough
  to read as depth rather than movement (0.985 → 1 in, 0.99 out), backdrop included, no translate.
- **A Calm switch sits in the tour's own header**, `aria-pressed`, turning every animation off:
  the camera cuts, nothing travels. It starts from `prefers-reduced-motion` and is remembered per
  device (`localStorage['tutorial:calm']`, a raw key like `theme` and `lang` — a preference about
  the person, not tenant data). One class, `.tut.is-calm`, carries it to the CSS half.
- The system setting still works on its own for anyone who never opens the switch.

The figure is keyed by **figure identity, not step index**, so steps sharing a screen never remount
it. The highlight is **one rect that travels with the camera**, living in the stage's coordinates
so its ring keeps the same weight at every zoom, and copying the target's own `border-radius` so
it hugs a pill as a pill and a card as a card. Explicit values, not framer's `layout` prop:
`LazyMotion` is mounted with `domAnimation`, which excludes layout animations.

Closing is the modal's own business: every route out (the ✕, Done, the finish CTA, and Escape via
`onCancel` + `preventDefault`) goes through one `requestClose`, which plays the exit **while the
dialog is still mounted** and only then calls `onClose` — the call that unmounts it. Calm skips
straight to the end. `finish.onClick` is optional as a result; the modal closes itself after a
tour's last action.

### What the browser found that jsdom could not

Four bugs that no test could have caught, because jsdom has no layout:

- **The figure was drawn at full size on every step.** The crossfade and the fit-to-stage scale
  were on the same element, and framer-motion writes `transform` for any animated `scale` — so
  `animate={{ scale: 1 }}` silently overwrote `transform: scale(0.9)` and the canvas hung out of
  the stage. Split in two: an `m.div` that owns opacity and nothing else, wrapping a plain `div`
  that owns the transform.
- **The modal was small and sat oddly.** Now sized around the figure rather than the text:
  `min(1520px, 92vw)` is where the stage can give the 1080px canvas its full width, and the height
  takes what the viewport has at `min(1040px, 92vh)`. The narration yields width as the window
  shrinks (`clamp(16rem, 24%, 22rem)`). Centring is explicit (`inset: 0; margin: auto`) rather
  than trusting the UA dialog styles.
- **"Buy" was missing from the header.** The mock language toggle was built out of
  `.segmented-control`, which is full-width by default (the real page passes `width: auto`
  inline) — so it ate the row and pushed the Buy chip out of `.app-header`'s `overflow: hidden`.
  It is now `LanguageToggle`'s markup element for element, and that figure lays out at its real
  1480px.
- **The tour taught the wrong path.** It sent the reader from the invoice back to Plans to find
  their unfinished order and upload there — but `CheckoutFlow`'s pay phase renders the slip card
  directly under the proforma, so paying and attaching happen on **one screen**. The pending-order
  banner is the way back for someone who closed the page first, not a step everyone takes. The
  payment figure now carries the invoice and the real `SlipUpload` together, and the banner is the
  last step, labelled as the recovery path.
