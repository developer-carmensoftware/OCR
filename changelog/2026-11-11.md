## Frontend: the page background no longer overflows by the scrollbar (branch `fix/bg-blob-width`)

`14:30` Found by running the JV filter suite in a real (headed) Chrome window: G-07 failed with
`overflow 3` at 375 px, while headless passed.
- **Cause:** `.bg-blob-mid` (the decorative wash on every page) was `width: 100vw`. `vw` counts the
  scrollbar, and headless Chrome has overlay scrollbars that take no width, so no earlier run saw it.
  Now `width: 100%`, which excludes the scrollbar.
- **Impact:** phantom only — `scrollWidth > clientWidth` — because `body { overflow-x: hidden }` clips it;
  nobody could scroll to it. It is what a reflow audit would flag.
- **QA:** `jv_filters_ui.mjs` gains `HEADED=1 SLOWMO=<ms>` (headless stays the default). Whole suite
  headed 67/67 with the fix. A headless run after it overlapped a branch switch in the shared
  worktree and missed V-03 once (66/67); V-03 then passed 3 of 3 alone (same seed). No full
  headless pass on this exact commit yet.
- **Not changed:** `tutorial.css` `.tut { width: 100vw }` (a modal below 62 rem).
- **Tooling trap:** `npx supabase` now fetches CLI 3.x, which rejects the repo's `[inbucket]` section;
  `npx supabase@2.121.0 start` brings the local stack up. A first headed run lost its DB mid-run (the
  containers were gone) and failed 24 cases with 500s — an outage, not a product result.

## Backend: a deep page of the JV queue is built from keys, not rows (branch `perf/activity-deep-page`)

`15:50` At 20,000 rows the last page was p50 1,124 ms / p95 1,865 ms, 14x the first page: `list_activity`
loaded `limit + offset` ORM rows per source, looked up cards and names for all of them, sorted, and kept 100.
- **Change:** past `DEEP_WINDOW` (500 rows) the page is built in two phases. Each source's own statement is
  reduced to `(id, when)` and merged on keys, then only the page's ids are loaded (`_deep_rows`). Shallow
  pages take the unchanged path, so the first page pays no extra round trip. Counts and `total` are untouched.
- **Measured** (20,000 rows, local DB, 20 runs, three repeats): deep page p50 ~235 ms / p95 ~335 ms
  (was 1,124 / 1,865: 4.7x / 5.6x). First page 76 / 86–113 ms, narrowed views 43–138 ms, as before. The
  300 ms p95 budget set for it is **missed by ~35 ms**; what is left is reading the 20k keys per source.
- **Tests:** 7 pytest for the deep path (page == merged slice and loads only its ids, past the end, manual
  skipped, a row deleted between the reads, key statements keep the join and select two columns, the 500
  boundary, same-instant source order). Mutations shown red then restored: an off-by-one slice (3 red), the
  stable source order broken (1 red).
- **Equivalence on a real DB:** `jv_filters_backend.py --deep-window 0` sends every page down the deep path;
  the whole browser suite is 67/67 that way, and 67/67 on `main` (headless) as the baseline.
- **Known edge:** rows with the same instant have no order the database promises on the shallow path; the
  deep path breaks ties by `id`, so two tied rows can swap places across the 500 boundary.
- **Not done:** a SQL `UNION ALL` (would remove the remaining 20k-key read), keyset paging (changes the API).
