### `15:15` — One document, two JVs: the duplicate guard was blind to its own postings

Found by the end-to-end test below, not by reading code. Re-forwarding one SIAMPAY
report in a second mail posted it to Carmen **twice — JV 966 and JV 967 for document
`RE2026-05269`**. [`docs/CARMEN_INTEGRATION.md`](docs/CARMEN_INTEGRATION.md) §0.1 promises
exactly the opposite ("a document forwarded twice is not charged twice"), and both arrival
modes carrying the same report is the ordinary case, not an edge one.

The guard was never missing — **only its write side was.** `finalize_extraction` sets
`extracted.is_duplicate` from `has_submitted_doc`, which reads
`credit_cards.submitted_at IS NOT NULL`. Only [`routers/carmen.py:154`](backend/app/routers/carmen.py#L154)
(the wizard's submit) ever stamped that column, so the ingest job checked a flag it never
set: it could see the wizard's postings and not its own. KBANK failed as
`duplicate_document` in the same run purely because a human had submitted it through the
wizard on 07-29.

`email_documents`' unique key is `(tenant, message_id, attachment)` — that catches the same
*mail* arriving twice, which is a different question from the same *document* arriving in
two different mails.

Two layers, in the order a fix should go:

1. **`_mark_submitted()` after a successful post** (`email_ingest_service`) — the five
   lines that were missing. Only on `Code == 0`: a JV Carmen declined must stay retryable.
   It logs and returns on failure rather than raising, because nothing here can un-post a
   JV Carmen has already accepted.
2. **`uq_credit_cards_submitted_doc`** (migration `20260804010000`) — partial unique index
   on `(tenant_id, bank_code, doc_no) where submitted_at is not null and deleted_at is null`.
   The application cannot close the check→post→stamp window by itself, and a future path
   that forgets to stamp should fail loudly instead of quietly double-posting. Same partial
   shape as `uq_credit_cards_task` (`20260615000007`): drafts and parked documents repeat
   freely, soft-deleted rows can be superseded. Verified zero existing violations before
   writing it.

Deliberately **not** reserve-then-post (stamp before the call, roll back on failure): it
needs an undo path, and the race it closes is already narrow — `_fetch_unseen` flags mail
`\Seen` inside the same IMAP connection it fetches from, so two overlapping polls cannot
draw the same message.

Verified live: stamped the row for JV 966 (it really is in Carmen), re-forwarded the same
report → `duplicate_document`, and `outbound_call_logs` shows **zero** POSTs to `/gljv`.
Three unit tests pin it — stamp on success, no stamp when Carmen declines, and an
already-submitted document never reaching Carmen at all.

**Pushed and verified biting:** `uq_credit_cards_submitted_doc` is live on the remote
(`credit_cards` is 232 rows, 22 of them submitted, so the index build needed no
`CONCURRENTLY`). Confirmed by attempting a second stamp on `RE2026-05269` — rejected with
`UniqueViolationError`, which is the loud failure the app path can no longer produce
silently.

**Left in dev Carmen: JV `967`.** That reversal is Carmen-side and cannot be done from
here — we hold no JV records at all (Carmen is the source of truth; §0 of the contract),
only an `email_documents` row saying we posted and got `967` back, which is true and stays.
Our own data is already consistent: exactly one `credit_cards` row for that document is
stamped, the one matching the legitimate JV `966`.

### `14:20` — §4 answered: Carmen issues a per-BU token. Three holes closed on the way in

Carmen settled the credential question (contract §4): **a token per BU with no expiry**,
minted when the customer switches Email Automation on, invalidated when they switch it
off. It is scoped to the BU rather than to a person, and Carmen's own permission model
still applies to it — so it does not die when an employee leaves and it does not carry
one user's rights into automation. Rotation is off-then-on; there is no separate rotate
path for Carmen to build. Their whole checklist is now three items, all inside the ON/OFF
switch they were already building ([`docs/CARMEN_INTEGRATION.md`](docs/CARMEN_INTEGRATION.md)
§2.1, §2.6, §4, §5 rewritten).

Reviewing our side to hold that credential turned up three problems already on this
branch, two of them exploitable:

**1. Any valid API key could write any BU's settings.** `_caller` checked only that a key
existed and was unrevoked; the handler then resolved the tenant from `payload.host/bu`,
which the caller supplies. `APIKey.tenant_id` and `APIKey.scopes` both existed and were
ignored. The interesting attack was never the credential — it was `tax_ids`: register your
own tax ID against someone else's BU and your documents post into their books. `_caller`
now returns a `Caller` (actor + tenant + `host:` scopes) and `_authorize` runs on every
handler, failing closed — a key with neither a tenant nor a host scope manages nothing.
`issue_api_key.py` grew a required `--host`. No key has been issued to anyone yet, so
nothing outside this repo breaks.

**2. Automated posting has never worked at all.** `post_gljv` reads its base URL from the
`current_carmen_uri` ContextVar, which only the request middleware sets. `run_ingest` has
no request, so every automated post raised `RuntimeError` inside the generic handler and
was filed as `unreadable_document` — a wrong reason, on a refunded document, that sends
whoever reads the ledger to look at the PDF. Invisible to tests because `post_gljv` is
mocked in all of them. The job now resolves `(token, carmen_uri)` per BU
(`posting_target`, falling back to `https://<tenants.host>`) and sets the ContextVar
itself; a BU with no known host parks as `carmen_rejected` with an honest message.

**3. The credential rode inside `PUT /settings`.** Every ordinary settings edit
re-transmitted the secret, as a plain `str` that validation errors and Sentry breadcrumbs
could carry. It now has its own `PUT/GET/DELETE /api/v1/carmen/settings/token`, typed
`SecretStr`.

**And one hole the new endpoint would have opened.** `carmen_uri` arrives from the caller
and we immediately make a server-side request to it carrying a credential — textbook SSRF.
It goes through `routers/auth._validate_uri` (https-only, `ALLOWED_CARMEN_HOSTS`
allowlist, loopback/private-IP rejection including what a hostname resolves to) before
`verify_token` fires, re-raised as the 422 field-error shape Carmen already renders.

What makes a credential without an expiry date manageable, all on our side:

- **Strict verification at save time** — `set_token` calls Carmen (`GET /department`) and
  a token Carmen rejects never reaches the database. The customer finds out on the
  settings screen, not at 3am.
- **`carmen_token_fp`** — first 8 hex of sha256, so both sides can name a credential in a
  support conversation without either revealing it.
- **`POST /carmen/email-ingest/health`** — re-proves every stored token, stamps or clears
  `carmen_token_verified_at`. **Deliberately not scheduled yet**: the ingest poll has no
  `cron.schedule` either, and both belong in one migration the day the mailbox goes live.
  The cron SQL is written out in the endpoint's docstring, using `value #>> '{}'` — not the
  `trim(both '"' …)` form that silently disabled every HTTP cron job until `20260715010000`.
- Dev-token fallback in `posting_target` is now gated on `app_debug`. One shared credential
  posting a real customer's books is exactly the blast radius the per-BU token exists to
  avoid.

Encrypt, not hash, and the line between them is worth keeping: a secret we only ever
*verify* (our own API key) is hashed; one we have to *present* to someone else (this
token, PDF passwords) has to come back out, so Fernet.

**DB** — migration `20260804000000_email_carmen_token.sql`: `carmen_uri`,
`carmen_token_fp`, `carmen_token_verified_at` on `email_ingest_settings`.

**Backend** — `routers/email_automation.py`, `services/email_settings_service.py`,
`services/email_ingest_service.py`, `models/email_automation.py`, `issue_api_key.py`.

**Tests** — 748 pass, ruff clean. New coverage on the parts that would fail silently:
`_authorize` cross-host and empty-scope denial, SSRF rejection of `169.254.169.254` and
friends before any outbound request, `set_token` storing nothing when Carmen returns 401,
`token_status` never containing the value, and `posting_target`'s dev-token fallback being
`app_debug`-only.

**Still open on the contract:** §2.5 (forwarding address, ours to decide), §3.4
(`document.*` events, yes/no from Carmen), the tax-ID field in Carmen's company master,
and confirmation that automated JVs are distinguishable in `JvhSource`.

### `16:10` — A reference spec Carmen can code from, separate from the contract

[`docs/CARMEN_API_SPEC.md`](docs/CARMEN_API_SPEC.md) — new. The contract explains *why*;
this one is *what to call*, and the two audiences are not the same person. Prompted by
feedback that the summary we sent could not be implemented from: it argued a position
where a developer needed field tables.

Modelled on OneApp's own FileService spec, which the Carmen side already reads — same
section order (Overview → Flow → Authentication → one section per endpoint → error tables),
same shape per endpoint (request fields with types and required markers, a concrete `200`
body, a Status/Message/Cause table), and the same Thai-prose-with-English-terms register.
Matching a house style people already scan beats inventing a better one.

All five routes: `GET`/`PUT /settings`, `PUT`/`GET`/`DELETE /settings/token`. Includes the
`status.blockers` vocabulary, the `Rule` object with `pdf_password`'s omit-keeps /
empty-clears semantics, both `422` codes with the shared `errors[]` body, and the two
things Carmen must not mis-read: `PUT /settings` replaces wholesale rather than merging,
and `DELETE /settings/token` drops our copy without revoking anything.

Linked from §2 of the contract so nobody hands out the wrong document.

### `16:35` — Two questions from review, and a wrong example in our own docs

**"ไม่มี POST เหรอ?"** — no, and the spec never said why. All five routes are
`GET`/`PUT`/`DELETE` because both writes replace a resource whose address (`host`, `bu`)
the *caller* already knows; there is nothing whose identity we assign. Left as `POST` it
would imply calling twice creates a second settings row or a second live token, which
would send Carmen down a delete-then-create path for rotation when `PUT` simply overwrites.
Now stated in the spec, together with a note that `POST /email-ingest/run|health` do exist
but belong to pg_cron and a different credential, so nothing looks missing.

**"ตั้งค่าครั้งแรกทำยังไง?"** — also absent, and it is the first thing Carmen will hit.
Walked the whole sequence against a BU that had never been configured rather than deriving
it from the code, which surfaced three things worth writing down:

- `PUT /settings/token` **creates the settings row itself** — no need to `PUT /settings`
  first, and doing the token first means a bad token stops the flow before any config is
  written.
- `ingest_address` is `null` until a row exists, and the tag is allocated by whichever of
  the two writes arrives first.
- **The `status` block changes shape**: when `blockers` is `["not_configured"]` there is no
  `documents_total` / `last_received_at` at all. A client that assumes those keys always
  exist breaks on day one.

Also confirmed and documented: `PUT /settings` does not disturb a stored token, and
`PUT /settings/token` does not touch `tax_ids`/`rules`.

**Fixed a live-fire error in our own documentation:** the example tax ID `0105536000123`
appears four times across both docs and **fails the check digit** — anyone copying it into
a test gets `422 invalid_checksum` and reasonably concludes our validator is broken.
Replaced with `0105536000127`, computed and verified against `is_valid_thai_tax_id`. Found
only because the first-run walkthrough was executed rather than written from memory.

### `15:40` — Contract §2 reconciled against the running service

The spec was written before the code ran, so §2.1/§2.6 were checked line by line against a
live instance and three pieces of drift fixed rather than left to be discovered by Carmen:

- **`invalid_uri` was undocumented.** Carmen can hit it on any `PUT /settings/token`, so
  it now appears next to `token_rejected` with what the check actually rejects.
- **"We re-verify daily" was an overpromise** — the endpoint is built and tested but not
  yet scheduled. Reworded to say when it starts.
- **Status codes were asserted, not assumed.** An unknown `(host, bu)` is `400`, not the
  `422` first written: `ValidationError` maps to 400 in `factory.py`, and `422` belongs to
  the per-field shape. Every code the section now claims — 401, 403, 400, 409, 422 — was
  fired against the running service and the response bodies pasted from what came back.

Also added: the `403` body and that scoping applies to reads too, the `detail`-alongside-
`errors` convention, which Carmen endpoint we call to verify a token (`GET /department` —
relevant to how narrowly they scope it), and a pointer to `/openapi.json` as the
machine-readable version so nobody hand-writes a client from prose.
