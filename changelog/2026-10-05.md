`10:35` **Settlement reports are reviewed in the same JV table as fee invoices** *(uncommitted, on
`feat/settlement-review-like-fee-invoice`)*

The settlement report (KBANK KB1P554V2) had its own read-only pane, `ARReviewPane`, because this
feature had its own settings screen and mapping table. Decision #29 (2026-09-22) folded both into the
credit-card mapping, so the review modal now uses `JvEditor` for both document types. The header,
pickers, comments, amounts and input-tax panel are the same controls for both.

Frontend

- `ccJv.buildJvRows` — new `settlement` option (`{ postType, totalRow }`), twin of
  `build_jv_rows(..., total_row=, grouping=)`: one credit leg per grouped type (`groupKey`: Detail
  keeps the label, Summary takes its first token), a negative group swaps to debit, and the three
  debit legs come from the total row. The settlement cases in `contracts/cc-jv.contract.json` (see
  Contract) pin it to the Python builder.
- `JvEditor` takes `settlement` and passes it through. This is the only change to it besides
  exporting `BU_WIDE`, plus an Amount label for a leg that has no line of its own.
- `ARReviewPane.tsx` and its CSS (`.arv*`, ~170 lines) deleted. Also deleted: 11 orphaned
  `review.ar*` keys (EN+TH), `JvHeaderCard`'s `readOnly`/`descriptionOverride` branch, the "AR
  reconciliation settings" button and the "Set the journal book" link.
- `useReviewDocument` — `totalRow` is state now. An edited debit leg writes into it, and an edited
  credit leg writes into its line (sign kept for a negative group). Approve sends both back in
  `extracted`, and saves rules on the settlement path too: a new settlement key is tagged with its
  layout's `source` (`SOURCE_BY_POST_TYPE`, moved to `api/arReconcile.ts`). The input-tax panel
  reads the total row, and `post_input_tax` follows its checkbox.
- The modal header has a Mapping button (gear, beside Close). It opens
  `#/CreditCardOCR/mapping?bank=<document's bank>` in a new tab, as the queue's button does, so the
  open document and its edits stay put.
- A bank with no active settlement rule shows that sentence and "Open settings".

Backend

- `approve_document` (settlement) still rebuilds figures and accounts from the posted `extracted`
  and the config. It now keeps each leg's comment from the request (`_with_comments`, matched by
  position and leg key).
- `PATCH /api/v1/config/accounting` passes `source`. `patch_config` applies it only to an entry
  it creates.

Contract

- `contracts/cc-jv.contract.json` gains two settlement cases on real KB1P554V2 figures. One is
  Detail. The other is Summary with a negative AMEX refund and a zero line. Both readers pass
  `settlement` through.

`10:55` **An open review follows a Credit breakdown switch saved on the mapping page** *(same branch,
uncommitted)*

Switching Detail/Summary on the mapping page and saving left an open review on the old grouping
until it was closed and reopened. Two causes:

- The modal read the grouping once, from `doc.ar_jv.post_type`. `useReviewDocument` now re-reads it
  (`getARSettings`) on the `accounting_config_updated` signal the mapping page sends. The rules
  already re-read on that signal inside `useAccountingConfig`.
- `useMapping.saveAllSettings` sent that signal between its two saves, before the Credit breakdown
  was written, so a tab re-reading at once got the old one. It now goes out after both. If only the
  second save fails, it still goes out, since the rules did save.

Tests: `useMapping.test.ts` +1 (the signal comes after the posting profile), `ReviewDocument.test.tsx`
+1 (the open JV regroups Detail → Summary on the signal). Frontend 1019/1019, eslint 0 errors,
build OK.

`11:30` **Settlement review: second pass for what the change could break** *(same branch, uncommitted)*

Read the settlement path end to end (ingest → review GET → screen → approve → input tax) with
the browser now building the JV. Fixed:

- **Screen and post can no longer part silently.** `approve_document` compares its rebuild with
  the rows the screen sent and refuses on any difference in legs, accounts or figures
  (`_as_shown`; it used to post the rebuild whatever the screen held). That covers a colleague's
  mapping save mid-review and a Credit breakdown switched from another browser. Comments still
  come from the screen.
- **The screen refuses what the server refuses.** A leg missing either code (the three debit legs
  even at zero) blocks Approve with `review.arUnmapped` (restored). Before, Approve was enabled
  and Carmen's post was refused afterwards.
- **One balance tolerance.** `JvEditor`'s imbalance check is now 0.005, as `is_balanced` uses.
  At 0.01, a one-satang difference could read "Balanced" and then be refused.
- **No Approve while rules re-read.** `blocked` includes `configLoading`, since the old rules stay
  on screen until the new ones land.
- **No rule saved from a grouping no longer shown.** A key re-mapped under Summary is not
  written once the bank was switched to Detail.
- **No AI guess for a settlement key.** JvEditor's fill is off for one, keeping the pipeline's
  standing "never guessed" rule (decision-log #36).

Checked and fine: KBANK has a registered vendor identity (the input-tax panel does not block);
`parseNum`/`num` agree on every string shape extraction produces; ingest, `_review_flags` and
auto-post are untouched.

Tests: `test_ar_approve.py` +5 (rebuild posts when it matches; four ways of differing are
refused; comments), `ReviewDocument.test.tsx` +2, plus a no-AI assertion. Frontend 1021/1021
(400 in credit-card after the AI change), backend full suite exit 0. Docs: decision-log #36.

`11:50` **KBANK rule: a "Detailed Credit Card AR Reconciliation" toggle with a merchant ID** *(same
branch, uncommitted)*

On the KBANK rule, the reconciliation toggle now decides which file is read, not a typed filename
pattern (decision-log #37):

- off reads `E-TAX_INVOICE_CARD_*` as a fee invoice;
- on reads only `SUM_<merchant_id>` as a settlement report;
- either way, the zip's `TAX_SUMMARY_BY_TAX_ID_CSV_*` is checked when it is attached.

Backend

- `imap.match_rules` + `kbank_file()`: KBANK's two files belong to the KBANK rule alone, whether
  it is on or off. That closes the double-booking gap where an "Other" `.pdf` rule could read the
  tax invoice beside a settlement report. Three more rules:
  - a settlement report is never read as a fee invoice;
  - the KBANK rule ignores its stored patterns;
  - a pre-merchant ON rule still reads any settlement report until it is re-saved.
- `RuleIn.merchant_id`: required (at least 6 digits) on `ar_reconcile`, stored as digits, kept
  when omitted, and echoed by GET. Filename patterns are no longer required on the KBANK rule.
- `pipeline._run_document`: a KBANK fee invoice reads its CSV row (merchant from the page, else
  from `E-TAX_INVOICE_CARD_<merchant>_`). The CSV's TIN goes into `foreign_tax_id`, and fee/VAT
  are cross-checked; net is not, because an invoice's total is not the settlement's net. A
  missing CSV is fine.
- `app.constants.SETTLEMENT_BANK = "KBANK"`.

Frontend

- The email-settings dialog no longer has a Document-type select. The KBANK rule gets the
  toggle, a "Reads …" line, and a required Merchant ID when the toggle is on. Its patterns field
  is hidden, and another bank resets the rule to a commission invoice.
- The rule row shows "AR reconciliation" or "Commission invoice", and KBANK's file in place of
  patterns.
- An error on a field the dialog does not show is printed below it rather than lost.
- The Mapping card hint (EN/TH) names the toggle.

Tests:

- **Backend:** +12 routing, +7 settings, +3 pipeline. Four tests used KBANK as a generic
  pattern bank and were moved to BBL/SCB; a bankless settlement rule is now `no_rule_match`.
- **Frontend:** the select-based page tests were rewritten for the toggle, plus a hook round
  trip.
- **Results:** backend full suite exit 0; frontend 1023/1023, eslint 0 errors, build OK. Not
  checked live: the settings page needs a real Carmen token in the browser.
