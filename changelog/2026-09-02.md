# 2026-09-02

## The input-tax record can no longer file with half an identity

`10:05` A statement posts **two** Carmen documents — the GLJV, then the ACTX record
claiming the VAT the bank charged. `build_input_tax_payload` refuses to build a partial
record and its docstring says so, but two fields still fell through to `""`: `TaxId` and
`BranchNo`. Carmen accepts a record with an empty tax ID and rejects it silently
afterwards, which is a VAT claim nobody finds out was lost — the same failure the wizard's
`InputTaxReconciliation` has blocked Submit on since it happened (see the incident note at
its lines 56-59). The review screen showed the identical warning and posted anyway.

Branch is **not** a refusal, because unlike those two it has a correct default. A tax
invoice stating no branch was issued by the head office, and the Revenue Department's code
for that is `00000` — the printed convention, not a stand-in for a fact nobody read. That
also settles `bay.py` / `paypal.py` / `siampay.py`, whose prompts declare
`branch_no: always null`: those issuers do file for real, and they file as head office.

### Backend

- **`cc_input_tax.build_input_tax_payload` refuses on a missing tax ID**, not just a
  missing legal name — both halves of the vendor's identity, one guard beside the other.
  The skip reason names which half is missing, so the ledger line and the `tax_note` toast
  say something actionable. Covers the auto-post path too, which has no human at all.
- `TaxId` now posts the resolved value rather than `... or ""`; the empty string is
  unreachable by construction.
- **`BranchNo` defaults to `00000`** (`_HEAD_OFFICE`) when the document names no branch,
  instead of posting `""`. A branch that *was* read still wins.
- **Whitespace is absence.** New `_clean()` trims every identity field before it is tested
  *and* before it is posted. Without it the guard above had a hole the width of one
  keystroke: a typed space is truthy, so it walked past the refusal and reached Carmen as
  the empty field the refusal exists to stop — and the review screen's own block cleared on
  it too (`identityMissing` now trims for the same reason). A blanked override still falls
  back to the registry rather than dropping the claim for a stray keystroke.
- New tests: `test_a_missing_tax_id_is_a_refusal_too_and_says_which_half_is_missing` (which
  also pins that a reviewer typing the missing half turns the refusal back into a record),
  `test_an_unread_branch_files_as_the_head_office`,
  `test_whitespace_is_absence_everywhere_an_identity_field_is_read`, and
  `test_a_blanked_override_falls_back_to_the_registry_rather_than_losing_the_claim`.

### Frontend

- **Approve blocks on an unfilable input-tax record.** `InputTaxPanel` reports `onBlocked`
  upward the way `JvEditor` already reports `onState`; `ReviewDocument` folds it into the
  same disabled state and the same sentence under the button. Only while the record will
  actually be filed — unticking it is a real answer, and a document with no VAT was never
  a problem.
- Every reason Approve is unavailable now resolves through one `blockReason`, so the
  sentence, `aria-describedby` and the `disabled` attribute cannot disagree.
- **Bug found by the above: the input-tax panel was reading a bank code the review screen
  had already resolved better.** `detectBankFromExtracted` reads the printed issuer name
  and misses whenever the header carries only a short code (`bank_name: 'KTC'` — the
  keyword list wants `KRUNGTHAI CARD`). The JV pane and the config write both fell back to
  `doc.bank_code`, which ingest wrote and is not a guess; the panel took the bare detection
  and so lost the vendor's registered name, tax ID and address for a bank whose registry
  entry was sitting right there. Resolved once into `bankCode` and read by all four
  consumers. Without it the new block would have refused nearly every document.
- New key `review.itxBlocked` (EN + TH), worded to name both ways out.
- **`InputTaxReconciliation` defaults `BranchNo` to `00000` too.** The wizard posts the
  ACTX record from the browser and email ingest posts it server-side, so the default has to
  exist twice; the two comments point at each other.
- **The Branch placeholder is the one on this screen that is not a complaint.** Every other
  placeholder in `.rd-modal` is amber italic and means "nobody filled this in". This one
  previews what will actually file, so it takes a muted, upright `--text-3` instead. Shown
  as a placeholder and never written into `extracted.branch_no` — nothing claims the
  statement printed `00000` when it did not.

## One field layout, not two

`10:40` The input-tax panel had its own: `.itx-line` / `.itx-f` / `.itx-k` / `.itx-sep` —
a sentence, `VENDOR ___ · TAX ID ___ · TAX PROFILE ___ · BRANCH ___`, laid out inline over
two ragged lines with a `·` between units. It needed those separators precisely because
nothing else told one field from the next.

- **The body is now a `.rd-doc` row of `.rd-f` units**, the same stacked label-over-box the
  document fields at the top of the dialog use. Each field gets its own column, so the
  separators had nothing left to do and went, along with the four classes that existed only
  to lay out a sentence. Widths join the other `.rd-f--*` modifiers (`--taxid`, `--profile`,
  `--branch`; vendor takes `--grow`), which is what stops the two rows drifting apart again.
- **The tax profile is a `CustomSearchSelect`**, the picker every other chosen value on the
  dialog uses. It was the one control that could not take the screen's field treatment — a
  native `<select>` rendering as the browser's own widget beside three flat boxes. The
  closed state now shows the code alone (`VAT07`); the description still names each option
  in the open list and on hover. To reach it, the picker's flat/hover/focus/chevron rules
  are scoped to `.rd-modal` rather than to `.rd-doc` and `.jv-table` by name — the rule was
  always "everywhere on this screen a value can be chosen", and naming containers one by one
  is what left this control behind.
- **The body reads like the document it previews: identity first, figures at the foot.** The
  four fields run Vendor / Tax ID / Branch / Tax profile — the vendor's identity together,
  then the filing choice — and a ruled-off `.itx-record` line carries the tax period and the
  three amounts. The amount labels are **Carmen's own column headings** for `BfTaxAmt` /
  `TaxAmt` / `TotalAmt`, which is what settles `Tax` over `VAT` for the middle one: the
  reviewer checks that figure against the ERP they are posting to, and a screen that renames
  it makes them do the matching. All three, not the tax alone; `2.10` says nothing about
  whether 2.10 is right, `30.00 · 2.10 · 32.10` is the record's whole arithmetic.
- **`.itx-grid`: four columns spanning the panel, shared by both rows.** This is the layout
  fix, and it took three tries to find. The fields were sized to their contents
  (16 / 9.5 / 6 / 7rem) and so stopped 25rem short of a 64rem dialog; anchoring the figures
  to the right edge under them balanced the *edges* and hollowed the middle, which is what
  read as unbalanced. The panel is read rather than filled in, so the tracks now span the
  width (`1.5fr repeat(3, 1fr)` — vendor holds a sentence, the rest hold codes) and every
  label shares a left edge with the one above it. `rd-f--vendor` / `--taxid` / `--profile` /
  `--branch` are deleted: sizing the cells *and* the tracks is what let the two rows stop in
  different places. Under 640px it drops to two columns with vendor spanning both.
- **The amounts right-align**, as `.jv-num` right-aligns every figure on this screen; they
  end on one edge and read as a sum rather than three separate numbers. Total carries weight
  and full ink where Net and Tax sit a tier back, so three figures do not read flat. The tax
  period keeps its column's left edge: it is a date, not a figure.
- **None of those four is a field, and none looks like one.** They are sums over `details`,
  the same lines `buildJvRows` builds the journal from and `applyJvAmount` writes every JV
  amount edit back into, so they follow the JV and cannot be typed into here — a VAT record
  disagreeing with the journal filed beside it is the one outcome worse than no record. The
  tax period is the same kind of thing, the month the document names. `.itx-fact` is built
  as `.rd-f` is — label over value, same 0.4rem inset, same 0.875rem — so the two rows read
  as one grid; **what tells them apart is the wash, not the layout**, which is the rule the
  screen already runs on (a field is washed, a value that is not a field is bare). Position
  says which row you are in, the box says whether you can type in it.
- **The collapsed line answers whether, not how much** — `Will be recorded` /
  `Will not be recorded` / `No VAT on this document`. `review.itxSummary` (`VAT 105.00 at
  7%`) is gone: the rate was the profile's and said twice, and four labelled figures on that
  line read as clutter on a row whose job is one yes-or-no.

## Open, not done

`10:20` Two things surfaced while reviewing the same screen and were deliberately not
built:

- **Add/remove detail rows.** `useOcrExtraction.addRow`/`deleteRow` exist with tests,
  `useOcrWizard` re-exports them and `ManualScan.tsx:171-172` passes them into
  `DetailTable` — which destructures them as `_onAddRow`/`_onDeleteRow` and throws them
  away. Dead plumbing across four files. In the **wizard** the buttons make sense (the
  document is on screen beside the table in a `SplitLayout`); in the **review modal** they

- **Credit-card documents have no doc-vs-table reconciliation.** If the LLM drops a whole
  line, nothing on the review screen says so: the JV balances (it is built from whatever
  lines exist) and Approve is enabled. AP invoice already reconciles against the printed
  footer (`repairDocFigure`); credit card has no equivalent. This is what an add-row button
  would be a poor substitute for.
- **Two vendor-identity registries can disagree, and now one of them blocks Approve.** The
  review screen measures `identityMissing` against `BANK_INFO` in
  `frontend/src/constants/banks.ts`; `build_input_tax_payload` refuses against the `banks`
  table. Migration `20260805010000` put the identity in the table precisely so the
  browser-less path could read it, and says in its own header that "the frontend constant is
  now the one to retire" — it never was. A bank present in the table but absent from
  `BANK_INFO` would block a document the server could file. Recoverable (the reviewer types
  the tax ID and it posts as an override) and not reachable today, since all eight seeded
  banks appear in both. Retiring `BANK_INFO` in favour of a field on the review payload is
  the fix; it is a separate change.

### Frontend

- **Five filter chips became three** — `Needs review` · `Posted` · `Not posted`. `All` has

- **The opening chip follows `auto_post`**: off → `review`, on → `success`. Held until

  correcting itself a beat later. `filter` is `null` until then.
- **`All clear` is now true in both modes** and the second person is gone from the page:
  *"Statements forwarded to {address} appear here."* The old sentence promised approval
  before posting to a BU that had switched approval off. It also serves an empty `Posted`;
  an empty `Not posted` keeps the plain line, because an empty pile of failures is not an

- **One name in three places** — `AI JV Automation` on the Home card, the queue and

### Backend

- **`FILTERS` is three buckets**: `unposted` merges `failed` + `rejected` + `skipped` +
  `received`. The old split is `status = "skipped" if charged is None else "failed"` — a
  billing fact, and both words mean "it did not post" to the person reading them. `all`
  stays a valid filter value; an unknown one (a `?filter=skipped` bookmark) still falls
  back to it rather than 400ing.
- **`attention` means "anomalous", not "you can fix it"** — new `_attention()`. Covers every
  `failed`/`rejected` (a failure nobody in the BU can clear is still a failure), the
  fixable `skipped` reasons as before, stale `received`, and **a `posted` row carrying an
  `error_message`** — the JV reached Carmen and the input-tax record did not, which is the
  quietest outcome in the system and had nothing anywhere saying so. The GROUP BY gained
  one filtered count for it. `FIXABLE_REASONS` now has one job: the Actions column.

### Frontend

- **Only `Needs review` carries a count.** Backpressure caps pending at 50, so it lives in

### Backend

- **`ATTENTION_WINDOW` = 7 days.** The dot now counts anomalies from the last week; `counts`

## Next: the dot's mark belongs to the BU, not to a browser

`15:40` Decided, **not built** — deliberately a separate change so it lands in one piece.

`ATTENTION_WINDOW` (7 days, shipped in `536f09f`) is a placeholder and reads like one: any
number of days is a guess about how long someone stays interested. What should put the dot
out is somebody *looking*, not the clock.

A client-side mark was built and thrown away before it was committed, for two reasons worth
recording so nobody rebuilds it:

- **`clearAppStorage()` runs on session expiry**, not only on logout
  ([`AuthContext.tsx:76`](../frontend/src/contexts/AuthContext.tsx#L76)). Sessions here die
  on a 30-minute clock, so a mark in `APP_STORAGE_BASES` is wiped several times a day and
  the dot is lit again at every login — the exact failure it was meant to fix. Keeping it
  would have meant an exception like `releaseNotesSeen`'s.
- **A read receipt is the wrong model for a shared queue.** The dot marks an unresolved
  condition on documents the whole BU shares. Same person on a laptop and a phone gets two
  independent marks; two people on one browser profile share one. If a colleague opens
  `Not posted`, sees five failures and fixes none, nobody else's dot should go out.

**The shape to build:** one timestamp per BU (`email_ingest_settings` already has the row),
set through its own small endpoint the way `PUT /email/settings/auto-post` is — never
through the settings save, which is a full replace. `GET /activity` returns
`newest_anomaly_at` per chip instead of a count to compare against, which also drops the
monotonicity problem a count comparison has (a stuck document that finishes lowers the
figure). Then `ATTENTION_WINDOW` and its comment come out in the same commit.

Still true either way, and out of scope for that change: **"seen" is not "fixed".** A dot
that goes out when someone looks says nothing about whether the failure was dealt with, and
there is no retry, so a failed row never resolves on its own. Giving a reviewer a way to
dismiss a row is a bigger change and has not been asked for.

## The dot goes out when the business unit looks at the chip

`15:55` The follow-up the 15:40 entry reserved, built. `ATTENTION_WINDOW` is gone; what
ends the dot is a person opening the chip, and because the mark lives on the server it ends
for everybody in the BU. Full reasoning, including the three designs tried and discarded:
[`07-human-in-the-loop.md` §12 addendum](../docs/email-automation/07-human-in-the-loop.md).

### DB

- New table **`email_queue_seen`** (`20260902000000`) — `tenant_id` PK, `seen jsonb`
  mapping chip → the anomaly count already acknowledged. Its own table rather than a column
  on `email_ingest_settings`, which already has the one row per BU: that row gates a
  **per-minute IMAP sweep** through `tags_awaiting_confirmation`'s `updated_at` filter, and
  its `WriterMixin` stamps `updated_by` on any ORM write — so a filter-chip click would
  reopen a mailbox connection and rewrite who last changed the BU's email settings. The
  migration header carries all three rejected designs so nobody re-derives one.

### Backend

- **`ATTENTION_WINDOW` deleted.** `attention` is a lifetime anomaly count again and now
  only sizes the pile for the screen-reader sentence; a new **`unseen: dict[str, bool]`**
  on `ActivityPage` decides the dot — true while a chip's count is above the mark.
- **`POST /api/v1/credit-card/activity/seen`** `{filter}` stores the count **this request**
  computes. A caller-supplied number would let one bad value silence that BU's dot for
  good. `filter` is validated against `FILTERS` before it becomes a JSON key; `all` is
  refused with the nonsense, having no chip and therefore no dot.
- `_per_pair` / `_anomalies` extracted so the list and the mark fold over the same numbers
  and cannot disagree about what a chip is worth. The seen row is read with **`db.get`**,
  not `db.execute` — the mock DB drives `execute` by a positional `side_effect`, so a
  `select` here would shift every other call in the handler by one.

### Frontend

- `useReviewQueue` clears the open chip's dot locally and fires `markChipSeen` without
  awaiting or reloading. Clearing locally is what stops a loop — the value that gates the
  POST is the value the POST clears — and a failed mark never touches `listError`, because
  a dot that stays on until next time is not worth an error message.
- `ReviewQueue.tsx` renders the dot from `unseen`; the sentence beside it still reports
  `attention`. No copy change in either language.

### Why a count and not a timestamp

The 15:40 note prescribed a per-BU **timestamp** compared against `max(created_at)`. It is
wrong, and the reason is worth keeping: `created_at` is when a document *arrived*, not when
it became anomalous. One that parks on Monday, gets a mark set on Tuesday and is rejected on
Wednesday still carries Monday — the dot would never come back. Same for a JV that posts
without its input-tax record days after arrival, which is the quietest failure in the system
and the one `test_a_posted_document_whose_input_tax_failed_still_gets_a_dot` exists for. A
count is evaluated at read time and has no such hole. Its own ceiling — it assumes anomaly
counts only rise, true while every anomalous status is terminal and nothing purges
`email_documents` — is marked with a `ponytail:` at the write site.
