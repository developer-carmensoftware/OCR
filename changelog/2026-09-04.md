## The queue's empty states stop being placeholders

`09:40` Reported on the screenshot: the caught-up screen *"ดูไม่เป็นทางการ และยังไม่เหมือน
ระบบ SaaS อื่น ๆ"*. It read:

> Statements forwarded to aragent+1ad4e0b6@carmensoftware.com appear here.

Five faults, four of them the repo's own rules:

1. **The address was prose.** 40 characters of identifier set in body copy, unspaced and
   unbreakable, wrapping mid-address — while `NotSetUp`, two branches away in the same
   file, gives that same string a mono field and a copy button.
2. **One screen answered three questions.** `clearFilter = review || success || today` sent

   the next step"*). Since yesterday's `All` chip this was also a genuine dead end: the dev

   way to reach its own log.
4. **Two unrelated empty states on one page** — that card, versus a bare grey
   `<p>Nothing here yet.</p>` for Not posted and All.
5. **A shadow on a card with nothing to click** — against `DESIGN.md:238`'s Flat-By-Default

## The Message column says the thing once

`10:35` Reviewed the **Not posted** tab on a real BU's screenshot. The column's whole job is
to tell a reader why a row did not become a JV, and it was refusing to:

| Printed on screen | Held in `error_message`, reachable only by hovering |
|---|---|
| `Carmen refused it` × 8 identical rows | Carmen's own verdict — the closed period, the bad dept |
| `already handled` | *"already submitted"* vs *"already waiting for review"* — two different next moves |
| `tax ID belongs to another company` | the tax ID |
| `rejected by somchai - rejected` | the reason somchai typed |

Three faults, one of them a real bug:

1. **The reviewer's typed reason was never on screen.** `QueueRow`'s rejected branch fed
   `{reason}` the `rejected_by_reviewer` *phrase* (`'rejected'`) instead of `error_message`,
   so every rejection read `rejected by <name> - rejected` — and the words a colleague left
   for the next person were tooltip-only. The reject dialog asks for them
   (`review.rejectReasonHint`, *"e.g. wrong company"*); nothing printed them.
2. **`tax ID belongs to another company` claimed more than the check establishes.** A BU's
   register holds an *array* of tax IDs, so a document carrying one that is not in it has
   failed to match — that is all. Same overreach in the stored detail
   (*"registered to another BU"*).
3. **`already handled` over a red `Failed` pill contradicted itself**, and covered both the
   already-posted case (nothing to do) and the twin-in-the-queue case (go look at the other
   row) with one vague phrase.

### The rule, after one wrong turn

First attempt joined phrase and detail — `duplicate — a copy is already waiting for review`,
`Carmen refused it — Code 1: …`. Rejected on sight as *"ไม่จำเป็นพูดซ้ำ ทำไมวกวน"*, and
correctly: a prefix that the detail immediately restates is a head the reader must skim past
to reach the part that differs. **The detail replaces the phrase; it never joins it.** The
i18n phrase is what stands in when there is no detail — a legacy row, or a Carmen refusal
with an empty body.

### Frontend

- `lib/reviewReasons.ts` — new `WITH_DETAIL`, deliberately two codes: `carmen_rejected` and
  `duplicate_document`. Those are the only ones whose phrase cannot tell two rows apart.
  Everything else keeps its translated phrase, and the two codes carrying a raw `str(exc)`
  from the PDF reader (`unreadable_document`, `wrong_pdf_password`) plus the paragraph-long
  `sender_not_allowed` stay on the hover title, where length costs nothing.
- `QueueRow.tsx` — the rejected branch prints `error_message` when a reviewer left one and
  drops the trailing clause when they did not. Two keys instead of one:
  `review.rejectedBy` (`reviewed and rejected by {name}`) and `review.rejectedByWith`
  (`rejected by {name}: {reason}`).
- `dict.ts` — `review.postedBy` becomes **`reviewed and posted by {name}`** /
  `ตรวจสอบและโพสต์โดย {name}`: the name is evidence that this document stopped at the queue
  and a person read it — the same job its sibling `scanned and posted by {name}` does for
  the manual path. `review.rcTaxIdMismatch` → `registered Tax ID does not match the
  document` / `เลขผู้เสียภาษีที่ลงทะเบียนไว้ไม่ตรงกับในเอกสาร`.

### The pill, and the colour that stayed

- `QueueRow.tsx` — `rejected` gets its own word. Both it and `failed` sit under Not posted
  and both stay red, but one means something broke and the other means a person read the
  document and said no; one pill for both had a BU counting somchai's judgement calls among
  its problems. New `review.statusRejected` (`Rejected` / `ถูกปฏิเสธ`).
- **Greying the duplicate row was tried and reverted.** "already posted to Carmen" names no
  problem — the JV exists, the copy is redundant — so `calm` looked right on paper. On the
  screen it was worse: *"มันทำให้สับสนกว่าเดิม และเกิดคำถามว่าทำไมมันไม่แดง"*. One exception
  in a column of red asks a question before it answers one. The words carry the nuance; the
  colour only says which pile the row is in.

### Backend

- `_carmen_verdict()` now returns the cell rather than a suffix to one: `Carmen: <what it
  said>`, or `Carmen refused it, no reason given (Code 1)` when it said nothing. The numeric
  code survives only in that second form — with no message it is the whole support ticket;
  with one it is noise in front of the sentence a human acts on.
- The two `duplicate_document` details are reworded to stand alone as the whole cell:
  `already posted to Carmen` and `a copy is already waiting for review`.
- `tax_id_mismatch` detail → `Tax ID {n} is not in this BU's register`. Not printed (support's

- `scripts/seed_review_demo.py` follows the new verdict format.

**Known gap:** those two duplicate lines and Carmen's verdict are English for a Thai reader.

system's and another person's. The duplicate pair *could*, by splitting the reason code in

## Auto-post posts what is ready to post

`11:45` `auto_post` meant *"post everything that passed the gate ladder"*. So a statement
whose lines did not reconcile, whose GL rule the AI had invented thirty seconds earlier, or
whose fee VAT was assumed at 7% because the footer could not be read, reached the customer's
ledger with exactly the same silence as a clean one.

The system knew. `_review_flags()` runs on every document and had the sentence written down —
it just wrote it to `review_payload`, a column `_finish()` immediately nulls on the way to
`posted`, and nobody ever read it. That is the 2026-08-18 note (*"warnings ถูกเมินตอน
auto-post"*), parked at the time. Yesterday's #22 closed one half of the gap: a charged
reading is kept for a human instead of thrown away. This closes the other: a charged reading
is **questioned** before it posts.

**`auto_post` now decides whether a _clean_ document waits. It can no longer decide that a
doubtful one does.**

|  | Nothing flagged | Anything flagged |
|---|---|---|
| `auto_post = true` | posts | **parks** — was: posted |
| `auto_post = false` | parks | parks |

The gate is `_review_flags()` being empty — deliberately the same function that paints the
queue's Message column, whose empty case already read **Ready to post**. One predicate, so a
document the reviewer would have been shown a reason for cannot post behind their back. Two
definitions of "worth a human's eye" drift silently in exactly one direction.

### Backend

- `email_ingest_service.py` — the fork computes `flags` once and reads
  `if not auto_post or flags:`. `_park_for_review` takes them from its callers instead of
  recomputing, since the same list is now the decision *and* the row.
- **A fifth flag, `doc_no_missing`.** The only one about what we could not *check* rather
  than what we read: both duplicate guards key on `doc_no` — `has_submitted_doc` and
  `_already_pending` answer False without one — so an unnumbered statement forwarded twice
  posts twice into real books with nothing able to catch it. A flag and not a `_Skip`,
  because a reviewer can post one on purpose: it stops the machine, not the person.
- **`REVIEW_BACKLOG_CAP` and `_already_pending` stop reading `not auto_post`.** Both were
  written when a BU with review off could not park anything; #51 ended that and this makes
  parking routine there. They had become holes on the main path — an auto-post BU had **no
  backpressure at all**, so a dead credential would charge for every document while its
  queue filled, and a re-sent statement parked a second identical row.
- **The `mapping_incomplete` raise is deleted.** It was the `and auto_post` half of a branch
  whose other half already fell through to the fork. `mapping_missing` is a flag, so it parks
  under both settings — one path, rather than two that can drift on what the row says. New
  rows carry no `reason_code`; `reasonFor` names the unmapped fields from the payload, and on
  a `pending_review` row Review already outranked the Fix-mapping link. The code stays in
  `reviewReasons.ts` for the rows that already have it.

### Frontend

- `ReviewFlag` gains `doc_no_missing`; `QueueRow.reasonFor` gains its rung — below the two
  mapping reasons (a reviewer can post this one as it stands), above `warnings`.
- `review.reasonDocNoMissing` — *no document number* / *ไม่มีเลขที่เอกสาร*.
- **The auto-post copy described the wrong feature.** *"Post without review — documents post
  to Carmen as soon as they are read. Nothing waits here for approval"* is now *"Post clean
  documents automatically"*, and the hint **names what still stops**: a warning, a GL mapping
  the AI had to guess, amounts that do not reconcile, a missing document number. A person
  flipping this switch is trusting it; the copy has to say what they are trusting.

### Docs

`06-decision-log.md` #24, `07-human-in-the-loop.md` §15 (with the five decisions and what a
BU will notice), diagrams 6/7/8 in `02-architecture.md`, `CARMEN_INTEGRATION.md` §0.1/§0.2/§3.3

## Nine banks through the real mailbox — and three guards that do not hold

`12:20` The section above ended with **"Not run: the end-to-end script itself"**. Run now, on
the live dev mailbox, against both configured BUs — not the two PDFs `email_ingest_e2e.py`
recycles, but all nine layouts in `Desktop/document_format` wrapped one-per-page into PDFs
and APPENDed with the `+tag` in `Delivered-To`, alongside a realistic pile of junk.

Four polls, **37 documents charged, ~$0.037**, nothing refunded:

| Run | BU | `auto_post` | Result |
|---|---|---|---|
| 1 | carmen | off | 9 parked, 0 failed |
| 2 | carmen | on | **8 posted — JV 1019-1026**, 1 parked, 0 failed |
| 3 | carmen | off | 9 parked (left in the queue to look at) |
| 4 | carmencloud | off (as configured) | 10 parked, 0 failed |

**What held.** All nine layouts read, `doc_no` extracted from every one, and `_resolve_bank`
named the issuer from the document itself in all nine — no rule-vs-document warning fired, so
the filename rules and the printed issuer agreed everywhere. Noise behaved identically with
`auto_post` on and off: no attachment → no row at all; a signature logo → `no_rule_match`; the
same message twice → **one** ledger row; `.xlsx` → `unsupported_attachment`; a disguised PDF →
`unreadable_document`; a locked one → `wrong_pdf_password`; untagged and unknown-tag mail →
`unrouted`, no row, no charge. A bank zip expanded correctly: the CSV dropped inside `_unzip`,
the summary PDF refused by name, and only the statement charged. `sender_not_allowed` fired on
carmencloud (which has `owner_emails` set) and named the addresses the mail actually carried.
Both `posted` and `pending_review` rows are visible in the queue, and every `posted` row
recorded its input-tax document with no note.

**The second factor is per-BU, and inverted between the two.** BBL and both SCB statements
print `0105555181506`, which is carmen's registered ID — clean there, `tax_id_mismatch` under
carmencloud. KBANK prints carmencloud's `0835553001610` — the reverse. Working exactly as
designed, and worth writing down: four of the nine samples belong to another company and can
never post unattended under carmencloud.

### Three findings, none of them fixed here

1. **`_already_pending` is unreachable for any document that also trips an earlier `_Skip`.**
   In `_run_document` the order is tax ID → `is_duplicate` → `_already_pending`, so a document
   that parks with `tax_id_mismatch` never reaches the guard whose own comment says *"a second
   identical row is the thing this check exists to prevent"*. Reproduced: BBL forwarded twice
   in two messages left **two identical `pending_review` rows** for `26079-0001954` in
   carmencloud's queue, both saying `tax_id_mismatch`. The guard only runs for documents clean
   enough to pass the two checks above it — the case where it is least needed. Moving it above
   the tax-ID check is the whole fix: it reads `bank_code` and `doc_no`, both known the moment
   extraction returns.

2. **`mapping_guessed` guards only the first document that needs the guess.**
   `fill_missing_mappings` saves what the AI invented with nothing marking it as AI-filled, so
   the next document carrying that payment type is not "guessed" any more and posts unattended
   — against the rule stated in `unmapped_payment_types`' own docstring (*"an LLM-guessed
   mapping must never post by itself"*, CARMEN_INTEGRATION §4). Demonstrated across runs 1 and
   2: KTC and SiamPay parked with `mapping_guessed`, then posted as JV 1023 and 1026 on the
   identical documents, on mappings no human ever confirmed. A source column on
   `bu_accounting_mapping_entries` that `_review_flags` reads until someone confirms would
   close it.

3. **A dead posting credential is invisible in the queue.** carmencloud's stored token is
   expired — `GET /Carmen.API/api/interface/accountCode` answered **401** during run 4 — but
   the call happens inside `_suggest_missing_mappings`, which catches `CarmenAPIError` and
   returns `{}`. So `mark_token_unverified` never runs, the bell says nothing, and the single
   symptom is one row reading `mapping_missing`, which sends the reader to the mapping page
   rather than to the credential. `carmen_token_verified_at` was already null. Carmen itself is
   fine — the browser's own session token fetched the same masters with a 200 minutes earlier;
   it is the stored unattended credential that is dead, and it is the only one the poll can use.

**Also seen, smaller.** `warnings` is not deterministic: the GHL invoice parked with *"the line
items do not add up"* in run 1 and posted in run 2 from the same PDF, so for that document the
auto-post gate turned on the model's variance rather than on the document — unlike `unbalanced`,
which is Python arithmetic and answers the same way every time. And the GHL payment type is
read as three lines run together (`TRANSACTION FEE 30-05-2026\nGross Amount 1,277,748.00
Baht\nDA00001562`), which `fill_missing_mappings` then stored as a mapping key: it carries a
date so it can never match next month's invoice, and `build_jv_rows` uses that same key as the
JV line's description.

### Operational note

The dev project's `email-ingest` cron fires every 10 minutes at the **deployed** backend
(`app.base_url` → onrender.com), which polls this same mailbox. Any live test has to pause it
(`select cron.alter_job(37, active := false)`) or the two race for the mail and the deployed
copy wins with main-branch code. `update cron.job` is denied to the app role; only the function
works.

## The queue row's Actions cell holds one button

มันรก"* and *"btn-icon rq-dismiss อยู่ตรงนี้ไม่ดี"*. Design: [`07-human-in-the-loop.md` §16](../docs/email-automation/07-human-in-the-loop.md).

### Frontend
