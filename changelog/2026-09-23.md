`10:35` **Email ingest — `owner_emails` matches whole addresses, not substrings.**
Branch `fix/ca102-m009-sender-exact-match`. CA-102 TC-M-009, ticket T-04a.

The QA report on M-009 said a message from an unregistered sender reached the review
queue. Checking it against the code showed that `sender_allowed()` exists and runs before
any charge. So the report was not about a missing check. It turned up a real precision
bug instead:

- **Bug:** `email_imap.sender_allowed()` lowercased the raw From/To/Cc text and tested
  each registered address with `in`. A registered `a@b.com` also admitted
  `xa@b.com`, `a@b.com.evil.io`, and a display name the sender typed as
  `"a@b.com" <x@evil.io>`.
- **Fix:** the headers are parsed by the existing `people_addresses()` (`getaddresses`)
  and compared as a set against `owner_emails` (stripped, lowercased). Empty
  `owner_emails` still accepts every sender. A header with no readable address is refused
  once a list is set. `28da9b0`
- **Test:** `test_sender_allowed` fixtures now use the comma-joined shape `fetch_unseen`
  actually builds. The old `"From: … To: …"` strings are not a real shape and parse to
  nothing. Added four cases, three of which failed before the fix. `fa0b4bb`
- Email suites: 321 passed.

**Unchanged on purpose:** the gate still reads From/To/Cc, so an auto-forward still passes
because the BU's own mailbox is in `To:`. This gate stops misdirected mail. It does not
stop someone attacking on purpose; the envelope `+tag` does that (decision-log #16). QA
should retest M-009 by sending *directly* from an unregistered address, not through a
forward filter.

Also: `CONTEXT.md` gains **Skipped**, **Failed** and **Owner emails**, the terms CA-102
used differently from this codebase.

No release note. A few rows move from posted to `sender_not_allowed` for a BU whose list
only ever matched as a substring, which is the gate working as documented.

`10:50` **Email ingest: a second copy of a queued document no longer rings the bell.**
Branch `fix/ca102-m027-duplicate-pending-no-bell`. CA-102 TC-M-027.

- **Bug:** `_run_document`'s `_park_or_finish` sends the `_already_pending` duplicate
  (`_Skip(reviewable=False)`) through `_finish` with notify on. Every re-sent copy
  therefore raised a `document_failed` notification, even though the copy the customer
  can act on is already waiting in the queue, which rang its own bell.
- **Fix:** that path passes `notify=reviewable`, so the duplicate finishes silently. It is
  the only `reviewable=False` raise site. `e57d39b`
- **Test:** `test_a_second_copy_of_something_already_in_the_queue_does_not_park` now also
  asserts that no `UserNotification` is created. It fails before the fix. `c75c40e`
- Email suites + `test_credit_card_activity_api`: 352 passed.
- `docs/email-automation/04-data-model.md`: the taxonomy row says the duplicate raises no
  notification, and drops the stale "review mode only".

**Deliberately unchanged:** the status stays **`failed`** even though CA-102 asked for
`skipped`. The duplicate is only detectable after extraction (it keys on `doc_no`), so it
has always been charged, and `skipped` means "stopped before the charge". Decided with the
owner. The QA Coverage Matrix gets a spec correction; the code keeps its meaning. Credit
logic and the duplicate-after-posted branch (CA-102 W-1) are also unchanged.

No release note (no visible change beyond one fewer notification).
