## Two bugs the queue test found, one of them in the ledger's own numbers

`17:10` A full pass over carmencloud (7 banks, 17 charged documents, JV 1027–1033) turned up

### GHL's mismatch warning was a false positive, on every invoice that bank sends

`_labeled_footer_value` takes the **first non-zero column** on the row labelled `GRAND TOTAL`,
and GHL is the layout this file's own header names as the one whose Net and Commission arrive
swapped — so the "grand total" it reads is the fee before VAT. Compared literally it misses
Σ fee + VAT by exactly the VAT, forever:

```
lines 39,653.73   printed 37,059.56   gap 2,594.17
      (fee+VAT)           (= fee_sum)       (= VAT exactly)
```

Every GHL document therefore carried a warning, parked for review, and could never auto-post
— and the reviewer was shown a contradiction, since the JV underneath said *Balanced*.

- `services/credit_card_service.py` — the anchor is interpreted before it is believed, the
  way the rest of this module treats every figure whose column it cannot trust. It
  corroborates the lines if it equals **either** reading, the grand total or the sub-total the
  fee sum already is; only a figure that is neither means a line fee was genuinely misread,
  which is the one thing the check exists to catch.
- `tests/unit/test_fee_invoice_clamp.py` — the GHL document reduced to two rows (verified to
  fail without the fix), and a note on the B7 case saying why 160.50 must still warn: it is
  neither 150.50 nor 140.00.

### The AI's GL answer was not stable, and the first approval makes it law

Seven documents, one Carmen master: `commission` came back `GEN/6080008` six times and
`307/6080008` once (PayPal); `net` came back `GEN/1011001` five times and `GEN/1011003` twice.
`commission`/`tax`/`net` are **BU-wide**, so approving the PayPal document wrote dept `307` as
the rule for every bank the BU receives.

Not the model — `call_text_llm` already pins `temperature=0.0`. The candidate list is what
moved: `score_and_pad` sorts by keyword score alone, and Python's sort is stable, so every
account with an equal score keeps **Carmen's response order** before the list is cut at
`limit`. `departments[:50]` truncates that same order. Nothing guarantees it between two
calls, so the same question could be asked with a different set of candidates and answered
differently, with no bug visible anywhere.

- `services/gl_suggestion_service.py` — `_by_code()` sorts accounts and departments at both
  entry points, before anything filters or truncates. Deliberately **not** in
  `utils/gl_filter.py`, where the order dependency physically lives: AP invoice shares that
  file and is out of scope. Sorting the input is enough, since every step downstream
  preserves order.
- `tests/unit/test_gl_suggestion_order.py` (new) — hands the same master in reversed order and
  asserts a byte-identical prompt. Both cases fail without the sort. Sized so a reordering
  changes list *membership*, not just position, which is the sharper failure.
- `components/credit-card/JvEditor.tsx` — an `Every bank` tag beside the three BU-wide rules,
  shown only while the value is still in play (guessed, or edited and unsaved). The reviewer
  cannot see scope from the row: the document in front of them names one bank and the answer
  binds all of them. Permanent tags on all three rows of every document would be noise; the
  point is the moment of decision. `BU_WIDE` is hoisted out of the inline literal it already
  used at line 113. EN + TH.

## The mismatch warning names the figure it is comparing against

`15:56` Reported from the queue: the amber banner on a GHL fee invoice reads *"The line
items do not add up to the document's printed grand total"* while the JV underneath it says
**Balanced**, and nothing on the screen reconciles the two. The reviewer is told to be
suspicious and given nothing to be suspicious about.

The banner is right and the screen is right — they are talking about different arithmetic.
The JV balances by construction (its debits are built from the same lines as its credits).

reviewer cannot see. On this document the lines are internally perfect: fee 37,059.56 + VAT
2,594.17 = 39,653.73, exactly the credit leg.

So the warning now carries both figures and the gap between them, which is also what decides
whether to care: two satang is a rounding artefact to wave through, two thousand baht is a
misread digit worth opening the PDF for.

## The BU reset script clears the fourth thing that remembers

`14:20` Preparing a from-scratch pipeline test on `dev.carmen4.com / carmencloud` —

### Scripts

- `scripts/reset_tenant_email.py` — `--clear-mapping` drops `bu_accounting_mapping_entries`
  + `bu_accounting_configs` for the BU. Hard delete, not the usual soft one:
  `get_accounting_config` returns an empty response for a *missing* row, which is the
  "never opened the mapping page" state the suggester is written for, while a soft-deleted
  config with live entries is a shape the app never produces. Off by default — replaying one
  mail should not cost a BU its mapping.
- Same file — `email_queue_seen` is deleted alongside `email_documents`. The table landed a
  month after this script was written; left behind, its per-chip high-water mark means a
  genuinely new queue opens already acknowledged and the attention dot stays dark.
- Same file — **`enabled_at` is now cleared in the `--keep-tag` branch**. It was the one
  column that branch forgot, and it quietly undid the script's own `--unread`: re-enabling
  stamps `enabled_at = now()` (`email_settings_service.py:555`), so every mail marked unread
  was then older than it and came back `skipped / ingest_paused`. The delete branch never had
  the bug — the whole row goes.
- Same file — `--clear-manual` soft-deletes the BU's **wizard** scans too. Found by looking at
  the screen after the first run: the module's Posted tab is two sources merged
  (`credit_card_activity._manual_stmt` — this BU's `email_documents`, plus every submitted
  `credit_cards` row with no email row behind it), so clearing the ledger emptied one half
  and left 19 hand-scanned JVs on screen, which reads as a reset that did not work.
- `scripts/email_ingest_e2e.py` — `OTHER_TENANT` moves off **carmencloud** to `…/demo`, and
  the teardown delete gains `and rules = '[]'::jsonb`. The script borrowed carmencloud as a
  scratch BU for the one-tax-ID-two-BUs case and then **deleted its whole settings row** in
  `teardown` — written when that BU had none. It has a live ingest tag now, so a routine e2e
  run would have released the tag and silently broken the customer-side Gmail forward. The
  guard is on the delete rather than on the constant, so re-pointing it stays safe.
- `scripts/reset_email_test.py` — one `sys.stdout.reconfigure` line. Attachment names are
  frequently Thai and the Windows console is cp1252, which raised `UnicodeEncodeError`
  mid-listing, after the query and before anything had been decided. Both scripts import
  from here.
