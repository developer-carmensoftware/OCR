## One voice in the review queue's Detail column, one name for the feature

`10:20` A wording pass over every string the queue can print, read end to end for the first
time. The column is fed from four places nobody had compared: `reasonFor`'s flag ladder, the
`review.rc*` dictionary, `error_message` written by `email_ingest_service.py`, and
`cc_input_tax.py`'s skip reasons. Three of the findings are defects rather than taste.

1. **The dialog said it twice.** `stopText` was written so a detail *replaces* the phrase —
   its own docstring names the vacuous head as the thing it removed. `ReviewDocument.tsx`
   kept a second copy that appended unconditionally, and since §13 made `duplicate_document`
   and `carmen_rejected` park at `pending_review`, the two met on screen daily:
   *"already handled · already posted to Carmen"*, and *"Carmen refused it · Carmen: Period
   2026-08 is closed"* — `_carmen_verdict`'s "say it once" broken by its caller.
2. **Two prefixes for one outcome.** `_post_input_tax` wrote `"JV posted; input tax not
   recorded: …"` and `build_input_tax_payload` wrote `"input tax skipped: …"`, both into the
   same cell — which is already prefixed by `Posted automatically ·`, so the old head
   restated the row it hung off. The Carmen branch nested a second colon:
   *"JV posted; input tax not recorded: Carmen: …"*.
3. **"Forwarding" named the wrong system.** Settings Step 3 uses that word for the rule the
   customer sets up in **their own** mailbox, so *"Forwarding is switched off right now"*
   sent them to Outlook to look for our switch.

Full reasoning and decisions 89–95: [`docs/email-automation/07-human-in-the-loop.md` §19](../docs/email-automation/07-human-in-the-loop.md).

### Frontend

- `lib/reviewReasons.ts` — `stopText` moves here from `QueueRow` and becomes the only thing
  that decides what a stopped row says. Structural param type, so both `ReviewDocument` and
  `ReviewDocumentDetail` satisfy it. `full` is the single flag the two surfaces differ on:
  the dialog appends the detail a cell keeps on its tooltip, and never repeats a detail the
  phrase was already replaced by.
- `components/credit-card/QueueRow.tsx` — the pending-with-a-reason branch calls `stopText`
  instead of printing the phrase alone, so Carmen's verdict now appears on the row that can
  still act on it rather than only on the dead one. The `received` branch gains a title
  saying nothing will retry it (`_claim` returns `None` on the dedupe hit, so it never is).
- `pages/ReviewDocument.tsx` — the reason banner calls the same helper. Removes the
  duplication above.
- `i18n/dict.ts` (EN + TH) — sentence case on every phrase the column can print. Three
  reasons re-nouned to match the settings field their Fix button opens:
  *Sender is not one of your email addresses* (**Your email addresses**), *No filename
  pattern matched* (**Filename patterns**), *The Carmen posting credential is no longer
  accepted* (**Posting credential** — also drops "expired", which a revoked token is not).
  Column header `Message` → **`Detail`**. New `review.rcStuckHint`.
  `notif.reason.carmenRejected` *declined* → *refused*, so the bell and the queue use one
  verb for one event; the two blocks now carry a comment naming each other.
- `pages/EmailSettings.tsx` — heading `Email Automation` → **`AI JV Automation`**, the name
  every message that sends a reader here now uses.
- `pages/ReviewQueue.test.tsx` — assertions updated; one case added, that a pending
  `carmen_rejected` row prints Carmen's verdict rather than the phrase.
  `components/common/NotificationBell.test.tsx` — the verb.

### Backend

- `services/email_ingest_service.py` — `Already posted to Carmen` / `A copy is already
  waiting for review` capitalised (they *are* the cell, not a tail on one). The input-tax
  note drops its `JV posted;` head and uses one prefix, `Input tax not recorded`, with an em
  dash before `_carmen_verdict` so the colon does not nest. `ingest_paused` names AI JV

- `services/cc_input_tax.py` — the four skip reasons take the same `Input tax not recorded`

- `services/email_settings_service.py` — the two enable-blocker messages name AI JV

## The AI's answer was computed, carried, and then hidden

`14:45` Found by testing, not by reading: the first document through the freshly-cleared
carmencloud parked correctly with all five GL rules filled by the AI — and the review dialog
showed *This business unit has no accounting configuration yet* over *There is nothing to
post*, with no pickers and no JV. Exactly the blank form `_suggest_missing_mappings` was
written to prevent, on the one BU state it was written for.

The two halves disagreed about what "no config" means. Backend: a BU with no
`bu_accounting_configs` row is the case worth spending an LLM call on, and since decision #25
the suggestion rides on `email_documents.review_payload.suggested` rather than being saved.
Frontend: `useAccountingConfig` reports an empty config as `null` (deliberately —
`AccountingReview` keys its own banner off that), and `JvEditor` bailed on `!config` before
looking at `overrides`, which `ReviewDocument` had already seeded from `suggested`. So the
answer existed in three places and was rendered in none.

Invisible until now because every parked document arrived at a BU that had a config row:
ingest used to save its guesses, and the reviewer screens have only ever been exercised
against BUs that had already used the wizard. `--clear-mapping` is what produced a BU in the
state the code claims to support.

### Frontend

- `components/credit-card/JvEditor.tsx` — `effective` starts from `config ?? {}` and returns
  `null` only when nothing is stored **and** nothing was suggested; the render guard keys off
  `effective` instead of `config`. Two lines, and the notice still appears for a BU with
  genuinely nothing to show.
- `pages/ReviewDocument.test.tsx` — two cases: a null config plus `suggested` renders the JV
  (fails without the fix, verified by stashing it), and null-plus-nothing still shows the
  notice. The file's fixture comment said *"every payment type is mapped, which is the state
  a parked document actually arrives in — ingest fills and saves before it parks"*, which
  stopped being true on 2026-09-04; that assumption is the reason the gap had no test.

## The JV header tells the truth about what is missing

`15:05` Three things the same empty BU exposed in the review dialog's header, all of them
about a field with nothing in it.

1. **An unset prefix looked set.** The picker's placeholder was the word *Book*, which is
   also what its values are — journal book names — so an empty control read as a chosen one.
   It is a dash now, the same `-` the wizard's own step-4 badge has always printed for it
   (`AccountingReview`), and the field carries `rd-f--missing` like DocNo and DocDate above
   it.
2. **A JV with no book could be posted.** `build_gljv_payload` sends `Prefix:
   config.file_prefix or ""`, so an unset book does not fail loudly — it posts into whatever
   Carmen makes of a blank one, which is not a decision anyone should take by accident. The
   reviewer is the last place that can notice, so Approve is now unavailable and says
   *Choose a prefix before posting*, through the existing `blockReason` ladder that
   already keeps the sentence and the disabled state from disagreeing.
3. **The description accused the statement of an omission it could not have made.** The
   field's placeholder was `review.fMissing` — *Not on the document* — in the amber italic
   `.rd-f-input::placeholder` sets, which DocNo and DocDate earn by being document fields the
   extractor could not fill. The description is BU config, was never on the document, and
   posts empty with nothing refusing it. It now says *Description* and takes the muted
   treatment `itx-branch` already had: that rule's own comment called itself *"the one
   placeholder on this screen that is not a complaint"*, and there are two of them now.

On the third: there is **no default header description anywhere** in either pipeline —
`buildGljvPayload` and `build_gljv_payload` both send `Description: ""` when the BU has set
none, and `descriptionForBank` only chooses between a per-bank entry and the BU-wide one.
What the wizard *does* default is the **line** descriptions (`Credit card commission`,
`Input Tax`, `Bank Account`, and the payment type for a credit leg, `ccJv.ts`), and the
review dialog already shares them — it calls the same `buildJvRows`. So the two surfaces
differ in wording only, which is what changed here.

- `components/credit-card/JvHeaderCard.tsx` — dash placeholder + missing-marking on Prefix;
  the description gets its own placeholder key rather than borrowing the document one, and
  `rd-f-input--optional` to opt out of the amber.
- `styles/pages/review-queue.css` — the muted-placeholder rule takes a second selector

- `pages/ReviewDocument.tsx` — `effectivePrefix` resolved the same way the header card

## The description is per bank on both screens now, not just one

`15:40` The wizard's config editor has always treated this field as per-bank: the box holds
`bank_descriptions[bank]` **raw**, and the BU-wide sentence sits in the placeholder. Its own
comment says why — feed the fallback into the value and the field cannot be cleared, because
deleting the last character resolves the fallback back into it under the cursor.

The review dialog did neither half. It showed the *resolved* value, so the BU-wide sentence
looked like this bank's own; and `patch_config` wrote the BU-wide field whenever the bank had
no entry yet. Together that meant a reviewer correcting the wording on an SCB statement
rewrote the wording for every other bank the BU receives — and then found their text reading
as a placeholder rather than a value, because the write had gone somewhere else.

### Frontend

- `components/credit-card/JvHeaderCard.tsx` — the box holds this bank's own entry; the
  BU-wide wording becomes the placeholder (`fallback || 'Description'`), which is what the
  muted "not a complaint" treatment added earlier was already right for: it is a preview of
  what will post, not a gap. Drops the `descriptionForBank` call — with the bank excluded it
  resolved to `config.description` and nothing else, so the field is named directly.

### Backend

- `services/accounting_config_service.py` — `patch_config` writes `bank_descriptions[bank]`
  whenever a bank is named, creating the entry rather than only updating an existing one; the
  BU-wide field is now only for an edit that named no bank at all. It is also the entry
  `description_for` prefers, so this is still the field that wins at posting time — the old
  rule's stated reason, applied one case wider.

### Tests

- `tests/unit/test_accounting_config_service.py` — the case asserting the old fallback is
  replaced by its opposite (a first edit starts that bank's entry and leaves the BU-wide one
  alone), plus one for the no-bank path.
- `pages/ReviewDocument.test.tsx` — the preview case now expects the BU-wide sentence as the
  *placeholder* with the field empty, and a new case for a bank that has its own wording.

email pipeline all green; `tsc` clean, eslint 0, ruff check + format clean.

## The BU reset script clears the fourth thing that remembers

`14:20` Preparing a from-scratch pipeline test on `dev.carmen4.com / carmencloud` —
new Carmen token, real forwarded mail, and the AI GL-suggestion path actually exercised.
Three guards already had a reset (`email_documents`, `credit_cards.submitted_at`, IMAP
`\Seen`); the fourth is the BU's own GL mapping, which is what stops
`_suggest_missing_mappings` from ever running once a payment type has been mapped. Testing
AI suggest and clearing old data turn out to be the same task.

### Scripts

- `scripts/reset_tenant_email.py` — `--clear-mapping` drops `bu_accounting_mapping_entries`
  + `bu_accounting_configs` for the BU. Hard delete, not the usual soft one:
  `get_accounting_config` returns an empty response for a *missing* row, which is the
  "never opened the mapping page" state the suggester is written for, while a soft-deleted
  config with live entries is a shape the app never produces. Off by default — replaying one
  mail should not cost a BU its mapping.
- Same file — `email_queue_seen` is deleted alongside `email_documents`. The table landed a
  month after this script was written; left behind, its per-chip high-water mark means a
  genuinely new queue opens already acknowledged and the attention dot stays dark.
- Same file — **`enabled_at` is now cleared in the `--keep-tag` branch**. It was the one
  column that branch forgot, and it quietly undid the script's own `--unread`: re-enabling
  stamps `enabled_at = now()` (`email_settings_service.py:555`), so every mail marked unread
  was then older than it and came back `skipped / ingest_paused`. The delete branch never had
  the bug — the whole row goes.
- Same file — `--clear-manual` soft-deletes the BU's **wizard** scans too. Found by looking at
  the screen after the first run: the module's Posted tab is two sources merged
  (`credit_card_activity._manual_stmt` — this BU's `email_documents`, plus every submitted
  `credit_cards` row with no email row behind it), so clearing the ledger emptied one half
  and left 19 hand-scanned JVs on screen, which reads as a reset that did not work.
- `scripts/email_ingest_e2e.py` — `OTHER_TENANT` moves off **carmencloud** to `…/demo`, and
  the teardown delete gains `and rules = '[]'::jsonb`. The script borrowed carmencloud as a
  scratch BU for the one-tax-ID-two-BUs case and then **deleted its whole settings row** in
  `teardown` — written when that BU had none. It has a live ingest tag now, so a routine e2e
  run would have released the tag and silently broken the customer-side Gmail forward. The
  guard is on the delete rather than on the constant, so re-pointing it stays safe.
- `scripts/reset_email_test.py` — one `sys.stdout.reconfigure` line. Attachment names are
  frequently Thai and the Windows console is cp1252, which raised `UnicodeEncodeError`
  mid-listing, after the query and before anything had been decided. Both scripts import
  from here.

### Applied

`14:22` Dry run then `--apply` on carmencloud with `--keep-tag --keep-sub --clear-mapping
--no-unread`: 45 `email_documents`, 1 `email_queue_seen`, 22 mapping entries + 1 config, 111

cleared. Tag `1ad4e0b6` and the active subscription survive by design.

`--no-unread` deliberately: the 43 known messages stay `\Seen`, because re-enabling with
