# 2026-11-06

## Config: `OPENROUTER_API_KEYS` alone counts as a configured key (branch `fix/openrouter-key-pool-guard`)

`13:57` Found while switching dev's `.env` to a funded OpenRouter account. With only the
`OPENROUTER_API_KEYS` pool set, six checks that ask "is a key set?" still read `OPENROUTER_API_KEY`.
- **Backend** ([`893d87b6`](../../commit/893d87b6)): when `openrouter_api_key` is empty, a `Settings`
  validator gives it the pool's first key. The pool already falls back to the single key, so this is
  the reverse. Which keys the calls use does not change.
  - **Before the fix:**
    - a credit-card scan answered a bare 500 (`ValueError`);
    - AP answered 500 "OPENROUTER_API_KEY is not configured";
    - the credit-card GL and payment-type suggestions were skipped silently;
    - the startup banner said "Not set".
  - PMS suggestions use the pool, so they kept working.
- **Tests:**
  - Unit: 4 cases (pool alone, single key alone, both, neither). The CI mirror passes at 82%
    coverage.
  - E2E in a real browser on local Supabase, with the backend given the pool alone:
    - **main (control):** AP returned 500 with the message, credit-card returned 500 (the log shows
      the `ValueError`), and no credit was charged.
    - **this branch:** the banner says "Configured". The AP and credit-card scans read the mock
      documents and open Step 2, charging 1 credit each. AI Suggest on Mapping Settings calls the
      AI (`credit_card_ocr/suggest`) and shows suggestions. No page errors.
- `.env.example` now says either variable alone is enough.
