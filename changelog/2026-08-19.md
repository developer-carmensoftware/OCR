## SQL performance audit — measurement pack (no behaviour change)

`15:30` **Answering "is the SQL actually fast, or just working?" with numbers instead of a
code read.** A full pass over the query surface — 181 SQLAlchemy statements, 182 `.execute()`
sites, 51 tables, 174 named indexes, 15 pg_cron jobs — turned up nine things worth checking.
But the cost of the risky ones depends on how much data exists, which the source cannot say,
so **this commit measures and changes nothing**: no schema, no runtime code, no cron.

### DB

- `db/queries.sql` — new **Performance audit** block, items 15–24, continuing the existing
  numbered convention. Ten read-only queries covering: measurability
  (`pg_stat_statements` present + window since last reset), latency trend per endpoint per
  week, CPU attribution per query, table size and per-partition growth, never-used indexes,
  buffer cache hit ratio and sort spill, seq-scan ratio, dead cron / 404 storms, pool
  pressure, and autovacuum lag. Deliberately a *pack you re-run*, not an admin page —
  the answer is a diff against last quarter, not a live chart nobody opens.
  - `UNIQUE`/`PRIMARY` are excluded from the unused-index query on purpose: they enforce
    constraints whether or not a query reads them, and one of them
    (`uq_credit_cards_submitted_doc`) *is* the duplicate-post guard.
  - Header carries the run instructions, because the obvious way to run it is the wrong one:
    driving this from a Python script while `uvicorn` is up is how the documented
    `EMAXCONNSESSION` outage happened. SQL Editor only, one item at a time.

### Docs

- `docs/SQL_PERFORMANCE_AUDIT.md` — the report skeleton, modelled on
  `LOAD_TEST_REPORT_V2.md` so it reads like the report the team already knows. Method,
  inventory, and each finding's *hypothesis* are filled; every measured cell is `—` until the
  queries run. Carries the pieces that make it a measurement rather than an opinion: a budget
  table fixed **before** measuring (p95 < 1500 ms admin / < 800 ms wizard, no query > 5% of
  DB CPU, cache hit ≥ 99%, temp spill = 0, seq scan < 5% over 10k rows), a three-value
  verdict (PASS / WATCH / FAIL), a headroom formula against the 30 s `statement_timeout` with
  its linearity assumption written down, and an explicit list of what the audit *cannot* see
  (pre-DB failures, literal normalisation hiding per-tenant plan differences, counter resets).
  - Rule recorded in the doc: a finding that measures clean keeps its row with `PASS`. A
    report that only retains the findings it got right is a report nobody can calibrate.

### What the code read found — hypotheses, not verdicts

Ranked by suspected cost. All nine are in the report with the metric that would confirm or
kill each one:

- **F1** `/admin/llm-usage` and `/admin/performance-logs` default their date range to `None`
  and neither frontend page sends one, so `ORDER BY created_at DESC LIMIT n` runs with no
  predicate on the partition key. Every index on both tables leads with `tenant_id`, so there
  is no ordered path for `MergeAppend` either — the expected plan is scan-all-partitions-then
  -sort, on the two fastest-growing tables in the schema.
- **F2** `last_used_q` in `GET /admin/tenants` sits *outside* the `include_engagement` gate
  that exists specifically to keep `TenantSelector`'s five other callers from paying for
  aggregates — and it is the most expensive query in the handler (`max()` per group over a
  partitioned table, no time bound).
- **F3** `carmen-webhook-push` is scheduled `* * * * *` against `/api/v1/admin/webhooks/push`,
  which exists on no branch that is merged. ~1,440 pg_net round-trips, 404s, and junk
  `performance_logs` rows per day, which then inflate every other query in this audit.
- **F6** `/usage-summary/totals` never calls `_assert_date_range()` though its sibling
  `/usage-summary` does — the only finding confirmable from source alone, so it is marked
  CONFIRMED rather than left pending. One-line fix, held back so this commit stays
  measurement-only.
- **F4/F5/F7/F8/F9** the nightly rollups are built and read by one service while the dashboard
  re-aggregates raw logs; `get_tenant_engagement_map` reads a tenant's whole never-purged
  history; `deleted_at`/`created_by` carry indexes the planner cannot use (`IS NULL` matches
  ~100% of rows) leaving `credit_cards` with 11; `submitted_at` has none at all; and nothing
  in the repo measures SQL — `performance_logs` times HTTP, so a slow page names the endpoint
  and never the query.

Also recorded in the report: the seven things the code already gets right (partitioned log
tables with retention, buffered writes for every high-volume log, TTL caches on both hot-path
lookups, atomic credit consumption, no N+1 anywhere, the per-checkout `statement_timeout`,
and the `ocr_tasks` composite index from the July pass). The wizard path costs ~6–9 queries
per request and holds no connection across the LLM call — it is not where the risk is.

## SQL performance audit — measured, then fixed

`16:45` **The measurements came back and I was wrong about which things mattered.** Items
15–24 were run against production; every number is now in `docs/SQL_PERFORMANCE_AUDIT.md`
with the query it came from. Branch `chore/sql-audit-cleanup`.

**The headline: the database is idle.** Total SQL execution across the whole instance is
**18.5 minutes over 68 days** — a 0.019% duty cycle — of which roughly a third is
application-owned (~5.7 s/day). The entire database is ~50 MB; `credit_cards` holds 255 rows,
`ocr_tasks` 342, `ap_invoices` 41. **Four of the nine hypotheses (F2, F4, F5, F8) do not
appear in the top-20 CPU consumers at all**, and F1 is below 0.8%. They are recorded in the
report with a PASS verdict rather than deleted — a report that keeps only the findings it got
right is one nobody can calibrate against.

So **no query was rewritten and no index was added.** What shipped is housekeeping, and every
item of it was found by measuring rather than by reading:

### DB — `20260819000000_audit_cleanup.sql`

- **`cron.job_run_details` had no retention** and is, at 17 MB, the largest object in the
  database — larger than every business table combined, with `est_rows = 0` because
  autoanalyze had never touched it. pg_cron does not purge its own history. New
  `fn_purge_cron_history()` + `cron-history-purge` daily at 03:40 UTC, 14-day window. 14
  rather than 7 because `admin/email_ingest.py::_cron_health` reads this table — though only
  for `max(start_time)` and the newest status, so any window longer than a job's period is
  safe, and every `email-*` job fires at least every 10 minutes.
- **`carmen-webhook-push` unscheduled.** It fired `* * * * *` at
  `/api/v1/admin/webhooks/push`, a handler that exists on no merged branch — the migration
  that schedules it was restored (`e72558b`) to unblock `db push` and brought its cron along.
  Measured cost: **exactly 1,440 404s per day for six days**, ~8,860 junk rows in
  `performance_logs`. Production was already clean (someone unscheduled it by hand on 08-17);
  this migration is what stops `db reset` or a fresh environment resurrecting it.
  `20260811000000` is deliberately left untouched — editing an applied migration is what
  broke `db push` here before.
- **`probe` unscheduled — a cron in production that exists in no migration.** `select 1`,
  every minute, almost certainly left behind by the SQL-Editor workaround for forcing a
  pg_cron launcher reload. No measurable CPU, but 1,440 rows/day into `job_run_details`,
  i.e. **half the growth of the item above**.
- **`ix_performance_logs_endpoint` dropped.** `idx_scan = 0` over an 89-day window, but the
  counter is not the argument: the only handler filtering that column uses
  `.contains()` → `LIKE '%x%'`, which a btree cannot serve at any data volume. Dropping the
  parent index cascades to every partition and stops new ones inheriting it. Scoped to this
  one index of the **105 that measured cold** — the rest are 16 kB stubs (~1.7 MB combined,
  each costing a migration line plus an ORM change), except the `(tenant_id, created_at)`
  pair, where the Performance page's tenant selector makes "unused for 89 days" weaker
  evidence.

### Backend

- `routers/admin/usage.py` — **`/usage-summary/totals` never called `_assert_date_range()`**
  though its sibling `/usage-summary` does, so `?from=2020-01-01` pruned no partition and
  summed the full retention window. One line. The 92-day cap turned out to be untested on
  *either* endpoint; the new `test_A2_rejects_date_range_over_92_days` was checked by removing
  the guard and confirming it fails, so it tests the fix rather than the mock.
- `middleware/performance.py` — **comment corrected, code deliberately unchanged.** It
  claimed the buffer reduces writes to "O(1) batch per 10s". Measured: **84,355 INSERT
  statements for 84,376 rows** — the batching is real per *transaction* and absent per
  *statement*. At ~1.3 s/day of database time that is not worth changing; the comment now
  says so, and records that the untested part is the Python side (500 statement compilations
  per flush is CPU that blocks the event loop on 0.1 vCPU).

### The finding the audit was not looking for

**Endpoint p50 has tripled since June** — `/admin/tenants` from 463 ms to 1,054 ms — but the
arithmetic rules out SQL: four cheap endpoints alone burn ~15,700 s of wall time in 4 weeks
against ≤456 s of *total* database execution, and `/notifications` shows a 1,220 ms median
while reading two queries off a table of under 200 rows.

A first attempt blamed a CPU floor from Render's `plan: free` (0.1 vCPU). **The control
experiment killed that**: `/api/v1/admin/webhooks/push` — the 404 storm above, which
accidentally left behind 8,820 samples of pure middleware-and-routing — has a p50 of **1 ms**,
and `/admin/auth/me` (JWT decode + a DB read) 9 ms. There is no floor. A second control,
`/maintenance/status`, is **flat** across five weeks, so the slowdown is endpoint-specific
rather than global drift. The withdrawn hypothesis is kept in §3.1c because it was wrong in an
instructive way.

Left as the strongest open lead, with evidence, in §3.1e: **269,875 `pgbouncer.get_auth()`
calls against 84,376 requests — 3.2 pooler authentications per HTTP request**, which a warm
pool should never do. That is application profiling and a separate piece of work.

## `15:09` Session drops every hour — it was our own cron, not Carmen

Pilot users kept getting thrown back to Carmen SSO mid-wizard, roughly hourly, with no
warning. Traced end to end today.

**Root cause.** `fn_purge_inactive_sessions()` (`20260721120000`) scrubbed every session with
`created_at < now() - 1 hour` and set `is_active = false`, on a `0 * * * *` schedule (confirmed
live in prod: 24 runs / 24 h, 0 failures). `auth/dependencies.get_current_session` 401s on
`not is_active`, and `lib/api/client.ts` turns any 401 into `ocr:unauthorized` → logout. The 1 h
cutoff was written when `SESSION_TTL_HOURS` was the 0.5 h code default ("2× the JWT TTL");
production runs **8 h** (`render.yaml`), so the job silently became the binding clock — every
session died 60–120 minutes after login, at the top of an hour, everyone at once. The 5-minute
expiry toast reads the JWT `exp`, so it was scheduled for minute 475 and nobody ever saw it.
Note this is a *different* killer from the one diagnosed on 07-23: since 07-27 a Carmen 401 no
longer flips `is_active`, which left this cron as the only thing revoking live sessions.

**Measured against prod before changing anything** (7 days of `ocr_sessions`): longest session
life **118 minutes** — under the cron's structural 120-minute ceiling, nowhere near the 480 the
JWT allows, so the job was provably the binding clock. **5 of 32** scrubbed sessions had a
request within 10 minutes of their scrub instant, i.e. the user was mid-work; that is a lower
bound, since anyone who paused 15 minutes and came back to a dead session isn't counted. 32
rows in 7 days also means the hourly cadence was 168 runs to touch ~4.6 rows/day.

### DB

- `15:09` **New `supabase/migrations/20260819010000_session_scrub_follows_jwt_ttl.sql`** —
  scrub cutoff `1 hour` → `8 hours`, i.e. `created_at + SESSION_TTL_HOURS`, which is exactly
  when the fixed-exp JWT dies. That is the tightest cutoff that can never touch a session still
  in use, so the job can no longer log anybody out. Not `last_used_at`: the JWT has no refresh,
  so an idle-based cutoff would only keep dead-JWT rows around longer. The interval is
  hardcoded and pinned by comment on both sides (migration ↔ `render.yaml`) — deliberately not
  read from `system_configs`, since the app reads the env var and a DB lookup would add a
  second source of truth rather than remove one.
- `15:09` **Schedule `0 * * * *` → `0 19 * * *`.** With a safe predicate the schedule is only a
  hygiene knob, and stage 2 (the 90-day row delete) never needed to run 24×/day. **pg_cron is
  UTC on Supabase**: 19:00 UTC = 02:00 ICT; `0 2 * * *` would have landed at 09:00 ICT, peak.
- `15:09` Everything else in the function is unchanged — two stages, `job_runs` bookkeeping,
  the `is_active = false` flip (still required: `_resolve_session_token` decrypts before it
  could notice a blanked token, so a scrubbed-but-active row would 500 instead of 401), and
  the `ix_ocr_sessions_scrub_pending` partial index (still on `created_at`, still valid).
- `15:35` **Applied to prod and verified.** `cron.job.schedule` = `0 19 * * *`; `prosrc` carries
  `interval '8 hours'`; a manual `select fn_purge_inactive_sessions()` returned 0 and left the
  live under-8h session `is_active` (1 → 1) — under the old cutoff that session would have been
  killed. `cron.job_run_details` is empty, which is expected twice over: 19:00 UTC hasn't come
  yet, and `unschedule` + `schedule` minted a new `jobid` that the old hourly history isn't
  attached to. **Still to confirm after the first 02:00 ICT run** — an empty `job_run_details`
  then means pg_cron's launcher never reloaded; re-issue one `cron.schedule` from the SQL Editor.

### Docs

- `15:09` `docs/Database_Design.md` — `ocr_sessions` lifecycle, the retention table, and the
  cron schedule table all said "hourly / `created_at + 1h`".
- `15:09` `docs/SQL_PERFORMANCE_AUDIT.md` §3.6b — the measured `0 * * * *` row keeps its value
  (it records what was measured on 2026-08-19) with a footnote pointing at this change, so the
  next audit doesn't read it as drift.
- `15:09` `render.yaml` — comment above `SESSION_TTL_HOURS` now says changing it requires a
  matching migration.

## `17:41` Frontend polish pass — contrast, one button vocabulary, font payload

Branch `polish/frontend-contrast-button-vocabulary`. An `/impeccable polish` pass over the
whole frontend. The detector came back near-clean (21 hits, 19 of them "Inter is an overused
font", a false positive for a product-register app), so the real findings came from
*measuring* the tokens rather than looking at them. Every number below is from
`frontend/scripts/contrast-audit.mjs`, added in this branch.

### Frontend — the defects that were actually costing something

- **`.btn-success` hover was 1.41:1 in light mode.** The rule hovered to `--emerald-mid` — a
  pale mint meant for borders — under an inherited `color: white`. The label vanished. It sat
  on the AP invoice's **"Generate Invoice → Carmen"** submit, i.e. the button that posts to
  the GL. Rest state was 3.43:1, also under AA.
- **`.modal-warning .btn-confirm` was 2.18:1.** White on bare `--amber`. Fixed by **deleting
  the per-type confirm colouring**, not by darkening it — see "Modal confirm buttons" below.
- **`.btn-primary` was 3.23:1 in dark mode** (hover 2.66:1). The dark theme defines
  `--primary-fill` precisely because `--primary` is too light to carry white, then applied it
  only to `.btn-confirm`; `.btn-primary` — 24 call sites, including the credit-card wizard's
  final submit — was never added to the rule.
- **`.btn-overwrite` and `.btn-danger:hover` were 4.27:1 light, 3.04:1 dark.**
- Root cause in all four: a token tier meant for badges, icons and borders was used as a
  button *background*. Fixed by introducing an explicit `--*-fill` / `--*-fill-hover` tier
  (emerald and rose — **not** amber, which is never an action colour) dark enough to carry
  white in **both** themes, and documenting the three-tier rule in `DESIGN.md` §2. The dark-mode `.btn-success` special case (label flipped
  to ink because the fill followed dark's light-teal `--emerald`) is gone — one fill, one
  label colour, both themes.

### Frontend — semantics

- **"Proceed anyway" no longer wears the success colour, and no longer changes colour at
  all.** `APReviewStep` rendered `btn-primary` when the document validated and
  **`btn-success`** when it did not, putting the reassuring green on the riskier of the two
  routes. First attempt made the invalid case `btn-outline` — which was worse: "Back" is also
  `btn-outline`, so the step-nav ended up with two identical grey buttons and no visible
  forward action. It is now `btn-primary` in both states. The document's condition is already
  stated three times over (the validation checklist above, the warnings beside the button, and
  the label itself — "Proceed" vs "Proceed anyway"); the button does not need to say it a
  fourth time in colour.

- **Modal confirm buttons are Carmen Blue whatever the modal's type.** `.modal-success`,
  `.modal-warning` and `.modal-error` each recoloured `.btn-confirm` on top of the icon, so the
  app's most common dialog — 32 `type: 'warning'` call sites — had a **solid amber OK button**,
  against the system's own rule that Caution Amber is "never used as an action color"
  (`DESIGN.md` §2). Dark mode never showed any of it: `[data-theme='dark'] .btn-confirm` is
  `!important` and painted all four blue, so the themes disagreed. The four
  `.modal-* .btn-confirm` rules are deleted; the 56px semantic icon carries the type on its
  own, and a dialog that destroys work opts in via `confirmVariant="danger"`. **`--amber-fill`
  was removed with them** — it had exactly one consumer, and leaving a dead tier around is an
  invitation to build the mustard button again.
- **Both wizards' submit-to-Carmen buttons are now `btn-primary`.** AP's was green, credit
  card's was blue — same action, two colours. `btn-success` is now reserved for genuine
  post-*completion* actions ("View JV in Carmen"), which is what `DESIGN.md` §5 always meant;
  the doc has been corrected to say *completion*, not *submission*.

### Frontend — one button vocabulary

Three parallel vocabularies were in use for the same footer role: `btn-secondary` +
`btn-primary` (`FormActions`, credit-card step 2), `btn-cancel` + `btn-submit`
(`AccountingReview`, step 3), and `btn-outline` + `btn-primary`/`btn-success` (AP steps 3-4).

- `.btn-cancel` and `.btn-submit` **deleted**. Their nine call sites (all credit-card
  components) moved onto the generic `.btn` + variant system that AP invoice, admin and
  `FormActions` already used. Mobile tap-target and `form-actions` reflow rules re-keyed off
  the variants.
- `.btn:disabled` tightened from `opacity: 0.65` to `0.45` — the retired `.btn-submit`
  disabled at 0.42 and `DESIGN.md` §6 documents 0.42-0.55. At 0.65 a disabled submit read as
  still pressable.
- `FormActions`' forward button rendered the arrow *before* the label on a forward action.
  Swapped; its Cancel moved to `btn-outline` to match the neutral slot everywhere else.
- **Two hand-rolled modals in `InputTaxReconciliation` are now `CustomModal`.** They were raw
  `createPortal` dialogs with no focus trap, no Escape, no `aria-modal` and no reduced-motion
  path. `CustomModal` gained a `confirmVariant?: 'confirm' | 'danger'` prop for the discard
  dialog. Six now-orphaned `.cc-modal-*` shell rules deleted.

### Frontend — systemic contrast

- **`--text-4` was 2.48-2.85:1 in both themes across 70+ call sites**, including the step
  wizard's upcoming-step labels — the one element `PRODUCT.md` principle 5 says must always be
  legible. Raised to the highest value the tier can take without collapsing into `--text-3`
  (3.36:1 / 3.45:1 on card). It is now documented as **decorative-only**: the step labels, the
  upload hint and both `::placeholder` rules moved to `--text-3`.
- **Bare semantic colours used as text on their own tinted surface**, 98 declarations:
  `--amber` on `--amber-light` measured **2.00:1**, `--emerald` 3.07:1, `--teal` 3.39:1,
  `--rose` 3.86:1. `--rose-text` and `--amber-text` already existed for exactly this and were
  half-adopted; added the missing `--emerald-text` / `--teal-text` and swept every
  `color: var(--x)` onto its tier. `border-color:` and `background:` uses deliberately
  untouched — the bare tokens are still correct there.
- **`--border-input` added** for form-control boundaries (3.21:1 light / 3.61:1 dark, the WCAG
  1.4.11 floor). `--border` stays at 1.19:1 for dividers, card edges and table rules, so the
  receding-surface look survives; only the controls a user has to find got louder.

### Frontend — payload and first paint

- **Fonts: 850 KB to 496 KB (−354 KB, −42%), 53 files to 37, 2 CSS requests to 1.**
  `index.html` was fetching DM Sans (variable, roman *and* italic, `opsz 9..40`,
  `wght 100..1000`) and DM Mono, while `base.css` separately `@import`ed Inter + IBM Plex Mono
  + a **second copy** of IBM Plex Sans Thai. DM Sans was referenced nowhere; DM Mono in three
  places, now on IBM Plex Mono (the documented data font). The `@import` is gone — being
  inside a stylesheet, it could not start until that stylesheet had parsed, putting the whole
  type system a round trip behind the page.
- **Dark-mode users no longer get a white flash on every full load.** `#app-loader` hard-coded
  `background-color: #eff0f5`, and the theme was applied from `main.tsx` — a module script
  that runs long after the loader paints. Moved to a three-line inline `<script>` in `<head>`,
  plus dark rules for the loader, wordmark and spinner.
- `<html lang="th">` to `lang="en"`, matching `readLang()`'s actual default.
  `LanguageContext` already kept the attribute in sync after mount; only the initial value was
  wrong, so every screen reader started the page in the wrong voice.

### Frontend — smaller fixes

- `ExtractionSkeleton`'s status strip is a `role="status"` live region, so "Reading document…"
  and its successors are announced. The elapsed counter is `aria-hidden` — inside the region
  it would be one announcement per second, drowning out the status change.
- `CustomModal` restores focus to the element that opened it and locks body scroll while open.
  Both live in an effect keyed on `show` **alone**: the keydown effect re-subscribes whenever
  `busy` flips, and sharing one effect would have yanked focus back to the trigger mid-submit.
- Upload-zone filename truncation moved from `slice(0, 29)` to CSS `text-overflow: ellipsis`
  with the full name in `title`. `slice` counts UTF-16 units, so it split Thai grapheme
  clusters.

### Tooling

- **`npm run contrast`** — `frontend/scripts/contrast-audit.mjs` parses the tokens out of
  `base.css`, resolves `var()` chains, composites alpha, and checks 27 pairs per theme against
  4.5:1 (text) or 3:1 (control boundaries). Exits non-zero on any failure. It is theme-aware:
  pairs whose dark rule swaps the whole declaration (`.btn-primary`, `.btn-outline`) carry an
  explicit dark override, so it measures what renders rather than what the light rule would
  have produced. None of this branch's defects were visible in review; all of them were
  obvious once measured.
