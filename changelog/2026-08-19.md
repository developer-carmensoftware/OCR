## SQL performance audit — measurement pack (no behaviour change)

`15:30` **Answering "is the SQL actually fast, or just working?" with numbers instead of a
code read.** A full pass over the query surface — 181 SQLAlchemy statements, 182 `.execute()`
sites, 51 tables, 174 named indexes, 15 pg_cron jobs — turned up nine things worth checking.
But the cost of the risky ones depends on how much data exists, which the source cannot say,
so **this commit measures and changes nothing**: no schema, no runtime code, no cron.

### DB

- `db/queries.sql` — new **Performance audit** block, items 15–24, continuing the existing
  numbered convention. Ten read-only queries covering: measurability
  (`pg_stat_statements` present + window since last reset), latency trend per endpoint per
  week, CPU attribution per query, table size and per-partition growth, never-used indexes,
  buffer cache hit ratio and sort spill, seq-scan ratio, dead cron / 404 storms, pool
  pressure, and autovacuum lag. Deliberately a *pack you re-run*, not an admin page —
  the answer is a diff against last quarter, not a live chart nobody opens.
  - `UNIQUE`/`PRIMARY` are excluded from the unused-index query on purpose: they enforce
    constraints whether or not a query reads them, and one of them
    (`uq_credit_cards_submitted_doc`) *is* the duplicate-post guard.
  - Header carries the run instructions, because the obvious way to run it is the wrong one:
    driving this from a Python script while `uvicorn` is up is how the documented
    `EMAXCONNSESSION` outage happened. SQL Editor only, one item at a time.

### Docs

- `docs/SQL_PERFORMANCE_AUDIT.md` — the report skeleton, modelled on
  `LOAD_TEST_REPORT_V2.md` so it reads like the report the team already knows. Method,
  inventory, and each finding's *hypothesis* are filled; every measured cell is `—` until the
  queries run. Carries the pieces that make it a measurement rather than an opinion: a budget
  table fixed **before** measuring (p95 < 1500 ms admin / < 800 ms wizard, no query > 5% of
  DB CPU, cache hit ≥ 99%, temp spill = 0, seq scan < 5% over 10k rows), a three-value
  verdict (PASS / WATCH / FAIL), a headroom formula against the 30 s `statement_timeout` with
  its linearity assumption written down, and an explicit list of what the audit *cannot* see
  (pre-DB failures, literal normalisation hiding per-tenant plan differences, counter resets).
  - Rule recorded in the doc: a finding that measures clean keeps its row with `PASS`. A
    report that only retains the findings it got right is a report nobody can calibrate.

### What the code read found — hypotheses, not verdicts

Ranked by suspected cost. All nine are in the report with the metric that would confirm or
kill each one:

- **F1** `/admin/llm-usage` and `/admin/performance-logs` default their date range to `None`
  and neither frontend page sends one, so `ORDER BY created_at DESC LIMIT n` runs with no
  predicate on the partition key. Every index on both tables leads with `tenant_id`, so there
  is no ordered path for `MergeAppend` either — the expected plan is scan-all-partitions-then
  -sort, on the two fastest-growing tables in the schema.
- **F2** `last_used_q` in `GET /admin/tenants` sits *outside* the `include_engagement` gate
  that exists specifically to keep `TenantSelector`'s five other callers from paying for
  aggregates — and it is the most expensive query in the handler (`max()` per group over a
  partitioned table, no time bound).
- **F3** `carmen-webhook-push` is scheduled `* * * * *` against `/api/v1/admin/webhooks/push`,
  which exists on no branch that is merged. ~1,440 pg_net round-trips, 404s, and junk
  `performance_logs` rows per day, which then inflate every other query in this audit.
- **F6** `/usage-summary/totals` never calls `_assert_date_range()` though its sibling
  `/usage-summary` does — the only finding confirmable from source alone, so it is marked
  CONFIRMED rather than left pending. One-line fix, held back so this commit stays
  measurement-only.
- **F4/F5/F7/F8/F9** the nightly rollups are built and read by one service while the dashboard
  re-aggregates raw logs; `get_tenant_engagement_map` reads a tenant's whole never-purged
  history; `deleted_at`/`created_by` carry indexes the planner cannot use (`IS NULL` matches
  ~100% of rows) leaving `credit_cards` with 11; `submitted_at` has none at all; and nothing
  in the repo measures SQL — `performance_logs` times HTTP, so a slow page names the endpoint
  and never the query.

Also recorded in the report: the seven things the code already gets right (partitioned log
tables with retention, buffered writes for every high-volume log, TTL caches on both hot-path
lookups, atomic credit consumption, no N+1 anywhere, the per-checkout `statement_timeout`,
and the `ocr_tasks` composite index from the July pass). The wizard path costs ~6–9 queries
per request and holds no connection across the LLM call — it is not where the risk is.

## SQL performance audit — measured, then fixed

`16:45` **The measurements came back and I was wrong about which things mattered.** Items
15–24 were run against production; every number is now in `docs/SQL_PERFORMANCE_AUDIT.md`
with the query it came from. Branch `chore/sql-audit-cleanup`.

**The headline: the database is idle.** Total SQL execution across the whole instance is
**18.5 minutes over 68 days** — a 0.019% duty cycle — of which roughly a third is
application-owned (~5.7 s/day). The entire database is ~50 MB; `credit_cards` holds 255 rows,
`ocr_tasks` 342, `ap_invoices` 41. **Four of the nine hypotheses (F2, F4, F5, F8) do not
appear in the top-20 CPU consumers at all**, and F1 is below 0.8%. They are recorded in the
report with a PASS verdict rather than deleted — a report that keeps only the findings it got
right is one nobody can calibrate against.

So **no query was rewritten and no index was added.** What shipped is housekeeping, and every
item of it was found by measuring rather than by reading:

### DB — `20260819000000_audit_cleanup.sql`

- **`cron.job_run_details` had no retention** and is, at 17 MB, the largest object in the
  database — larger than every business table combined, with `est_rows = 0` because
  autoanalyze had never touched it. pg_cron does not purge its own history. New
  `fn_purge_cron_history()` + `cron-history-purge` daily at 03:40 UTC, 14-day window. 14
  rather than 7 because `admin/email_ingest.py::_cron_health` reads this table — though only
  for `max(start_time)` and the newest status, so any window longer than a job's period is
  safe, and every `email-*` job fires at least every 10 minutes.
- **`carmen-webhook-push` unscheduled.** It fired `* * * * *` at
  `/api/v1/admin/webhooks/push`, a handler that exists on no merged branch — the migration
  that schedules it was restored (`e72558b`) to unblock `db push` and brought its cron along.
  Measured cost: **exactly 1,440 404s per day for six days**, ~8,860 junk rows in
  `performance_logs`. Production was already clean (someone unscheduled it by hand on 08-17);
  this migration is what stops `db reset` or a fresh environment resurrecting it.
  `20260811000000` is deliberately left untouched — editing an applied migration is what
  broke `db push` here before.
- **`probe` unscheduled — a cron in production that exists in no migration.** `select 1`,
  every minute, almost certainly left behind by the SQL-Editor workaround for forcing a
  pg_cron launcher reload. No measurable CPU, but 1,440 rows/day into `job_run_details`,
  i.e. **half the growth of the item above**.
- **`ix_performance_logs_endpoint` dropped.** `idx_scan = 0` over an 89-day window, but the
  counter is not the argument: the only handler filtering that column uses
  `.contains()` → `LIKE '%x%'`, which a btree cannot serve at any data volume. Dropping the
  parent index cascades to every partition and stops new ones inheriting it. Scoped to this
  one index of the **105 that measured cold** — the rest are 16 kB stubs (~1.7 MB combined,
  each costing a migration line plus an ORM change), except the `(tenant_id, created_at)`
  pair, where the Performance page's tenant selector makes "unused for 89 days" weaker
  evidence.

### Backend

- `routers/admin/usage.py` — **`/usage-summary/totals` never called `_assert_date_range()`**
  though its sibling `/usage-summary` does, so `?from=2020-01-01` pruned no partition and
  summed the full retention window. One line. The 92-day cap turned out to be untested on
  *either* endpoint; the new `test_A2_rejects_date_range_over_92_days` was checked by removing
  the guard and confirming it fails, so it tests the fix rather than the mock.
- `middleware/performance.py` — **comment corrected, code deliberately unchanged.** It
  claimed the buffer reduces writes to "O(1) batch per 10s". Measured: **84,355 INSERT
  statements for 84,376 rows** — the batching is real per *transaction* and absent per
  *statement*. At ~1.3 s/day of database time that is not worth changing; the comment now
  says so, and records that the untested part is the Python side (500 statement compilations
  per flush is CPU that blocks the event loop on 0.1 vCPU).

### The finding the audit was not looking for

**Endpoint p50 has tripled since June** — `/admin/tenants` from 463 ms to 1,054 ms — but the
arithmetic rules out SQL: four cheap endpoints alone burn ~15,700 s of wall time in 4 weeks
against ≤456 s of *total* database execution, and `/notifications` shows a 1,220 ms median
while reading two queries off a table of under 200 rows.

A first attempt blamed a CPU floor from Render's `plan: free` (0.1 vCPU). **The control
experiment killed that**: `/api/v1/admin/webhooks/push` — the 404 storm above, which
accidentally left behind 8,820 samples of pure middleware-and-routing — has a p50 of **1 ms**,
and `/admin/auth/me` (JWT decode + a DB read) 9 ms. There is no floor. A second control,
`/maintenance/status`, is **flat** across five weeks, so the slowdown is endpoint-specific
rather than global drift. The withdrawn hypothesis is kept in §3.1c because it was wrong in an
instructive way.

Left as the strongest open lead, with evidence, in §3.1e: **269,875 `pgbouncer.get_auth()`
calls against 84,376 requests — 3.2 pooler authentications per HTTP request**, which a warm
pool should never do. That is application profiling and a separate piece of work.
