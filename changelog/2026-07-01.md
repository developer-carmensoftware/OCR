## Uncommitted — Full audit + hardening of `/pricing` + `/order-review` purchase flow

`16:30` Traced the whole customer purchase flow (catalog → checkout → proforma/slip → order history) and the admin Order Review console end-to-end, frontend+backend+DB. Fixed every real finding; dismissed the false positives (QR being "disabled" is an intended config gate, not a bug; duplicate/double-charge is already prevented by the per-tenant open-order unique index + sessionStorage resume).

### Found in the process: a live production bug
- `fn_cancel_expired_orders()` (pg_cron, hourly since `20260619000001_billing_cron.sql`) has been **erroring on every run since 2026-06-23** — that day's status-collapse migration (`20260623000200_credit_order_status_v2.sql`) dropped the `'pending'`/`'cancelled'` enum values this function still referenced. Every hourly invocation raised `invalid input value for enum` and recorded a failed `job_runs` row. Discovered while implementing the new expiry behavior below; fixed in the same migration.

### New: expired orders park `on_hold` instead of auto-cancelling (product decision)
A buyer's internal payment-approval chain can run past the 14-day proforma window. Auto-cancelling (the old, broken behavior) would force them to restart; instead an expired `in_progress` order now flips to a new `on_hold` status so the quota admin can contact the buyer, then approve or void it whenever that resolves.
- `on_hold` briefly existed once before (`20260622030000_add_order_on_hold.sql`, a *manual* admin-park control) and was folded back into `in_progress` the next day by the 4-status simplification. This pass reintroduces the value with a narrower, fully-automatic trigger (expiry only) — same enum value, different feature.
- **DB** — `20260701070739_add_on_hold_status.sql` (re-add the enum value, own tx) + `20260701071021_widen_open_order_index_and_fix_expiry_cron.sql` (widen `uq_credit_orders_one_open_per_tenant` to include `on_hold`; replace the broken function with `fn_hold_expired_orders()` — `in_progress` + `expires_at < now()` → `on_hold`; reschedule the cron job as `hold-expired-orders`). `supabase/schemas/51_billing.sql` brought in line.
- **Backend** — `models/enums.py` (`CreditOrderStatus.ON_HOLD`); `routers/credits.py` (`_OPEN_STATUSES` — on_hold blocks a new order, and tenant can still upload a slip or cancel; a slip landing on a held order flips it back to `in_progress` since the buyer clearly engaged); `routers/admin/credits.py` (`_DECIDABLE` — approve/reject/hold/cancel all accept `on_hold`; `get_kpi` gains an `on_hold` bucket in the funnel + `status_counts`).
- **Frontend** — `on_hold` threaded through `OrderStatus`/`AdminOrderStatus`/`OrderStage`, a new "On Hold" queue tab + KPI bucket (folded into "Unpaid") in Order Review, and a distinct buyer-facing banner/badge ("we'll contact you to confirm") in the pricing + order-history pages. New `OPEN_ORDER_STATUSES` export replaces three duplicated `status === 'in_progress'` filters.

### Other fixes from the audit
- **No proration discount on upgrades** (provider decision, full price every purchase) — `create_order` no longer computes/subtracts `proration_credit`; `credit_service.proration_credit()` stays unused for an easy re-enable. Removes the old "upgrade estimate doesn't match the invoice" bug for free.
- **Buyer-step total was misleading** — labeled the pre-VAT pack price "Total due"; relabeled to "Subtotal (excl. VAT)" + an explicit "final total incl. VAT is on the invoice" note. `useCheckout` now stores the session's `amount_thb` straight from the server response instead of recomputing it client-side.
- **No server-side buyer validation** — `BuyerInfoInput` now validates `tax_id` (13 digits, non-digits stripped), `email` format, and length caps matching the `billing_documents` columns; this data prints on the tax invoice and keys Carmen AR posting.
- **Approved-order toast could be missed** — `useOrderHistory`'s polling toast only fired on `in_progress→paid`; now fires from either open status (`in_progress`/`on_hold`) to either terminal success status (`paid`/`complete`).
- **Silent prefill failure** — if Carmen/last-invoice prefill fails, the buyer now sees an inline "couldn't load your saved details" note instead of a silently blank form.
- **Removed `PromptPayQR.tsx`** — dead code, only re-exported from the barrel, never rendered (the flow shows bank-transfer details on the proforma; QR stays paused behind an empty `billing.promptpay_id` config on the backend, which is the intended re-enable path).
