`19:30` **feat(order-review): checkbox-driven bulk decisions (Approve/Hold/Post) + new manual-hold endpoint** (uncommitted)

- User feedback: admins don't always need the slip in-app — often they just check the amount + payment date against their own bank statement externally, then decide. Per-row action buttons were also design churn (every stage would eventually want its own button crammed into an Actions column). Replaced both with one mechanism: **checkbox selection is the only per-row control**; a floating bottom action bar offers whichever bulk actions apply to the current tab. No inline row buttons anywhere — checking one row and clicking "Approve (1)" is the same path as checking twenty.
- **Per-tab bulk actions**: To Review → Approve + **Hold** (new); On Hold → Approve only (already parked, Hold doesn't apply); To Post → Post (checkbox only appears on rows with a mapped AR code — unmapped rows show "Awaiting Mapping" and are fixed via the drawer/Customer Mapping tab instead). **Reject stays per-order only** — it needs a written reason shown to the buyer, so it isn't batchable; reached via the drawer.
- **New backend endpoint** `POST /admin/credit-orders/hold-batch` (`HoldBatchRequest`/`HoldBatchResponse` in `schemas/credits.py`) — batch-transitions `in_progress` → `on_hold`, a manual on-demand version of the hourly `fn_hold_expired_orders` expiry sweep. Deliberately distinct from the existing `hold_order` endpoint, which only ever edited `admin_note` and never changed status (kept as-is, unrelated). No migration needed (`on_hold` already a valid enum value).
- **Approve** batch-fires via `Promise.allSettled` over the existing single-order `approveOrder` endpoint (no batch-approve endpoint exists); **Post**/**Hold** use their real batch endpoints. All three funnel through one shared `busy` flag and one `afterBulkAction` cleanup (drop from selection, refresh list + KPI, close the drawer only if its open order was in the acted-on set). Toast phrasing adapts singular vs plural per action.
- **Column changes**: removed the Payslip column entirely (slip is only viewed via the drawer now); Document Date → **Payment Date**, sourced from `slip_uploaded_at` (falls back to `created_at` pre-slip) since that's what admins actually cross-check against their bank, not the order-creation date.
- **New `BatchActionBar.tsx`**: a floating, `position: fixed` bottom bar (portaled, framer-motion slide/fade with `prefers-reduced-motion` fallback) — the same "act on the selection" role as the drawer's `.orev-actionbar`, but for a multi-row selection instead of a single order. Shows "{n} selected" + a clear button + one button per available bulk action.
- Backend: `tsc`-equivalent (`python -c "import app.routers.admin.credits"`) clean. Frontend: `tsc --noEmit`, `eslint`, `npm run build` clean.

### Found in the process: a live production bug
- `fn_cancel_expired_orders()` (pg_cron, hourly since `20260619000001_billing_cron.sql`) has been **erroring on every run since 2026-06-23** — that day's status-collapse migration (`20260623000200_credit_order_status_v2.sql`) dropped the `'pending'`/`'cancelled'` enum values this function still referenced. Every hourly invocation raised `invalid input value for enum` and recorded a failed `job_runs` row. Discovered while implementing the new expiry behavior below; fixed in the same migration.

### New: expired orders park `on_hold` instead of auto-cancelling (product decision)
A buyer's internal payment-approval chain can run past the 14-day proforma window. Auto-cancelling (the old, broken behavior) would force them to restart; instead an expired `in_progress` order now flips to a new `on_hold` status so the quota admin can contact the buyer, then approve or void it whenever that resolves.
- `on_hold` briefly existed once before (`20260622030000_add_order_on_hold.sql`, a *manual* admin-park control) and was folded back into `in_progress` the next day by the 4-status simplification. This pass reintroduces the value with a narrower, fully-automatic trigger (expiry only) — same enum value, different feature.
- **DB** — `20260701070739_add_on_hold_status.sql` (re-add the enum value, own tx) + `20260701071021_widen_open_order_index_and_fix_expiry_cron.sql` (widen `uq_credit_orders_one_open_per_tenant` to include `on_hold`; replace the broken function with `fn_hold_expired_orders()` — `in_progress` + `expires_at < now()` → `on_hold`; reschedule the cron job as `hold-expired-orders`). `supabase/schemas/51_billing.sql` brought in line.
- **Backend** — `models/enums.py` (`CreditOrderStatus.ON_HOLD`); `routers/credits.py` (`_OPEN_STATUSES` — on_hold blocks a new order, and tenant can still upload a slip or cancel; a slip landing on a held order flips it back to `in_progress` since the buyer clearly engaged); `routers/admin/credits.py` (`_DECIDABLE` — approve/reject/hold/cancel all accept `on_hold`; `get_kpi` gains an `on_hold` bucket in the funnel + `status_counts`).
- **Frontend** — `on_hold` threaded through `OrderStatus`/`AdminOrderStatus`/`OrderStage`, a new "On Hold" queue tab + KPI bucket (folded into "Unpaid") in Order Review, and a distinct buyer-facing banner/badge ("we'll contact you to confirm") in the pricing + order-history pages. New `OPEN_ORDER_STATUSES` export replaces three duplicated `status === 'in_progress'` filters.
