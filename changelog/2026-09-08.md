# 2026-09-08

## A cross-tenant test suite that runs against a real database, and the five things it found

`09:30` Until today the claim "one BU cannot see another BU's documents" rested on code
review. Of ~1,200 backend tests, **none touched a real database** — `make_mock_db()` returns
whatever row the test seeded regardless of the WHERE clause, so a test asserting a 404 goes
on passing after the `tenant_id` filter is deleted. Exactly one test in the repo
(`test_email_review_api.py:124`) compiled a statement and checked the filter was in it.

New package `backend/tests/tenancy/` seeds three real tenants on the dev database, drives
the real app over HTTP, and asks the question the mocks could not: *does BU-B actually get
BU-A's row back?*

    BU-A  isolation-test.local  / bu-alpha   ingest on,  auto_post ON,   subscription
    BU-B  isolation-test.local  / bu-beta    ingest on,  auto_post OFF,  credit balance
    BU-C  isolation-test2.local / bu-alpha   ingest off                  (same bu_code as A)

BU-C exists because `(host, bu_code)` is the tenant key and **all eight dev BUs sit on one
host** — the half of the composite key that matters had never been exercised anywhere.

**79 backend tests + 13 frontend. Five failures, all real** — 75 backend pass with 4 red,
12 frontend pass with 1 marked `it.fails`.

### Findings

1. **`PUT /admin/maintenance/tenant/{tenant_id}` ignores `tenant_scope`.**
   `routers/admin/maintenance.py:94` binds the principal as `_admin` and never consults it,
   so an admin scoped to one BU can take **any other BU offline** — verified: 200, and the
   `tenant_config_overrides` row was really written. The only client-supplied-tenant-id
   admin writer with no scope check.
2. **`GET /admin/email-ingest/business-units` hands every BU's ingest tag to any scoped
   admin.** The tag is the routing credential: anyone holding it can post documents into
   that BU by emailing them. Global by design (`configs:write`), but the thing it discloses
   is a key, not a listing.
3. **`GET /admin/ar-customer-profiles` returns every BU's buyer name and tax ID** to a
   scoped admin — 9 profiles across all BUs in the test. `PATCH /{profile_id}` is unscoped
   too.
4. **Two dev BUs post under one Carmen credential** (`carmen` and `carmencloud`, same token
   fingerprint). Per-BU storage exists precisely so one leak cannot post for two customers;
   on dev that property is not being exercised. Data condition, not a code defect — but
   worth deciding about before the same pattern reaches production.
5. **`ocr_last_tenant` outlives logout** (`contexts/AuthContext.tsx`). `getCarmenUrl()` reads
   it as its fallback, so after BU-A signs off on a shared workstation the "Go to Carmen"
   link still resolves BU-A's host. Adjacent, found while reading it: `lib/url.ts:9` reads
   `sessionStorage['ocr_user']` while `AuthContext` writes `ocr_user:v1`, so that helper's
   active-session branch is dead and it always falls through to the stale key.

Nothing leaked on the customer-facing data plane: all 24 read-isolation tests pass, including
the only endpoint that returns line items (`GET /email/documents/{id}` → 404, not 403).

## Fixing four of the five findings — same idioms already in the codebase

`14:30` Four of the five findings above are fixed. Each reused the exact idiom already
established for the same shape of problem elsewhere in the codebase, rather than inventing
a new one — see `backend/tests/tenancy/_run.py` for how to reverify.

- **Finding 1 — `PUT /admin/maintenance/tenant/{tenant_id}` now checks `tenant_scope`.**
  `routers/admin/maintenance.py` gained the same `_assert_scope()` helper `quotas.py` and
  `credits.py` each already carry their own copy of — not centralized, because three
  independent copies is this codebase's existing convention for this helper, not an
  oversight. `set_tenant_maintenance` calls it before writing.
- **Finding 2 — `GET /admin/email-ingest/business-units` now narrows to the caller's own
  BU** when scoped, same resolve-then-filter shape `list_email_documents` already uses one
  function above it in the same file. A global admin sees every BU unchanged.
- **Finding 3 — `/admin/ar-customer-profiles*` now requires a global admin.**
  `ArCustomerProfile` has no `tenant_id` column at all — it's keyed on `(buyer_tax_id,
  buyer_branch)`, a company, and the same buyer can legitimately be one customer's AR code
  and another's. There is no valid tenant slice of this table to hand a scoped admin, so the
  fix is a new idiom for this codebase (`if not admin.is_global: raise 403`) rather than a
  filter — commented in-place so it isn't later "fixed" into `_assert_scope` by mistake.
- **Finding 5 — `logout()` now clears `ocr_last_tenant`.** One line next to the existing
  `sessionStorage.removeItem(STORAGE_KEY)`. While tracing it, found and removed the actual
  root of the smell: `lib/url.ts` had been reading a *different*, dead key (`ocr_user`)
  since commit `f5b3888` renamed `AuthContext`'s key to `ocr_user:v1` without updating this
  file — proved (not just observed) that the branch had been unreachable and redundant
  ever since, since `login()` always sets both keys together and nothing separates them
  except the deliberate expiry path that keeps `ocr_last_tenant` on purpose. Deleted the
  dead branch rather than repointing it at the versioned key, since that would've added a
  `lib/ → contexts/` import direction that exists nowhere else in this codebase.

**Finding 4 (two dev BUs sharing one Carmen credential) is a data condition, not code** —
left as-is, and `test_carmen_live.py::test_two_bus_do_not_share_one_carmen_credential` stays
red on purpose until someone rotates one of the two tokens on dev. It's the one test in the
suite that's supposed to still be failing.

**Verification:** `tests/tenancy` 78/79 passing (only finding 4 red, as intended); full
existing backend suite (1263 tests) and full frontend suite (677 tests) both still 100%
green — no regression. `ruff check`/`format`, `eslint`, `tsc --noEmit` all clean on every
touched file.

## Two email-review fixes: dropped GL suggestions on tax mismatch, self-notifications on approve/reject

`16:00` Backend-only, `services/email_ingest_service.py`.

- **GL mapping suggestion now survives a `tax_id_mismatch` (or plain-duplicate) park.**
  `_run_document` raised `_Skip("tax_id_mismatch", ...)` and the plain `is_duplicate` check
  *before* the GL-mapping-suggestion block ever ran, so `mapping_suggested` stayed the `{}`
  it was initialized to and `review_payload["suggested"]` went out empty — every
  Department/Account picker on the review screen started blank and red-outlined instead of
  AI-prefilled, even though the AI had the chance to fill them. Reordered: the mapping block
  now runs right after the (free, non-reviewable) `_already_pending` check and before both
  reviewable skips, so any document that still reaches a human carries its suggestion. Pure
  reorder, no logic changes; `_already_pending` itself stays ahead of the LLM call since that
  one discards the document outright and a suggestion for it would never be seen.
- **Fell out of the same reorder: a re-sent copy of a document that parked *with a reason* no
  longer queues twice.** `_already_pending` matches on `status='pending_review'` regardless of
  `reason_code`, but it sat *after* the tax-ID check — so a bank re-sending a statement whose
  tax ID had already parked one row raised `tax_id_mismatch` again and put a second identical
  row in front of the same reviewer, which is the exact thing that guard exists to prevent.
  Now consulted first, so it covers the reason-carrying parks too.
- Priority change worth knowing: when a document has *both* a foreign tax ID and a Carmen
  credential that turns out dead while reading the GL master, the row now reads
  `carmen_unauthorized` (and flags the token via `mark_token_unverified`) rather than
  `tax_id_mismatch`. That is the more actionable of the two — a dead credential fails every
  document of the BU — but it is a change, not an accident.
- **Approving or rejecting from the review queue no longer rings the reviewer's own bell.**
  `_finish()` is the shared terminal-status writer for both the unattended auto-post pipeline
  and the two human review verbs, and it fired `document_posted`/`document_failed`
  unconditionally — so a human clicking Approve got notified about the thing they just did.
  Added `_finish(..., notify: bool = True)`; `approve_document()` and `reject_document()` now
  pass `notify=False` explicitly (reject already produced no notification by accident of its
  status/reason strings, made deliberate instead). The two auto-pipeline call sites keep the
  default — nobody was watching those.

**Verification:** three new cases in `tests/unit/test_email_ingest_pipeline.py`
(`test_a_tax_mismatched_document_still_carries_its_gl_suggestion`,
`test_approving_your_own_review_rings_no_bell`,
`test_a_resent_copy_of_a_tax_mismatched_document_does_not_queue_twice`). Each was run against
the pre-fix service file (stashed, then restored byte-identical) and each failed there with
the symptom it names — `suggested == {}`, a real `UserNotification` row, and
`'pending_review'` where `'failed'` belongs — so all three discriminate rather than merely
pass. Full backend suite 1345 tests green; `ruff check` and `ruff format --check` clean.

Also driven end to end against the dev database: an SCB statement whose printed tax ID
(`0105555181506`) is not in carmencloud's register was pushed through `_process_attachment`,
parked as `tax_id_mismatch`, and came back carrying all four suggestions
(`VSA-INT`/`VSA-INT-P` → GEN 1021004, `MCA-INT`/`MCA-INT-P` → GEN 1021005) — the same pairs
the sibling BU has curated by hand for those payment types. Rejecting it from the review
screen then wrote **no** notification row.

**Pending release note** (user-visible, batch into the next release): documents held for a
tax-ID mismatch now arrive with the AI's GL suggestions already filled in, and approving or
rejecting from the review queue no longer sends you a notification about your own click.

## Vitest 5 pinned out: it silently deletes every jest-dom matcher from the type system

`13:12` Dependabot PR #207 (`test-tools` group) failed both `Frontend (Node)` and the Vercel
deploy with ~200 `TS2339` errors — `toBeInTheDocument`, `toHaveValue`, `toHaveAttribute`,
`toBeDisabled` "does not exist on type `Assertion<void, HTMLElement>`" across 30+ test files.
Not our code: the group carried `vitest` and `@vitest/coverage-v8` **4.1.11 → 5.0.0**.

Vitest 5 widened its assertion type to two parameters —
`interface Assertion<R extends void | Promise<void> = void, T = unknown>` (verified against
the published `@vitest/expect@5.0.0` tarball, `dist/index.d.ts:644`). `@testing-library/jest-dom@7.0.1`,
the latest release, still augments the one-parameter form (`types/vitest.d.ts:5`:
`interface Assertion<T = any>`). Arity mismatch means the `declare module 'vitest'` block
never merges, and `skipLibCheck: true` swallows the error in the lib file — so the matchers
simply vanish from the type with no diagnostic pointing at the cause. Vitest 5 exposes a
`Matchers<R, T>` interface as the intended augmentation point; jest-dom has not moved to it.

Vercel failed for the same reason, not a second problem: `build` is `tsc -b && vite build`
and `tsconfig.json` has `include: ["src"]`, which covers `src/**/*.test.tsx`.

**Runtime was never affected** — the matchers execute fine; this is types only.

- `.github/dependabot.yml` — `vitest` and `@vitest/*` majors ignored, same shape as the
  existing `typescript` major ignore, with the removal condition written down (a jest-dom
  release that augments vitest 5). The group still ships the rest, so dependabot's next run
  should re-open #207 with only the `@testing-library/react` 16.3.2 → 16.3.3 bump in it.
- Declined the alternative: a local `.d.ts` re-augmenting `Assertion<R, T>` would buy us
  vitest 5 for ~5 lines, but a major we gain nothing from is not worth adopting ahead of the
  ecosystem, and tsc would not catch its other breaking changes.

**Verification:** current tree (vitest 4.1.10) `tsc --noEmit` clean and 677/677 frontend
tests green — the baseline the pin protects. `dependabot.yml` parses.

Upstream: [vitest#10411](https://github.com/vitest-dev/vitest/issues/10411),
[jest-dom#620](https://github.com/testing-library/jest-dom/issues/620).

## `17:10` The auto-post switch has one writer, and it is Carmen's

`auto_post` was writable from two places, and one of them wrote it destructively.
`PUT /api/v1/carmen/settings` is a **full replace** whose `auto_post` defaulted to `False`
when absent — so any caller that did not know the field turned review back on. Our own
`#/email-settings` page is exactly such a caller (`useEmailSettings.put()` re-sends the whole
settings body on every edit and has never carried the field): a BU on auto-post that
corrected a filename pattern silently went back to approving every document.

Deleting the second writer is the fix, and the one kept is the one that owns the *setting*.
Contract: [CARMEN_INTEGRATION.md §2.7](../docs/CARMEN_INTEGRATION.md) (new), decisions #98/#99
in [07-human-in-the-loop.md §21](../docs/email-automation/07-human-in-the-loop.md).

**Frontend**

- Deleted `components/credit-card/QueueSettings.tsx` (the gear on the review queue), its
  `.rq-settings*` block in `styles/pages/review-queue.css`, `setAutoPost` in
  `lib/api/emailReview.ts`, `emailReview.autoPost` in `lib/api/endpoints.ts`, and the six
  `review.settings` / `review.autoPost*` strings from both `en` and `th` in `i18n/dict.ts`.
- `pages/ReviewQueue.tsx` — the bar keeps Refresh and Upload documents. `GET /email/status`
  still reports `auto_post` and the page still fetches it; it is read-only now, and it is
  what a support thread reads.
- **`pages/EmailSettings.tsx` gains the switch instead** — a checkbox in the connection
  block, under *Posting without review*, wired to a new `ctrl.setAutoPost` that PUTs the
  same `/api/v1/carmen/settings`. One endpoint, two clients of it (as `enabled` and the
  rules already are), not two writers. It is the service path for a BU whose Carmen has not
  shipped the control, and it is what exercises the field end to end — that page exists to
  prove the contract without Carmen, and a field no client of ours sends proves nothing.
  `auto_post` is added to `EmailSettings` (read) and **optionally** to `SettingsPayload`
  (write); `useEmailSettings.put()` deliberately leaves it out of the base body, so every
  other save on that page omits it and the server keeps what is stored. New
  `useEmailSettings.test.ts` pins exactly that, both ways (decision #100).

**Backend**

- Deleted `PUT /api/v1/email/settings/auto-post` (`routers/email_review.py`),
  `es.set_auto_post`, and the `AutoPostIn` schema (plus its `models/schemas/__init__.py`
  export).
- `SettingsIn.auto_post` is now `bool | None = None` and `save_settings` writes it only when
  it is not `None` — the one field on that payload that merges rather than replaces, the
  idiom `_merge_rule` already uses for `pdf_password_enc`. This reverses a deliberate earlier
  choice: it rested on the reset being recoverable, and what made it recoverable was the gear
  now deleted.

**Docs** — new §2.7 in `CARMEN_INTEGRATION.md` (what the switch buys, what it cannot buy,
omit-means-keep) plus checklist item 8 for the Carmen team; `03-api-reference.md`,
`04-data-model.md`, `02-architecture.md`, `07-human-in-the-loop.md` §21, and the
email-ingestion section of `CLAUDE.md`.

**Verification:** full backend `tests/unit` + `tests/integration` green; frontend
`tsc --noEmit` clean, `ReviewQueue.test.tsx` 78/78, eslint clean on the touched files. Two
tests replaced rather than dropped — one pins that this router has no `auto-post` path, one
pins merge-on-omit both ways (omitted keeps `True`, explicit `False` writes).

**Until Carmen ships their toggle** a BU already on auto-post stays on it (that is the merge
working), and it is still settable two ways: `#/email-settings` in this app, or an operator —
`PUT /api/v1/carmen/settings` accepts `Bearer <admin jwt>` (`configs:write` + tenant scope).
