# 2026-07-16

## `10:00` Pilot data autopsy → two fixes

Read the real prod pilot data (23 tenants, 125 extractions, 11 failures) to answer a
go-to-market question, and the answer turned out to be two bugs rather than a pricing
strategy. Everything below is scoped to those two — no re-quota, no billing changes.

### Backend — user-facing error messages

- `10:00` **`services/llm_service.py` — raw `json.JSONDecodeError` reached end users.**
  `json.loads()` on the vision output was unguarded, and `factory._error_response` puts
  `str(exc)` straight into the response `detail`. One pilot BU's accountant saw
  **"Unterminated string starting at: line 34 column 22 (char 839)"** three times in
  one minute on 2026-07-07 (same photo each time, three different truncation points —
  the model returns `usage 0/0/0` and cut-off content non-deterministically) and never
  opened the product again. A second BU hit the same error on 2026-07-09 — their last
  action ever. Now raises `LLMParseError` (already wired to 422 in `factory.py`); the
  parser detail stays in the server log where it belongs.
- `10:00` **`exceptions.py` — `LLMParseError` given a user-facing default message.**
  Follows the `PdfPasswordRequired` idiom so both extract paths share one string
  without a new constants module.
- `10:00` **`services/ap_invoice_service.py` — `RuntimeError("LLM returned invalid
  JSON")` → `LLMParseError`.** It had a guard but raised an untyped error (→ 500) with
  a message written for a developer. Same message as the credit-card path now.
- `10:00` `tests/unit/test_llm_parse_error.py` — drives `extract_from_image` with a
  truncated LLM response; asserts `LLMParseError`, a readable message, and that no
  `JSONDecodeError` vocabulary can reach `detail`.

### DB — session purge

- `10:00` **`20260716000000_session_purge_by_age.sql` — `session-purge` never deleted
  anything.** The predicate was `is_active = false and last_used_at < cutoff`, but
  `is_active` only flips false on explicit logout or a Carmen 401
  (`carmen_service.py:95`). A user who closes the tab leaves the row `is_active = true`
  forever, so the purge never matched it and the Fernet-encrypted Carmen token stayed
  in the DB indefinitely. Observed on dev: **41 live rows, oldest 16 days, zero
  inactive.** Now purges on `created_at < now() - 1 hour` — 2x the JWT TTL
  (`session_ttl_hours = 0.5`, applied to the JWT `exp` in `routers/auth.py:251`), so a
  row can never outlive the session it belongs to. Function name unchanged:
  `cron.schedule('session-purge', ...)` calls it by name.

### Tooling

- `10:00` `backend/db/queries.sql` — added the adoption queries this autopsy ran, as
  items 11–14 (funnel, per-BU usage, quota ceiling, weekly curve), with notes on
  reading them: `posted_to_carmen` over `tried`, `active_weeks = 1` means a one-day
  look, and `SET timezone = 'UTC'` once per session.

### Notes for the eventual prod deploy (no action taken)

- **prod runs `prod-deploy/vercel-render-neon`, an older fork.** Its DB is a strict
  subset of dev — missing `tenant_subscriptions`, `billing_documents`,
  `document_sequences`, `consent_logs`, `user_notifications`, `credit_packs.kind`,
  9 `credit_orders` columns, and every log-table partition. Expected for an
  un-updated version, but it means the fix above only reaches customers on deploy.
- **`_MIGRATIONS` entry `("203_partition_log_tables", None)` is marked "DDL handled by
  create_all()" — `create_all()` cannot create partitions.** prod's log tables are
  plain where dev's are partitioned, and prod has no `_supabase_migrations`. Do not
  point `supabase db push` at prod's existing DB expecting it to reconcile.
- **prod's `cron_service.py` (deleted on main) hard-deletes sessions hourly at
  `session_ttl_hours`.** Once main ships, that behaviour is gone — the migration above
  is what replaces it. The 30-minute session policy itself is unaffected: it lives in
  the JWT `exp`, identical on both branches.
