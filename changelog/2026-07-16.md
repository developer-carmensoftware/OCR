# 2026-07-16

## `13:00` Admin: Extractions page, per-BU engagement, nav by question

Yesterday's pilot review took ~12 hand-written SQL queries against prod to answer "how
is the pilot going." Two findings drove this work:

1. **14 admin pages already existed** — including Quota & Modules (which edits quota
   limits) and Jobs (which shows `job_runs`). They went unused because nobody knew they
   were there. That is a discoverability failure, not a missing feature.
2. **Two things were genuinely invisible:** why an extraction failed, and whether a BU
   is alive.

Reference SQL for the new views: [`backend/db/queries.sql`](../backend/db/queries.sql)
items 11–14.

### Backend

- `13:00` **`usage_analytics_service.get_extraction_failures` + `GET /admin/extraction-failures`
  — `ocr_tasks.error_message` was never selected anywhere in the admin surface.**
  `get_error_breakdown` counts failures and the Usage page renders `errors: 4`, but there
  was no way to see *why*: for a month an `errors: 4` cell sat on screen for a BU that had
  hit the same wall four times in an hour, with nothing to click. Returns raw rows and no
  grouping — at ~11 failures/month (~220 at 20× beta scale) the caller groups client-side,
  so filtering costs no round-trip. `tenants:read`, `_assert_date_range` (92 days),
  `_resolve_tenant` — filenames and `carmen_user_id` are in the payload, so tenant scoping
  is a privacy boundary here, not just a filter.
- `13:00` **LLM stats merged in Python, not joined.** `llm_usage_logs.task_id` is
  `VARCHAR(36)` against a `PGUUID`, unindexed, on a partitioned table — a cast-join is a
  hash join across every partition in range that cannot be pushed below the `LIMIT`. Second
  query with a bounded `IN` list instead (same shape as `task_stats_map` in
  `get_usage_summary`). **A task absent from `llm_usage_logs` reports `null`, not `0`:**
  "the model was never called" and "the model was called and returned nothing" are
  different diagnoses, and the second one is the signature of the live JSON bug.
- `13:00` **`usage_analytics_service.get_tenant_engagement_map`** — per-tenant `tried` /
  `ok` / `failed` / `posted_to_carmen` / `active_days` / `active_weeks` / `days_idle`, one
  bulk pass, no N+1. Week and day buckets are pinned with an explicit `AT TIME ZONE 'UTC'`:
  the pool's checkout listener (`database.py`) sets `statement_timeout` but **not**
  `timezone`, so a bare `date_trunc('week', <timestamptz>)` resolves in whatever session TZ
  the pooler hands us and would not reproduce against `queries.sql`.
- `13:00` **`GET /admin/tenants` gains `include_engagement` (default `false`).** Off by
  default is load-bearing: `TenantSelector` calls this endpoint on five other admin pages
  purely to fill a `<select>` that reads `id/name/host/bu_code`. With the flag off the
  response is byte-identical to before, and a test asserts it issues no extra queries.
- `13:00` `tests/unit/test_admin_extractions.py` — 14 tests: the 92-day guard fires before
  any query runs, scoped admins can't read another BU's filenames, `null`-vs-`0` LLM stats,
  `posted_to_carmen` summed across both document tables, and the `include_engagement=False`
  regression guard.

## `16:20` Split extract vs suggest in LLM usage accounting

Every module makes two kinds of LLM call and both logged under the same `module_id`:
the vision extract (one per document) and the GL-mapping suggestion
(`gl_suggestion_service`, `ap_invoice_service.suggest_for_items`). So `count(*)` grouped
by module blended them — "LLM calls" was really extracts + suggestions, and there was
no way to read actual usage (the thing a user presses a button for) off any per-module
number.

- `16:20` **`20260716010000_llm_call_type.sql` — new `llm_usage_logs.call_type`
  (`extract` | `suggest`).** The only prior discriminator was incidental: suggestions
  never pass `task_id`, extracts always do. That is a fact about current wiring, not
  intent, and inverts silently the day someone traces a suggestion back to its document.
  Backfilled from `task_id` (correct for history *because* no suggestion has ever carried
  one). Nullable; `ALTER` on the pg_partman parent propagates to all partitions.
- `16:20` `llm/client.py` tags the vision path `"extract"` and the text path `"suggest"`;
  `llm_usage_logger.log_llm_usage` persists it; ORM column added.
- `16:20` **`usage_analytics_service.py` — `get_usage_summary` / `get_usage_totals` now
  return `extract_calls` and `suggest_calls` split out, and `avg_llm_latency_ms` averages
  **extract only**.** Blending a 5-12s vision call with a fast text one produced a latency
  that described neither call (it was in the payload but rendered nowhere — a latent
  wrong number).
- `16:20` **`Overview.tsx` — error-rate denominator fixed from `llm_calls` to
  `documents`.** `errors` counts FAILED `ocr_tasks`; dividing by extract+suggest inflated
  the denominator and understated the real failure rate (pilot: 6.4% shown vs 8.8% real).
- `16:20` `UsagePage.tsx` — the `LLM Calls` column becomes `Scans` + `Suggestions`, and
  the daily chart plots `extract_calls` (the GL suggestions riding along would roughly
  double a "how much are they using it" line). `documents` was never affected — it comes
  from `ocr_tasks`, and a suggestion creates no task.
- `16:20` Tests: both client paths must keep tagging their `call_type`, and
  `log_llm_usage` must persist it.

## `17:00` Make the Quota & Modules page legible

The page put `6/30` (quota) next to `133 calls` (usage) with no hint they measure
different things, so it read as a contradiction — how is quota not full when there
are 133 calls? They are not comparable: quota counts documents charged (net of
refunds, resettable), while the usage column counted blended LLM calls (extract +
suggest, full history, never reset). A tenant that scanned 66 documents shows ~133
calls and, after refunds/resets, maybe `6/30` quota.

- `17:00` **`quota_admin_service.py` — usage-by-module now splits `scans` (extract)
  from `suggestions`.** Scans is the quota-comparable number: one per document
  attempted. Suggestions ride along and never touch quota.
- `17:00` `QuotaModulesPage.tsx` — the Usage column headlines **scans**, not the
  blended call count, with suggestions on a quiet second line; the overview chart
  plots scans; the detail row breaks out scans / suggestions / tokens / cost.
- `17:00` The quota cell gains a `documents charged` sub-label and a hover title;
  the page description now spells out the consumption order (subscription → free →
  top-up) and why quota and scans rarely match (a failed scan is refunded from quota
  but still counted). This also answers the recurring "does free quota fill before
  top-up?" — yes, and `_try_consume_free` enforces it.

## `17:40` Quota & Modules: show the bucket that's actually moving

Follow-up to 17:00. The page still showed only the free-trial quota, but scans are
charged `subscription → free → top-up`, so a subscribed tenant's free bar is frozen
while real usage lands on the subscription. Live on dev/carmencloud: free stuck at
`6/30` (last touched 2026-06-29, before they subscribed 07-07) while a successful scan
today incremented the active subscription (`53/200`) — the paying customer's usage was
invisible on the page.

- `17:40` **`credit_service.active_subscription_map(db, tenant_uuids)`** — new bulk helper
  next to `_try_consume_subscription` so the cycle-roll `case(cycle_start < fn_cycle_start
  (...), 0, docs_used)` has ONE home (a second copy in the admin service would be
  money-path drift). Returns the one active, in-window sub per tenant; `used` is
  cycle-adjusted so a rolled annual cycle reads 0, not last cycle's count.
- `17:40` `quota_admin_service.get_tenants_quota_overview` now also returns
  `subscription` (allowance/used/period_end | null) and `credit_balance` per tenant, both
  bulk, keyed by `str(tenant_id)`.
- `17:40` `QuotaModulesPage.tsx` — the QUOTA cell headlines the **active bucket**
  (subscription if any, else free) as the moving bar, with a quiet reserve line for the
  rest (`reserve: free 6/30 · 40 credits`). Answers the recurring "why is the bar frozen
  when I'm scanning" — because the subscription is absorbing it.
- `17:40` **`nearLimitCount` KPI fixed** — it tested the free quota's pct, so a subscribed
  tenant at 95% of their plan never counted as near-limit (their free quota is frozen

- `17:40` Test: `active_subscription_map` short-circuits on empty, maps rows keyed by

## `18:10` Make the module toggles actually enforce

The Credit Card OCR / AP Invoice switches on Quota & Modules wrote `tenant_modules.enabled`
but **nothing read it at extract time** — `ocr.py`, `ap_invoice.py`, `quota_service`
never checked it, so turning a module off changed a flag and nothing else. A toggle that
does nothing is worse than no toggle: an admin could believe they'd cut a tenant's access
while scans kept going through.

- `18:10` **`quota_service.assert_module_enabled(module_id)`** — extract-time gate.
  **Opt-out semantics:** blocks ONLY on an explicit `enabled=False` row; a missing row (the
  common case — most tenants have never had one written) is allowed, so enabling
  enforcement can't lock out existing tenants. Fail-open on infra errors, like
  `consume_document` — only an explicit disabled row raises.
- `18:10` `exceptions.ModuleDisabled` → 403 (wired in `factory.py`), carrying a
  user-facing message.
- `18:10` `ocr.py` / `ap_invoice.py` call the gate **before `consume_document`** (same
  pre-charge placement as the PDF check), so a disabled module 403s without burning a
  credit.
- `18:10` Frontend: both extract hooks surface the 403's `detail` in a "Module
  unavailable" modal instead of a bare `HTTP 403`. (Credit-card's `lib/api/ocr.ts` already
  passed `detail` through; AP's `_fetchExtract` now reads it too.)
- `18:10` `tests/unit/test_module_gate.py` — the five cases that matter: explicit
  `enabled=False` blocks, no-row allows, `enabled=True` allows, no tenant context is a
  no-op, and a DB error fails open.

## `18:30` Make the module switches show the truth (opt-out display)

Follow-up to 18:10. Enforcement is opt-out (no `tenant_modules` row = allowed), but the
page derived the switch from `modules_enabled` — the rows filtered `enabled=True` — so a
tenant with no row showed the switch **OFF** while actually being able to scan. Worse, the
same visual "OFF" meant two opposite things: no row (allowed) vs an explicit disabled row
(blocked). Toggling on-then-off to "make sure" silently flipped the second into effect.

- `18:30` `quota_admin_service` overview now returns `modules_disabled` (ids with an
  explicit `enabled=False` row) alongside `modules_enabled`, from one query over both
  states.
- `18:30` `QuotaModulesPage.tsx` — the switch is `checked = !modules_disabled.includes(id)`
  (default ON, matching the extract gate). The MODULES column flips to show the
  *exceptions* — turned-off modules as red "X off" chips, "All enabled" otherwise — since
  under opt-out everything is on by default and the useful signal is what's been cut. The
  KPI "Modules enabled" (a sum that was 0 for everyone) becomes "Modules restricted" =
  tenants with any module off.
- `18:30` i18n: `allEnabled`, `moduleOff`, `kpi.modulesRestricted`; dropped the now-orphan
  `none` and `kpi.modulesEnabled`.

### Known scope limits

- Extractions covers **post-charge** failures. `ensure_pdf_openable` runs before
  `create_task` (`routers/ocr.py` Phase 1 is deliberately DB-free so a locked file cannot
  burn a credit), so password-protected and corrupt PDFs 400 without ever writing an
  `ocr_tasks` row. Zero on that page ≠ zero in reality; the page description says so.
- The dev tenant is **not** excluded from the funnel KPIs. `queries.sql` filters it by
  hostname; there is no `is_internal` column on `Tenant` and hardcoding a hostname in
  application code is worse than a one-row difference.
