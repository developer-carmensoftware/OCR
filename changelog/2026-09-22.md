### `04:10` — Frontend: ticket 0 — the credit-card mapping screen speaks Thai

Prerequisite for the `cc_ar_reconcile` collapse (see the planning note below). The four
components behind `#/CreditCardOCR/mapping` carried **zero** `useT` calls — every label,
tooltip, placeholder and status line was hardcoded English — while the AR settings screen
they are about to merge with is fully bilingual. Translating after the merge would have
meant resolving the same conflicts twice.

- `i18n/dict.ts` — 71 new `cc.*` keys in both `en` and `th`: top-level config
  (`cc.cfg*`), company information (`cc.company*`), the account-code mapping table
  (`cc.map*`), the payment-type modal (`cc.pt*`), and the save-validation modals
  (`cc.val*`, `cc.saveSuccess*`). Every English string is unchanged in wording, so this is
  invisible to an EN reader.
- `components/common/MappingRow.tsx`'s `deptPlaceholder` / `accPlaceholder` **defaults**
  (`'Dept...'` / `'Acc...'`) were reaching the screen untranslated — `PaymentTypeModal` is
  the one caller that never passed them. Found by the browser pass, not by any test. Fixed
  at the caller (`cc.ptDeptPh` / `cc.ptAccPh`, deliberately short so the modal's narrow
  columns still fit) rather than by making the shared component a `useT` consumer.
- `PaymentTypeModal` had two callbacks using `t` as the payment-type parameter name,
  shadowing the `t` from `useT()`. Harmless today — neither calls `t()` — but the next edit
  that does would get "t is not a function" at runtime with nothing failing first. Renamed
  to `pt`.
- `components/credit-card/TopLevelConfigSection.tsx`, `CompanyInfoSection.tsx`,
  `MainMappingTable.tsx`, `PaymentTypeModal.tsx` — literals swapped for `t()`. The
  description-hint ternary in `TopLevelConfigSection` collapses from four branches to three
  (`ownDescription` truthy and both-falsy produced the same sentence); behaviour identical.
- `hooks/mapping/useMapping.ts` — `COMPANY_REQUIRED_FIELDS.label` → `labelKey: TKey`,
  because the same list names the fields in the form *and* names them again in the "fill
  these in" modal, so one translated string has to reach both. `topLevelRequired` likewise.
  Both validation modals and the save-success modal now go through `t()`.
- `lib/glFieldLabels.ts` — `glFieldLabel(key)` → `glFieldLabel(key, t)`, same for
  `glFieldList`. Three new keys (`cc.glCommission` / `cc.glTax` / `cc.glNet`) hold the
  wording. Passing `t` in rather than duplicating the list into the `cc.*` namespace is
  what keeps this the only copy — which is the whole reason the file exists. Callers
  updated: `MainMappingTable`, `QueueRow` (×2), `useMapping`. Note `QueueRow`'s
  `reason.fields.map(glFieldLabel)` had to become an arrow — point-free would have passed
  the array index as `t`.
- **No new test.** `i18n/dict.test.ts` already gates EN/TH key parity, non-empty values,
  and — the one that matters here — that both languages use the same `{placeholder}` set
  per key. `tsc` fails the build on a missing TH key independently.

761 tests pass (including `ccJv.contract.test.ts` and `PaymentTypeModal.test.tsx`),

### `06:25` — Frontend: stop asking a phone to swipe sideways to fill in a field

The `04:45` pass fixed the form but left the actual defect standing: the account-code
mapping grid and the payment-type rows are forms people fill in, and they still made a
phone user scroll horizontally to reach the Account field. Scaling padding was the trap
`/impeccable adapt` names outright — *"rethinking the experience for the new context, not
scaling pixels"*. This pass replaces the grid/modal half of `04:45` with the project's own
answer to the same question: `review-queue.css` already turns `.rq-table` into cards at
720px (`thead{display:none}`, `td::before{content:attr(data-label)}`) because a queue row
is a record, while `.jv-table` keeps its columns and scrolls because a JV is a ledger where
alignment is the information. A mapping row is the first kind — nobody reads a dept code
down a column, they fill one row at a time — so it goes to cards, not to a wider scrollbar.
Consolidates the `04:45` pair of breakpoints (768/640) into this one 720px number; three
sizes on one page was the smell.

- `components/common/MappingRow.tsx` + `styles/components/mapping-row.css` — the two

### `04:10` — Planning: collapse `cc_ar_reconcile` into the credit-card flow

Decision #28 (2026-09-18) made the settlement JV's debit side identical to the fee
invoice's, which leaves the two builders differing in exactly two places — where the debit
figures are read from (`total_row` vs Σ across details, a *document-layout* fact) and how
the credit side is grouped (a *user option*). The second module, second mapping store and
second settings screen are all v1.1 artefacts of a premise that no longer holds.

Agreed shape, to be built as one atomic PR after the ticket above merges: one builder in
`cc_jv` (`ar_reconcile_jv.py` deleted, browser twin still covering only the fee-invoice
branch), `ar_reconcile_mappings` folded into `bu_accounting_mapping_entries` with a new
nullable `source` column, `banks.settlement_grouping` replacing the `SUPPORTED_BANKS` /
`RECONCILABLE_BANKS` constants, the module gate dropped (`module_id` kept so
`daily_usage_summary` still splits the cost), and `#/CreditCardOCR/ar-settings` merged into
`#/CreditCardOCR/mapping`. Detail/Summary becomes a per-bank posting option rather than a
module of its own. Full decision list in the plan file; decision-log entry #29 to be
written with the implementation.

### `15:30` — Playwright verification against the dev DB, and two bugs it found

`npm run test`/`build`/`tsc` only prove the code runs; they mock every DB call, so neither
caught what a live request against a real database does. Ran the merged mapping page
end-to-end (Playwright MCP, session via `scripts/seed_browser_session.py`, revoked after)
against the dev project (`ycykjisvvrrbgeiirqre` — confirmed distinct from the
`lhlncsjqxttcdegkqvid` prod ref before touching anything).

**Migration applied to dev, not prod.** `supabase db push` failed first with `relation
"ar_reconcile_settings" already exists` — the dev DB had that table's DDL (2 settings rows,
20 mapping rows of real seeded test data) but no matching row in `_supabase_migrations`,
because migration `20260909020000_ar_reconcile.sql` had been applied by hand at some point

doing anything, then `supabase migration repair --status applied 20260909020000` (not

showed the JV preview with all three debit legs (commission/tax/input tax) blank and a
"cannot post, off by 25,091.00" banner — for every mapping state, unrelated to Detail vs
Summary. Root cause: `ar_reconcile_service.latest_real_sample()` (pre-existing, from commit
`2731543`, not part of this ticket) picks a tenant's most recently parked KBANK settlement

### `17:40` — Ticket D: one JV-description mechanism, not two

Two more fields pointed at as duplicates: `#description` (fee-invoice, per-bank wording
in `TopLevelConfigSection`) and `#settlement-template` (settlement, in the Settlement
card) — both are "the JV description," just for different document types. This reopens
decision #7 from earlier today's collapse ("Two JV-description mechanisms stay — out of
scope"), on purpose this time: confirmed with the user this is a real storage/rendering
merge, using the settlement side's template-tag mechanism as the base, with the
fee-invoice side's plain-string behavior kept as its backward-compatible default so no
other BU's JV wording changes.

**Why this was bigger than the last two tickets:** `build_gljv_payload` (`cc_jv.py`)
runs for every tenant's fee-invoice JVs sent through email ingest, and its browser twin
`buildGljvPayload` (`ccJv.ts`) runs for every wizard submission — a careless merge would
silently change the description text every other BU's books already carry. The
backward-compat rule is what makes it safe: **a saved value with no template tag in it
renders exactly as it does today** (`base - doc_date`); a value containing
`{Settlement_Date}`/`{Tax_Invoice_No}`/`{Bank_Name}` is treated as a full template
instead, and the auto date-append does not additionally happen.

**Backend**

- `cc_jv.py` — new `_has_template_tags()`, `render_description()` (the shared
  tag-or-fallback decision, taking a raw string) and `resolve_jv_description()` (the

  a config object but no pre-rendered string wants). `build_gljv_payload` gains
  `doc_no: str | None = None` and its `description is None` fallback now calls
