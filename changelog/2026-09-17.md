# 2026-09-17

`10:05` **Commission JV — the statement banks get a reconciliation anchor, so a short
reading can no longer post.** Branch `fix/commission-jv-recon-anchor`.

The report: the same commission document gave complete detail rows through the manual
wizard but repeatedly short ones through email ingest — and the email JV's debit/credit
still tied out exactly. Traced to three things, all in `main`, all shared by both paths.

1. **Balance is an identity, not a check.** `cc_jv.build_jv_rows` takes Cr from one leg
   per detail row and Dr from `Σ commis_amt / Σ tax_amt / Σ total` over the *same* list.
   Every layout guarantees `pay = commis + tax + net` per row, so **any subset balances**
   — 9 of 12 rows ties out perfectly, just smaller. `consolidated()` in `ccJv.ts` is the
   same arithmetic. `_review_flags`' `unbalanced` compares per row, so it catches a
   misread row and never a missing one.
2. **The one figure that knows how many rows there should be was deliberately discarded,
   for exactly these layouts.** `ROW_RULES` rule 2 told the model to SKIP
   `TOTAL / รวม / จำนวนเงินรวม` and `_strip_noncard_rows` deleted it again if it leaked.
   KTC/GHL/PAYPAL/SIAMPAY keep their footer (`reconMismatch` → parks) and BAY keeps its
   summary for the VAT spread; BBL/KBANK/SCB had nothing to compare against at all.
3. **Multi-page PDFs lost everything after page 1.** `extract_stateless` hardcoded
   `extract_pages_as_pdf(file_bytes, [0], …)` because "credit-card docs are single-page".

### Fixed during self-review (`/code-review` on the diff, before commit)

Three of the findings were bugs in the change itself, two of them serious:

- **A false `totalMissing` on every SCB statement.** The first cut took "the last
  summary-shaped row" as the anchor, but a real SCB statement prints TOTAL, then
  WITHHOLDING TAX, then NET AMOUNT — and `_is_summary_row` matches all three, with the
  last two carrying no gross. So a correctly-read statement reconciled against nothing and
  reported itself unverifiable, which would have parked every SCB document and disabled
  auto-post for that BU. New `_is_total_anchor()` excludes NET AMOUNT / WHT rows and
  requires a *readable* amount, so a total read as `0.00` also falls through to
  `totalMissing` rather than claiming a gap the size of the statement.
- **A reverted precedence change.** The change had also flipped `finalize_extraction` to
  route the normalizer on `detected or bank_code`. That broke the wizard's own
  "Re-extract with &lt;bank&gt;" override — a merchant name leaking into the issuer field
  (`บริษัท โรงแรมกรุงเทพ จำกัด` → BBL, tier 1a) would send a KTC fee invoice down the
  statement branch, where the non-zero-`pay_amt` filter drops **every** fee row
  (`pay_amt` is null by design there). And it bought nothing on the email path it was
  aimed at: `_resolve_bank` already returns `detected or rule_bank`, so detection has won
  before `finalize_extraction` is reached. Reverted to the single `bank_code or detected`.
- **Only the *absence* of a total was gated on the anchor codes**, so a generic document
  that leaked any summary row got reconciled against whatever it carried. Both branches
  are gated now.
- The one fixture built from a real SCB statement was being called with `bank_code=None`,
  which is precisely what hid the first bug — restored to `"SCB"` with
  `assert ext.warnings == []`.

### Known gaps, deliberately not in this change

- **BAY has the same exposure.** `_normalize_bay_statement` consumes its summary row for
  the VAT spread but never compares `s_gross` against Σ gross, so a short BAY reading still
  auto-posts with no warning. It already holds both figures — the comparison is one line,
  and the honest fix is one shared reconcile helper called from both branches rather than
  three of the four statement layouts. Worth doing next.
- **Page cap vs billing.** Sending up to 5 pages for `charged_docs=1` makes CLAUDE.md's
  "credit card charges **per file** … pages don't matter for a card statement" false: one
  credit can now buy ~5× the vision tokens, and `SUM(charged_docs)` understates real cost
  by that factor. Either bill `billable_pages()` here as AP invoice does, or keep a lower
  page cap and warn on truncation. Flagged to the user as a pricing decision, not decided
  here.
- `_STATEMENT_ANCHOR_CODES` is a third hand-maintained copy of "which layouts mandate a
  total", alongside the ROW_RULES whitelist string and the layout files. Adding a bank
  silently skips the anchor check instead of failing; generating the whitelist text from
  the set would make them impossible to disagree.
