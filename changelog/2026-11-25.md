## LLM usage row written off the request path (branch `perf/llm-usage-log-off-request-path`)

- `15:00` **Backend (`llm/client.py`, `services/shared/llm_usage_logger.py`, `lifecycle.py`):** `log_llm_usage` was awaited before every LLM call returned, so each `/suggest` and `/extract` waited for one extra DB round trip (about 330 ms measured on dev). The two call sites now use `schedule_llm_usage`, which starts the insert as a task (context vars copied at schedule time) and keeps a reference until it finishes; shutdown calls `drain_llm_usage()` so a deploy does not drop the rows of calls that just ended. A failed insert is still logged and never raised. Cost rows are written the same way and with the same content, only later.
- Tests: `test_usage_service.py::TestScheduleLlmUsage`.

## AP Invoice: Step 4 prefetches the AI suggestion, the button applies it (branch `fix/ap-suggest-prefetch-not-apply`)

- `16:00` **Frontend (AP Invoice):** supersedes the auto-fill of #415. Entering Step 4 now asks for the suggestion in the background and applies nothing (no toast, rows stay empty); the AI Suggest button applies the answer, instantly when it has arrived. The prefetch is used only when the request would be the same (same rows, same Invoice Description, same vendor); typing a description first, or a failed prefetch, makes the button ask again. A prefetch costs one LLM call even if the button is never pressed. User-visible, park for the monthly release note.
- `16:00` **Frontend (AP Invoice):** the suggestion toast read its count before React had run the row update, so a successful suggestion could say "AI could not generate new suggestions". The update now runs synchronously (`flushSync`) before the toast. Found in the real-browser run.
- Tests: `useAPSubmission.test.ts` (`F2b: autoSuggest prefetch`, 6 cases). Real-browser run on a local stack, BU carmencloud: prefetch at +74 ms with rows empty, one click filled all 10 rows with no second request.

## AP Invoice: a restored draft on Step 4 prefetches the suggestion too (branch `fix/ap-suggest-prefetch-on-restore`)

- `16:30` **Frontend (AP Invoice):** the prefetch added in #418 ran only from the Step 3 "Continue" button, so a draft restored straight onto Step 4 (after a session drop and re-login) never asked, and the AI Suggest button had to start from nothing. The prefetch is now one effect on entering Step 4, so both the button and Restore trigger it; rows stay untouched until the button is pressed. Found from a tester's QA run (GL data loaded after Restore, no `/ap-invoice/suggest`). User-visible, park for the monthly release note.
- Tests: `useAPInvoice.test.ts` (restore onto Step 4 asks once and fills nothing; fails if the effect is removed). Real browser, local stack, BU carmencloud: Restore -> request at the restore, rows empty and no toast; one click filled 10/10 with no second request.
