## Backend

`10:23` `GET /api/v1/carmen/notifications?uri=&bu=&since=` → `{"has_notification": bool}` — interim
poll substitute for the unbuilt `CARMEN_INTEGRATION.md §3.2` webhook (`notification.created`
was only ever a proposal; nothing sends it). Same Carmen-token auth as `/settings`,
read-only — polling never marks anything read.

- **A badge, not a feed.** §3.2's own payload deliberately carries no message text, so the
  badge only ever needed a bool. The full list stays the in-app bell's endpoint
  (`GET /api/v1/notifications`) rather than becoming a second copy of that contract to keep
  in sync.
- `services/notification_service.py` — new `has_notification()`, one `EXISTS` instead of
  `list_notifications`' 50-row fetch + count. `since` given → anything created after it;
  omitted → anything unread. **`since` is the mode that works**: unread only ever clears
  through our own bell, so for a BU whose staff live in Carmen and never open our app the
  badge would otherwise go true on the first document and stay true forever. The cursor is
  the caller's; we store no state for it.
- `services/email_ingest_service.py` `_finish()` now calls `notification_service.notify()`
  for `status in ("posted", "failed")`, writing `document_posted`/`document_failed` rows so
  the endpoint has email-automation outcomes to report at all. `skipped` stays silent on
  purpose — same rationale as the existing `except _Skip` handling (a customer's own
  filename/sender rule saying "not this file" isn't a failure).
- `routers/email_automation.py` — new `read_notifications` route next to `read_settings`,
  no new auth/rate-limit code (`_caller`/`_resolve` already cover it).
- Docs updated to match: `docs/CARMEN_INTEGRATION.md` §3, `docs/CARMEN_API_SPEC.md`
  (bumped to v4.2, new §6 for Carmen's own developers),
  `docs/email-automation/03-api-reference.md`.

## Security

`13:45` **Email Automation Settings API: the admin path authorised nothing.** Found in a
security review of the email-automation code. `_caller()` accepted any structurally valid
admin JWT as a full operator — no permission check, no `tenant_scope` check — and
`_resolve()` returned early on that path, so no ownership was proven either. Every other
admin surface in the codebase goes through `require_permission`, and the sibling
`require_maintenance_auth` in the same module enforces `configs:write`.

Impact: a holder of a **read-only `viewer`** JWT, or a support admin scoped to one tenant,
could read every BU's `tax_ids`, `owner_emails` and `ingest_address`, rewrite their rules
and `owner_emails` gate, and overwrite or delete any tenant's Carmen posting credential.
The `ingest_address` is the sharp end: `_fresh_tag` documents the tag as *being* the
authorization to write a document into that BU's ledger, so leaking it hands over a path
to post a fabricated JV into that customer's Carmen books using their own stored token.

- `routers/email_automation.py` — the `Bearer` branch now builds a real `AdminPrincipal`
  and requires `configs:write` (`_ADMIN_PERM`); `Caller` carries the principal;
  new `_assert_in_scope()` enforces `tenant_scope` in `_resolve()`, the one place a
  request's `uri`/`bu` becomes a concrete tenant.
- **`configs:write` on the reads too, not `configs:read`** — `viewer` holds every `*:read`
  permission there is (`20260615000002_seed_control_plane.sql`), and a GET here returns the
  ingest capability. Reading it is a config-administration act, not a dashboard glance.
- A `Caller` with no Carmen token *and* no principal is refused (403), not defaulted to
  unrestricted — "no scope recorded" reading as "every tenant" is the bug itself.
- `routers/admin/deps.py` — extracted `decode_admin_principal()`, now the single place a
  signed admin JWT becomes an identity; `get_current_admin` and `require_maintenance_auth`
  both use it (two duplicated decode blocks removed, error strings unified). Dropping
  `perms`/`tenant_scope` on the floor while reading a username off the raw payload is
  exactly how this hole appeared.
- Tests: `viewer` / `order_reviewer` / no-perm tokens are 403; scoped admin off-tenant is
  403, on-tenant passes; global admin unchanged. 914 backend tests green.
- `docs/email-automation/03-api-reference.md` §Auth model updated.
