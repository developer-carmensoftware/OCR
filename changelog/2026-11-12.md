## DB: two indexes for the JV queue's manual source, and a way to count round trips (branch `perf/sql-hygiene`)

`12:20` A SQL pass over the whole system (against `docs/SQL_PERFORMANCE_AUDIT.md`, which found the database idle:
SQL under 3% of request time). Nothing is slow today; this closes the one growth cliff that code written after the
audit opened, and records what was measured and rejected.
- **`ix_email_documents_task_id`** (partial, `task_id is not null`). The manual queue lists a card only if no email
  document owns its task (`NOT EXISTS … task_id = credit_cards.task_id`); that FK had no index, so every list and every
  counts request sequentially scanned all of `email_documents`. `input_tax.py` and the admin email list read the same column.
- **`ix_credit_cards_tenant_when`** on `(tenant_id, coalesce(submitted_at, created_at) desc) where deleted_at is null`, the
  expression the queue orders by (`_manual_when`). It matches that expression and the predicate character for character.
- **Measured** (20,000 rows, EXPLAIN ANALYZE, control = ANALYZE only): manual list 8.3 → 0.6 ms; manual counts 4.5 → 2.6 ms;
  narrowed manual views 4.5–13.7 → 0.4–4.0 ms. Searches (`ILIKE '%q%'`) unchanged at ~10 ms.
- **Does it affect anything else?** 39 distinct statements that touch the two tables were re-planned with and without
  (24 service calls exercised, plus the admin list and the input-tax UPDATE): 20 change, every change is a Seq Scan
  replaced by one of the two indexes, none gains a Seq Scan. Writes: 5,000 rows into each of `email_documents`,
  `ocr_tasks`, `credit_cards` 365 → 393 ms (~8%). pgTAP passes; the browser suite is 67/67 with the indexes, and 67/67
  with every page forced down the deep path; CI backend job exit 0.
- **Tried and not added:** `pms_events (tenant_id, created_at desc)` (the single-column index already serves the list at
  0.1 ms); a covering index for the chip counts (the planner kept its sequential scan).
- **Not checked:** the full 97-migration chain on an empty database. It stops at file 5 here (pg_cron can only be created in
  the `postgres` database), so the migration was applied to the populated local DB twice instead, to prove it is idempotent.
- **`scripts/qa/db_roundtrips.py`** counts pool checkouts, ORM statements and server statements per request. Locally one
  checkout costs 5 server statements for 1 ORM statement (pool_pre_ping, BEGIN, `SET statement_timeout`, the query,
  ROLLBACK), and a request after the session cache expires costs double. No connection churn locally (0 new connects); the
  pooler's authentications per request cannot be measured without Supavisor. This is the evidence for the checkout-cost
  phase of the SQL plan; nothing in the application changed.
- **Found, not fixed:** every cron function that logs to `job_runs` re-raises after writing its `failed` row, so the row
  rolls back with the failing statement and a failing purge leaves no trace on `#/admin/jobs` (eight live functions, none
  has failed yet). Fixing it means redefining all of them; recorded in the migration header.
- **Also found:** the cron routes (`/carmen/email-ingest/confirmations`, `/email/ingest`, `/pms/process/run`) are logged to
  `performance_logs`, ~1,730 rows/day, about as much as real traffic. Left alone for now: the August audit measured the
  confirmations route at p50 2.3 s for one SELECT, the cleanest control we have for connection overhead.

## Infra: Supabase CLI 3.1.0 (branch `chore/supabase-cli-3`)

`13:55` `npx supabase` resolves to CLI 3.x, which refuses `supabase/config.toml` (`[inbucket]` is no longer
supported), so everyone had been typing `npx supabase@2.121.0` and CI was pinned to 2.121.0 with a note to move "in its own
PR". This is that PR; the aim was zero behaviour change, checked rather than assumed.
- **`config.toml`:** `[inbucket]` → `[local_smtp]`; `[auth.email]` and `[auth.sms]` `enable_signup` → `enabled` (same values);
  `[experimental.pgdelta] enabled = false` pinned, because 3.x turns pg-delta on by default for `db diff` / `db pull`.
- **`ci.yml` and `deploy.yml`:** both pinned to `3.1.0` (the deploy workflow was `latest`, so its `db push` would have hit
  the same config error). `CLAUDE.md` says which CLI to use.
- **Checked locally, same Docker stack, each CLI from an empty database:** all 97 migrations apply on 3.1.0 and on 2.121.0;
  pgTAP 3/3 on both; `pg_dump` of `public`, the extensions (pg_cron, pg_net, pg_partman, vault, vector, …), the default ACLs
  and every `anon`/`authenticated`/`service_role` grant: **identical** between 2.121.0 on the old config, 2.121.0 on the new
  config, and 3.1.0 on the new config (the only differing lines are pg_dump's random `\restrict` token).
  `db push --db-url <local> --dry-run` on 3.1.0, the call `deploy.yml` makes, reports "up to date". The new config also works
  on 2.121.0, so nobody still on 2.x breaks.
- **A planned pin I did not add, and why:** 3.x's own docs say an unset `auto_expose_new_tables` falls back to `true`, so I
  planned to pin it `false`. Measured: unset on 3.1.0 is **identical** to 2.121.0, and pinning `false` is the change — it
  strips `service_role`'s default privileges (314 differing lines). `anon`/`authenticated` hold nothing either way. It stays
  unset, with a comment saying why.
- **Found, not fixed (already broken on 2.121.0 too, so not caused by this):** `db diff` fails with "no files matched pattern:
  supabase/schemas/40_quotas.sql" — `schema_paths` still lists the file removed with the retired quota engine. The pgdelta pin
  could not be exercised for the same reason.
- **Not testable here:** the remote `db push`, and the deploy workflow itself (it has never passed).

## Backend: fewer database round trips on the hottest paths (branch `perf/fewer-round-trips`)

`14:30` From the SQL pass: SQL is under 3% of request time, but each pool checkout costs four server statements around the one
query: two BEGIN/ROLLBACK pairs, one of them the pre-ping (`db_roundtrips.py --breakdown` lists them). So the saving is counted in checkouts, measured with
`scripts/qa/db_roundtrips.py` against a 20,000-row tenant (local DB, in-process; "server" = statements the server saw):

| request | checkouts before → after | server statements before → after |
|---|---|---|
| `/auth/usage`, warm | 2 → 1 | 10 → 6 |
| `/auth/usage`, session cache expired | 4 → 2 | 20 → 11 |
| `/notifications`, warm | 1 → 1 (ORM statements 3 → 2) | 7 → 6 |
| any endpoint, session cache expired | 3 → 2 | 16 → 11 (`/email/documents`) |

Each saved round trip is a few milliseconds against a warm pooler, so this is overhead removed, not a promised speed-up; the numbers above
are counts, not latencies.
- **`/auth/usage`:** balance and subscription now share one session (`credits.get_usage`). Each half keeps its own fail-soft: a failed
  read gives 0 / None for that half only, and the session is rolled back between them (a failed statement aborts the transaction).
  `get_credit_balance` and `get_active_subscription` stay for their other callers and share the same helpers.
- **Session validation** (`auth/dependencies.py`): on a cache miss, one `UPDATE ocr_sessions SET last_used_at = now() … RETURNING
  carmen_token_encrypted` replaces a SELECT in one session followed by the throttled UPDATE in another. A revoked or deleted session
  matches nothing (still a 401) and is no longer written to. The cache TTL equalled the throttle, so every miss was followed by a touch anyway.
- **`/notifications`:** total and unread come from one aggregate (`count(*)`, `count(*) filter (where read_at is null)`), then the page.
  `paginate()` itself is unchanged for its other callers.
- **Tests:** 15 new or changed unit tests fail against the old code and pass against the new (the helper that scripts the notifications
  statements moved with the change; one test, a revoked session answering 401, passes on both by design). CI backend job exit 0, coverage 83%;
  mypy reports the same 139 errors as `main`, none in the changed files.
- **Not done:** the activity counts (three statements → one). It saves 2 of ~8 statements on a page that is compute-bound and needs the
  mock-DB helper and the "CASE appears once" test rewritten; gated on the prod numbers (checkout overhead as the server sees it).
