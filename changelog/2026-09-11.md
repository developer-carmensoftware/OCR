## `ARReviewPane` reshaped to match `JvEditor`, then made editable

`12:15` Two asks in one thread, both aimed at the same seam: the AR reconciliation table in
the review modal (`ARReviewPane`) and the credit-card JV table beside it (`JvEditor`) already
share the `.jv-table` CSS vocabulary but still read as two different tables.

**Column order and shape, to match `JvEditor`'s.** Reordered `ARReviewPane`'s columns from
`Payment type, THB amount, Dept, Account, Debit, Credit` to `Dept, Account, Payment type,
Debit, Credit` — GL identity first, footer collapsed to `colSpan={3}` the same way
`JvEditor`'s does. Dropped the **THB amount** column entirely (dead weight once the point of
the table shifted to posting rather than reconciling against the printed report by eye — the
figure is still on `ar-settings`) along with `totalThb`/`thb` and the now-unused
`review.arColThb` i18n key. Moved the **control (debit) leg to the top** of `tbody` to match
`JvEditor`'s debit-first convention, which meant flipping the `.arv-row-control` raised-border
rule from `tr + tr.arv-row-control` (the row itself, when it had a predecessor) to
`.arv-row-control + tr` (the row *after* it) on both the desktop and the phone-width stacked
layout — the row no longer has a predecessor to key off.

**Then: AR mapping became editable inline, not just visually aligned.** The ask that started
the column work turned out to be about function, not just looks — "can this finish in the
review modal, the way commission does, without a trip to `#/CreditCardOCR/ar-settings`". It
can, because `jv_for_document()` already rebuilds the JV fresh from `ar_reconcile_mappings` on
every read (review-open *and* approve), so there was never a draft-staging problem — only a
missing write path scoped for a screen that has loaded none of the rest of the bank's
settings.

**Backend**

- `ar_reconcile_service.upsert_mapping_rows()` — upserts just the rows a reviewer touched for
  the bank's *current* `post_type`, unlike `save_settings`'s full delete+reinsert of both
  mapping sets. Raises `ValidationError` if the bank has no setting row, or if the caller's
  `post_type` no longer matches the bank's (same "deliberate act with visible cost" reasoning
  `post_type` gets everywhere else — a stale screen fails loudly rather than writing rows
  nothing will read).
- `ARMappingPatchIn` schema (`bank_code`, `post_type`, `rows: list[ARMappingItem]`), and
  `PATCH /api/v1/ar-reconcile/mappings` wiring it to the service — the review modal's save
  path, `PUT /settings` stays the settings screen's full-replace path.
- 7 new unit tests (`test_ar_reconcile_service.py`) + 2 router tests
  (`test_ar_reconcile_api.py`): insert, update-in-place, stale-`post_type` refusal, no-setting
  refusal, blank-code skip, uppercasing, and 422 on an unknown `post_type`. 36/36 in both files.

**Frontend**

- `ARReviewPane.tsx` grew the same shape `JvEditor.tsx` already has: `overrides` /
  `guessedKeys` / `onOverride` / `onUndo` / `onState` props, `useGlMasters()` +
  `allowedAccountsForDept`/`isAccountAllowed` for department-scoped account pickers, and an
  internal background AI-fill effect (`suggestPaymentTypes`, the same shared endpoint
  `ar-settings`'s Auto-Map already calls) ported near-verbatim from `JvEditor`'s own. Mapped
  legs and non-zero orphans (now `newTypes`, grouped by exact printed label so two lines
  sharing one unmapped label ask once, not twice) get `CustomSearchSelect` pickers with the
  `jv-tag--ai`/`jv-tag--undo` badges; the control leg and genuinely zero-amount lines
  (`zeroLines`) stay read-only — a clearing-account change is a once-per-bank setup choice,
  not a per-document one.
- `ReviewDocument.tsx`: new `arOverrides`/`arGuessedKeys`/`arUnmapped` state (mirroring
  `overrides`/`aiKeys` exactly, but AR-scoped — writing an AR correction into `overrides`
  would save the right codes under the wrong feature's keys, same reason `ruleCount && !isAR`
  already guarded the credit-card write off). `arBlockReason` now reads live `arUnmapped` from
  `ARReviewPane`'s `onState` instead of the stale `arJv.unmapped` fetched at modal-open, so
  Approve un-disables the moment every picker is filled rather than staying stuck until a
  round-trip. `approve()` gained an AR mapping-save step, parallel to the existing
  `patchAccountingConfig` block: if `arOverrides` is non-empty, `patchARMappings()` first, then
  re-fetch the document (no separate preview endpoint needed — `jv_for_document` is
  never cached) so the subsequent `approveDocument` call posts the just-saved mapping's rows;
  a still-blocked result after that save surfaces as `postError` rather than proceeding.
- 2 new i18n keys (`review.arMappingSaveFailed`, `review.arStillBlocked`) plus `arNewType`
  for a new/unmapped row's note, EN+TH; reworded `review.arMappingLivesElsewhere` since the
  mapping itself is no longer one of the things the settings-page link is for (Detail/Summary,
  the description template, and the control account still are).

**Tests** — `ReviewDocument.test.tsx`'s AR block rewritten for the new shape: `paneRows()`
now reads a picker's `<select>` value when a cell has one (the mocked `CustomSearchSelect`)
and falls back to text otherwise, fixtures use account codes from the shared masters mock
(picker options are matched against real option values, not the arbitrary KBANK codes AR
used while read-only), and the "unmapped" test checks `.jv-row--needed` row count instead of
a `.missing-cell` class the mock never renders. 71/71 in that file, 729/729 frontend overall;
`tsc`, `lint`, `build`, `npm run contrast` and `npm run styles` (including `ARReviewPane.tsx`
by name) all clean.

Release note pending (user-visible: AR review can now be finished from the review modal). No
`VERSION` bump here — batched per release, per the changelog convention.

## Two follow-ups from screenshots: a Summary seeding gap, and a quieter merge row

`13:25`

**`ar-settings`: switching to Summary could show 0/0 mapped with no rows to map.**
`useARReconcile.load()` only seeded the sample vocabulary when **both** `Detail` and
`Summary` arrived empty (`seeded = detail.length === 0 && summary.length === 0`) — so a BU
that had mapped Detail by hand (`7/7`) but never opened the Summary tab saw `0/0` and no way
to fill it beyond typing custom types by hand. Seeding is now decided **per post type**: each
set is seeded independently from the same `getSamplePaymentTypes()` call (fetched once, used
for whichever side is empty) rather than gating on the other side's state. New regression test
`seeds Summary on its own when Detail is already mapped and Summary is not`. 15/15 in
`ARReconcileSettings.test.tsx`.

**Review modal: a Summary merge's folded-in lines are a disclosure now, not always-on rows.**
`ARReviewPane`'s `.arv-row-src` rows (the printed labels a scheme leg folded from — e.g. `VS
INTER UP PREM` + `VS LOCAL UP PREM` under `VS`) used to render unconditionally under every
merged leg. Collapsed by default now, toggled from a control next to the leg's own label,
local `expanded: Set<string>` state, no change to the underlying `groups`/`merged`
computation.

`14:40` **Follow-up: the toggle moved out of the Payment type cell into its own leading
column.** First pass put a `[chevron] VS  2 folded in` button inline at the start of that
cell — but Dept and Account are wide `CustomSearchSelect` pickers occupying the first two
columns, so a control meant to expand the *whole row* sat visually stuck in the row's middle
rather than at an edge, which is where every other row-expand in this app puts it
(`ExtractionsPage`'s admin table: a dedicated leading icon-only column, `ChevronRight` ↔
`ChevronDown` swap, not a rotate). Matched that precedent: new `.arv-c-toggle` leading column
(narrow, unlabelled header via `sr-only`, empty on every non-merged row), `.arv-toggle-btn`
icon-only button styled like `.admin-icon-btn`'s bordered affordance (a local copy, not a
shared class — that table isn't in the admin bundle, and reusing an unreachable class is
exactly the `.rd-ar-hint` mistake from 2026-09-09). The Payment type cell now just shows the
label plus a plain `{n} folded in` count — no longer the click target. 3 new i18n keys
(`arExpandCol`, `arExpandFolded`, `arCollapseFolded`), EN+TH.

**Tests** — `ReviewDocument.test.tsx`'s Summary-merge case checks the collapsed state first
(`.arv-row-src` absent, row reads `['', 'GEN', '510300', 'VS2 folded in', '', '25,091.00']`
— leading empty cell for the toggle column), clicks the icon button by its accessible name
(`'Show 2 lines folded into VS'`), then checks the constituent rows appear. 730/730 frontend;
`tsc`, `lint`, `build`, `npm run styles`, `npm run contrast` clean.

## Bug: `settlementTotalMissing` fired on every KBANK settlement report, not occasionally

`14:55` User report: the `warn.settlementTotalMissing` banner ("The report's own TOTAL line
could not be read...") was appearing on every KBANK settlement report for this tenant, every
POS terminal — not the occasional hard-to-read scan the warning implies. A sample document
they shared (KB1P554V2, merchant 451005282039001 — the same one `test_ar_settlement_normalize.py`
already uses) showed the `TOTAL BY MERCHANT ID` line printed perfectly legibly
(`22`, `25,091.00`, `582.99`, `40.81`, `24,467.20`), which ruled out a vision-model misread and
pointed at the prompt instead.

**Root cause: two contradictory instructions in the same prompt, and the later one won.**
`kbank_settlement.py`'s `LAYOUT` tells the model "add ONE final summary row from the TOTAL BY
MERCHANT ID line — EXCEPTION to the skip-summary-rows rule." But `shared.py`'s `ROW_RULES`,
appended *after* the layout text on every prompt, restates the general "SKIP rows labeled
TOTAL" rule with its own exception whitelist — `(BAY statement; KTC/GHL/PAYPAL/SIAMPAY fee
invoices)` — that KBANK's settlement report was never added to. The model saw "add it" early
and "skip it, and the add-it exception doesn't apply to you" later, and the later instruction
(closer to the output) won — a generic LLM recency failure, not a document-quality one. This
also explains why it was 100% reproducible rather than intermittent: the model wasn't
attempting to read a hard figure, it was following an instruction not to emit the row at all.
`_normalize_ar_settlement` was reporting correctly (`summary` really was `None`); the bug was
upstream of it.

**Fix** — one line, `backend/app/llm/prompts/shared.py`: added `KBANK settlement report` to
`ROW_RULES`' exception whitelist. `_PROMPT_VERSIONS["KBANK_SETTLEMENT"]` bumped `1.0.0` →
`1.1.0` (only that entry — the whitelist text is shared across every bank prompt, but the
exception clause was already reachable/correct for all the others, so this is the only prompt
whose actual extraction behavior changes).

Considered and rejected: a code-level fallback like `_normalize_bay_statement`'s "gross ≈ Σ
others" heuristic for a mislabeled total row. Doesn't apply here — the row isn't mislabeled,
it's never emitted at all, so there's nothing for a fallback to locate; the fix has to be
where the row gets dropped.

**First fix attempt did not work — caught by a live test, not left as an assumption.** The
user provided their own KBANK settlement report (KB1P554V2, merchant 451005282039001, TOTAL
BY MERCHANT ID = 25,091.00 — printed cleanly, ruling out a scan-quality cause) and a real,
paid OpenRouter call was made against it (`extract_stateless(..., doc_type=AR_RECONCILE,
page_indexes=[-1])`, `gemini-2.5-flash-lite`). Result: still 7 rows, no `TOTAL`. The
`ROW_RULES` whitelist theory was real but insufficient on its own.

**Root cause, corrected: the layout's own instruction was losing to its neighbors, not to
`ROW_RULES`.** Right before `kbank_settlement.py`'s "add the TOTAL BY MERCHANT ID row"
instruction sit three vivid warnings to IGNORE other summary-shaped blocks ("adding them
would post the day's takings two or three times over"). The model was generalizing that
warning to the visually similar `TOTAL BY MERCHANT ID` line instead of reading it as the one
exception — a pattern-matching failure inside one layout's own text, not a cross-instruction
conflict with `ROW_RULES`. Rewrote the layout: explicitly states `TOTAL BY MERCHANT ID` is
"NOT one of the ignored blocks above," moved the requirement into its own
`MANDATORY FINAL ROW` section (broken out of the repeated "Critical:" pattern so it can't be
swept up by it), and reframed as a countable contract — "if the block prints N payment-type
rows, details[] MUST contain N+1 objects" — rather than a soft "then add one more."
`_PROMPT_VERSIONS["KBANK_SETTLEMENT"]` → `1.2.0`.

**Verification** — confirmed live, twice, against the user's real document: 8/8 rows
extracted both times, `TOTAL` row present with the exact printed figure (`pay_amt =
'25,091.00'`). The stale parked document from before the fix (`email_documents` id
`293378a4-…`, `doc_no 210726E00035291`, KBANK, `pending_review`) was retired via the app's
own `reject_document()` service call (not a raw DELETE — this table has no hard-delete path
by design) so it can't be confused with a fresh re-scan. `test_ar_settlement_normalize.py`
(7/7), `test_prompts.py` + `test_llm_row_clean.py` (15/15), broader kbank/settlement/prompt
test slice all green — unaffected, since the normalizer itself was never the bug. `ruff`
clean. The one-off live-test script lives outside the repo, in the session scratchpad, not
committed (real paid API calls, not a pytest case).

`15:55` **Second verification pass: through the real email ingest pipeline, not just
`extract_stateless` directly.** The direct-extraction test above proves the prompt fix; it
does not prove the fix survives dedup/park/normalize/entitlement in the actual pipeline
`run_ingest()` drives. Targeted `dev.carmen4.com/carmen` (`af0786cd-…`), the one tenant with
a KBANK `ar_reconcile` email rule already configured, `auto_post=False` — deliberately not
the tenant from the first test pass, which has `auto_post=True` and would have auto-posted a
real JV to Carmen with no review.

Two real-mailbox findings along the way, neither a code bug:
- **A self-sent test email never reaches the inbound pipeline.** Sending via SMTP from the
  ingest mailbox's own account to its own `+tag` alias lands only under Gmail's `\Sent`
  label — no delivery pass runs, so `Delivered-To`/`X-Original-To`/`Received: … for` (what
  `tag_from_recipients()` actually reads; deliberately never `To:`, so a customer's own
  auto-forward address can't be read as a tag) never get attached, and the "AR Agent" label
  filter that `run_ingest()`'s poll reads never fires. Worked around with a raw IMAP
  `APPEND` carrying a hand-set `Delivered-To` header straight into that label — same
  downstream code path as a genuine delivery, since the poller only cares about the label
  and envelope headers, not how a message arrived there.
- **`is_entitled()` is a separate gate from `auto_post` and from credit balance.** The
  target tenant had 3,539 credits (plenty) but no active `tenant_subscriptions` row, so
  email ingest held the mail unread (`retry_later`) — the monthly-package check email
  ingest applies on top of what the manual wizard needs. A 1-day `tenant_subscriptions` row
  (`sub_starter`, 200 docs) got the poll past that gate; deleted immediately after the run
  rather than left to expire, so a billing table carries no stray test row even briefly.

Result: `run_ingest()` → the document parked (`pending_review`, since `auto_post=False`)
with **`extracted.warnings == []`** — no `settlementTotalMissing`. `review_payload.details`
shows exactly the 7 card-type rows; the model's 8th (`TOTAL`) row was consumed by
`_normalize_ar_settlement` for the cross-check and correctly dropped before storage — the
same "TOTAL row is consumed, never posted" contract `test_clean_report_keeps_its_rows_and_says_nothing`
already pins. Both the test document and the 1-day subscription were cleaned up immediately
after: the document via `reject_document()` (audit trail kept, same as the earlier cleanup),
the subscription row deleted outright rather than left to expire.
