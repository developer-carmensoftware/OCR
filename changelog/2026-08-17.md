### Gmail-side setup (not code — but the feature does not work without it)

- The label filter must match on **`deliveredto:aragent@carmensoftware.com`** in *Has the
  words*, **not** `to:(aragent@carmensoftware.com)`. On a forwarded mail the `To:` header
  is the customer's own address; the alias appears only in `Delivered-To`. Measured against
  Gmail search directly: `to:` → 0 hits, `deliveredto:` → matches (and covers every `+tag`).
  The old `to:` filter is why the first forwarded test document landed in `INBOX`.
- The filter must **not** mark mail as read. `_fetch_unseen()` searches `UNSEEN`, so
  anything read before the poll — by a filter or by a person opening it — is invisible to
  the pipeline for good.

### Backend

- `services/email_ingest_service.py` — new `sweep_confirmations()`: searches the mailbox
  `UNSEEN FROM forwarding-noreply@google.com`, follows the `vf-` link, stamps
  `gmail_confirmed_at`. Reuses `auto_confirm_forwarding` / `gmail_confirm_link` /
  `gmail_confirm_code` / `tag_from_recipients` unchanged — no new dependency. Split from
  the document poll because the two are not comparable work: a full ingest batch runs 3-5
  minutes (attachments are serial), this is a search that usually matches nothing.
  - Marks a confirmation seen **whether or not Google took the link**. A link we cannot
    follow is almost always dead, and retrying it every minute is 1,440 requests/day for a
    forward the customer can re-trigger with Gmail's own "Resend email".
  - A confirmation whose tag is outside the window is deliberately left unseen for the
    10-minute poll — marking it seen here would destroy the only copy.
- `services/email_settings_service.py` — new `tags_awaiting_confirmation(db, hours)`.
  `gmail_confirmed_at is null` is true forever for a BU that never sets up forwarding, so
  the 24 h `updated_at` window is what makes the sweep quiescent: nobody configuring →
  empty set → **no IMAP connection at all**. Measured in-process: an idle tick is one
  SELECT; a tick with someone mid-setup is ~4 s of IMAP, off the event loop.
- `_record_run` — takes `job_name`/`rows`, and **writes nothing for a run that found no
  mail**. `job_runs` has no retention and no partitioning, and `#/admin/jobs` shows the
  newest 100 rows with no job-name filter, so a scheduled poll's idle ticks would bury
  every other job's history within hours (43k rows/month at 1-minute cadence). A failure
  always writes; "the poller is alive on a quiet day" is what `keep-warm` is for.
- `_connect()` — extracted, and every IMAP connection now carries
  `timeout=IMAP_TIMEOUT_SECONDS` (60). `imaplib` previously used the global socket
  timeout, which nothing sets: a mailbox that accepts the connection and then goes silent
  wedged a worker thread forever, and `asyncio.to_thread` cannot be cancelled. Harmless at
  one manual poll a day; not at one tick a minute.
- Module-level `asyncio.Lock` — a tick that finds a sweep in flight returns
  `{"status": "busy"}` and writes nothing, rather than queueing behind it.
- `routers/email_automation.py` — `POST /email-ingest/confirmations`, same
  `require_maintenance_auth` as its siblings, cron SQL in the docstring.
- Tests — 8 new in `test_email_ingest_pipeline.py`, including the performance claim
  asserted rather than believed (empty waiting set → `IMAP4_SSL` is never constructed) and
  the `job_runs` idle-skip in both directions. Whole backend suite green.

`14:00` **Backlog hardening — running out of documents no longer eats the customer's mail.**
Found while sizing the pipeline for "a few hundred unread bank mails". Throughput was never
the problem (10 messages/poll × 6 polls/hour ≈ 1,440 documents/day, and a 200-message
backlog drains in about an hour and a half); what the volume exposes is what happens at the
edges of a long batch.

- **`InsufficientCredits` was filed as `unreadable_document`.** It fell through to the
  generic handler at the bottom of `_run_document`, so a BU that ran out mid-backlog got a
  ledger full of rows blaming the PDF, while the mail — flagged `\Seen` on the way in by
  `_fetch_unseen` — was gone, and this feature has no retry. A customer topping up got
  nothing back. Now: the exception exits ahead of the generic handler with its own log line,
  `_release()` deletes the claim row (the claim IS the dedupe, so leaving it means "already
  handled" for ever), and the poll clears `\Seen` on everything it handed back, so the next
  poll picks the same mail up again. Nothing was charged, so nothing is refunded.
- **The rest of that BU's batch is skipped, not hammered.** The exhausted tag is collected
  for the run and checked against the *tag* — which the envelope already gave us — so the
  remaining messages cost not even the one SELECT that resolving them would. Another BU's
  mail in the same batch is unaffected, which is why this is a per-tag skip and not an
  abort.
- **`run_ingest` is serialised against itself** (`_poll_lock`, same shape as the sweep's).
  A slow batch outlasting its 10-minute interval used to let the next cron tick start on
  top of it: the work would dedupe, the DB connections would not, and the pool is 15 for
  the whole application.
- **`IMAP_BATCH_SIZE` 20 → 10.** `_fetch_unseen` builds the entire batch, attachment bytes
  included, before the first document is processed — so the batch size is also the memory
  ceiling: 20 × `MAX_FILE_SIZE_MB` ≈ 100 MB resident at the peak on a small instance. Ten
  halves that and still clears 1,440 documents/day. Streaming one message at a time is the
  real fix if the peak ever matters again.
- Tests — 5 more (claim released, message handed back after a partial post, exhausted tag
  skipped without a lookup, `\Seen` cleared for handed-back mail, second poll skipped).

`15:00` **A bank's `.zip` is now opened, not thrown away.** Three test forwards in a row

```

TAX_SUMMARY_BY_TAX_ID_CSV_0835553001610_20260721.csv 1.4 KB          not a document
KB1P554V2_SUM_451005282039001_20260721.pdf            23 KB   %PDF-   the summary
```

- `services/email_ingest_service.py` — new `_unzip()`, called from `_attachments()`: a
  `.zip` part is expanded in place and its members are handed on **as if each had been
  attached directly**. Nothing else in the pipeline changes, which is the point — the BU's
  `filename_patterns` now match the *inner* filenames, so the customer decides which
  members are documents. Verified against the real archive above with the BU's live rules:
  the e-tax invoice matches (`E-TAX_INVOICE_CARD` → KBANK) and costs one document, the
  summary PDF gets a `no_rule_match` ledger row and costs nothing, the CSV is dropped by
  the extension filter that was already there. One mail, one credit.
- Guards, because zip is where this goes wrong: the member's **declared** size is checked
  before `read()` inflates it (same `MAX_FILE_SIZE_MB` ceiling as the mail itself — the
  zip-bomb guard), members count against the existing `MAX_ATTACHMENTS_PER_MESSAGE` cap,
  entry paths are reduced to their filename, a corrupt archive is logged rather than
  raised, and an unreadable member (encrypted, most likely) is skipped without costing the
  other documents in the same archive. Nested zips are deliberately not recursed into.
- Encrypted archives are **not** opened: `_attachments()` runs inside `_fetch_unseen`,
  before any tenant is resolved, so the BU's configured passwords do not exist yet. Worth
  revisiting the day a bank ships one — the rule already carries a password field.
- Tests — 6 new, built on the real archive's shape.

### Backend

- `routers/admin/email_ingest.py` (new, registered in `routers/admin/__init__.py`):
  - `GET /admin/email-ingest/documents` — the ledger, filtered by BU / status / reason code /
    date, left-joined to `ocr_tasks` for `charged_docs`. Returns per-status `counts` computed
    over the same filters **minus** status, so picking a status narrows the table without
    making the tallies lie, and a truthful `total` from its own `count()` (`/jobs` still
    reports `len(rows)`, which caps at `limit`).
  - `GET /admin/email-ingest/health` — reads cron liveness from **`cron.job_run_details`, not
    `job_runs`**. `_record_run` deliberately writes nothing for a poll that found no mail, so
    on `job_runs` a quiet mailbox and a dead scheduler are the same picture; pg_cron records
    every firing. Wrapped in try/except → a database without pg_cron reads "not scheduled"
    instead of 500ing.
  - `GET /admin/email-ingest/business-units` — one row per configured BU. Gated on
    **`configs:write`, not a read permission**: the row carries the ingest tag, and the tag is
    the authority to write documents into that BU's ledger and spend its credits. `viewer`
    holds every `*:read`, so a read gate would hand that out. Same reasoning `PUT
    /carmen/settings` already applies to `ingest_address`.
  - `POST /admin/email-ingest/poll` and `/confirmations` — `configs:write`. Mirrors of the
    `/api/v1/carmen/*` jobs rather than calls to them, because `middleware/maintenance.py`
    allowlists the `/api/v1/admin` prefix only: the carmen route 503s exactly when an operator
    most needs it.
- The poll's timeout is the interesting part. `adminFetch` aborts at 30s while a full batch
  runs minutes, so the endpoint waits `POLL_WAIT_SECONDS` (25) and then answers
  `{"status": "running"}` — under `asyncio.shield`, so the poll keeps going. Without the
  shield the timeout would cancel a poll that had already charged a document and half-posted
  a JV. Four answer shapes in total (`summary` / `busy` / `disabled` / `running`), each with
  its own copy on the button.

`16:50` **`scripts/reset_email_test.py` — put a test mail back the way the pipeline found
it.** Re-forwarding a document does not re-test it: three separate guards remember it, and
each is doing its job in production — the `email_documents` claim row, the `credit_cards`
duplicate check on `doc_no` + `submitted_at`, and the IMAP `\Seen` flag `_fetch_unseen`
