# 2026-09-24

`11:00` **GL mappings scoped per bank — a BU handling more than one bank no longer shares
one payment-type map across all of them.** *(uncommitted)*

The user flagged it from the Map Payment Types dialog (`pm-dialog`'s "Show additional
mappings" list): the entries there aren't specific to the selected bank. Tracing it
confirmed a real bug, not just a display gap — `bu_accounting_configs` is one row per
*tenant* (by design, `uq_bu_accounting_config_active`), and `bu_accounting_mapping_entries`
hung off `config_id` alone with no bank of its own. `save_accounting_config` deletes every
entry for the config and reinserts from whatever the browser tab has loaded, so saving the
Mapping page while bank B is selected could silently overwrite bank A's already-confirmed
mappings if that tab last loaded them for bank A.

- **DB:** `20260924000000_bank_scoped_mapping_entries.sql` — adds
  `bu_accounting_mapping_entries.bank_code` (nullable, FK `banks.code`), backfills it from
  `bu_accounting_configs.bank_code` (the only bank the table has ever recorded), widens
  `uq_bu_mapping_entry_active` to `(config_id, field_type, bank_code)`. A single-bank tenant
  sees no behavior change — the config row's own `bank_code` stays what's queried when
  nothing else is named.
- **Backend (`accounting_config_service.py`):**
  - `get_accounting_config(db, tenant_id, bank_code=None)` — entries filtered to
    `bank_code or row.bank_code`.
  - `save_accounting_config` deletes/reinserts only this bank's entries, stamping
    `bank_code` on every new row.
  - `patch_config` (the review screen's writer) and `fill_missing_mappings` (email-ingest's
    additive writer, currently unwired but kept correct) scope reads/writes the same way.
  - `get_account_usage` reports the entry's own `bank_code`, falling back to the config's.
  - `ConfigPatchRequest.bank_code`'s docstring updated — it now scopes `mappings` as well as
    `description`.
  - `routers/config.py` GET gains `?bank_code=`. `email_ingest_service.py`'s two
    `get_accounting_config` call sites (auto-pipeline gate, approve-and-post) now pass the
    document's own `bank_code`.
- **Frontend:**
  - `lib/api/config.ts`: `getAccountingConfig(bankCode?)` appends `?bank_code=`.
  - `useBankConfig.ts`: the initial fetch is scoped to the wizard-detected bank (not the
    config's stored default, which `normalizeConfigShape` doesn't necessarily agree with);
    a new effect re-fetches and replaces `savedMappings`/`savedCustomTypes` when the bank
    dropdown changes. Exposes `mappingsBankCode` — set in the same batch as those two, so a
    consumer effect can key off it instead of `bank` (which commits a render before its
    fetch resolves, which would otherwise let a stale "applied" guard skip the real update).
  - `useMapping.ts`: the config-apply effect now replaces (not merges) `mappings` and
    payment-type state on a bank change — the previous bank's fixed fields and custom types
    must not bleed into the new one. `usePaymentTypes.ts` gains `resetPaymentTypes()` for
    this; `initFromData` itself stays a merge (it deliberately preserves unsaved edits,
    pinned by `usePaymentTypes.test.ts`).
- **Tests:** `test_accounting_config_service.py` +3 (bank-scoped insert, one bank's
  correction leaving another's entry alone). `useBankConfig.test.ts` +3,
  `useMapping.test.ts` +1 (bank switch replaces, not merges). Backend full suite and
  frontend full suite (716 tests) both green. `tsc --noEmit` clean.
- **Not done:** the `pm-dialog` "Show additional mappings" toggle itself is unchanged — the
  user floated dropping it now that the list is naturally per-bank and shorter, but that's a
  cosmetic call, not something this fix requires.
- **Migration not yet applied** — `supabase db push` needs to be run against the remote
  project before any of the backend changes take effect there.

No release note yet: internal correctness fix, not a new capability. Add one once the
migration has actually shipped.

`14:56` **QA: real multi-BU email-automation run — no cross-BU leak, but a silent-loss defect

Requested test: prove that with several BUs sharing one mailbox label, no document can cross
from one BU's ledger/GL/Carmen posting into another's, using real mail, real LLM, and real dev

bank-document messages, full report at
[`docs/email-automation/qa/2026-09-24-multi-bu-report.md`](../docs/email-automation/qa/2026-09-24-multi-bu-report.md).

  poll's own summary, zero log line, `job_runs` still `status='success'`. A customer's document
  could vanish with nothing anywhere to investigate. Not root-caused; recommend adding a
  found-vs-returned mismatch counter to `fetch_unseen` so the next occurrence leaves a trail.

`17:54` **QA report corrected after root-cause analysis — F-1 is not a poller bug; F-6 is
precedence, not order.**

Re-analysed every finding above before planning fixes; two conclusions in the `14:56` entry were
wrong. The report is rewritten in place (with a correction note at its top); this entry records
what changed.

- **F-1 re-diagnosed.** The poller is ruled out: `mark_seen` only ever names UIDs the poll
  returned; no parse-failure warning was logged; `cron.job_run_details` shows no dispatch after the
  07:12 UTC pause; `job_runs` holds only this run's polls; Gmail's `FROM` search (the confirmation
  sweep's) is exact. So something outside the code marked those messages read — who is not known.
  The finding stays HIGH as a **design** issue: `SEARCH UNSEEN` makes `\Seen` the queue's only
  "decided" marker, so any other reader of the mailbox (support opening `AIAGENT@` included) makes
  mail vanish with no trace. Fix direction: a keyword only this system writes (`$OcrDone`).
- **F-4 added (LOW):** `fetch_confirmations` fetches `(RFC822)`, which marks mail read — contrary to
  its own docstring and to `sweep_confirmations`' reliance on foreign confirmations staying unread.
- **F-6 re-diagnosed.** The GL-suggestion-before-tax-check order is deliberate (so parked documents
  get suggestions). The bug is precedence: a 401/403 from the suggester parks the document as
  `carmen_unauthorized` and pre-empts its own `tax_id_mismatch`/"already posted" verdict.
- **F-5 origin found:** `doc_type` is a `RuleIn` field on the unmerged
  `feat/detailed-cc-ar-reconciliation` branch — on `main` this is version skew.
- The mailbox numbers quoted during the run (296–334) were IMAP sequence numbers, not UIDs
  (real UIDs 366–404). No conclusion changes.
