# 2026-08-31

## Failures now name their own cause (Carmen boundary + email ledger)

`09:20` Three email-ingest documents on **2026-08-28** were reported as
`carmen_rejected — "Carmen rejected the JV"`. Carmen had rejected nothing: it answered
**HTTP 401**, because that BU's stored posting token died between two polls (it posted
JV 1011 at 09:21 UTC and was refused at 09:35). Proving that needed a manual join of
`email_documents` against `outbound_call_logs` — the only place the status code survived.
Root cause: `carmen_service.post_gljv` returned `resp.json()` **without ever reading
`resp.status_code`**, so a 401's framework body (`{"Message": "Authorization has been
denied…"}`) reached the caller as an ordinary result with no `Code`. `post_input_tax` was
fixed for exactly this in July; its four siblings were not.

### Backend

- **`carmen_service` never discards an HTTP status again.** New `_json_or_raise()` /
  `_fail()`: any status ≥ 400 raises `CarmenAPIError`, and the message carries
  `HTTP <status>: <body>`. Applied to `post_gljv`, `put_gljv`, `post_input_tax`,
  `put_input_tax`, `post_invoice`, and to every GET helper's raise. `wrap_network_error`
  is deliberately untouched — a connection that never reached Carmen has no status, and
  its friendly wording is what the user should read.
- **New `reason_code: carmen_unauthorized`** (`email_ingest_service`) for a 401/403 from
  the posting call and for the two pre-post guards (no stored token, no known host).
  `carmen_rejected` now means only what its name says: Carmen read the JV and declined it.
  A dead credential and a bad JV are fixed by different people on different screens.
- **The first 401 flags the credential.** `es.mark_token_unverified()` clears
  `carmen_token_verified_at` — the same "unproven" signal `sweep_token_health` writes — so
  the settings screen stops claiming a credential verified days ago. Wrapped so it can
  never cost the ledger row it accompanies.
- **Ledger messages carry Carmen's verdict, not our summary of it.** `_carmen_verdict()`
  renders `Carmen returned Code 1: Insufficient balance`, or `…Code 1 with no message`,
  reading `UserMessage` → `InternalMessage` → `Message`. Same helper for the input-tax
  post. The generic `except Exception` handler (which files everything as
  `unreadable_document`) now records `TypeError: …` etc., so a bug in the pipeline stops
  reading as "your PDF is bad".
- **A rejected JV is re-submittable again.** `routers/carmen.py` stamped `submitted_at`
  on `Code >= 0`, so a rejection was recorded as submitted and the retry was answered
  "already submitted to Carmen" — the duplicate guard reporting a failure it caused
  itself, over Carmen's actual complaint. Now stamps only on `Code == 0`.

- `carmen_unauthorized` added to the `#/admin/email` reason filter, the notification

### Findings recorded, not changed

- **AP invoice reads Carmen's verdict differently.** `useAPSubmission.ts` treats only
  `Code < 0` as failure, where the credit-card wizard and the input-tax step use
  `Code !== 0` — so a `Code: 1` rejection would toast success there. Behaviour change on a
  working posting path; needs Carmen's `/invoice` contract confirmed first.
- **`outbound_call_logs` stores no response body** — only status, url, duration. It is
  what made today's diagnosis possible *and* incomplete. Not adding a column: the fixes
  above put the text where a human already looks.
- **A 401 still costs a credit** (the charge precedes the post, by design — decision #17).
  Flagging the credential shortens the window; halting a BU's run after an auth failure is
  a separate decision.
- **dev BU `dev.carmen4.com/carmencloud` has three ingest rules all using
  `filename_patterns: [".pdf"]`**, so no rule identifies a bank and `detect_bank_code`
  guessed `KBANK` for the PayPal and SiamPay invoices — those posted with KBANK's GL
  mapping. Config problem on that tenant, not a code defect.

## `11:00` Credit Card landing page — one activity table, two sources

Requirement + mockup from the customer: clicking the AI button should show notification
data first and the upload button second, in a table with `Source · Function · JV No. ·
Timestamp · Status · Message · Actions`, where the action button appears only on rows that
need one and the JV number opens the JV.

Half of it already shipped on 2026-08-28 — `#/CreditCardOCR` has been the review queue, not
the wizard, since then. What was missing was the **Source** column, which only means
anything if manual scans join the list, and the single mixed-status table (the page had four
tabs instead).

Scope confirmed with the requester before building: Credit Card only (`#/APInvoice` keeps
its wizard), sources Email + Manual, one table + filter chips, actions = Review + Fix
mapping.

**`Function` is deliberately not built.** At this scope it is 1:1 with `Source` on every row
("Email → Credit Card Commission Tax", "Manual → JV Creation"), so it carries no
information. Add it the day AP invoice or bank e-Tax joins the table.

### DB

- `20260831000000_credit_cards_jv_no.sql` — `credit_cards.jv_no varchar(50)`, nullable,
  no backfill. Carmen returns the JV number on a manual submit and we threw it away; the
  Manual rows cannot link into Carmen without it. Scans posted before this migration
  render `—`, which is honest — we genuinely do not know their JV number any more.
  **Not yet pushed.**

### Backend

- `routers/credit_card_activity.py` (new) — `GET /api/v1/credit-card/activity`, params
  `filter=all|review|success|failed|skipped`, `limit`, `offset`. Returns `ActivityPage`
  (`Page[ActivityRow]` + `counts`), newest first.
  - Its own router, not another route on `email_review.py`: that file's whole contract is
    email documents and a manual scan there would make its docstring a lie. Approve /
    reject / detail / status stay put.
  - ⚠️ **The anti-join is the correctness of the whole feature.** Email ingest calls the
    same `finalize_extraction` the wizard does, so every ingested document ALSO has a
    `credit_cards` row. Without
    `NOT EXISTS (email_documents.task_id = credit_cards.task_id)` one forwarded statement
    is listed twice — once as Email, once as Manual — and every count on the page is wrong.
  - Manual rows are `submitted_at IS NOT NULL` only, timestamped by `submitted_at`. An
    abandoned draft is not a notification; the user was sitting right there.
  - Merged in Python rather than a SQL UNION (`ponytail:` comment names the ceiling).
    `count_rows()` per statement, summed — never `len(data)`.
- `routers/email_review.py` — `_to_row` → public `to_review_row`, imported by the new
  router so the two screens cannot build the same document differently.
- `routers/carmen.py:proxy_gljv` — one line beside the existing `submitted_at` stamp:
  `card.jv_no = res["InternalMessage"]`, the same field `email_ingest_service` reads.
- `models/schemas/email_automation.py` — `ActivityRow(ReviewDocument)` (+ `source`) and
  `ActivityPage(Page[ActivityRow])` (+ `counts`). Subclasses, so the browser renders one
  row component for both sources.
- `tests/integration/test_credit_card_activity_api.py` (new, 6 tests). The first asserts
  the anti-join against the **compiled SQL** — a mock DB cannot execute it, and that
  predicate is exactly the thing a future refactor would drop without noticing.

### Frontend

- `pages/ReviewQueue.tsx` — `<ul>` of two-line cards → `<table>` with a real `<thead>`;
  four tabs → five filter chips (All / Needs review / Posted / Not posted / Skipped) each
  with its count; Manual scan → a primary **Upload documents** button. `useFitRows` now
  measures `tr` off `<tbody>`.
  - **No wrapper div around the table.** `useFitRows` finds the space below a list by
    walking the next siblings of the ref'd element *and* of its parent; with the ref on

    one level too deep and the measured page size comes out a row too tall.
  - The three empty states are unchanged in content but re-gated: **not set up** now needs
    `counts.all === 0` (a BU with manual scans has a history even with forwarding off), and
    **all caught up** only shows under All / Needs review.
- `components/credit-card/QueueRow.tsx` — rewritten as a `<tr>`. `reasonKey()` and
  `REASON_KEY` reused verbatim as the Message column. New: Source cell (Mail / Upload

### `13:40` A `pending_review` row to look at — `scripts/seed_review_demo.py`

The dev database has never held one. Both BUs run `auto_post = false`, but the deployed
backend predates the review fork so nothing has ever parked, and `IMAP_HOST` is empty
locally so the real pipeline cannot be run to make one. The Needs-review chip, the amber
pill and the Review button were therefore all unviewable against real data.

Seeds the three rows the screen and `approve_document` actually need —
`ocr_tasks → credit_cards (submitted_at NULL) → email_documents (pending_review)` — with
`review_payload.extracted.id` pointing at the `credit_cards` row, because that is what
`_mark_submitted` stamps on approve. `submitted_at` stays NULL, so the fixtures do **not**
leak into the activity table's Manual half.

Two documents, deliberately:

- **`DEMO-CLEAN-0001`** — reconciles, `flags: ["mapping_guessed"]`. ⚠️ Approve is live on
  this one and posts a real JV into that BU's Carmen.
- **`DEMO-BENT-0002`** — line 3's `total` is 251.85 short, `flags: ["unbalanced"]`. That is
  exactly the arithmetic `AccountingReview` refuses to submit, so Approve is disabled by the
  app's own rule and the whole modal is safe to click through.

`--clean` removes both, matched on the `demo-review_` filename prefix every row carries.
Raw asyncpg on the transaction pooler rather than the app's ORM — a one-off fixture should
not drag in config validation, the LLM client, or a slot from the 15-connection Supavisor
budget uvicorn is already using.
