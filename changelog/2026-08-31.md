## Failures now name their own cause (Carmen boundary + email ledger)

`09:20` Three email-ingest documents on **2026-08-28** were reported as
`carmen_rejected — "Carmen rejected the JV"`. Carmen had rejected nothing: it answered
**HTTP 401**, because that BU's stored posting token died between two polls (it posted
JV 1011 at 09:21 UTC and was refused at 09:35). Proving that needed a manual join of
`email_documents` against `outbound_call_logs` — the only place the status code survived.
Root cause: `carmen_service.post_gljv` returned `resp.json()` **without ever reading
`resp.status_code`**, so a 401's framework body (`{"Message": "Authorization has been
denied…"}`) reached the caller as an ordinary result with no `Code`. `post_input_tax` was
fixed for exactly this in July; its four siblings were not.

### Backend

- **`carmen_service` never discards an HTTP status again.** New `_json_or_raise()` /
  `_fail()`: any status ≥ 400 raises `CarmenAPIError`, and the message carries
  `HTTP <status>: <body>`. Applied to `post_gljv`, `put_gljv`, `post_input_tax`,
  `put_input_tax`, `post_invoice`, and to every GET helper's raise. `wrap_network_error`
  is deliberately untouched — a connection that never reached Carmen has no status, and
  its friendly wording is what the user should read.
- **New `reason_code: carmen_unauthorized`** (`email_ingest_service`) for a 401/403 from
  the posting call and for the two pre-post guards (no stored token, no known host).
  `carmen_rejected` now means only what its name says: Carmen read the JV and declined it.
  A dead credential and a bad JV are fixed by different people on different screens.
- **The first 401 flags the credential.** `es.mark_token_unverified()` clears
  `carmen_token_verified_at` — the same "unproven" signal `sweep_token_health` writes — so
  the settings screen stops claiming a credential verified days ago. Wrapped so it can
  never cost the ledger row it accompanies.
- **Ledger messages carry Carmen's verdict, not our summary of it.** `_carmen_verdict()`
  renders `Carmen returned Code 1: Insufficient balance`, or `…Code 1 with no message`,
  reading `UserMessage` → `InternalMessage` → `Message`. Same helper for the input-tax
  post. The generic `except Exception` handler (which files everything as
  `unreadable_document`) now records `TypeError: …` etc., so a bug in the pipeline stops
  reading as "your PDF is bad".
- **A rejected JV is re-submittable again.** `routers/carmen.py` stamped `submitted_at`
  on `Code >= 0`, so a rejection was recorded as submitted and the retry was answered
  "already submitted to Carmen" — the duplicate guard reporting a failure it caused
  itself, over Carmen's actual complaint. Now stamps only on `Code == 0`.

### DB

## `11:00` Credit Card landing page — one activity table, two sources

Requirement + mockup from the customer: clicking the AI button should show notification
data first and the upload button second, in a table with `Source · Function · JV No. ·
Timestamp · Status · Message · Actions`, where the action button appears only on rows that
need one and the JV number opens the JV.

Half of it already shipped on 2026-08-28 — `#/CreditCardOCR` has been the review queue, not
the wizard, since then. What was missing was the **Source** column, which only means
anything if manual scans join the list, and the single mixed-status table (the page had four
tabs instead).

Scope confirmed with the requester before building: Credit Card only (`#/APInvoice` keeps
its wizard), sources Email + Manual, one table + filter chips, actions = Review + Fix
mapping.

**`Function` is deliberately not built.** At this scope it is 1:1 with `Source` on every row
("Email → Credit Card Commission Tax", "Manual → JV Creation"), so it carries no
information. Add it the day AP invoice or bank e-Tax joins the table.

## `14:50` Review screen rebuilt — verify on the left, post on the right, map in place

Two complaints, both real: fixing a GL mapping meant leaving for `#/CreditCardOCR/mapping`
in a new tab and coming back to re-read the document, and the four stacked blocks in a
60rem modal never had the line items and the JV they produce on screen together, which is
the only comparison the reviewer is there to make.

Reading the pipeline changed the framing before any code was written. `_run_document` calls
`_suggest_missing_mappings` **before** parking and `fill_missing_mappings` saves the AI's
guesses to the BU config immediately; if it still could not map, the document became
`failed/mapping_incomplete` and never reached review at all. So a parked document has **no
blanks to fill** — every field is filled and every rule is already live. The reviewer is
checking a machine's decision, not finishing data entry, and four equal blocks that read
like four tasks were wrong about what the screen is for.

### The finding that shaped it

`buildJvRows` in consolidated mode (the default for every bank) emits one credit leg per
payment-type line and exactly three debit legs, so **a JV row is 1:1 with an accounting-config
key**:

| JV row | config key |
|---|---|
| credit "VISA" | `paymentAmount.VISA` |
| debit "Credit card commission" | `mappings.commission` |
| debit "Input Tax" | `mappings.tax` |
| debit "Bank Account" | `mappings.net` |

Two lines of one payment type produce two rows bound to **one** key. A picker therefore edits
a *rule*, not a row, and every row using it moves together. That killed the "remember for next
time?" checkbox the design started with: honouring "this JV only" needs a shadow config the
system has no concept of, posting a JV that disagrees with the stored rule with no trace. A
correction now always persists, says so before the button that does it, and offers Undo.

### DB / API

- ⚠️ **`PUT /config/accounting` could not be used and must not be.** `save_accounting_config`
  assigns `file_prefix`, `file_source`, `description` and `branch` unconditionally (omit one
  and it is wiped) and does `DELETE` + re-insert on every mapping entry.
  `fill_missing_mappings`'s own docstring already said why that is dangerous from a
  concurrent writer: *"using it here would delete their work between two clicks."* Two
  reviewers on one BU's queue is the expected case (07-human-in-the-loop #4).
- **`set_mappings()` + `PUT /api/v1/config/accounting/mappings`** (new) — upserts the named
  field types and touches nothing else. The third writer of that table and the only one that
  overwrites: `fill_missing_mappings` refuses to, by design, and a correction is an overwrite
  by definition. The dept/account pair is re-checked against Carmen's `DefaultAccount`
  server-side; a filtered dropdown is a convenience, not a control. Carmen being unreachable
  does not block the save — the JV posts through Carmen anyway, which is where a genuinely
  bad pair gets caught.

### Pipeline

- **`mapping_incomplete` now parks for review instead of failing**, unless `auto_post` is on
  (nobody is coming then). It was terminal because nothing could fix it in place; now
  something can. `_review_flags` gains `mapping_missing`, ranked above `mapping_guessed` — a
  guess posts and may post wrong, a gap cannot post at all.
- **`review_payload` gains `unmapped` and `guessed`** — which payment types need an account,
  and which rules the AI invented. Stored rather than re-derived: the review screen would
  have to diff the document against a config that keeps moving. `guessed` in particular is
  the difference between pointing at one rule and shrugging at all of them, which is what
  the bare `mapping_guessed` flag amounted to.

### Frontend

- **`ReviewDocument.tsx` rebuilt.** Modal `min(96rem, …)`, sticky identity + the four
  reconciliation totals + footer, and two panes that scroll independently: *What the document
  says* / *What will post*. The four block frames and their ✓/⚠/⛔ headers are deleted — a
  problem is now marked on the thing that has it (the offending line row, the amber Doc No,
  the TOTAL row). Input tax moved into the footer beside Approve, where its decision is made.
  Below 900px the panes stack, document first.
- **`JvEditor.tsx`** (new) — the right pane. Deliberately not a variant of `AccountingReview`,
  following the precedent `HeaderCard`/`ReviewDocCard` already set: data entry and
  verification are different jobs. The arithmetic is not duplicated (both call `buildJvRows`).
  Reuses `CustomSearchSelect`, `allowedAccountsForDept`/`isAccountAllowed`, and
  `suggestPaymentTypes`.
- **`JvRow.key`** (new field on the row builder) names the config entry that produced a row.
  Deriving it from row order would couple the screen to `buildJvRows`' internals; a row
  genuinely knows which rule made it. `buildGljvPayload` ignores it — the Carmen contract
  test is untouched and still passes.
- **AI fill is not fired on open.** Ingest already suggested for everything that arrived, so
  the only gap is one the reviewer creates by editing a Transaction cell. Fired once per
  unmapped type.
- **Approve order: rules first, JV second.** If Carmen then refuses, the corrected rule still
  stands — it was wrong before and is right now, independently of this document, and the
  reviewer is standing there to retry. The reverse can leave a rule silently unsaved behind a
  JV that already posted.
- **`useGlMasters`** (new) — module-cached accounts + departments. `useMappingData` refetches
  everything plus GL prefixes on every mount, which is right for a page opened on purpose and
  wrong for a modal opened once per document.
- **`AccountingReview`'s `embedded` mode and `AccountingState` are deleted** along with
  `.form-actions--embedded`. They existed only for the old review screen; a mode with no
  caller rots.

### Bugs found and fixed on the way

- **`CustomSearchSelect` ignored Escape.** Harmless on the mapping page, which has no dialog
  above it; inside this modal the key fell through and closed the whole thing, throwing away
  the reviewer's edits. It now closes its own list and stops there, and its portaled panel
  carries `.css-select-panel` so a dialog above can tell "a list is open" from "nothing is
  open" (containment cannot, since the panel is portaled to body).
- **The integration suite's rate-limit isolation had stopped isolating.** `_isolate_rate_limiter`
  built its IP counter *inside* the fixture, so every test restarted at `10.0.0.0` and
  collided with every other test's opening requests, while the middleware's `_windows` dict
  lives for the whole process. Past ~120 requests on a shared address the `default` bucket
  popped and a 429 landed on whichever test happened to be running — it was
  `test_feedback_api` here, purely because four tests were added to `test_config_api`. The
  counter is now module-level and two octets wide.

### The part that needed care

`details` is not display. `build_input_tax_payload` files the VAT record from it **line by
line**, so a figure that moved only on the journal would post a tax record disagreeing with
the journal it accompanies. Editing the JV therefore has to write back:

- `JvRow.lines` (new) records which detail rows a leg was summed from. A credit leg carries
  one index; a consolidated debit leg carries all of them. Deriving this from row order
  would couple the screen to `buildJvRows`' internals, the same reason `key` is on the row.
- `applyJvAmount()` (new, in `lib/ccJv.ts`) does the write-back. One line is exact. Several
  is a **judgement, not arithmetic**: the figure is shared out in proportion to what each
  line already carries, which is the relationship the bank charged by (commission and its
  VAT are per-transaction percentages), and the last line absorbs the rounding so the parts
  add to exactly what was typed — one satang out and the JV refuses to balance over an edit
  the reviewer made correctly. `ccJv.applyAmount.test.ts` pins all of it, including the
  round trip: type on the JV, land in the lines, rebuild, read the same number back.
- A leg summed from several lines is marked (dotted underline + a title saying so), because
  typing into it changes all of them.
- Amount cells are only editable on the side the leg actually carries. A JV row's other
  side is structurally empty, and an input there invites a one-sided journal.

Also: **two lines of one payment type produce two legs with the same description**, so the
line number is part of each amount's accessible name. Without it the second leg is
unreachable by anything that finds a control by its label, screen readers included — found
by a test that could not tell the two apart.

**Capability deliberately dropped:** there is no longer a way to add or delete a whole
detail line here. Correcting figures is now the JV's job and it covers every real
correction; a document *missing an entire transaction* was never fixable by typing anyway
and is a reject-and-rescan. Say so rather than quietly leaving people to find out.

`DetailTable` itself is untouched — the wizard's Step 2 still uses it exactly as before.

### `16:20` Same screen again — one column, and one statement of each number

Two panes were the wrong shape. The comparison they were built for reads top to bottom, not
left to right: here is the document, here is the entry it produces. Splitting it made the
eye cross the screen, and 96rem of modal to hold both was a wall on a laptop.

**Cut, because it said nothing new:**

- **The four-number summary strip.** Gross was the journal's own credit total, and
  Commission / VAT / Net were three of its debit rows. Four numbers, every one of them
  already on screen one block below. `review.sumGross` and its three siblings are deleted.
- **`.rd-panes` / `.rd-pane` / `.rd-pane--jv`** and the second neutral surface that told
  the two columns apart. One column needs no such signal.

**Reshaped:**

- Modal `min(96rem, …)` → `min(64rem, …)`. One column needs what the JV's five columns ask
  for and nothing beyond it.
- Document fields go `repeat(auto-fit, minmax(11rem, 1fr))` — they are short and
  independent, so they reflow to the modal rather than sitting in a grid built for one
  width. Four or five to a row at full size, two on a phone.
- Spacing carries the grouping now that no border does: `--space-5` between the document
  and the journal, `--space-3` within each. Tight inside, generous between.
- Type scale tightened to five deliberate steps: 0.66rem labels, 0.83rem table cells,
  0.875rem document values, 0.9rem the totals row, 1.05rem the identity in the header.
  The totals row is the only thing that steps up, because it is the line the decision turns
  on and the only place the JV says whether it balances.
- Amount inputs and document fields now share one rule — flat, then a box on hover and
  focus — so the whole screen behaves one way rather than two.
- Dept and account columns get fixed widths (8.5rem / 11rem) so codes line up down the
  page; description takes the slack; on a phone description is the column that goes, since
  it is derived text and the pickers are not.
