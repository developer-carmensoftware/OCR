## Four scroll locks, one page: closing a dialog could leave the page frozen

`10:10` A page that could not be scrolled until a hard refresh. Four components each
locked background scroll the same hand-rolled way — save `document.body.style.overflow`,
set `hidden`, put the saved value back on cleanup (`CustomModal`, `ReviewDocument`,
`OrderDrawer`, `TutorialModal`). That pattern does not compose: whenever two of them
overlapped, the second one saved `'hidden'`, and if it released *after* the first, it put
`'hidden'` back on a page with no dialog left on it. Nothing on screen explained it, and
nothing but a reload cleared it.

Reproduced in a test against the old code, two shapes:

- **A page lock plus a dialog inside it, torn down together** — `ReviewDocument` holds a
  lock for its whole life and its Reject / Discard confirmations are second locks;
  confirming either unmounts the dialog *while the confirmation is still shown*.
- **Two overlapping siblings released out of LIFO order** — e.g. a `type: 'loading'`
  overlay and an error dialog from different `CustomModal` instances on one page.

A third shape, a plain nested `unmount()`, does **not** leak on React 19 — it tears the
subtree down child-first. Only the two above do, which is why this looked intermittent.

### Frontend

- `hooks/useScrollLock.ts` (new) — one counted lock. First caller in remembers the page's
  own overflow, last one out restores it; arrival and release order stop mattering. Global
  counter, because the thing being locked is global. Exports `__resetScrollLock` for tests.
- `CustomModal`, `ReviewDocument`, `OrderDrawer`, `TutorialModal` — all four call
  `useScrollLock(open)` instead of touching `document.body` themselves. `CustomModal` and
  `ReviewDocument` keep their focus-restore effects, which were tangled into the same
  block; `OrderDrawer` and `TutorialModal` keep their keydown effects. Net: four copies of
  the bug replaced by one hook.
- `hooks/useScrollLock.test.tsx` — both leaking shapes above, plus lock/restore and the
  inactive case. The two shape tests fail against the old per-component pattern.

**Not done:** no release note yet — batched into the next release (`release_note_batching`),
and `VERSION` does not move. Worth one bullet when it goes out: it is user-visible.

## "Every bank's documents come out labelled KBANK" — a filename rule was allowed to name the issuer

`10:30` Reported: with one ingest rule per bank configured, documents from *several* banks
all arrive in the queue as **one** bank. Not cosmetic — `bank_code` picks the extraction
layout, the JV source (`KBANK → ACKB`), the per-bank GL description, and the **vendor
identity on the input-tax record** (`banks.legal_name` / `.tax_id` / `.address`). A wrong
bank posts a correct-looking JV against the wrong vendor.

**Root cause: a filename substring outranked the printed issuer.** `_run_document` took
the bank off the matched rule (`matched[0]["bank_code"] if len(matched) == 1`) and only
consulted the document when the rule named none (`bank_code or detect_bank_code(...)`).
`filename_patterns` is a plain case-insensitive substring test and `.pdf` is a *documented*
escape hatch — so **one** rule carrying a broad pattern becomes the sole match for every
file the other rules' narrower patterns miss, and labels all of them itself. It also fed
`extract_stateless(bank_code=…)`: a GHL invoice read with the KBANK layout mismaps its
columns *and* is told to emit `bank_name: "ธนาคารกสิกรไทย"`, which then confirms KBANK to
every later reader, the browser included. That is the reported shape, end to end.

This is the third visit. `2026-08-28` closed as "configuration" (a one-character typo in
`owner_emails`), `2026-08-31` closed as "config problem on that tenant, not a code defect"
(three rules all `.pdf`). Both were true; neither was the whole story. **The configuration
could not be got wrong safely, which is the part that was ours.**

Two things found on the way:

- **`detect_bank_code`'s `raw_text` tier has never been able to fire.** No prompt in
  `llm/prompts/` has ever asked the model to return `raw_text`, so `llm_service` popped `""`
  every time. The 2026-08-31 note blaming "กสิกร appearing in raw_text" cannot be what
  happened. Deleted, in both the backend helper and its frontend mirror.
- **The combined prompt performs "Step 1 — Identify the bank" and then never asks for the
  answer**, leaving detection to keyword-match `bank_company_name` / `bank_name` — the
  fields a wrong layout dictates.

### Backend

- `email_ingest_service._run_document` — the rule's bank becomes `rule_bank`: a fallback,
  not a verdict. Extraction is always called with **no** bank (the combined auto-detect
  prompt), and `_resolve_bank()` decides once, before `finalize_extraction`, so
  `credit_cards.bank_code` and `email_documents.bank_code` are one decision instead of two
  independent ones. `rule_bank` still seeds `bank_code` up front, so a row that fails
  *before* extraction still names an issuer for the "several BUs failing on the same bank"
  signal.
- **A disagreement is now visible.** When the rule and the document name different banks,
  `_resolve_bank` appends a user-facing warning naming both — it rides the existing
  `warnings` flag onto the queue row and renders as the amber banner in the review modal.
  This is the only place a mis-scoped pattern shows up before it has posted a JV.
- `llm/prompts/shared.py` — `OUTPUT_RULES` gains **`bank_code`**: which BANK REFERENCE
  entry issued this document, "the ISSUER, never the merchant's own bank account printed on
  it". Shared by both builders on purpose. `_PROMPT_VERSIONS` all bumped: the output
  contract changed for every prompt, not one layout.
- `schemas/ocr.py` — `ExtractedCreditCardData.bank_code`, with a validator that keeps it
  only if it is one of ours (LLM output is untrusted: `"KASIKORN"`, `""`, `"xx"` → `None`).
- `utils/bank_detect.py` — exports `BANK_CODES`; `model_bank_code` is tier 0, ahead of every
  keyword tier. The reader looking at the page beats keyword-matching the two or three
  header fields it chose to fill in. `raw_text` tier and parameter deleted.

### Frontend

- `constants/banks.ts` — same two edits, so its "mirrors backend `bank_detect.py`" claim
  stays true: `ext.bank_code` first, `raw_text` tier gone.
- `pages/ReviewDocument.tsx` — `bankCode` is now `doc?.bank_code || bank`, not the reverse.
  The ledger row is the document's own answer; re-detecting in the browser put a weaker

## Tooling — the knowledge graph had been unbuildable since a graphify upgrade

`11:05` Running `graphify update .` wrote a **0-node** graph over `graph.json`,
`graph.html` and `manifest.json`. First reading was "relative path, wrong scan root". That
was wrong, and worth recording because the real cause was sitting in a tracked file.

**`.graphifyignore` was a whitelist** — `node_modules/`, `dist/`, `*.generated.py`, then:

```
# only index src/, ignore everything else
*
!src/
!src/**
```

Current graphify applies the `*` catch-all first and prunes the tree before the negations
can rescue anything, **from every scan root** — `detect()` returned 0 files for the repo
root, for `backend/app`, and even for `frontend` where `src/` *is* top-level. So the corpus
had been empty for some time; `graphify update` simply had no shrink-guard to stop it
writing the emptiness out, where the full build path does (#479). The file dates to
2026-05-15 and the graph was last built 2026-08-24, so the semantics changed under it.

- **`.graphifyignore` is exclusions only now**, naming the directories to skip
  (`backend/`, `docs/`, `supabase/`, …) instead of a `*` + negation whitelist a future
  version can reinterpret. Same intent, same scope, nothing left to misread.
- **The scan root stays the repo root.** Pointing `.graphify_root` at `frontend/src`
  instead — the corpus the graph actually covers — looked tidier and was wrong: graphify
  writes its outputs beside the scan root, so bare `graphify update` produced a **second**
  `graphify-out/` inside `frontend/src/` and left the tracked one stale. Scan root and
  output directory are the same decision.
- **`CLAUDE.md` no longer says `graphify update .`** — that literal command is what wiped
  it. Bare `graphify update` reads `.graphify_root`. It also now states that the graph is
  frontend-only and what adding the backend would cost.
- `.graphify_python` (a machine-specific interpreter path), the label sidecar and its
  signature, and any stray `frontend/src/graphify-out/` are gitignored — all regenerated
  by every build.

**Rebuilt:** 296 files → **1,748 nodes · 4,921 edges · 112 communities**, 99% EXTRACTED,
**0 tokens** — AST only. `source_file` is now repo-relative (`frontend/src/lib/...`), which
matches how everything else in this repo cites a file. Communities are auto-named after
their most central node (`apiFetch`, `LanguageContext.tsx`, …); hand-written names were
tried first and are **not worth writing** — `graphify update` regenerates them from
scratch on every run, so they last exactly until the next code change.

The 13 uncached "images" are bank logos and Carmen brand marks; vision extraction on those
costs money and yields nothing a graph can use, so they are skipped, as the 2026-08-24
build's `0 input · 0 output` shows it also did. Add them the day a real architecture
diagram lands in `assets/`.

Health check is honest about two things, both expected for a frontend-only scan: **438
dangling-endpoint edges** (imports of `react`, `lucide-react` and friends — the other end
is outside the corpus) and **163 collapsed same-endpoint edges** (a file importing another
on three lines is one edge in an undirected graph). No import cycles.

**Still frontend-only.** Deleting the `backend/` line from `.graphifyignore` adds it, but
also ~87 documents whose semantic extraction costs real LLM tokens — a different graph and
a spending decision, not a repair. Worth noting that today's bug lived entirely in
`backend/`, where the graph could not have helped.
