# 2026-09-03

## The review queue's first page fits the first screen

`09:15` The queue is the Credit Card module's landing page, so its first page is the first
thing a reviewer sees — and at the app-wide 15 rows it ran past the fold, making "scroll"
the first gesture of every visit. It now seeds **10**.

### Frontend

- `hooks/useRowsPerPage.ts` — `readRowsPerPage`/`useRowsPerPage` take an optional
  `fallback`, so one list can start smaller than the app-wide default without owning its
  own state or its own storage key. `DEFAULT` is now the literal `15` rather than
  `ROWS_PER_PAGE[0]`, which keeps every other table exactly where it was.
- `ROWS_PER_PAGE` gains `10` as its smallest option. Not cosmetic: `Pager` hides itself at
  `total <= ROWS_PER_PAGE[0]`, so without it a queue holding 11–14 rows would show 10 and
  hide the arrows that reach the rest. It also makes 10 a choice `readRowsPerPage` will
  accept back out of `localStorage` instead of falling through as an unknown value.
- `pages/ReviewQueue.tsx` — `useRowsPerPage(10)`. The preference stays shared and stored:
  a reader who has ever picked a size still gets that size here, the fallback only decides
  the first visit.
- `Pager.test.tsx` — the "hides below the smallest size" case moved from `total={12}` to
  `total={8}`; 12 is now above the smallest option, so the bar correctly appears.

**Not done:** no release note — a page-size default is batched into the next release's
notes (see `release_note_batching`), and `VERSION` does not move for it.

## The rows-per-page control stops looking like it came from another app

`09:25` `Pager`'s `<select>` was the only OS-drawn control on the bar: ~26px tall beside
28px arrow buttons, border-only hover where the buttons also change background, no
transition where the buttons ease, and a native triangle 8px from two lucide chevrons
stroked at 2px. Three of those are invisible on their own; together they read as foreign.

### Frontend

- `styles/components/pager.css` — `.pager__select` now wears `.pager__btn`'s box: `height:
  28px`, the same border, radius, hover (`--muted` background + `--fg` border) and 120ms
  `--ease-out-premium`.
- `-webkit-appearance/appearance: none` + a real `<ChevronDown size={13} strokeWidth={2}>`
  from lucide, absolutely positioned over the select's right padding and `pointer-events:
  none` so the click still opens the list. Reusing the icon the arrows already import beats
  a data-URI arrow: same family, same weight, and it follows `currentColor` into dark mode.
  Dropping the native chrome is safe — the popup the browser opens is themed by
  `color-scheme: dark` on `select` (`base.css`), not by `appearance`.
- `.pager__size` gains `position: relative` to anchor the caret. The mobile `min-height:
  44px` (admin.css) still wins over the 28px, and the caret stays centred with it.

Everywhere else in the app a native select keeps its native arrow (`.admin-select`,
`.tbl-select`) — those sit alone in a row of filters with nothing to clash against. This
one has two chevrons for neighbours, which is the whole reason it needed its own.

`09:30` **Correction to the above, from the reviewer:** the complaint was the *option list*,
not the closed box — and it was right. A native `<select>` does not draw its list in the
page. The browser draws it, as an OS popup, and CSS reaches almost none of it: no radius,
no shadow, no padding, no hover colour, no font. `color-scheme: dark` (base.css) flips it
to the OS's dark palette and `option { color }` lands on some browsers, but that is the
whole of it. Every rule in `pager.css` stopped at the closed control, which is exactly what
it looked like.

- `components/common/Pager.tsx` — the `<select>` is now `InlineSelect`, the app's own
  listbox (portal panel, `--popover`, `--shadow-lg`, `--radius-md`, the open/close
  animation, a `Check` on the current value, arrow keys and Escape). Reused, not written:
  it has been in `components/common/` serving the AP and credit-card tables all along.
- `styles/components/pager.css` — `.pager__select`/`.pager__caret` are gone with the native
  control. `.pager__size-select .isel-trigger` dresses the trigger as `.pager__btn`
  instead, since InlineSelect's own trigger is a borderless ghost meant for a table cell.
- `styles/pages/admin.css` — the mobile 44px tap-target rule follows the class rename.
- `Pager.test.tsx` / `DataTable.test.tsx` — the control is a listbox trigger, not a
  `combobox`: `fireEvent.change` becomes open-then-pick. Option queries need
  `{ hidden: true }`, because the panel is a `<datalist>` that the UA stylesheet hides and
  `inline-select.css` un-hides — jsdom loads no CSS, so it stays hidden to role queries.

**Watch:** InlineSelect renders its own panel on touch too, so the OS picker sheet a native
select would have opened on a phone is gone. Options are 32px against the 44px the mobile
rule asks of controls — if that bites, it is `.isel-option`'s `min-height`, and it is a
change to every InlineSelect in the app, not to this one.

## Four scroll locks, one page: closing a dialog could leave the page frozen

`10:10` A page that could not be scrolled until a hard refresh. Four components each
locked background scroll the same hand-rolled way — save `document.body.style.overflow`,
set `hidden`, put the saved value back on cleanup (`CustomModal`, `ReviewDocument`,
`OrderDrawer`, `TutorialModal`). That pattern does not compose: whenever two of them
overlapped, the second one saved `'hidden'`, and if it released *after* the first, it put
`'hidden'` back on a page with no dialog left on it. Nothing on screen explained it, and
nothing but a reload cleared it.

Reproduced in a test against the old code, two shapes:

- **A page lock plus a dialog inside it, torn down together** — `ReviewDocument` holds a
  lock for its whole life and its Reject / Discard confirmations are second locks;
  confirming either unmounts the dialog *while the confirmation is still shown*.
- **Two overlapping siblings released out of LIFO order** — e.g. a `type: 'loading'`
  overlay and an error dialog from different `CustomModal` instances on one page.

A third shape, a plain nested `unmount()`, does **not** leak on React 19 — it tears the
subtree down child-first. Only the two above do, which is why this looked intermittent.

### Frontend

- `hooks/useScrollLock.ts` (new) — one counted lock. First caller in remembers the page's
  own overflow, last one out restores it; arrival and release order stop mattering. Global
  counter, because the thing being locked is global. Exports `__resetScrollLock` for tests.
- `CustomModal`, `ReviewDocument`, `OrderDrawer`, `TutorialModal` — all four call
  `useScrollLock(open)` instead of touching `document.body` themselves. `CustomModal` and
  `ReviewDocument` keep their focus-restore effects, which were tangled into the same
  block; `OrderDrawer` and `TutorialModal` keep their keydown effects. Net: four copies of
  the bug replaced by one hook.
- `hooks/useScrollLock.test.tsx` — both leaking shapes above, plus lock/restore and the
  inactive case. The two shape tests fail against the old per-component pattern.

**Not done:** no release note yet — batched into the next release (`release_note_batching`),
and `VERSION` does not move. Worth one bullet when it goes out: it is user-visible.
