## The chip is grouped by name, not by a second CASE

`17:05` `GET /activity` 500ed on every filter once the schema landed:

```text
GroupingError: column "email_documents.dismissed_at" must appear in the
GROUP BY clause or be used in an aggregate function
```

`_chip_expr()` was called twice — once in the SELECT, once in the GROUP BY — and SQLAlchemy
renders the second call with a **fresh set of bind parameters** (`$10..$15` where the SELECT
used `$1..$6`). Postgres compares those two CASEs textually, cannot see them as one
expression, and so treats `dismissed_at` inside the SELECT''s CASE as an ungrouped column.

### Backend

- `routers/credit_card_activity.py` — `group_by(literal_column("chip"), …)`. The CASE is
  rendered once and the GROUP BY refers to its output name; Postgres resolves a bare name
  there against the output columns when no input column shares it, and `email_documents` has
  no `chip`.

### Why nothing caught it

Both guards were blind to it in the same way, and that is the part worth keeping:

- **Every compiled-SQL assertion here used `literal_binds`.** With values inlined the two
  renderings come out identical and the statement is *valid* — the bug only exists once real
  bind parameters are used, which is only in production.
- **The mock DB never executes SQL**, so the twenty-odd handler tests around it exercised
  the Python and none of the Postgres.

New `test_the_chip_is_grouped_by_name_not_by_a_second_case` compiles with **real binds** and
asserts the CASE appears exactly once plus `group by chip`. Verified against the dev
database afterwards: all five filters answer — `today` 0, `review` 1, `success` 27,
`unposted` 24, `all` 52.

## The Review chip holds everything that wants a human

`14:05` `Needs review` was one status. `Not posted` was everything else — including the
seven causes somebody in the BU can clear in a minute from the settings screen, filed under
the chip [`07-human-in-the-loop.md`](../docs/email-automation/07-human-in-the-loop.md) §12
itself calls the one nobody works. That is the 2026-08-28 `sender_not_allowed` incident in
one sentence: the fix was one field away and the strip pointed nowhere near it.

§12 considered exactly this re-key — *"Needs review / Needs a fix / Posted / Nothing to do"* —
and declined it: *"it costs a vocabulary the API does not speak."* The API speaks it now.

### Backend

- `routers/credit_card_activity.py` — `FILTERS` (a map of statuses) is gone. `_chip_expr()`
  is a SQL `CASE` and **the only definition of chip membership there is**: the list filters
  on it, the counts group by it, so a row cannot be counted under one chip and listed under
  another. The alternative was this rule written twice — a WHERE clause and a Python fold —
  and the two drifting.
  - `review` = parked documents **plus** undismissed `FIXABLE_REASONS`.
  - `success` = `posted`. `unposted` = what is left.
  - Exactly one chip per row, which is what keeps `counts["all"]` a true total.
- **`coalesce(reason_code, "")` is load-bearing.** `NULL IN (...)` is NULL, not false, so
  without it the negated predicate `unposted` rests on evaluates to NULL for every row with
  no reason code — silently dropping every `received` row out of the strip while still
  counting it in `all`. Guarded by a compiled-SQL test, since the mock DB runs no SQL.
- `_attention` re-drawn. It already meant "something is off", not "you can fix it"; it now
  also means **not** "there is work here", because `review` holds work by definition and a
  dot drawn from its size would be lit whenever the feature was doing its job.
  - `pending_review`: only those carrying a `reason_code`. A statement waiting for an OK is
    the feature working; one that stopped on a Carmen refusal is not.
  - `rejected`: no longer counts. A reviewer''s own decision is not an anomaly, and a signal
    you set off by doing your job is one you learn to ignore.
  - `skipped`: fixable **and undismissed**. "Seen" was never "fixed" — but "put away" is
    answered.
  - `failed` still counts all: since a charged refusal parks, what is left there is a crash
    or an unhandled bug, which is what the dot is for.
- `ponytail:` a `CASE` in a WHERE clause cannot use an index. Correct at 342 rows
  (`docs/SQL_PERFORMANCE_AUDIT.md`); the comment names the upgrade path.

### Frontend

- `lib/api/emailReview.ts` + `endpoints.ts` — `dismissRow(id)`.
- `hooks/credit-card/useReviewQueue.ts` — `dismiss` is **optimistic**: the row leaves the
  list and the two counts move by hand. A spinner and a refetch per row would make clearing
  a morning''s noise feel like work. A failure puts it back and says so.
- `components/credit-card/QueueRow.tsx` — an ✕ beside the fix link, not a second full
  button: putting a row away is the lesser of the two things to do with it, and two equal
  buttons in that column read as a choice rather than as an action and an escape.
- **Only on the Review chip.** Elsewhere the row is not in anybody''s way, and "stop showing
  me this" on a history view is an invitation to hide history. Never on a parked document —
  Reject is the verb for those, and it records who and why.
- `.rq-c-act` grows 8.5rem → 10.5rem for the pair.

## A document we charged for stays reviewable

`13:40` The pipeline charges a credit the moment the vision call returns, then threw the
reading away. A document that was read successfully and then hit a **decision** gate — a
foreign tax ID, a payment type nothing maps, a Carmen refusal — became a dead red row, and
the only recovery was to re-scan the same file by hand and pay for it twice.

The rule was already written down, in the refund boundary''s own comment: *"a duplicate, a
foreign tax ID, an unmappable GL account and a Carmen refusal are all decisions taken about
a document we successfully read, not failures to read it."* The queue did not honour it.
`mapping_incomplete` stopped being terminal on 2026-08-31 for exactly this reason (§10 #30);
this is that change applied to every sibling.

**The criterion, in one line: charged and read means reviewable.**

### Backend

- `services/email_ingest_service.py` — new `_park_or_finish` closure inside `_run_document`.
  `charged is not None and extracted is not None` sends a refusal to the review queue with
  its reason recorded; anything else finishes on the ledger as before. The `_Skip` and
  `CarmenAPIError` handlers both route through it.
- Now parks instead of failing: `tax_id_mismatch`, `duplicate_document`,
  `mapping_incomplete`, `unreadable_document` (no postable amounts), `carmen_unauthorized`,
  `carmen_rejected`. All six were charged and none of them was a failure to read.
- `_park_for_review` takes `reason_code` / `error` and writes them to columns that already
  existed. **No migration.**
- **`_Skip` gains `reviewable`,** false in exactly one place: a second copy of something
  already in the queue. Its twin is already there and postable, and parking this one would
  put two identical rows in front of the reviewer — which is what the check prevents.
- **The generic `except Exception` still fails, deliberately.** It can fire *after*
  `post_gljv` returned zero (`_mark_submitted` and `_post_input_tax` both run past that
  point), and offering an Approve button on a JV already in Carmen''s books invites a double
  post. The refund boundary now also drops `extracted` before re-raising, so "the money went
  back, so there is nothing to park" is true by construction rather than by tracing which
  handler the re-raise reaches.
- **A Carmen transport failure parks with the caveat attached** — *check whether the JV
  posted before approving this document* — the same sentence `approve_document`''s 503
  returns. `_mark_submitted` never ran, so `has_submitted_doc` cannot catch a JV that landed
  as the socket died; that is the risk the approve path already takes, and the row now
  carries the warning to the person taking it.
- **The bell is batched, not per document.** `_park_for_review` notifies nothing;
  `_notify_pending` raises one extra `document_blocked` row per BU per poll when the queue
  holds anything with a `reason_code`. A dead credential fails *every* document of the BU,
  which is precisely the twenty-row burial that function''s batching rule exists to prevent.
  `document_failed` is gone from this path — the document is waiting, not finished.
- `_pending_count` gains `blocked_only` rather than growing a near-identical sibling: both
  numbers are the same question about the same rows.

### Consequences worth stating

- **Parked failures count toward `REVIEW_BACKLOG_CAP` (50).** A BU whose Carmen token dies
  now fills its queue and then has mail handed back unread. That is the cap working — and
  those 50 all become postable the moment the token is replaced, so working them off
  produces 50 JVs rather than being cleanup.
- **`auto_post = true` no longer means "post or destroy".** A BU with review switched off
  can now accumulate a queue. That is the point: the alternative was burning the credit.
- A `_FakeDB` without `scalar` was silently exercising `_already_pending`''s fail-open catch
  in every review-mode test. Adding one exposed it — the fake now documents why its default
  must be `None` and not `0`.

**Not done:** no retry sweep, unchanged from `01-requirements.md`''s non-goals. Approve stays
user-triggered; a parked failure waits for a person, it does not queue for a robot.

## Four scroll locks, one page: closing a dialog could leave the page frozen

`10:10` A page that could not be scrolled until a hard refresh. Four components each
locked background scroll the same hand-rolled way — save `document.body.style.overflow`,
set `hidden`, put the saved value back on cleanup (`CustomModal`, `ReviewDocument`,
`OrderDrawer`, `TutorialModal`). That pattern does not compose: whenever two of them
overlapped, the second one saved `'hidden'`, and if it released *after* the first, it put
`'hidden'` back on a page with no dialog left on it. Nothing on screen explained it, and
nothing but a reload cleared it.

Reproduced in a test against the old code, two shapes:

- **A page lock plus a dialog inside it, torn down together** — `ReviewDocument` holds a
  lock for its whole life and its Reject / Discard confirmations are second locks;
  confirming either unmounts the dialog *while the confirmation is still shown*.
- **Two overlapping siblings released out of LIFO order** — e.g. a `type: 'loading'`
  overlay and an error dialog from different `CustomModal` instances on one page.

A third shape, a plain nested `unmount()`, does **not** leak on React 19 — it tears the
subtree down child-first. Only the two above do, which is why this looked intermittent.

### Frontend

- `hooks/useScrollLock.ts` (new) — one counted lock. First caller in remembers the page's
  own overflow, last one out restores it; arrival and release order stop mattering. Global
  counter, because the thing being locked is global. Exports `__resetScrollLock` for tests.
- `CustomModal`, `ReviewDocument`, `OrderDrawer`, `TutorialModal` — all four call
  `useScrollLock(open)` instead of touching `document.body` themselves. `CustomModal` and
  `ReviewDocument` keep their focus-restore effects, which were tangled into the same
  block; `OrderDrawer` and `TutorialModal` keep their keydown effects. Net: four copies of
  the bug replaced by one hook.
- `hooks/useScrollLock.test.tsx` — both leaking shapes above, plus lock/restore and the
  inactive case. The two shape tests fail against the old per-component pattern.

**Not done:** no release note yet — batched into the next release (`release_note_batching`),
and `VERSION` does not move. Worth one bullet when it goes out: it is user-visible.

## "Every bank's documents come out labelled KBANK" — a filename rule was allowed to name the issuer

`10:30` Reported: with one ingest rule per bank configured, documents from *several* banks
all arrive in the queue as **one** bank. Not cosmetic — `bank_code` picks the extraction
layout, the JV source (`KBANK → ACKB`), the per-bank GL description, and the **vendor
identity on the input-tax record** (`banks.legal_name` / `.tax_id` / `.address`). A wrong
bank posts a correct-looking JV against the wrong vendor.

**Root cause: a filename substring outranked the printed issuer.** `_run_document` took
the bank off the matched rule (`matched[0]["bank_code"] if len(matched) == 1`) and only
consulted the document when the rule named none (`bank_code or detect_bank_code(...)`).
`filename_patterns` is a plain case-insensitive substring test and `.pdf` is a *documented*
escape hatch — so **one** rule carrying a broad pattern becomes the sole match for every
file the other rules' narrower patterns miss, and labels all of them itself. It also fed
`extract_stateless(bank_code=…)`: a GHL invoice read with the KBANK layout mismaps its
columns *and* is told to emit `bank_name: "ธนาคารกสิกรไทย"`, which then confirms KBANK to
every later reader, the browser included. That is the reported shape, end to end.

This is the third visit. `2026-08-28` closed as "configuration" (a one-character typo in
`owner_emails`), `2026-08-31` closed as "config problem on that tenant, not a code defect"
(three rules all `.pdf`). Both were true; neither was the whole story. **The configuration
could not be got wrong safely, which is the part that was ours.**

Two things found on the way:

- **`detect_bank_code`'s `raw_text` tier has never been able to fire.** No prompt in
  `llm/prompts/` has ever asked the model to return `raw_text`, so `llm_service` popped `""`

## Tooling — the knowledge graph had been unbuildable since a graphify upgrade

`11:05` Running `graphify update .` wrote a **0-node** graph over `graph.json`,
`graph.html` and `manifest.json`. First reading was "relative path, wrong scan root". That
was wrong, and worth recording because the real cause was sitting in a tracked file.

**`.graphifyignore` was a whitelist** — `node_modules/`, `dist/`, `*.generated.py`, then:

```
# only index src/, ignore everything else
*
!src/
!src/**
```

Current graphify applies the `*` catch-all first and prunes the tree before the negations
can rescue anything, **from every scan root** — `detect()` returned 0 files for the repo
root, for `backend/app`, and even for `frontend` where `src/` *is* top-level. So the corpus
had been empty for some time; `graphify update` simply had no shrink-guard to stop it
writing the emptiness out, where the full build path does (#479). The file dates to
2026-05-15 and the graph was last built 2026-08-24, so the semantics changed under it.

- **`.graphifyignore` is exclusions only now**, naming the directories to skip
  (`backend/`, `docs/`, `supabase/`, …) instead of a `*` + negation whitelist a future
  version can reinterpret. Same intent, same scope, nothing left to misread.
- **The scan root stays the repo root.** Pointing `.graphify_root` at `frontend/src`
  instead — the corpus the graph actually covers — looked tidier and was wrong: graphify
  writes its outputs beside the scan root, so bare `graphify update` produced a **second**
  `graphify-out/` inside `frontend/src/` and left the tracked one stale. Scan root and
  output directory are the same decision.
- **`CLAUDE.md` no longer says `graphify update .`** — that literal command is what wiped
  it. Bare `graphify update` reads `.graphify_root`. It also now states that the graph is
  frontend-only and what adding the backend would cost.
- `.graphify_python` (a machine-specific interpreter path), the label sidecar and its
  signature, and any stray `frontend/src/graphify-out/` are gitignored — all regenerated
  by every build.

**Rebuilt:** 296 files → **1,748 nodes · 4,921 edges · 112 communities**, 99% EXTRACTED,
**0 tokens** — AST only. `source_file` is now repo-relative (`frontend/src/lib/...`), which
matches how everything else in this repo cites a file. Communities are auto-named after
their most central node (`apiFetch`, `LanguageContext.tsx`, …); hand-written names were
tried first and are **not worth writing** — `graphify update` regenerates them from
scratch on every run, so they last exactly until the next code change.

The 13 uncached "images" are bank logos and Carmen brand marks; vision extraction on those
costs money and yields nothing a graph can use, so they are skipped, as the 2026-08-24
build's `0 input · 0 output` shows it also did. Add them the day a real architecture
diagram lands in `assets/`.

dangling-endpoint edges** (imports of `react`, `lucide-react` and friends — the other end
is outside the corpus) and **163 collapsed same-endpoint edges** (a file importing another
on three lines is one edge in an undirected graph). No import cycles.
