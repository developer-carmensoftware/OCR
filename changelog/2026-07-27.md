## Session resilience — mid-wizard logout no longer eats the user's work

### `10:40` The fix is survival, not prevention

Pilot feedback: users are dropped to the login screen mid-wizard ("หลุด"). Diagnosed
2026-07-23 — two independent 30-minute clocks, neither refreshing, split ~50/50 as the
killer (`performance_logs` 401 rows with an empty `tenant_id` = our JWT expired; rows that
keep `tenant_id` = Carmen killed it). The feedback week 07-15..22 was B-dominant 29:10.

**Carmen exposes no token refresh and no remaining-lifetime**, so the useful life of a
session is capped at Carmen's 30 minutes no matter what we build on our side. A sliding
OCR JWT would only buy time in which the user can edit but cannot post. So this ships the
other half: when the drop happens, the work survives it.

### `10:40` Frontend

- **`lib/draft.ts`** (new) — `saveDraft` / `loadDraft` / `clearDraft` / `clearAllDrafts` +
  `draftPromptMessage`. localStorage, namespaced through the existing `appKey()`, 6h TTL,
  `{ at, data }` envelope; corrupt or aged-out entries delete themselves on read.
  The key sits **outside `APP_STORAGE_BASES` on purpose** — `clearAppStorage()` is what the
  `ocr:unauthorized` handler calls, so a draft inside that list would be destroyed by the
  exact event it exists to survive. Same carve-out `ocr_carmen_uri:` already documents.
- **Both wizards** save on every change past step 1 and offer the document back once, on
  entry, via the page's existing modal — `useOcrExtraction.restoreDraft()` /
  `useAPExtraction.restoreDraft()` set state directly rather than replaying
  `applyExtractedData` (which mints fresh `_uid`s and rewrites the mapping handoff).
  Credit-card snapshot carries `originalHeader`/`originalDetails` (the correction-feedback
  baseline — omit them and a restored doc logs its whole content as user corrections) and
  `jvRows`/`carmenJvId` (a drop between the GLJV post and step 4 is recoverable too).
  AP carries `groupSources` (else ungrouping a restored invoice loses the merged rows) and
  calls `loadGLData()` when restoring straight to step 4, which normally gets its chart of
  accounts from the 3→4 transition.
  **Never auto-restores**: it would bury a fresh scan, and on a shared PC it would surface
  someone else's document unasked.
- **`AuthContext`** — `ocr:unauthorized` now sets `ocr_session_expired` and deliberately
  does *not* call `clearAllDrafts()`; drafts die on logout, tenant switch, reset, or TTL.
- **`ProtectedRoute`** — new `expired` state (amber, `Clock`): "Session Ended … any
  unsubmitted document has been saved". The old copy read like a first-time access wall.
- **`test/setup.ts`** — the localStorage stub had no `length`/`key()`, so every
  key-enumerating helper (`clearAppStorage`, and now `clearAllDrafts`) silently no-opped
  under test. Added; `draft.test.ts` covers TTL, corruption, and cross-tenant isolation.

### `10:40` Backend

- **`carmen_service._on_response` no longer deactivates the session on a Carmen 401**
  (`_deactivate_current_session` deleted; no caller, no test referenced it). Carmen is
  authoritative over its own token, not over our session — one rejected lookup, even a
  transient one with both tokens healthy, was permanently flipping
  `ocr_sessions.is_active = false`. The request still returns 401; the row stays truthful
  for `#/admin/sessions`.
- `docs/Database_Design.md` §`ocr_sessions` corrected: it still documented the removed
  behaviour, and still claimed the purge was "inactive > 30 days" when
  `20260721120000_session_scrub_keep_history.sql` scrubs the credential at `created_at + 1h`
  and deletes the row at 90 days.

### `11:20` Self-review pass before the release build

Six findings from re-reading the diff. Three were reachable bugs:

- **Version-gated the draft envelope** (`DRAFT_VERSION`, bump on any snapshot-shape change).
  `loadDraft` cast `data` to `T` unchecked, so a draft written before a deploy that renamed
  a field would set `undefined` into state and throw on render — with the restore prompt as
  the trigger and nothing clearing the draft on a crash, that is a white screen on every
  entry until the 6h TTL expired. Collection fields in both `restoreDraft`s also carry
  `??` fallbacks as a backstop.
- **AP restored the vendor but not `vendorSearch`**, which is the text the vendor input
  actually renders — and `autoMatchVendor` early-returns on `prev.code`
  (`useAPVendor.ts:96`), so it could never repopulate. The field read empty while the
  payload carried the right vendor. Both are now restored together.
- **Re-extract was a dead button after a restore.** `extraction.reExtract` early-returns on
  an empty file list; a restored document has no `File`. Now explains that the image is not
  kept and to upload it again.

Three were debt, fixed while the context was loaded:

- **400ms debounce on both save effects.** `lineItems` gets a fresh identity per keystroke,
  so the whole invoice was being `JSON.stringify`d into a synchronous `localStorage.setItem`
  on every character — tens of KB at 50-100 rows. Named ceiling: unmounting inside the
  window drops the last edit.
- **AP now clears its draft at step 5** instead of saving it. `handleGenerate` sets step 5
  on success, so closing the tab on the success screen used to leave a draft that offered to
  restore finished work. Credit card deliberately keeps saving at step 4 — that step is a
  second Carmen post (input tax) that still has to happen; both asymmetries are commented.
- **`EXPIRED_FLAG_KEY` is written before `setUser(null)`.** `ProtectedRoute` reads it during
  render, not from state; the old order worked only because React 18 batches.

Also verified and left alone: `.modal-msg` is `white-space: pre-line` so the prompt's
paragraphs render; `SplitLayout`/`DocumentPreview` accept a null preview and `showPreview`
defaults false, so a fileless restore cannot crash the pane; `useAccountingConfig` reads the
server with localStorage as fallback, so it self-heals after `clearAppStorage()`;
`onGoMapping` rewrites `ocr_wizard_state` before opening the mapping page;
`restorePromptedRef` survives StrictMode's double-mount; the restore effects' stale closures
only call setters.

Noted, not fixed (pre-existing, own ticket): **`/carmen/invoice` has no duplicate-submit
guard** the way `/gljv` does — it posts unconditionally and stamps `submitted_at` after.
Not reachable from the restore path, since a successful submit lands on step 5.

### `10:40` Deliberately not done

- **Sliding / refreshable OCR JWT** — bounded by Carmen either way. Note for whoever
  revisits: `fn_purge_inactive_sessions` scrubs at `created_at + 1h`, so raising

- **`X-Carmen-Auth: expired` response header** (mirroring the `X-Maintenance` pattern) to
  keep a Carmen-expired user editing behind a banner instead of kicking them. ~25 lines,
  but with drafts persisted both killers collapse into one recovery path, and a user who
  cannot reach Carmen cannot finish anyway. Add it if the reconnect round-trip is still
  the complaint.
- **Settling B1 (idle timeout) vs B2 (new token invalidates old)** — needs the Carmen team
  or the two-tab experiment, not code.
