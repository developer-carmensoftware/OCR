# 2026-09-10

## `#/email-settings` rebuilt as the reference for Carmen's own screen

`12:00` Carmen's draft of the customer-facing settings screen is a conventional card form
with `SAVE SETTINGS` / `RESET` at the bottom. Ours was a different idea of the same thing —
three numbered steps, chip lists with a per-item Add button, one collapsed rule list with an
edit form, and no Save button at all (every control PUT on change). Both being different was
the problem: our copy exists so the contract can be exercised end to end, and it is the thing
handed over as "here is the screen", so it should be the layout they are building rather than
an argument with it.

**Frontend**

- `pages/EmailSettings.tsx` rewritten to Carmen's layout on our `ui-*` kit (`PageHeader`,
  `Card`, `Switch`, `Button`, `Badge`): a URI/BU strip, a **Service status** card (Ready
  badge, ingest address + COPY), an **Automation settings** card (two toggle cards, two
  textareas, one card per rule with `ADD RULE`), a **Posting credential** card, and a sticky
  Save/Reset bar. That kit's CSS already loads app-wide from `index.css`, so the page's own
  sheet dropped from 420 lines to ~250 and `.email-setup__input` — a local copy of
  `.admin-form-input` — is gone.
- `hooks/email-settings/useEmailSettings.ts` is now a dirty form: `draft` / `patch` / `save`
  / `reset` / `dirty` replace the five write-through setters. One `PUT` per editing session
  instead of one per keystroke, which the 20/min rate limit cares about. The list fields live
  in the draft as **raw text** — splitting per keystroke eats the separator the user is
  halfway through typing — and one `splitList()` parses all three at save.
- **`auto_post` is still sent only when that switch is what moved.** It is the one
  merge-on-omit field (§2.7), and a Save button lengthens rather than removes the race with a
  colleague editing the same BU on Carmen's screen. `seedDraft()` is now the single place
  that decides what the form carries, and therefore the only way `doc_type` could go missing
  from a full-replace save again — the case the existing tests were written for.
- Owner emails and tax IDs become textareas (comma or newline), every rule is expanded and
  editable, `Active` is a switch on every rule including a new one, and field errors render
  under the input named by `field` rather than in a block at the foot of the step.
- Dropped: the Gmail confirmation block. The poll follows Google's link itself, so it was a
  card-sized explanation of something that needs no one. What survives is a single amber line
  in Service status, shown only if Google ever goes back to printing a code.
- Added a `beforeunload` guard while the form is dirty — the page has no in-app nav links, so
  that covers the realistic way to leave it.
- `components/admin/ui/Switch.tsx` gained an optional `ariaLabel`. The two toggle cards put
  the caption on the far side of the card, which left `role="switch"` with no accessible
  name; the review switch is the one control that lets a document post unseen, so it is not
  one to leave unnamed. Additive — every existing caller passes `label` and is untouched.

**Tests** — `EmailSettings.test.tsx` and `useEmailSettings.test.ts` rewritten against the new
surface, keeping every `doc_type` guarantee and adding: Save is disabled until something
changes, nothing reaches the server before it, Reset restores what the server last confirmed,
a rejected save keeps what was typed, `pdf_password` untouched is sent as `null` not `''`,
and `splitList` drops a trailing separator. 718/718 pass; `tsc`, `lint`, `npm run styles` and
`npm run contrast` clean.

**Docs** — `docs/CARMEN_INTEGRATION.md` §2.8 "Reference screen layout": the section order,
what each card holds, which three blocks are ours and skippable (posting credential, live
status/blockers, document type), and the two save rules that matter more than the layout.

No `VERSION` bump and no release note: the route is linked from nowhere and reached by typing
the hash, so this is internal.

## AR preview: which grouping built these rows, and which group each leg is

`14:58` `ARPreviewOut` gained `post_type`, and `ARPreviewRow` gained `key` — the group the leg
posts under, empty on the counterpart leg that belongs to all of them. `build_ar_jv_rows` fills
the first; `jv_for_document` and `/ar-reconcile/preview` fill the second. `build_gljv_payload`
reads rows by name and ignores extras, so nothing downstream moves.

Both exist for the review screen. Without them the browser would have to re-derive `group_key`
to put a printed payment type beside the leg it became, or slice the `Tax Inv.# … - ` prefix
back off `desc` — a second, weaker copy of the grouping rule, held in the language that does
not own it.

On the TypeScript side `ARPreview.post_type` is the `'Detail' | 'Summary'` union rather than
`string`, matching `ARSettings` and `ARPreviewRequest` in the same file. The review pane
switches its whole table on `post_type === 'Summary'`; against `string` a drift from the
server's `PostType.SUMMARY` would render every Summary document as *Detail* — the wrong
grouping rule, on the one chip that exists to name the grouping rule. The union makes that a
compile error.

`test_every_leg_carries_the_group_it_posts_under` pins `key` on both post types and spells out
the join the browser performs, so the contract is stated on the side that owns it.

## The settlement report's review pane is a reconciliation now, not a borrowed readout

`14:58` The question was whether a Detail-recon document needs its own review modal, on the
grounds that it posts no input tax. It does not — `ReviewDocument` has replaced the whole
`JvEditor` + `InputTaxPanel` half on `doc_type === 'ar_reconcile'` since it shipped, and
`post_input_tax` is hard-coded `false` there with the backend enforcing the same
independently. A second modal would have duplicated the portal, focus trap, scroll lock,
Escape handling, skeleton and footer for nothing.

What was wrong is the pane inside it. `ARJvPreview` is the **settings screen's** worked
example, and it was mounted in the dialog unchanged: heading `JV PREVIEW`, a footer printing
`"5 lines · "` because the dialog passes `postType=""`, an empty state advising you to
configure the bank, an unmapped warning saying the document "would wait for review" to a
reviewer reading it *in* the review queue — and every string hardcoded English on a bilingual
surface.

**Frontend**

- New `components/ar-reconcile/ARReviewPane.tsx`. One table on the shared `.jv-table`
  vocabulary, read left to right: the payment type the report printed, its THB amount, then
  the dept/account/debit/credit of the leg it became. Detail is one row per printed line. In
  **Summary** the constituents render as their own quiet rows beneath the scheme key with the
  figures they contributed — their sum is the Credit cell one row up, so the merge is
  checkable rather than asserted. The control-account leg is ruled off inside the table so
  the totals total what is on screen; a line the report prints at zero is kept, marked *no
  journal line*, so the table cannot silently hold fewer rows than the paper.
- A `Detail` / `Summary` chip names the grouping. It was invisible before, and a one-scheme
  day makes the two identical.
- `JvHeaderCard` gained `readOnly` + `descriptionOverride`, and `ReviewDocument` passes both
  on the AR path. **Three latent bugs go with it:** Doc no. and Doc date drove the `Tax Inv.#`
  and `JvhDate` of a JV the server rebuilds on approve, so what was typed changed the screen
  and not the post; a retyped prefix cleared the block and was then dropped, because the
  config write is skipped when `isAR`; and the Description field was showing the *credit-card*
  per-bank wording, which is a different sentence about a different document — it now shows
  `ar_jv.description`, the one that posts.
- With the prefix field read-only, the "journal book required" block reason carries a link to
  `#/CreditCardOCR/mapping` (`.rd-blocked-fix`).
- All new copy through `dict.ts`, EN + TH.
- `ARJvPreview` keeps the settings screen and loses the `label` prop the dialog added.

**Backend** — `ARPreviewRow.key` (the group the leg posts under, empty on the counterpart leg)
and `ARPreviewOut.post_type`. `build_ar_jv_rows` fills the first; `jv_for_document` and
`/ar-reconcile/preview` fill the second. Extra keys are ignored by `build_gljv_payload`, so
nothing downstream moves. Without them the browser would have had to re-derive `group_key` or
slice the `Tax Inv.# … - ` prefix off `desc` — a second, weaker copy of the grouping rule.

**A real catch from `npm run styles`** — the guard list now covers `ARReviewPane`,
`JvHeaderCard` and `ReviewDocument`, and it immediately failed `.ar-hint` in the dialog. That
class lives in `pages/ar-reconcile.css` and was reachable only because `ARJvPreview` happened
to be mounted there and imported that sheet; replacing it would have shipped the hint styled
by nothing. It is `.rd-ar-hint` in `review-queue.css` now — the sheet the dialog actually
reaches. Exactly the failure the script was written for on 2026-09-09.

**Tests** — the AR block in `ReviewDocument.test.tsx` rewritten against the pane: the Detail
join row by row, the Summary merge showing both folded labels and their figures, a zero line
kept and marked, no editable control in the header, the AR description winning over the
credit-card one, an unmapped leg painting its cells and naming itself at the button, and the
journal-book link. New `test_every_leg_carries_the_group_it_posts_under` pins `key` on both
post types and spells out the join the browser performs. 724/724 frontend, AR backend suites
green; `tsc`, `lint`, `build`, `npm run contrast` and `npm run styles` clean.
