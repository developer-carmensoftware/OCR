## `10:30` Settings API — name the BU with `uri`, the value Carmen already has

### Why

Carmen passes a full origin (`https://hotelgroup.carmenwork.com`) to `/auth/exchange` and
has done since day one. The Settings API asked for a bare `host` instead, so their side had
to derive a hostname for this one API — and our own settings screen did the same thing in
reverse (`hostOf(user.uri)` threw the scheme away before every call). One value, two
spellings, and a class of "Unknown business unit" that is really a formatting mistake.

**This is not a partial revert of `e870788`.** That commit removed `carmen_uri` because it
was the *destination* of outbound requests: a caller could have its token verified against
one Carmen and its JVs posted to another. `uri` here is a lookup key that stops at
`resolve_tenant`; the origin still comes from `tenants.host` via `_safe_carmen_uri`, and
since that row's host was itself produced by this same `urlparse(...).hostname` at login,
the two cannot disagree. Where they would, the lookup is a `400` before anything is sent.

### Backend — **breaking for Carmen's callers**

- `SettingsIn` / `TokenIn` take `uri` and no longer read `host`; the five settings routes
  take `?uri=&bu=` — [`routers/email_automation.py`](../backend/app/routers/email_automation.py),
  [`models/schemas/email_automation.py`](../backend/app/models/schemas/email_automation.py).
- `_tenant_host(uri)` is the whole change: `urlparse(...).hostname`, lowercased, falling
  back to the raw value so a bare host still resolves. Deliberately **not** `_validate_uri`
  — that ends in a blocking `socket.getaddrinfo`, i.e. a DNS lookup on unauthenticated
  input, which is the exposure the rate limiters at the top of that module exist to bound.
  There is nothing to validate in a value we never call.
- `_resolve` no longer shadows its `uri` parameter with the derived origin — the local is
  `origin` now, so a reader can see the two are different things.
- `build_settings_response` drops its `host`/`bu` arguments and reports `tenant.host` /
  `tenant.bu_code`. The body is a function of the tenant, not of the request; previously it
  echoed the caller's raw string, so `HotelGroup.CarmenWork.com` came back uppercased for a
  tenant stored lowercase. Same for the three log lines, which now record one canonical
  value and no longer interpolate caller-controlled text.
- **Untouched, and worth confirming in review:** `_safe_carmen_uri`, `posting_target` and
  `set_token`. No caller-supplied string reaches any of them — that is the invariant.

### Frontend

- `useEmailSettings` sends `user.uri` as-is; `hostOf()` is gone. `ctrl.host` now comes from
  the response (`settings?.host`), which the change above makes trustworthy —
  [`hooks/email-settings/useEmailSettings.ts`](../frontend/src/hooks/email-settings/useEmailSettings.ts),
  [`lib/api/emailAutomation.ts`](../frontend/src/lib/api/emailAutomation.ts),
  [`lib/api/endpoints.ts`](../frontend/src/lib/api/endpoints.ts).
- Shipped in the same commit as the backend on purpose: with `host` gone there is no
  version of the frontend that works against both, so they deploy together.

### Tests

- `test_email_automation_router.py` +5: every spelling of the origin (scheme, case, port,
  path, whitespace, bare host) collapsing to one lookup key; a value naming no host left to
  the lookup; **the security pin** — `uri="https://evil.com"` must still verify against the
  tenant's own origin; an unknown origin never reaching Carmen at all; and the same pin at
  route level on `PUT /settings/token`, which is the call that carries a credential.
- `test_email_settings_service.py` +1: the response reports the tenant's identity, not the
  caller's — an echo nothing tested before. Full backend suite green, ruff clean, `tsc`
  clean.

### Docs

- [`CARMEN_API_SPEC.md`](../docs/CARMEN_API_SPEC.md) → v4.0, with a change banner at the top
  of the endpoint table and the `invalid_uri` row corrected: it is reported against
  `carmen_uri` (an origin we derived), never against the `uri` a caller sent.
- [`CARMEN_INTEGRATION.md`](../docs/CARMEN_INTEGRATION.md) §1 rewritten around `uri`, §2.1
  gains the paragraph explaining why this does not weaken the token-proof argument, and
  §2.6's "there is no `carmen_uri` field" is rewritten rather than deleted — the promise it
  makes (one origin, never a caller's) is exactly what must not be read as relaxed. The
  status banner at the top carries the breaking-change notice, since that is what the
  Carmen team reads first.

### Uncommitted / in progress

  sending `host` gets a `422`. Our own frontend is the only other caller and moves with it.

## `09:10` Email Automation — the forwarding handshake completes itself

### Why

The 2026-08-07 entry below claimed the last manual step was solved by reading Gmail's
confirmation **code** out of the subject and showing it on the settings screen. Measured
against four real confirmation mails in the dev mailbox today — Thai personal Gmail and
English Workspace — **that code does not exist**. Google prints no code in the subject and
none in the body; the only thing it sends is a confirmation link. Every real subject still
opens with a bare `(` where `#code)` used to sit, which is exactly why the pattern looked
right: `_GMAIL_CONFIRM_CODE` only ever matched the fixtures we wrote for ourselves.

So the feature shipped on 2026-08-07 has never worked against a real mail, and the
"customer pastes the code" flow it describes cannot work at all — there is nothing to
paste. Following the link is what a human click does, and it is now the only mechanism.

Verified end to end before any of this was written: a forwarding address that had never
been confirmed went live after a server-side GET + POST, with nobody touching Gmail.

### Backend

- `auto_confirm_forwarding(link)` — GET the link, then POST to the URL it lands on. Two
  requests because the link is not the confirmation: it 302s to an interstitial whose
  entire content is `<form action="" method="post">` with one button, no hidden field and
  no CSRF token. Both run on one client so Google's cookies survive the hop —
  [`services/email_ingest_service.py`](../backend/app/services/email_ingest_service.py).
- **`vf-` only, never `uf-`.** The same mail carries an almost identical cancel URL one
  letter away; following it would silently undo the setup the customer just asked for.
  `_GMAIL_CONFIRM_LINK` is anchored on the host and the literal `/mail/vf-`, and the test
  that pins this runs against a **real captured mail**, not a fabricated one.
- Host allowlist (`mail-settings.google.com`, `mail.google.com`) checked on **every
  redirect hop**, not just the first URL — `follow_redirects` would otherwise let a
  redirect walk the poll off Google entirely. Its own client, because the shared one in
  `carmen_service.py` deliberately never follows redirects (SSRF guard).
- Never raises, same contract as `record_gmail_code`: a poll is mostly about invoices and
  a failed confirmation must not take them down with it.
- `_fetch_unseen` now carries a `body`, populated **only** for mail from
  `forwarding-noreply@google.com` — decoding every bank mail's HTML signature block to
  find nothing is work the ingest path does not need.
- `es.record_gmail_confirmed()` stamps the outcome —
  [`services/email_settings_service.py`](../backend/app/services/email_settings_service.py).
- `gmail_confirm_code` and its column are kept, unused in practice, as the fallback if
  Google brings the code back. Both are now documented as expected-null rather than
  expected-set.
- Tests +5 in `test_email_ingest_pipeline.py`: confirm-vs-cancel link, a real mail carrying
  no code at all, a non-Google link never followed, the BU marked confirmed, and a failed
  confirmation leaving it unmarked without breaking the poll. Full backend suite green.

### DB

- [`20260807020000_email_gmail_auto_confirm.sql`](../supabase/migrations/20260807020000_email_gmail_auto_confirm.sql)
  — `email_ingest_settings.gmail_confirmed_at`. The outcome, not another code: it is what
  the screen reads to say "connected" instead of waiting forever for a code that will
  never arrive. **Not yet pushed.**

### Frontend

- The confirmation card now has three states instead of two: confirmed automatically (with
  the timestamp), a waiting code (the fallback that should never appear), and "we complete
  it for you — you should not have to click anything" —
  [`pages/EmailSettings.tsx`](../frontend/src/pages/EmailSettings.tsx).
- `gmail_confirmed_at` added to the response type —
  [`lib/api/emailAutomation.ts`](../frontend/src/lib/api/emailAutomation.ts).

### Known blind spot

The link format is not a documented Google API. If Google changes it, auto-confirm stops
silently and the screen falls back to waiting for a code that also will not come. Nothing
in CI can catch that — no live test against Google exists or should. **If customers report
that forwarding never activates, check this first.**
