## `12:10` — Backend: ticket 08 — deterministic KBANK settlement parser (drop the LLM call)

Implemented `.scratch/kbank-settlement-jv/issues/08-deterministic-settlement-parser.md`, the
last of the 8 tickets from the 2026-09-18 KBANK settlement redesign. Deliberately sequenced
last per its own blocking note: the JV shape (ticket 03) and the extraction engine could not
change in the same pass without losing the ability to tell which half caused a wrong figure.

- `services/kbank_settlement_text.py` (new) — `parse(pdf_bytes) -> ExtractedCreditCardData |
  None`. Reads every word on the page via PyMuPDF `get_text("words")`, buckets them into
  printed rows by y-position (±2pt) rather than trusting PyMuPDF's own block/line order —
  which on this report puts the column-header row after its data rows in content-stream
  order, and splits the NET AMT figure on the `TOTAL BY MERCHANT ID` line into its own
  content block, landing after a page-width separator but on the same printed row. Produces
  the exact shape `llm/prompts/kbank_settlement.py` asks the vision model for, including the
  unfiltered anchor row appended to `details[]`, so `credit_card_service
  ._normalize_ar_settlement` needs no change to accept either source. Verified against the
  real sample file (not committed — see privacy note below): reproduces every field the
  vision path currently extracts, and the result survives the real normalizer with zero
  warnings — three-way self-consistent, same as the LLM reading. Requires `REPORT NO.
  KB1P554V2`; returns `None` (never guesses, never raises) on a version mismatch, a missing
  NET AMT or tax invoice number, an encrypted PDF, or anything else unexpected.
- `services/ocr_service.py` — `extract_stateless` tries the deterministic reader (in a
  thread executor, matching the file's existing PyMuPDF calls) immediately before the vision
  call, scoped to `doc_type == AR_RECONCILE and bank_code == "KBANK"` only. `None` falls
  straight through to the unchanged vision path. Charging is unaffected — `consume_document`
  already ran per file, before this point, regardless of which path reads it.
- **Privacy**: the committed test fixture is built in memory (PyMuPDF `insert_text` at
  chosen coordinates) rather than the customer's real PDF — no binary asset added to the
  repo. It deliberately reproduces both structural quirks above (header-after-data
  insertion order; NET AMT as a separate call sharing the total row's y) and carries the
  real worked example's own money figures (needed to prove fidelity against the actual
  sample), with merchant name/ID/account number/tax invoice number all scrubbed.
- Tests: `test_kbank_settlement_text.py` (new, 9 tests) — the full layout with scrubbed
  identity; survives `_normalize_ar_settlement` unchanged; a future report version, a
  missing NET AMT, a missing total row, a missing tax invoice number, an encrypted PDF, and
  malformed bytes all return `None`; a per-terminal `MERCHANT ID` row is never mistaken for
  the `SUMMARY MERCHANT ID` one. `test_ocr_service.py` (new, 3 tests) — the hook itself: a
  readable settlement skips the vision call entirely, a shape mismatch falls through to
  vision unchanged, and the parser is never even attempted outside
  `doc_type == AR_RECONCILE and bank_code == "KBANK"`. Full backend suite: 1395 passed, 79
  skipped (pre-existing, unrelated), 0 failed.

## `11:20` — Frontend: two review-screen regressions found by an end-to-end test

Ran the real sample zip through the live dev pipeline — IMAP append, the actual poll
endpoint, then the review queue and approve flow in a real browser via Playwright,
against the `carmencloud` dev tenant (already fully configured: KBANK AR settings,
commission/tax/net mapping, VS/MC/JCB credit mapping — only the `KB1P554V2_SUM` email
rule was missing, added for this test). The backend side was flawless: deterministic
parse (zero LLM cost), TIN verified via the CSV sidecar, figure cross-check clean,
parked for review with `flags: []`. Approving it posted a real JV to the dev Carmen
instance (**JV #1082**) and filed its own input-tax record with no error — but the
review screen itself had two bugs neither ticket 03 nor ticket 06 caught, because
nothing had exercised this exact path since either shipped.

- `components/ar-reconcile/ARReviewPane.tsx` — `rows.find(r => !r.key)` singular
  assumed the pre-2026-09-18 shape (one derived control leg). Since ticket 03,
  `build_ar_jv_rows` always emits **three** fixed debit legs (commission / input tax /
  bank account), all with `key: ""` — `.find()` kept only the first and silently
  dropped the other two from the table. The footer's `Balanced 25,091.00 / 25,091.00`
  still summed correctly (it reads `jv.total_debit`/`total_credit` from the server,
  not the rows this component chose to render), so a reviewer saw a document that
  balanced while two of its three debit legs — 40.81 and 24,467.20 of the 25,091.00 —
  were simply invisible. Fixed to `.filter()`, rendering all of them.
- `pages/ReviewDocument.tsx` — the Approve button unconditionally sent
  `post_input_tax: false` for every AR document, on a comment dating from before
  ticket 06 ("a reclassification claims no input tax"). Ticket 06 made the settlement
  JV file that claim itself once the fee invoice stopped being processed, but this one
  call site was never updated — so every AR document approved through the review
  screen (the default path; `auto_post` starts `false`) silently skipped its own
  input-tax record, the exact regression ticket 06 was written to prevent. Fixed to
  send `true` unconditionally — AR has no panel offering a reviewer the choice the
  way a fee invoice's own toggle does, so there is nothing to make conditional on.
- Tests: `ReviewDocument.test.tsx`'s AR fixtures (`AR_CONTROL` → `AR_CONTROL_ROWS`,
  three real worked-example legs instead of one derived one) and every assertion
  reading the pane's rows updated to match — these are what let the bug through
  unnoticed, since they still asserted the old one-leg shape. The "files no
  input-tax record" test rewritten to assert the opposite. Full frontend suite: 761
  passed; `tsc --noEmit` and `npm run build` clean.
- Also noted, not a code issue: the dev tenant's pre-existing KTC/SCB rules use a bare
  `".pdf"` filename pattern, broad enough to intercept the e-tax invoice before the
  double-booking guard or `no_rule_match` ever sees it — it parked as
  `wrong_pdf_password` instead of a clean skip. Worth telling a real customer to scope
  filename patterns narrower than a bare extension.
- The local dev backend (`uvicorn`, port 8010) had been running without `--reload`
  since before this session's ticket 08 commit, so it was silently serving stale code
  — restarted with `--reload` partway through testing once an LLM charge appeared on
  a document ticket 08 should have read for free.
