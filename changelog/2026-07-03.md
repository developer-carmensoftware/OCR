## `17:20` Unify all fee-invoice formats — footer-VAT spread, rate-agnostic (real-sample QA)

- `17:20` **Insight (real docs)**: all 4 processor formats (KTC/GHL/PayPal/SiamPay) are structurally identical — N fee line items + a footer (Subtotal/VAT/Grand). The old per-issuer split ("SiamPay = one row per line" vs "others = one row from totals") was an artifact of the samples (SiamPay's happened to have 2 lines); ANY issuer can bill multiple lines. Old SiamPay path also rebuilt VAT per-line at hardcoded 7% — the one format that would break on a non-7% document.
- `17:20` **Backend** `credit_card_service.py`: `_normalize_fee_invoice` rewritten to one uniform handler. Prompt now emits N line rows + a `TOTAL` summary row (footer Subtotal/VAT/Grand); backend consumes the summary and spreads its PRINTED VAT across the lines proportional to fee (`_spread_footer_vat`), rounding absorbed by the last row — works for 1 or N lines and ANY VAT rate (figure read, never assumed). Falls back to per-row `_solve_fee_row` when no summary row (legacy single-row shape stays correct). `_is_summary_row` now excludes "Subtotal".
- `17:20` **Prompts** `ktc/ghl/paypal/siampay.py`: all four rewritten to the uniform "line rows + TOTAL summary row" shape. Versions KTC/GHL/PayPal→1.2.0, SiamPay→1.3.0, COMBINED→2.4.0.
- `17:20` **Tests**: 6 new spread-path tests on real numbers (SiamPay 2-line, KTC single-line, 10%-VAT rate-agnostic, VAT-derived-when-blank, garbled-label arithmetic detection, legacy-shape fallback). Validated the normalizer against 13 real samples across all 4 formats — VAT & Grand match to the satang. 60 unit tests pass.
