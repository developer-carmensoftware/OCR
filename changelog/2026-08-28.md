# 2026-08-28

## Email Automation — human-in-the-loop review (in progress, branch `feat/email-hitl-review`)

Design settled and written up in
[`docs/email-automation/07-human-in-the-loop.md`](../docs/email-automation/07-human-in-the-loop.md).
Email ingest currently posts to Carmen with nobody in between — the right shape for a pipeline
people already trust, the wrong one for a BU switching it on for the first time. A document now
parks at `pending_review` until someone approves it, and the BU turns that off with a per-BU
`auto_post` switch once it has seen enough. The Credit Card module's landing page becomes the
review queue; the wizard moves to its own route.

### Uncommitted / in progress

Nothing shipped yet — the branch is not merged and neither cron job is scheduled in production
anyway. Work lands one ticket per commit; the list is in the design doc's task breakdown.

### DB

`09:55` **`20260828000000_email_review_queue.sql`** — `email_documents` gains
`review_payload jsonb`, `reviewed_by varchar(36)`, `reviewed_at timestamptz`; a partial index
on `(tenant_id, created_at desc) where status = 'pending_review'`; `email_ingest_settings` gains
`auto_post boolean not null default false`.

- **`review_payload` narrows a documented rule rather than repealing it.** `CLAUDE.md` and
  `04-data-model.md` both say extracted line items are never persisted. They now say: not
  persisted **after a document is resolved**. A document waiting on a human keeps its payload
  because the only alternative is a second vision call the customer pays for twice; `_finish`
  clears the column to `NULL` on every terminal transition.
- **The built JV rows are deliberately not in the payload.** The review screen derives them live
  from `details` against the *current* accounting config, the way `AccountingReview` already
  does — a reviewer must see what would post now, not what would have posted at extract time.
- **Neither is the Carmen credential.** Token and URI are re-read at approve time; they rotate,
  and `sweep_token_health` may have unverified them while the document sat.
- `auto_post` defaults `false`, so every BU with the feature on wakes up in review mode. That is
  the direction you can walk back from. Its known sharp edge — `PUT /settings` is a full replace,
  so an older Carmen client omits the field and silently resets it — is accepted and recorded in
  the migration with its upgrade path.

### Backend

`10:05` **The review fork** — `_run_document` takes `auto_post` and, when it is off, calls
the new `_park_for_review()` instead of `build_gljv_payload` + `post_gljv`. Everything above
that line is unchanged, so a document that reaches a human has already survived every gate a
machine can judge: sender, rules, PDF password, module, charge, extraction, tax-ID check,
duplicate check, GL mapping, and the zero-amount guard.

- **The payload is the raw `/extract` shape**, not a bespoke one — `applyExtractedData` in the
  browser consumes that verbatim, so neither side needs a mapping layer. `raw_text` is dropped.
- **`_review_flags()` computes the reason line once, at park time**: `mapping_guessed` (whether
  the AI had to invent a GL mapping — unrecoverable later, since `fill_missing_mappings` has by
  then saved the guess and it looks like any other), `unbalanced` (the same per-line arithmetic
  `AccountingReview.imbalancedLines` does in the browser), `warnings`. The queue must paint a
  row without loading every payload or resolving the accounting config per row.
- **`_finish` now nulls `review_payload`** on every terminal transition. Every status it writes
  is terminal, so the payload has no reader left — this is what keeps "line items are not
  persisted" true in the sense that survives this feature.
- `run_ingest`'s summary gains `pending_review` in its initial shape, not just when it happens:
  on a BU in review mode it is the *normal* outcome, and a key that appears only sometimes is
  one `#/admin/email` cannot render honestly.
- Six new tests, including the two negatives that matter: `post_gljv` is not awaited and
  `submitted_at` is not stamped when a document parks, and `refund_document` is not awaited
  either — the credit was spent at extraction and stays spent (decision-log #17).

`10:20` **Backpressure and the duplicate a parked document hides** — two guards that only
exist because a document can now sit still for a day.

- **`REVIEW_BACKLOG_CAP = 50`.** Past fifty unreviewed documents, ingestion stops for that BU
  and the mail is handed back unread — the same shape as running out of credits: no ledger
  row, nothing charged, replays once someone clears the queue, bounded by the existing 14-day
  hold window. Without it a BU that stops reading its queue keeps paying for a pile nobody has
  looked at, and none of it is refundable once the vision call has run. Skipped entirely when
  `auto_post` is on, where nothing parks and the count would be a query for nothing.
- **`_already_pending()`.** `is_duplicate` reads `credit_cards.submitted_at`, which stays NULL
  for the whole review window — so a bank re-sending, or someone forwarding twice, sails past
  it and parks a second identical row. Checked ingest-side only: `has_submitted_doc` is shared
  with the wizard, where a pending row means nothing and blocking on one would stop a user
  scanning a document they are holding. Fails open, and never matches a document with no
  `doc_no` — two unnumbered statements are not evidence of anything.

`10:35` **`auto_post` on the settings API** — field on `SettingsIn`, persisted by
`save_settings`, echoed by `to_response` on both the configured and unconfigured paths.
Deliberately **not** a blocker in any state: review mode is the safe one, so a BU sitting in
it is working as designed, and listing it would put a warning chip on the correct
configuration. Also pinned `auto_post` in the two test fixtures — `SimpleNamespace` has no
default, and `MagicMock` would have made it silently truthy.
