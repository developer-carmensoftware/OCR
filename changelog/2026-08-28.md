# 2026-08-28

## Email Automation — human-in-the-loop review (in progress, branch `feat/email-hitl-review`)

Design settled and written up in
[`docs/email-automation/07-human-in-the-loop.md`](../docs/email-automation/07-human-in-the-loop.md).
Email ingest currently posts to Carmen with nobody in between — the right shape for a pipeline
people already trust, the wrong one for a BU switching it on for the first time. A document now
parks at `pending_review` until someone approves it, and the BU turns that off with a per-BU
`auto_post` switch once it has seen enough. The Credit Card module's landing page becomes the
review queue; the wizard moves to its own route.

### DB

`09:55` **`20260828000000_email_review_queue.sql`** — `email_documents` gains
`review_payload jsonb`, `reviewed_by varchar(36)`, `reviewed_at timestamptz`; a partial index
on `(tenant_id, created_at desc) where status = 'pending_review'`; `email_ingest_settings` gains
`auto_post boolean not null default false`.

- **`review_payload` narrows a documented rule rather than repealing it.** `CLAUDE.md` and
  `04-data-model.md` both say extracted line items are never persisted. They now say: not
  persisted **after a document is resolved**. A document waiting on a human keeps its payload
  because the only alternative is a second vision call the customer pays for twice; `_finish`
  clears the column to `NULL` on every terminal transition.
- **The built JV rows are deliberately not in the payload.** The review screen derives them live
  from `details` against the *current* accounting config, the way `AccountingReview` already
  does — a reviewer must see what would post now, not what would have posted at extract time.
- **Neither is the Carmen credential.** Token and URI are re-read at approve time; they rotate,
  and `sweep_token_health` may have unverified them while the document sat.
- `auto_post` defaults `false`, so every BU with the feature on wakes up in review mode. That is
  the direction you can walk back from. Its known sharp edge — `PUT /settings` is a full replace,
  so an older Carmen client omits the field and silently resets it — is accepted and recorded in
  the migration with its upgrade path.

### Backend

`10:05` **The review fork** — `_run_document` takes `auto_post` and, when it is off, calls
the new `_park_for_review()` instead of `build_gljv_payload` + `post_gljv`. Everything above
that line is unchanged, so a document that reaches a human has already survived every gate a
machine can judge: sender, rules, PDF password, module, charge, extraction, tax-ID check,
duplicate check, GL mapping, and the zero-amount guard.

- **The payload is the raw `/extract` shape**, not a bespoke one — `applyExtractedData` in the
  browser consumes that verbatim, so neither side needs a mapping layer. `raw_text` is dropped.
- **`_review_flags()` computes the reason line once, at park time**: `mapping_guessed` (whether
  the AI had to invent a GL mapping — unrecoverable later, since `fill_missing_mappings` has by
  then saved the guess and it looks like any other), `unbalanced` (the same per-line arithmetic
  `AccountingReview.imbalancedLines` does in the browser), `warnings`. The queue must paint a
  row without loading every payload or resolving the accounting config per row.
- **`_finish` now nulls `review_payload`** on every terminal transition. Every status it writes
  is terminal, so the payload has no reader left — this is what keeps "line items are not
  persisted" true in the sense that survives this feature.
- `run_ingest`'s summary gains `pending_review` in its initial shape, not just when it happens:
  on a BU in review mode it is the *normal* outcome, and a key that appears only sometimes is
  one `#/admin/email` cannot render honestly.
- Six new tests, including the two negatives that matter: `post_gljv` is not awaited and
  `submitted_at` is not stamped when a document parks, and `refund_document` is not awaited
  either — the credit was spent at extraction and stays spent (decision-log #17).

`10:20` **Backpressure and the duplicate a parked document hides** — two guards that only
exist because a document can now sit still for a day.

- **`REVIEW_BACKLOG_CAP = 50`.** Past fifty unreviewed documents, ingestion stops for that BU
  and the mail is handed back unread — the same shape as running out of credits: no ledger
  row, nothing charged, replays once someone clears the queue, bounded by the existing 14-day
  hold window. Without it a BU that stops reading its queue keeps paying for a pile nobody has
  looked at, and none of it is refundable once the vision call has run. Skipped entirely when
  `auto_post` is on, where nothing parks and the count would be a query for nothing.
- **`_already_pending()`.** `is_duplicate` reads `credit_cards.submitted_at`, which stays NULL
  for the whole review window — so a bank re-sending, or someone forwarding twice, sails past
  it and parks a second identical row. Checked ingest-side only: `has_submitted_doc` is shared
  with the wizard, where a pending row means nothing and blocking on one would stop a user
  scanning a document they are holding. Fails open, and never matches a document with no
  `doc_no` — two unnumbered statements are not evidence of anything.

`10:35` **`auto_post` on the settings API** — field on `SettingsIn`, persisted by
`save_settings`, echoed by `to_response` on both the configured and unconfigured paths.
Deliberately **not** a blocker in any state: review mode is the safe one, so a BU sitting in
it is working as designed, and listing it would put a warning chip on the correct
configuration. Also pinned `auto_post` in the two test fixtures — `SimpleNamespace` has no
default, and `MagicMock` would have made it silently truthy.

`10:50` **`routers/email_review.py`** — the BU's own view of its queue:
`GET /api/v1/email/documents`, `/documents/{id}`, `/status`, all on `get_current_session`.

- **A separate router from `email_automation.py` on purpose.** That one answers *Carmen's
  server* and authenticates by replaying the customer's raw Carmen token; this one answers
  *our own frontend*, where the user already holds a session JWT.
- **The tenant filter is in the WHERE clause, not an `if` after the fetch.** `/documents/{id}`
  is the only endpoint in the application that returns extracted line items, so "exists but
  is not yours" must be indistinguishable from "no such row" — asserted against the compiled
  SQL, since a filter applied after the fetch is the bug this endpoint cannot afford.
- **Row total is Σ`pay_amt`**, the gross, which is what lands on the credit side of the JV and
  therefore what a reviewer is agreeing to. Summing `total` would show the net and quietly
  understate every row.
- **A row whose payload has vanished still renders** with zeroes. Someone else's approve
  clears `review_payload` on the way to `posted`; 500-ing on the losing side of that race is
  worse than one bare row.
- `/status` reuses `build_settings_response`'s `blockers` verbatim rather than re-deriving
  them, so the queue screen and the settings screen cannot disagree about whether a BU is set
  up. `make_test_client` gained an optional `session=` override — `FAKE_SESSION.tenant_id` is
  deliberately not a UUID (`test_carmen_proxy` relies on that) and this router parses it.

`11:15` **Approve and reject** — `POST /documents/{id}/approve` and `/reject`, with
`approve_document` / `reject_document` living next to the pipeline in
`email_ingest_service.py` rather than in a module of their own: approve *is* the second half
of `_run_document`, and it has to stay consistent with `_finish`'s semantics (which nulls
`review_payload`). Split across two files, those two are one refactor away from disagreeing.

- **Posts under the BU's credential, not the reviewer's.** Deliberately not through
  `routers/carmen.py:proxy_gljv`, which reads `session.carmen_token` — an ingested document
  posted that way would be attributed to whichever colleague opened the queue. The token is
  re-read at approve time, never stored at park time: it rotates, and `sweep_token_health`
  may have unverified it while the document sat.
- **The rows posted are the rows the reviewer saw.** Rebuilding them server-side would risk
  posting something other than what was on screen when the button was pressed.
- **`FOR UPDATE` on the claim.** Two reviewers in one BU is the expected case (the bell has
  no user to address), so the loser of that race must find a row that is no longer pending
  rather than post the same JV twice.
- **`has_submitted_doc` is re-checked**, because `is_duplicate` was computed before the
  document waited — and a wait is exactly when someone keys the same statement in by hand.
- **A Carmen rejection is a 400 with Carmen's own words, not a 503.** `CarmenServiceError`
  maps to 503, which reads as "try again later" — wrong for a closed period or an unknown
  dept code. The document stays `pending_review`: the only place in this feature where a
  failed post is not terminal, because the reviewer is standing right there.
- **A Carmen *outage* says something different.** The JV's fate is unknown and `submitted_at`
  is stamped on success only, so nothing on our side can tell them — the message names that
  explicitly rather than saying "failed" and inviting a second click that double-posts.
- Reject is terminal, stores an optional trimmed reason (empty becomes `NULL`, not `""`), and
  **never refunds** — decision-log #17 unchanged.

`11:35` **`document_pending_review` in the bell** — `_notify_pending()` raises **one row per
BU per poll** carrying a count, not one per document: a bank sending a twenty-attachment zip
would otherwise bury every other notification the customer has. Per BU and not per person
because `user_notifications` has no user column and there is no users table to point at.

Never raises — the documents are parked either way, and an exception there would turn a
successful poll into a `FAILED` job run. Also fires on the poll's *error* path, since
documents parked before a crash are real and waiting.

### Frontend

`11:40` **The bell learned the new row.** `TYPE_META` (`ClockAlert`, warning tone), a
`notifText` case, and `en` + `th` keys. It is the only row in the bell that **asks** for
something rather than reporting what already happened, so clicking it goes to the queue at
`#/CreditCardOCR` instead of opening the detail modal — a modal there would be a dead end

`11:55` **The audit row keeps the name, not just the id.** New migration
`20260828010000_email_review_reviewer_name.sql` adds `reviewed_by_name varchar(100)`, filled
from `session.username`, alongside `reviewed_by`.

> ⚠️ **This started as an edit to `20260828000000`, which was wrong** — that migration had
> already been pushed. `db push` never re-runs an applied migration, so the edit would have
> lived in the repo while the database went on without the column, and the ORM would have been
> declaring a column Postgres does not have: every query on `email_documents` failing at once.
> Reverted to exactly the file that was applied, and the column moved to its own migration.
> The rule in `CLAUDE.md` — never edit an applied migration — is there for this.

Everywhere else in this codebase only `carmen_user_id` is stored and the display name is
resolved later through `tenant_lookup.username_map` — which reads `ocr_sessions`, scrubbed at
90 days, and whose own docstring says older ids "fall back to the raw id". That is fine for a
usage chart. It is not fine for the record of who approved a journal entry: ask in a year and
it answers with a UUID. The id stays the identity; the name is copied at decision time so it
cannot decay. Surfaced on `GET /admin/email-ingest/documents` (name first — nobody debugging a
JV wants to read a UUID), and it degrades to the id when a session carries no username.

`12:15` **The wizard moves to its own file** — `pages/CreditCardOCR.tsx` → `pages/ManualScan.tsx`,
a `git mv` plus one renamed function. `useOcrWizard` and every step component are untouched.

`#/CreditCardOCR` still renders it, so **this commit changes nothing a user can see**; it only
gives the queue somewhere to move into. The header edits that belong with the split (title,
Back pointing at the queue rather than at Carmen) are deliberately held back: right now `Back`
would navigate to `#/CreditCardOCR`, which is this same page, so it would reset the wizard
instead of leaving it.

`12:45` **The automation page is live at `#/CreditCardOCR`** — the queue takes the landing
route Carmen's SSO deep-links to, and the wizard moves to `#/CreditCardOCR/manual`.

- **Four states, and none of them is a generic empty.** Work waiting (the list), **all clear**
  (reads as success, because that is where a working BU spends most of its time), **not set up**
  (the only place the feature can be discovered, so the one screen here allowed to sell), and a
  **failed fetch** — deliberately its own state with a retry, because "nothing is waiting" and
  "we could not ask" mean opposite things to someone deciding whether to go home.
- **Not-set-up has three sub-states** off the `blockers` the settings service already returns:
  never configured, configured-but-off, and not entitled. The last one **hides the address** —
  one that silently drops everything sent to it is worse than none.
- **Status and rows are fetched together and gated on one `loading`.** Resolving them separately
  makes the page flash the "not set up" screen on a BU that has twenty documents waiting.
- **The reason line** is one phrase, never a list, chosen in priority order: amounts do not
  reconcile → GL mapping guessed → extraction warnings → nothing flagged. Ordered by how much it
  should stop someone, since with review on most parked documents are fine and the reviewer's
  real job is finding the two that are not.
- `+ Manual scan` is `.btn-outline`, not primary: on this page the main action is approving what
  the robot already did.
- Row page size is measured off `.rq-row-main`, the fixed-height half of a row, and the skeleton
  is the real row with its content hidden — the two lessons `OrderHistory` paid for.
- 11 new tests covering all four states and the reason-line priority; `npm run contrast` green;
  new `review.*` keys in both `en` and `th`.

`13:20` **Status tabs on the queue** — Needs review · Posted · Not posted · Skipped, each
with its count. This reverses the earlier decision that the list should only ever show
`pending_review`; a customer wanting to answer "did that one go through?" should not have to
ask us.

- **Tabs are grouped by what the answer means, not by which code path wrote it.** `problem`
  is `failed` + `rejected`: they differ in who said no, which the row shows, but not in what
  is now owed. `skipped` absorbs `received` so a row stuck mid-flight is still findable.
- **A resolved row renders differently, because it has to.** `_finish` clears
  `review_payload` on every terminal transition, so a posted document has no amount, no date
  and no line count — showing `0.00` would be a wrong number, not a missing one. Those rows
  show the JV they became and who posted it, or the reason they did not, read off the ledger
  columns that are kept for ever. They are also not clickable: there is nothing left to open.
- **Zero counts are shown, not hidden.** A count that disappears makes the strip reflow as
  documents resolve, and "0" is itself the answer to "did anything fail?".
- The heading still counts what needs a **human**, from `counts.review`, not what the current
  tab happens to show — someone reading Skipped still wants to know if anything is owed.
- An empty Posted tab says "nothing here yet", never "you are all caught up": those are
  different claims and the second must not borrow the first's tick.
- Tabs are hidden entirely from a BU with no mail at all — four zeroes above an explanation of
  what the feature is would be scaffolding, not navigation.

`13:25` **Fixed a test-isolation defect the tabs exposed.** The HTTP rate limiter is an
in-memory sliding window keyed per IP, and every `TestClient` request arrives from the same
one — so the count accumulated across the whole session and the `default` bucket (120/60s)
popped once the suite grew past it. Five new requests were enough to start failing five
*unrelated* tests with 429. Each test now gets its own client IP, patched at
`get_client_ip` rather than by reaching into the middleware's instance state.
