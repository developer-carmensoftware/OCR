# 2026-07-15

## `09:00` Pre-beta hardening: money-path races, billing correctness, dead alerting

Full-system audit ahead of opening the beta to real users (target: tens of BUs, up
to ~100). Three parallel passes — backend core, frontend flows, infra/DB/config —
then fixes for everything that could corrupt money, duplicate an ERP posting, or
fail silently under concurrency. Branch: `feature/beta-hardening`.

**Uncommitted / needs operator action before beta** — see the bottom section.

### Backend — money & integrity

- `09:00` **`routers/credits.py` `upload_slip` — double credit grant (race).** The
  order was fetched and status-checked with **no row lock**, then written
  unconditionally. An admin `approve_order` landing between that read and write
  (it locks, grants credits, sets `PAID`) was silently reverted to `IN_PROGRESS`
  by the slip write — making the order decidable again, so a second approve
  **granted the credits twice**. Now re-reads under `FOR UPDATE` and re-checks
  `_OPEN_STATUSES` before mutating. The lock is taken *after* the FileService
  upload, so it's held only briefly. (`cancel_order` already did this.)
- `09:00` **`routers/ocr.py` — one credit charged for a whole multi-file batch.**
  `consume_document()` ran once per *request* while each file got its own task and
  its own vision-LLM call: 30 receipts in one POST cost **1** document. Now
  `consume_document(increment=len(file_data))`, and failures refund exactly the
  files that failed (`refund_document(charged, increment=len(errors))`) instead of
  only refunding when *every* file failed. Verified `consume_document` draws all N
  from a single tier (all-or-nothing per tier), so the per-tier refund is exact.
- `09:00` **`routers/ocr.py` — new `MAX_FILES_PER_EXTRACT = 10`** → 422 before any
  file is read or charged. `files: list[UploadFile]` was unbounded and every file
  is read fully into memory: N×20 MB on a 512 MB instance was an OOM vector as well
  as a billing surprise.
- `09:00` **`services/ap_invoice_service.py` — the 10-page LLM cap was bypassable.**
  Only the explicit-`selected_pages` path enforced `MAX_PAGES_PER_CALL`; with no
  selection, `normalize_pdf_for_llm` returned unencrypted PDFs **untouched**, so a
  100-page upload went to the vision LLM whole (10–100× token cost, likely
  context-overflow failure, 120s-held task). The no-selection path now checks the
  page count and truncates to the first `MAX_PAGES_PER_CALL` pages via the existing
  native-fidelity `extract_pages_as_pdf`, matching the invariant `utils/pages.py`
  already documented.
- `09:00` **`routers/carmen.py` `proxy_gljv` — no duplicate guard at submit.** The
  documented dedup key `(tenant_id, bank_code, doc_no, submitted_at IS NOT NULL)`
  was only an advisory `SELECT` at *extract* time (TOCTOU); the submit endpoint
  posted to Carmen with no check at all, so a double-click / retry / second draft
  of the same `doc_no` created **duplicate JVs in the ERP**. Now, before posting:
  the card row is locked `FOR UPDATE` and held through the post + `submitted_at`
  stamp (serialising concurrent same-card submits), rejecting with the existing
  `DuplicateDocumentError` → **409** if (a) this card was already submitted, or
  (b) another submitted card shares `(tenant, bank_code, doc_no)`. A malformed /
  cross-tenant / absent `credit_card_id` keeps the legacy no-guard behaviour.
- `09:00` **`services/credit_service.py` `topup_order` — unlocked read-then-grant.**
  Plain `SELECT` + `status == PAID` check + grant: two concurrent top-ups, or a
  top-up racing an approve, could both pass and credit twice. Now `.with_for_update()`.
- `09:00` **`services/credit_order_service.py` `post_ar_batch` — commit per order.**
  A single batch-end commit held every order's `FOR UPDATE` lock across every Carmen
  HTTP round-trip, and a commit failing *after* Carmen accepted a post left the order
  `PAID`, so a retry **re-posted a duplicate AR entry**. Each order now commits
  immediately after its own outcome. (`routers/admin/credits.py`'s trailing commit is
  now a harmless no-op safety net.)

### Backend — tenancy & disclosure

- `09:00` **Fail-closed tenant filters.** `services/ocr_service.py:get_all_tasks` and
  `services/correction_service.py:get_correction_hints` applied the tenant filter
  **conditionally** (`if tenant_id:`), so an empty tenant context returned *all
  tenants'* tasks / pooled every tenant's correction stats. Both now return empty
  when there is no tenant context.
- `09:00` **`routers/admin/usage.py` `tenant_ranking` ignored admin scope** — it ranks
  tenants against each other and handed a tenant-scoped admin every other tenant's
  error rate / latency / cost / volume. Now funnels through `_resolve_tenant` like
  its siblings; `usage_analytics_service.get_tenant_ranking` gained a `tenant_id`
  filter applied to both metric branches.
- `09:00` **Removed the MFA stub** (`routers/admin/auth.py`). `/auth/mfa/verify`
  returned success **without checking any TOTP**, never re-issued the token, and
  nothing ever inspected `mfa_passed` (it defaults to `True`) — so an MFA-enabled
  admin's login token was already fully authorised and the whole flow was theatre.
  Deferred honestly instead: endpoint deleted, `mfa_required` always `False`. The
  `mfa_secret` column stays for a real implementation later.
- `09:00` `exceptions.py`: `InsufficientCredits` said "Monthly free document quota"
  for what is a one-time **lifetime** 30-doc trial. (Subscription-tier "monthly"
  copy elsewhere is accurate and untouched.)

### Frontend

- `09:00` **`hooks/credit-card/useOcrSubmission.ts` — "Saved Successfully" on a failed
  submit.** A network drop / early 5xx set `carmenError` but not `carmenRejected`, so
  the flow fell into the *"Saved Successfully (Carmen issue)" — "has been saved to the
  database"* modal and advanced to Step 4, while an error toast fired at the same
  time. Nothing was saved: the DB write is Carmen-post-submit bookkeeping that only
  runs on success. Now a distinct `carmenFailed` path shows an honest **"Submission
  failed"** error modal ("may not have been saved — check Carmen before retrying to
  avoid a duplicate"), stays on Step 3, and does not advance.
- `09:00` `lib/api/carmen.ts`: `submitToCarmen` tags a 409 with
  `code = 'DUPLICATE_DOC_NO'` and `useOcrSubmission` re-throws it to the existing
  duplicate modal — that branch was **dead code** until now, because `submitToCarmen`
  threw a bare `Error` with no `.code`. Pairs with the backend 409 guard above.
- `09:00` `useOcrSubmission.ts`: double-submit guard via a **ref**, not the
  `submitting` state — state updates are async, so two clicks in one tick both read
  the old value and both post; `submitToCarmen` is not idempotent.
- `09:00` **`hooks/ap-invoice/useAPExtraction.ts` — auto-retry could double-charge.**
  `_fetchExtractWithRetry` re-POSTed `/extract` up to 3× on network drops and 5xx.
  A *failed* extraction is refunded server-side, but a response lost after a
  *successful* one is not — and the client cannot tell those apart — so a retry paid
  twice for one document (and re-ran the LLM). Retry removed (`_fetchExtract`),
  matching the credit-card path, which never retried. A 5xx now surfaces an honest
  "Server Error" modal instead of *"Could not read this invoice — try a clearer
  scan"*, which blamed the user's file for a server fault.
- `09:00` `components/pricing/CheckoutFlow.tsx`: **slip upload failed silently** in the
  money path — `submitSlip` re-throws, but `handleSlip` had no catch and `SlipUpload`
  swallows it, so the spinner just stopped with zero feedback. Now toasts the real
  server message (which also surfaces the "order already voided" 409). Reads the
  thrown error, not `c.error` — that state is stale in the same tick (the same bug
  `handleConfirm` has). New `checkout.slipError` key (EN + TH).
- `09:00` `components/admin/OrderWorkspace.tsx`: the proforma fetch's
  `.catch(() => {})` left the document column showing a **loading skeleton forever**
  with no way to tell "loading" from "failed". Added `docsErr` to the reducer
  (mirroring the existing `slipErr`) + `orev.doc.errFallback` (EN + TH).
- `09:00` `hooks/ap-invoice/useAPValidation.ts`: **"Adjust" wrote tax onto a
  non-taxable row.** With a header tax target > 0 and no line where `taxPct > 0`, the
  diff landed on the last row — whose `taxType` says it carries no tax — producing an
  internally inconsistent row that could post to Carmen. Now returns the rows
  untouched (the existing no-op convention), leaving the reconciliation banner up as
  the honest signal that the tax profile needs fixing first.
- `09:00` `main.tsx`: **SSO token could reach Sentry.** The one-time token arrives in
  the URL hash and is only stripped later inside a React effect, so the pageload
  transaction / breadcrumbs could carry it off-site. It can't be stripped before
  `Sentry.init` (the effect still needs to read it), so `beforeSend` +
  `beforeSendTransaction` now redact `token=…` from URLs, transaction names and
  navigation breadcrumbs.
- `09:00` `components/common/UserConsentModal.tsx`: initialised its own language to
  `'en'` regardless of the app language — a Thai user met the PDPA consent form in
  English. Now seeds from `useT().lang`; the in-modal toggle still overrides.

## Known / deferred (tracked, not fixed this round)

- Wizard state is lost on refresh or a mid-wizard 401, re-consuming a credit (checkout
  already persists to sessionStorage; the wizards don't). Mitigated by the 8h session TTL.
- `audit_logs` / `outbound_call_logs` buffer up to 10s in memory (`lifecycle.py`) — a hard
  kill or spin-down loses that window, which undercuts "tamper-evident" in the trust doc.
- `anomaly_alerts` has no notification channel (dashboard only); no watchdog on `job_runs`
  for a cron that stops firing, and none on `partman-maintain` (if partitions run out,
  `llm_usage_logs` inserts fail *silently* → cost tracking breaks invisibly).
- Non-constant-time master-key compare (`admin/deps.py:18,136`); 5xx typed-exception
  messages returned verbatim to clients (`factory.py:103-113`).
- `round2(1.005)` → `1.00` (binary half); `formatThb("1,234")` → `'0'`.
- 5 `react-hooks/exhaustive-deps` warnings in `useAPInvoice.ts` (stale-closure trap).
