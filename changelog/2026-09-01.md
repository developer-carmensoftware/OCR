# 2026-09-01

## One pagination control, and the reader picks the page size

`10:45` Every list in the app had its page size **measured off the viewport**
(`useFitRows`) rather than chosen. Two separate widgets rendered the result: `Pager` under
the five customer-facing lists, and DataTable's own inline block under the eleven admin
pages. Neither offered a "Rows per page" control, and on a 4K panel a table would fetch
40 rows nobody asked for.

Measuring also carried a live hazard. In server mode the measurement fed the fetch, and
the rows it asked for changed the space left below the table — 15 rows leave room that
measures as 17, 17 leave room that measures as 15 — so DataTable needed a monotonic
high-water guard to stop the tab fetching forever (shipped as a bug on 2026-08-24). A
number the reader picked cannot oscillate, so the guard and its regression test go too.

### Frontend

- **`Pager` is now the only pagination control**, and grows an optional `onLimitChange`:
  present renders `Rows per page: [15 ▼] 1–15 of 393 ‹ ›`, absent keeps today's bar. A
  native `<select>` over `[15, 25, 50, 100]` — 100 is the lowest backend cap among the
  lists that get it (`/credit-card/activity` and `/credits/orders` are both `le=100`), so
  no option can 422.
- **DataTable renders it too**, deleting its own 27-line block. Sixteen screens that had
  two pagination vocabularies now have one. An explicit `pageSize` (only
  `ExtractionsPage`'s nested table) still fixes the size and hides the control.
- **The choice is remembered** — new `hooks/useRowsPerPage.ts`, one global
  `localStorage['rowsPerPage']`. Deliberately **not** `appKey()`: like `theme` and `lang`
  it is a UI preference, not tenant-scoped business data, so it survives logout and is
  never wiped. `useTableQuery` seeds its default from it *synchronously*, so an admin
  table's first fetch already asks for the right size instead of fetching 25 then 50.
- **Visibility rule changed** from `total <= limit` to `total <= 15`: at 20 rows the
  arrows are dead but "show me 15" is still a real choice.
- **A page turn keeps its rows.** Skeletons now render only when there is nothing to keep
  (`loading && rows.length === 0`); otherwise the table carries `aria-busy` and dims.
  Every arrow click used to blank the table and repaint it.
- **Deleted**: `hooks/useFitRows.ts` + its two test files, and
  `DataTable.fetchloop.test.tsx` — the loop it guarded against cannot occur any more.
- `common.rowsPerPage` added (EN + TH); `admin.common.table.range` / `.prev` / `.next`
  removed with the block that used them.

### Frontend — one fewer request per page turn

- **`useReviewQueue` no longer refetches the review status on every page turn.**
  `Promise.all([getReviewStatus(), listActivity(…)])` ran on `[filter, limit, offset,
  nonce]`, so each arrow click cost two round trips and one of them could not possibly
  return anything new — status is configuration (`enabled` / `entitled` /
  `ingest_address` / `blockers`), not content. Split into two effects: config on `[nonce]`,
  content on `[filter, limit, offset, nonce]`.
- The property its docstring guards is preserved: `loading` stays true until status has
  landed, so the "not set up" screen still cannot flash on a BU with documents waiting.
  Each call keeps its own error flag now, ORed — otherwise a list success would clear a
  status failure and the page would paint a state it could not actually determine.

### Backend

None. Every endpoint already answers the `Page<T>` envelope and takes `limit`/`offset`.
Noted but not touched: `credit_card_activity.list_activity` fetches `limit + offset` rows
from *each* of its two sources before merging in Python, so limit=100 at offset 300 reads
400 per side. It already carries a `ponytail:` comment pointing at a `UNION ALL` if a BU
ever pages that deep; at 342 rows in the largest business table it stays cheap.
