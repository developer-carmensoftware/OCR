## `04:05` — Planning: KBANK settlement AR-reconciliation redesign

Collapsed the KBANK settlement flow from two documents / two JVs (settlement report +
encrypted e-tax invoice, per FRD §6.1) down to one: the settlement report
(`KB1P554V2_SUM_*`) has a complete, unencrypted text layer and carries every figure both
halves needed. Verified against a real sample zip (`E-TAX_INVOICE_CARD_*` confirmed
`NEEDS_PASS 1`; `KB1P554V2_SUM_*` confirmed readable, three-way self-consistent). Broke the
redesign into 8 tracer-bullet tickets and recorded them locally pending tracker choice
(Jira, held on authorization).

- Tickets: `.scratch/kbank-settlement-jv/issues/01`–`08` — CSV sidecar ingestion
  (`TAX_SUMMARY_BY_TAX_ID_CSV_*`, never charged/ledgered), the double-booking guard
  (`covered_by_settlement_jv`), the combined-JV arithmetic (three fixed debit legs read
  from the report's own total row, replacing the derived control leg in
  `ar_reconcile_jv.py`), the TIN second factor (feeds the CSV's TIN into the existing
  `foreign_tax_id` check), the CSV/report figure cross-check (warnings, not hard stops),
  the settlement JV's own input-tax posting (reuses `cc_input_tax.build_input_tax_payload`
  unchanged), review-flag/settings-screen cleanup, and — last, gated on everything above
  shipping — a deterministic PyMuPDF text-layer parser for KBANK settlements (vision call
  kept as fallback for a scanned copy).
- Decisions: combined JV only, no 1-vs-2-JV toggle (`debit_dept_code`/`debit_account_code`
  columns kept unread so the split shape could return without a migration); FRD §6.1 to be
  amended (v1.2) rather than treated as fixed, recorded as decision #28 in
  `docs/email-automation/06-decision-log.md`; the settlement JV files its own input-tax
  record now that the e-tax invoice stops being processed; continuing on
  `feat/detailed-cc-ar-reconciliation` rather than a fresh branch; email-ingest-only, no
  wizard path for settlement reports.
- Net effect once shipped: 2 credits / up to 2 reviews per settlement day → 1 credit / up
  to 1 review.

## `04:43` — Docs: record the filename-version single point of failure as a known risk

No code change. User flagged (correctly) that `KB1P554V2` — the pattern the KBANK
settlement rule matches on — is the settlement report's *program version number*
(`REPORT NO. KB1P554V2` on the page), not a permanent bank identifier, and asked why
reading only that one file is safe. It's safe for bank *identification* (routing was
always rule-based, never content-based, even before this branch), but the collapse to one
document in ticket 03 does introduce a real regression: v1.1's two-document shape degraded
gracefully if the settlement report's filename pattern ever broke (the fee invoice's own
rule would keep the commission JV posting); v1.2 has no fallback, so a version bump on
KBank's side (`KB1P554V3`) would silently stop every JV for that BU, via `no_rule_match`,
which is deliberately outside `NOTIFIABLE_SKIPS`.

- `docs/email-automation/06-decision-log.md` #28 — added a "Known risk" section: the
  mechanism, why it compounds with ticket 02's static `enabled`-flag guard (silently
  skips the fee-invoice fallback too, on the same non-alerting path), and the two
  mitigations considered (broaden the rule to `_SUM_`, version-agnostic; vs. scope it to
  `_SUM_<merchant id>_`, rejected — doesn't scale to a BU with multiple properties, one
  rule per merchant ID, one more silent-drop point per property).
- `.scratch/kbank-settlement-jv/issues/02-double-booking-guard.md` — added the same note
  as a build constraint: ship either a freshness check (not a static toggle) or pair the
  static-flag version with an alert; explicitly do not ship the static flag with no
  alerting.
- Deliberately not fixed yet, per explicit instruction — recorded so it's a documented
  decision, not a gap discovered later.
