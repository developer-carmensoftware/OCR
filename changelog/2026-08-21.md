# 2026-08-21

## Uncommitted / in progress

### Backend

- `15:39` **Unbounded list endpoints now page.** New `app/utils/pagination.py::paginate()`
  and a shared `Page[T]` envelope (`models/schemas/common.py`) so every list endpoint
  answers the same `{total, limit, offset, data}` shape — converging the three that grew
  organically (`{total, data}`, `{count, has_more, data}`, `{total, tasks}`).
  `total` is counted off the *unlimited* statement, with `ORDER BY` stripped so Postgres
  doesn't sort rows it only tallies.
  - `GET /api/v1/notifications` — `limit`/`offset` (default 8, cap 50). `unread_count`
    still spans every row, not the window; the bell's badge would be wrong otherwise.
  - `GET /api/v1/credits/orders` — `limit`/`offset` (default 8, cap 100) + `open_only`,
    replacing the flat `LIMIT 100`. A boolean rather than a raw `status` filter: the only
    split the UI makes is open-vs-settled, and `_OPEN_STATUSES` lives server-side.
  - Response shape changed on both (bare array → envelope) — frontend updated in the
    same commit.
  - Tests: new `tests/unit/test_pagination.py` (3 — total ≠ page size, no LIMIT/ORDER BY
    inside the COUNT, window preserved on the row query), plus notification-service and
    `/orders` cases for the total/unread/out-of-range behaviour.

### Frontend

- `16:20` **Page size is measured, not decided.** The 8-per-page constant is gone.
  New `hooks/useFitRows.ts` measures a rendered row and the list's own gap, then fits
  as many as the space allows — the bell panel's scroll box, and for the orders page
  whatever is left between the list's top and the bottom of the window (minus the
  pager, measured off the sibling rather than guessed). Re-measures on resize via
  `ResizeObserver`. Returns a **callback ref**: these lists mount and unmount (a
  dropdown panel, a skeleton swapped for real rows) and a plain ref never re-runs the
  measurement. Both call sites clamp to the backend's own limit (50 / 100).
  Chicken-and-egg is handled by pointing the ref at the skeleton list too, so the
  count is right before the first page lands. Tests: `useFitRows.test.ts` (5 — the
  scroll-container box, the gap belonging to every row but the last, the
  window-bounded branch, the never-zero floor), plus a `useNotifications` case that
  the window refetches when the measurement changes. `ResizeObserver` stubbed in
  `test/setup.ts` (jsdom ships none).

- `15:39` **Both paged lists get real prev/next, not a growing list.**
  - New shared `components/common/Pager.tsx` (+ `styles/components/pager.css`):
    `‹  1–8 of 30  ›`, renders nothing when everything fits on one page. ponytail —
    no numbered page buttons; two arrows and a range stay one line at any total,
    numbered pages need ellipsis logic the moment there are more than a handful.
  - Bell: `offset` state, pager sits outside the scrolling list so the arrows stay put.
    The release-note row pins to **page 1 only** (on page 3 it would read as a third
    release) while still counting toward the badge, which is global.
  - Order history: open orders and settled history are now two server-side lists.
    The pending banner must show **every** open order — an `on_hold` one from three
    weeks ago still needs the customer to act, and would fall off a page of
    newest-first rows — while the settled history is the half that pages.
    `Pricing.tsx` and `OrderHistory.tsx` stop re-deriving the split client-side.
  - Known ceiling (`ponytail:` comments on both hooks): offset paging, so a row
    arriving while the reader sits on page 2 shifts what page 2 holds. Also, an
    approve/reject reached while the reader is on settled page 3 skips its in-page
    toast — the row is not in the fetched window. The bell still notifies.
  - New `lib/api/page.ts` mirrors the backend envelope.
  - Files: `lib/api/{page,credits,notifications}.ts`, `hooks/credits/useOrderHistory.ts`,
