### `17:30` — First end-to-end run of the ingest pipeline, and one gap it exposed

pilot's variable names (`EMAIL_INGEST_MAILBOX`/`_APP_PASSWORD`, which nothing reads any
more) to the ones `config.py` actually binds — `IMAP_HOST`/`_USER`/`_PASSWORD`/`_FOLDER`,
`EMAIL_INGEST_ADDRESS`, `CARMEN_DEV_TOKEN`. Migration `20260803000000` pushed after
dropping a stale `email_documents` left over from the pilot: it predated the migration
system entirely (never in `supabase migration list`), used the approval-flow schema
(`rule_id`, `suggestion`, `posted_by`, `rejected_at`), and held 6 rows of test data. The
unique index on `(tenant_id, message_id, attachment)` cannot be created against a table
whose column is `attachment_name`, which is how it surfaced.

`dev.carmen4.com/carmencloud` configured through the real `PUT /carmen/settings` path
(API key auth), which allocated ingest tag `35faa453`.

**Result — every stage before posting is verified against a real KTC document:** IMAP
fetch → tag→tenant → dedupe claim → file open → quota + credit charge → LLM extract →
tax-ID gate → GL mapping → JV rows. It stops at `carmen_rejected` / "No Carmen posting
credential", which is the expected wall until §4 is answered. The tax-ID gate was
exercised **in both directions** — a deliberately wrong tax ID produced
`tax_id_mismatch`, the document's real one passed.

**Gap found and fixed:** `_finish` was only passed `bank_code`/`doc_no` on the success
path, so every *failed* row recorded `NULL` for both even when extraction had already
resolved them. That silently disables the one early warning the design has for a bank
changing its form ("one BU failing is a bad document, several BUs failing on the same
issuer at once is a form change" — `2026-08-03 13:20`): it cannot be computed without
`bank_code` on failures. Both are now hoisted above the `try` and passed on all three
failure paths. Verified by the ledger itself — the row before the fix reads
`(None, None)`, the row after reads `(KTC, 55-2569-05-01-000058)`.

### `18:30` — All eight banks through one tenant: multi-rule works, two real problems surface

The question being tested was whether a single BU can carry settings for several banks at
once. It can: **8 rules and 5 tax IDs on one tenant**, written and read back through
`PUT/GET /carmen/settings`, then all eight sample documents ingested in one poll.

**Every document cleared the tax-ID gate and every bank was identified correctly.** The
five tax IDs are five different legal entities across the eight documents (BBL+SCB share
one, KTC+PAYPAL another, GHL+SIAMPAY a third), so this exercised the list properly rather
than matching one number eight times.

| Document | detected | doc_no | outcome |
| --- | --- | --- | --- |
| KTC | `KTC` | 55-2569-05-01-000058 | `carmen_rejected` — cleared everything, token is the only wall |
| SIAMPAY | `SIAMPAY` | RE2026-05269 | `carmen_rejected` — same; its item codes were already mapped |
| KBANK | `KBANK` | 311225E00032857 | `duplicate_document` — **correct**, that doc was really submitted on 2026-07-29 |
| BBL | `BBL` | 26079-0001954 | `mapping_incomplete`: `002205903321` |
| SCB | `SCB` | 262302202523 | `mapping_incomplete`: VSA-INT-P, VSA-INT, MCA-INT-P, MCA-INT |
| BAY | `BAY` | 26S-0778187 | `mapping_incomplete`: VISA, V-PLAT & INF, M-PREMIUM |
| PAYPAL | `PAYPAL` | TH260505V0000256 | `mapping_incomplete`: Online Payment Services |
| GHL | `GHL` | M202605-057161 | `mapping_incomplete`: `TRANSACTION FEE 30-05-2026` |

Most of the `mapping_incomplete` results are the system working: those are real card types
the BU has never mapped, and mapping each once makes every later document deterministic.
BBL's `002205903321` looks wrong but is not — `bbl.py` deliberately maps the
`หมายเลขร้านค้า` column to `transaction` because its per-row values are terminal IDs, which
are stable per terminal.

**Problem 1 — GHL's payment type contains a date, so it can never be mapped.** The line
description is `TRANSACTION FEE 30-05-2026`, and `ghl.py` maps the line description to
`transaction`. Next month's invoice reads `TRANSACTION FEE 30-06-2026`, which is a
different key. `unmapped_payment_types` will therefore park **every GHL document forever**,
no matter how many times the customer maps one. Email automation cannot work for GHL until
the date is stripped from the key (the mapping key should be the fee *kind*, not the fee
*instance*). Worth checking whether any other issuer embeds a date or invoice number the
same way — this only became visible because a real document was run end to end.

**Problem 2 — a transient LLM truncation permanently kills a document.** GHL failed the
first run with `unreadable_document`; the log shows the model's JSON was cut mid-string
(`Unterminated string ... line 2 column 24`) inside a long Thai company name. Re-sending
the identical file extracted it cleanly. So **1 of 8 documents hit a transient failure on
the first attempt**, and with `ponytail: single pass, no retry` at the top of the ingest
service that document was marked `failed` for good — credit correctly refunded, but the
document silently lost. This is the case `2026-08-03 13:20` explicitly wanted separated
from permanent ones ("a retry costs a credit when it burned real tokens… permanent
failures must fail immediately"). The reason codes already distinguish them; what is
missing is a sweep that retries the transient ones.

### `18:10` — A misread payment type no longer parks a document the BU already mapped

Two different problems were hiding behind "the mapping didn't match", and only one of
them is blocked on Carmen:

| | needs | blocked by §4? |
| --- | --- | --- |
| payment type genuinely never mapped | chart of accounts from Carmen | **yes** — `suggest_payment_types(payment_types, accounts, departments, …)` takes both lists, and `get_account_codes`/`get_departments` each need a Carmen token |
| type already mapped, but the extractor dropped a Thai vowel mark | nothing but the BU's own saved keys | **no** |

The second is fixed here. `canonical_payment_type()` in `cc_jv.py` retries a failed exact
lookup against a folded form — Unicode `Mn` marks (Thai vowels/tones are separate
combining code points), whitespace and case removed — and both `unmapped_payment_types`
and `build_jv_rows` now resolve through it. The canonical key is also what reaches the JV
description, so the BU's own curated wording lands in their books rather than the misread.

**Deliberately not a similarity score.** This tenant really has
`04-4100-03 SiamPay Service - Processing Fee` and `04-4100-04 SiamPay Service -
Transaction Fe`. A new `04-4100-05 …` type scores **0.977** against the `-03` key, and
`difflib.get_close_matches(cutoff=0.8)` returns it — silently posting a brand-new payment
type to someone else's GL account. Folding never touches digits or letters, so that case
still parks. Ambiguity is not guessed either: if the folded form matches more than one
saved key the original is returned and the document parks, because parking is the
recoverable direction on a money path. `test_cc_jv.py` pins all of it, including the
0.977 case as its own test.

Verified live, not just in unit tests: the saved key in the DB was temporarily de-voweled
to `คาบรการ Merchant Discount Rate (MDR)` while the extractor read the document correctly
as `ค่าบริการ …`. The run cleared mapping and reached `carmen_rejected` instead of
`mapping_incomplete`. Key restored afterwards.

**Still open, and worth stating plainly:** a genuinely new payment type is charged,
refunded, marked `failed`, and nothing tells the customer. There is no `awaiting_mapping`
state (status is only `received|posted|failed|skipped`), no retry (`ponytail: single pass`
at the top of the ingest service), and no notification — so the document simply goes
quiet and the customer must notice, map it, and forward the mail again. The contract's §4
"confirm the rule once at next login" flow does not exist yet. Cheapest fix that removes
the silence is a notification naming the unmapped type, using the bell that already ships;
the suggest-then-confirm flow should wait until §4 says which side owns the screen.

**Test-environment note worth keeping:** the ingest mailbox is a personal Gmail with ~10k
unread, and the poller marks everything it fetches `\Seen`, so pointing it at `INBOX`
chews the owner's real backlog 20 at a time without ever reaching the test mail. Fixed by
polling a dedicated label (`IMAP_FOLDER=ocr-test`) and **writing test mail into it with
IMAP `APPEND` rather than SMTP**. A Gmail filter cannot do this job: mail sent from an
account to itself skips the inbound delivery pipeline (the received copy carries no
`Delivered-To` header, unlike genuine inbound mail), and filters run on that pipeline —
so no filter rule, wildcard or literal, will ever match self-sent test mail. Helper:
`send_test_mail.py` (scratchpad, not committed).

### `16:10` — The two credentials, finally named separately (closes Q3 + Q4)

"Auth key" had been one word covering two unrelated things, which is why the question kept
going in circles. They are:

| | **Key 1 — Settings** | **Key 2 — JV posting** |
| --- | --- | --- |
| Issued by | **us**, to Carmen | **Carmen**, to us |
| Used for | Carmen calls our API to store a BU's settings | we call Carmen's API to post a JV |
| Blocked on anything? | **no** — entirely ours to issue | **yes** — see below |

**Key 1: we issue one API key + HMAC signing, and that closes Q4.** Stored the same way
`secure_configs` already stores secrets. Nothing to negotiate, nothing to wait for; the
message to the Carmen team is just "here is the key, send it with your requests".

An alternative was considered and dropped: reuse the logged-in user's Carmen token via the
existing `/auth/exchange` path, so no new secret exists anywhere. It works — the settings
screen always has a human in front of it — but it is more moving parts for both sides than
issuing one key. Recorded because it is the fallback if Carmen would rather not hold a key
of ours.

Either way **the settings screens stay on Carmen's side**; we are only the store, and every
write carries who changed it.

**Key 2: ask for it to not exist.** The proposal is that **Carmen pulls finished documents
from us and posts them internally**, on their own schedule. No credential leaves either
side, and it sidesteps what killed the previous proposal.

That previous proposal — Carmen creates one ordinary `ocr-integration@` user per host — is
**dead**: every BU has a licensed user cap, so a service account is a purchase, not a
configuration change. Worth writing down because it is the kind of constraint that is
invisible from the code and would otherwise be re-proposed.

What this costs, stated up front so it is not discovered later:

- Carmen writes one scheduled job: fetch JSON from us → call the JV posting they already
  have → return the JV number. That number must come back; the read-back loop (E5) cannot
  be rebuilt retroactively without it.
- **The read side loses its background access too.** Mapping layer 2 (history) and E5 both
  read `spGetListJvBySource`, which needs a Carmen token. Mitigation without asking for
  anything: **snapshot the history whenever a real user session is already talking to
  Carmen** — the wizard does this today. A customer who only ever uses email automation and
  never logs in gets no snapshot, so layer 2 is unavailable and E5 does not run for them.
  That degrades to layer 1 (their own config), which is the main path anyway.

Upgrade path, in the contract: if Carmen can ever issue a machine credential that does
**not** consume a user seat, we move to posting directly and E5 becomes complete. Not a
prerequisite for starting.

### `15:30` — Ingest address: one mailbox, a `+tag` per tenant (closes Q2)

`ocr+<tag>@carmensoftware.com`. The customer never types it — Carmen shows it to copy,
through the `ingest_address` field the contract already has.

**It must be `+`, not `_`.** A separate mailbox per tenant means the mail admin creates each
one by hand against a cap of roughly 30 — which cannot serve 100 customers. Subaddressing
has no cap and needs no administration at all.

Consequences for routing:

- **The tag identifies the owner *before* the LLM is called.** Quota checks, per-tenant rate
  limits, and dropping junk mail all become free and happen at the front door instead of
  after we have paid for an extraction.
- **The TIN gate moves back to verification**, which is the job it is actually good at. A
  tag is guessable, so it decides *who to check against* and never *whether to trust*. Every
  TIN check in the plan stays exactly as it was.
- **Q5 (one tax ID spanning several BUs) stops being a blocker** — it now only matters in
  the fallback path where the `+tag` was stripped in transit. No `(bank, merchant code) →
  BU` table until a real case appears.

### `13:20` — Requirements captured in conversation

- **Quota exhausted mid-month → notify and stop.** Documents wait in the queue: not dropped,
  no credit charged. "Out of quota" must never count as a failed attempt, or five quiet days
  would kill a document that was never broken.
- **Alerts go to us only, never to the customer**, and only when something is abnormal. A
  daily digest of 300 successful documents is a digest nobody opens.
- **Users can fix a wrong JV themselves in Carmen after it posts.** This reframes the whole
  project: the goal is *make a mistake visible fast enough to fix*, not *prevent every
  mistake*. It is also why the read-back loop is worth building — the correction an
  accountant makes is the ground truth, for free, forever.
- **A retry costs a credit** when it burned real tokens, but is tied to an actual LLM call,
  not to claiming the work. Permanent failures (wrong PDF password, corrupt file) must fail
  immediately rather than being charged five times.
- **Zero total → do not post, do not charge.** We absorb that extraction's cost; it is
  cheaper than billing a customer for an empty JV.
- **No backfill mechanism needed** — forwarding only ever brings new documents; older ones
  go through manual upload.
- **We cannot know a bank changed its form unless the customer tells us.** The one available
  early warning is the shape of the failure: one customer failing is a bad document, several
  customers failing on the same issuer at once is a form change.
