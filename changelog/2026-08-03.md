### `16:10` — The two credentials, finally named separately (closes Q3 + Q4)

"Auth key" had been one word covering two unrelated things, which is why the question kept
going in circles. They are:

| | **Key 1 — Settings** | **Key 2 — JV posting** |
| --- | --- | --- |
| Issued by | **us**, to Carmen | **Carmen**, to us |
| Used for | Carmen calls our API to store a BU's settings | we call Carmen's API to post a JV |
| Blocked on anything? | **no** — entirely ours to issue | **yes** — see below |

**Key 1: we issue one API key + HMAC signing, and that closes Q4.** Stored the same way
`secure_configs` already stores secrets. Nothing to negotiate, nothing to wait for; the
message to the Carmen team is just "here is the key, send it with your requests".

An alternative was considered and dropped: reuse the logged-in user's Carmen token via the
existing `/auth/exchange` path, so no new secret exists anywhere. It works — the settings
screen always has a human in front of it — but it is more moving parts for both sides than
issuing one key. Recorded because it is the fallback if Carmen would rather not hold a key
of ours.

Either way **the settings screens stay on Carmen's side**; we are only the store, and every
write carries who changed it.

**Key 2: ask for it to not exist.** The proposal is that **Carmen pulls finished documents
from us and posts them internally**, on their own schedule. No credential leaves either
side, and it sidesteps what killed the previous proposal.

That previous proposal — Carmen creates one ordinary `ocr-integration@` user per host — is
**dead**: every BU has a licensed user cap, so a service account is a purchase, not a
configuration change. Worth writing down because it is the kind of constraint that is
invisible from the code and would otherwise be re-proposed.

What this costs, stated up front so it is not discovered later:

- Carmen writes one scheduled job: fetch JSON from us → call the JV posting they already
  have → return the JV number. That number must come back; the read-back loop (E5) cannot
  be rebuilt retroactively without it.
- **The read side loses its background access too.** Mapping layer 2 (history) and E5 both
  read `spGetListJvBySource`, which needs a Carmen token. Mitigation without asking for
  anything: **snapshot the history whenever a real user session is already talking to
  Carmen** — the wizard does this today. A customer who only ever uses email automation and
  never logs in gets no snapshot, so layer 2 is unavailable and E5 does not run for them.
  That degrades to layer 1 (their own config), which is the main path anyway.

Upgrade path, in the contract: if Carmen can ever issue a machine credential that does
**not** consume a user seat, we move to posting directly and E5 becomes complete. Not a
prerequisite for starting.

### `15:30` — Ingest address: one mailbox, a `+tag` per tenant (closes Q2)

`ocr+<tag>@carmensoftware.com`. The customer never types it — Carmen shows it to copy,
through the `ingest_address` field the contract already has.

**It must be `+`, not `_`.** A separate mailbox per tenant means the mail admin creates each
one by hand against a cap of roughly 30 — which cannot serve 100 customers. Subaddressing
has no cap and needs no administration at all.

Consequences for routing:

- **The tag identifies the owner *before* the LLM is called.** Quota checks, per-tenant rate
  limits, and dropping junk mail all become free and happen at the front door instead of
  after we have paid for an extraction.
- **The TIN gate moves back to verification**, which is the job it is actually good at. A
  tag is guessable, so it decides *who to check against* and never *whether to trust*. Every
  TIN check in the plan stays exactly as it was.
- **Q5 (one tax ID spanning several BUs) stops being a blocker** — it now only matters in
  the fallback path where the `+tag` was stripped in transit. No `(bank, merchant code) →
  BU` table until a real case appears.

### `14:00` — Eight real bank documents read end to end

Samples in `C:\Users\User\Desktop\document_format\`. This replaces guesses that had been
derived from the prompt files rather than from documents.

- **Every issuer tax ID matches `BANK_INFO` in the frontend constants, 8 for 8.** Two
  independent sources agreeing closes C2 — the negative-control list for the TIN gate is
  correct as written.
- **All eight carry a merchant/customer code**, which contradicts the prompts for KTC, GHL
  and SIAMPAY (they say `merchant_id: always null`). C7 now covers all eight, not a subset.
  GHL's `DA00001562` appears inside a line description and it is **not yet confirmed to be
  stable** across periods — one more invoice from the same customer settles it.
- **`สำนักงานใหญ่` is the tax branch on every document and is useless for routing a BU.**
  BBL prints it twice on one page, for the bank and for the merchant. KBANK is the only
  issuer with a real business branch field (`ชื่อสาขา`, e.g. สาขาภูเก็ต).
- **All eight are arithmetically self-consistent**: line items sum to the printed total, fee
  × 7% is the VAT, gross − fee − VAT is the net, fee × 3% is the WHT where present. This
  makes D-5 a plain arithmetic check with real coverage — no model checking another model's
  work.
- Dates are mixed: Buddhist year (`2569` on KTC and GHL), two-digit (`27/05/26`), and
  Gregorian. The date check has to be a plausible-range test, not a format match.

### `13:20` — Requirements captured in conversation

- **Quota exhausted mid-month → notify and stop.** Documents wait in the queue: not dropped,
  no credit charged. "Out of quota" must never count as a failed attempt, or five quiet days
  would kill a document that was never broken.
- **Alerts go to us only, never to the customer**, and only when something is abnormal. A
  daily digest of 300 successful documents is a digest nobody opens.
- **Users can fix a wrong JV themselves in Carmen after it posts.** This reframes the whole
  project: the goal is *make a mistake visible fast enough to fix*, not *prevent every
  mistake*. It is also why the read-back loop is worth building — the correction an
  accountant makes is the ground truth, for free, forever.
- **A retry costs a credit** when it burned real tokens, but is tied to an actual LLM call,
  not to claiming the work. Permanent failures (wrong PDF password, corrupt file) must fail
  immediately rather than being charged five times.
- **Zero total → do not post, do not charge.** We absorb that extraction's cost; it is
  cheaper than billing a customer for an empty JV.
- **No backfill mechanism needed** — forwarding only ever brings new documents; older ones
  go through manual upload.
- **We cannot know a bank changed its form unless the customer tells us.** The one available
  early warning is the shape of the failure: one customer failing is a bad document, several
  customers failing on the same issuer at once is a form change.
