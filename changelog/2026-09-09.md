## `reset_tenant_email.py --keep-settings` — the hand-it-to-a-tester reset

`10:55` The script had two depths of reset and neither was the one you want before handing a
BU to a tester. Default deletes `email_ingest_settings` (the tag is released, so the
customer's forwarding address changes and the Gmail handshake has to be redone);
`--keep-tag` keeps the tag but still disables the row and nulls the Carmen token, so the
tester's first job is re-enabling automation rather than testing it.

`--keep-settings` leaves that table entirely alone and clears only what *remembers a
document*: `email_documents`, `email_queue_seen`, the posted `credit_cards`, `\Seen`.
Automation stays on with its tag, token and handshake, so a forwarded mail flows on the next
poll with no setup first.

It also has to be a separate flag rather than a `--keep-tag` tweak: `--keep-tag` nulls
`enabled_at` deliberately (re-enabling stamps it to *now*, after which every replayed mail is
older than it and lands `ingest_paused`). `--keep-settings` never re-enables, so the existing
`enabled_at` — NULL on carmencloud — stays correct and the arrival filter in `_run_message`
stays inert.

**The verb and the SQL now come from one function.** A third case meant two parallel
three-way branches — the plan line printed before `--apply`, and the statement the
transaction runs — and that plan is the only thing an operator reads before agreeing to a
destructive run, so drift between them would print `keep` while deleting the row.
`_settings_plan()` returns both; `--self-check` (hidden flag, no DB, no args) asserts the
three pairs, including that `--keep-settings` wins over `--keep-tag` and that the disable
branch still nulls `enabled_at`.

Repo-root `scripts/` is outside CI's `ruff check app/ tests/`, so it was checked by hand
against `backend/pyproject.toml` — which also cleared a pre-existing 100-column overrun on
the settings print line.

## `11:24` Lite — a fourth subscription tier at 100 documents / ฿290

The catalog opened at Starter (200 docs / ฿490/mo), so a tenant leaving the 30-document
signup grant faced a 6.6× jump in volume as their first paid step. **Lite** closes that gap:
100 documents/month at ฿290, under the ฿300 a single hotel can approve without procurement.

Priced as a **subscription**, not a top-up, which is what keeps the ladder honest:

    Lite          100/mo   ฿290     ฿2.90/doc   ← new
    Starter       200/mo   ฿490     ฿2.45/doc
    Growth        500/mo   ฿990     ฿1.98/doc   Popular
    Professional 1500/mo   ฿2,490   ฿1.66/doc

More documents, cheaper per document — the rule the `≈ ฿X / doc` line on every card makes
visible. The same ฿290/100 as a *top-up* would have been ฿2.90/doc against `pack_small`'s
฿4.00/doc, so five 100-packs (฿1,450) would have beaten one 500-pack (฿2,000) for identical
credits. Nothing needed repricing.

Two invariants checked before shipping, both still hold:

- **Annual→monthly lock.** `credit_service.purchase_block_reason` rests on "the smallest
  annual price > the largest monthly price". Lite annual is ฿3,132 > Pro monthly ฿2,490. A
  cheaper tier is exactly what could have broken this.
- **Downgrade guard** ranks by `credits`, so Lite lands at the lowest rank automatically.

**No backend change.** `GET /credits/packs` is generic over `credit_packs`, `annual_price()`
derives ฿3,132 on read, and `usePricingCatalog` splits by `kind`. No new customer-facing
i18n keys either — `{name}` interpolates from `PLAN_META`.

### `12:02` The CTA at 4-up — three things the narrower card broke

Going 3-up → 4-up took each card from ~276px to ~203px (~160px of content), and three
elements had been sized for the old width. All three were found by looking at the rendered
page, not the code.

- `12:02` **The CTA label no longer fit.** `.plan-cta` was `white-space: nowrap`, so
  "Upgrade to Professional" (~165px against ~112px of room) was clipped by the card's
  `overflow: hidden`. The label was the problem, not the button: it restated the `<h3>` two
  lines above it. Visible text is now the action alone — `plan.ctaChoose` / `ctaUpgrade` /
  `ctaRenew` ("Upgrade plan"), EN + TH — and the tier-specific phrase moved to `aria-label`,
  so a screen reader moving button to button still hears four distinct actions instead of
  "Upgrade plan" four times. One line in both languages, no truncation, no two-line button.
- `12:02` `.plan-cta` — `min-height: 2.75rem` (WCAG 2.5.5 target size) pins all four CTAs to
  one height, which is what keeps the price row level; `padding-inline` 1.25rem → 0.75rem
  (the button is `width: 100%`, so the wider inline padding only squeezed the label). `nowrap`
  deliberately **not** restored: an over-long translation should wrap and be seen, not be
  clipped invisibly.
- `12:02` **`.plan-price-amount` was `clamp(1.5rem, 2.8vw, 2rem)`** — viewport-scaled type
  ignores the container, so at 4-up it still resolved to 2rem and "฿2,490" pushed "/ month"
  onto its own line, dropping Professional's price below the other three. Now a fixed
  `1.6rem` + `white-space: nowrap`, with `nowrap` on `.plan-price-period` too. Fixed rem over
  clamp is also what the product register asks for; fluid type is a brand-surface device.
- `12:02` **"Upgrade to Lite" was a lie.** The label branched on *"is there an active plan"*,
  never on direction, so any smaller tier was announced as an upgrade. Starter was the only
  tier below Growth/Pro before, so it stayed rare; a tier below Starter puts it on every
  subscriber's first card. Added `plan.ctaDowngrade` / `plan.downgrade` and a real
  `isDowngrade` branch, so the disabled card now reads **Downgrade** and its tooltip says
  when that becomes possible.
- `12:02` The downgrade reason moved from a visible line to a **hover tip on a wrapper**.
  It cannot sit on the button: `.btn:disabled` sets `pointer-events: none`, and browsers
  suppress `title` on disabled controls either way. It cannot be a visible line either —
  one taller card desyncs the price row, which is the bug above in a different costume.
  `.plan-cta-tip` carries the `title`; an `.sr-only` span (`position: absolute`, zero layout
  cost) plus `aria-describedby` carries the same sentence to assistive tech.
- `12:02` **`PlanCard.test.tsx` is new** — 5 tests over the downgrade state and the label

## `15:40` Detailed Credit Card AR Reconciliation — the other half of the settlement pair

FRD v1.1 asks for the lump credit-card control account to be split into per-scheme
receivables when KBANK's merchant settlement report (`KB1P554V2_SUM_*.pdf`) arrives by
email. **The JV is the second half of a pair**, and reading that backwards was the most
expensive mistake available: `credit_card_ocr` already posts the settlement's cash side
(`Cr. 1021000` lump, `Dr.` bank / commission / input tax), and this one posts
`Dr. 1021000` — clearing that lump — with `Cr.` one line per card scheme. The two share a
tax invoice number on purpose; neither is a duplicate of the other.

On the sample report (settlement 21/07/2026, Σ THB AMT 25,091.00):

    Detail    Dr 1021000  25,091.00   Cr ×7   VS INTER NON-PREM … JCB PREM
    Summary   Dr 1021000  25,091.00   Cr ×3   VS 15,471.00 · MC 9,320.00 · JCB 300.00

### The FRD is written against Carmen's codebase, not this one

§5's DDL is MySQL (`AUTO_INCREMENT`, `ENUM`, `property_id`) over tables named `carmen_*`,
writing `gl_jv_header` / `gl_jv_detail` directly. This app cannot write `gl_jv_*` — it posts
through Carmen's `/gljv` endpoint — so the two settings tables are re-homed to Postgres keyed
by `tenant_id`, and `carmen_ar_ingestion_logs` is **dropped**: it would duplicate
`email_documents` and `ocr_tasks`, which already record every read and its outcome.

Two more things it asks for turned out to exist already. `carmen_ar_reconcile_mapping` is the
shape of a table we have (payment type → dept + account), and the "เปิดตัวจัดการ Mapping"
modal on FRD page 10 **is a screenshot of `PaymentTypeModal.tsx`** — "Required for this scan:
N items", "(11/11 mapped)", "Show additional mappings". Its row moved to
`components/common/MappingRow.tsx` and now serves three callers instead of two copies.

### `credit_cards.doc_type` — the bug that would have shipped

`has_submitted_doc` keys on `(tenant_id, doc_no, doc_date)`. The settlement report's
`TAX INVOICE NUMBER` (`210726E00035291` on the sample) is the number printed on KBANK's
commission tax invoice, which the wizard has always posted as `doc_no`. Same tenant, same
date: whichever arrived second would have been refused as a copy of the first, on a money
path, silently. `doc_type` (`fee_invoice` default, backfilled) joins the key at both call
sites. It is also why `bank_code` is still *not* in that key — the opposite fix for the
opposite failure, now documented together on `CreditCard`.

### The `unbalanced` flag was wrong for this document — found by a failing test

`_review_flags` asserts `gross = commission + tax + net` per line, which every layout
satisfied until this one: the settlement report prints THB AMT per payment type and leaves
VAT AMT and NET AMT as dashes, so the identity is false for **every** row and a clean document
parked with `unbalanced`. The flag now takes the same question asked the right way for this
shape — `is_balanced` over the built JV rows — so it still means one thing to the reader and
to the auto-post gate, which are deliberately one predicate.
