## `12:05` Frontend — notification panel is a full-width sheet on phones

The bell's dropdown ran out of frame on mobile. Two causes, both in the panel (the trigger
was fine):

1. `NotificationBell` set the panel's horizontal position as an **inline** `right`, and inline
   style beats every media query — so the panel's mobile layout was unfixable from CSS.
2. `max-height: min(72vh, 30rem)` — on mobile browsers `vh` is the *large* viewport, so the
   bottom rows of the list sat under the collapsing URL bar with no way to reach them.

- [`frontend/src/components/common/NotificationBell.tsx`](../frontend/src/components/common/NotificationBell.tsx)
  — the `useLayoutEffect` anchor now sets `right` only above 480px; below that only `top`
  (the vertical anchor is still accurate) and CSS owns left/right.
- [`frontend/src/styles/components/notification-bell.css`](../frontend/src/styles/components/notification-bell.css)
  — `vh` → `dvh`; new `max-width: 480px` block turns the panel into a full-width sheet on the
  same `0.75rem` gutter as `.app-container`, height bounded by
  `calc(100dvh - var(--header-bottom) - 0.75rem)` so it can't overrun a landscape viewport.
- Two tests in `NotificationBell.test.tsx` pin the breakpoint branch — the CSS above is dead
  if the component ever starts setting inline `right` again.

## `13:35` Frontend — header actions get their own row on phones

The logo overlapped the notification bell on mobile. `.app-header-actions` is `flex-shrink: 0`
and needs ~270-315px for its four controls; at 360px the header has ~316px of content width
total, so `.brand` (`flex: 1 1 0%`, `min-width: 0`) collapsed to zero while its `.logo-box`
(`flex-shrink: 0`, 38px) kept its width and **spilled out of the collapsed box, underneath the
bell**. `.app-header`'s `overflow: hidden` then clipped whatever fell off the right edge.

First attempt wrapped the actions onto a second row. Reverted — a two-row sticky header read as
broken, and it cost ~100px of a 640px phone viewport. The row stays a single row at every width;
what changes is how many controls live in it.

- [`frontend/src/components/common/AppHeader.tsx`](../frontend/src/components/common/AppHeader.tsx)
  — below 640px the action cluster becomes a `⋯` popover. The bell stays in the row (it is the
  only control carrying *state* rather than a preference); credits, language and theme move into
  the menu. Uses the **native `popover` attribute**, so light-dismiss, Escape and focus handling
  are free, and the panel paints in the top layer — which is what makes it work at all, since
  `.app-header` sets `backdrop-filter` and would otherwise become the containing block for a
  fixed panel and clip it to `overflow: hidden`.
- One DOM node switches role at the breakpoint via `matchMedia`, rather than rendering the
  cluster twice. Rendering twice would mount `UsageIndicator` twice and fire its `/usage` fetch
  twice. `window.matchMedia?.()` is an optional call: jsdom lacks it, and "can't measure" falls
  back to the full row.
- [`frontend/src/styles/layout.css`](../frontend/src/styles/layout.css) — `max-width: 640px`
  block. 640px is measured, not picked: the full row needs ~559px of content width and a 640px
  viewport clears it by ~25px. Hides the logo tile and separator (decoration yields to the
  title; the module accent still reads from the `::after` line and the back button), and raises
  back/bell/`⋯` to the **44px tap target** DESIGN.md mandates on mobile but the 36px controls
  never met. `--header-height` stays 4rem — the header is still one row.
- Result at 360px: the title keeps ~162px, so "AI JV Automation" renders in full instead of
  collapsing to zero width.
- No control was removed, per adapt.md's "never hide core functionality on mobile": the credit
  badge is the only route to `#/pricing` from the wizards, and `useDarkMode` has no
  system-preference fallback, so hiding the theme toggle would strand whoever is in the wrong
  theme. Everything is one tap away.
- `nav.moreActions` added to both `en` and `th` in `i18n/dict.ts`.
- [`AppHeader.test.tsx`](../frontend/src/components/common/AppHeader.test.tsx) — 4 new tests pin
  the breakpoint branch, the single-node invariant, and the no-matchMedia fallback.

### `14:00` Follow-up — closed popover was still visible

Shipped broken and fixed in the same session. The base rule was
`.app-header-menu { display: flex }`, unscoped. A closed popover is hidden by the UA rule
`[popover]:not(:popover-open) { display: none }`, and **an author `display` overrides the UA
sheet** — so the panel stayed laid out inline in the header row at all times, on top of the
module title. Both reported symptoms (visible when closed, overlapping the logo/title) were
that one declaration.

- Scoped it to `.app-header-menu:not([popover])`, so only the desktop node gets a `display`
  value and the closed popover falls back to the UA's `display: none`. The open panel keeps its
  own `display: flex` under `:popover-open`.
- Not covered by a test, deliberately: vitest stubs CSS imports to `''` (a stylesheet assertion
  passes vacuously — it did, until a second assertion caught it), and `node:fs` doesn't
  typecheck because node types are scoped to `tsconfig.node.json` on purpose. The invariant is
  documented at the rule instead.

### `14:40` Follow-up 3 — menu size and spacing on a real scale

Every position value in the menu was arbitrary; three of them were measurably wrong.

- **The two popovers on this header didn't line up.** The bell panel sits at its measured
  `rect.bottom + 8`; the menu used `top: var(--header-bottom)`, whose trailing `0.75rem` is a
  *content* gap and whose `--header-height: 4rem` overshoots the compact header. Net: the menu
  hung 4–8px lower than the bell. Replaced with `--header-popover-top`, derived from the real
  compact header (`--header-top` + its padding-block + the 44px control + the bell's own 0.5rem).
  Verified: both compute to **84px** at 481–640px and **80px** at ≤480px.
- **Right edge overshot its trigger by ~10px.** `right: 0.75rem` is the container gutter, but the
  `⋯` button sits one header-padding further in. Now `--header-popover-right` = gutter + header
  padding-inline (28px / 22px per band), so the dropdown hangs off its button.
- **Width was elastic.** `width: max-content` + `min-width: 13.5rem` meant the panel resized with
  the credit count's digits (711 → 1,250), sliding the Buy CTA every time the balance changed.
  Now a fixed `16rem`, so the trailing edge is stable.
- Rows: `gap: 0` (adjacent, as menus and `.notif-bell__list` both behave — hover separates them)
  and `padding: 0 0.5rem`, which with the panel's `0.25rem` gives a **12px text inset identical
  to `.notif-bell__item`**. Was `0.625rem` → 14px, off by 2 from the panel beside it.
- All three inputs are restated in the ≤480px band, where the header padding and gutter both
  shrink; miss one and the alignment drifts again.
- [`notification-bell.css`](../frontend/src/styles/components/notification-bell.css) — the mobile
  sheet's `max-height` now derives from the same `--header-popover-top` instead of
  `--header-bottom`, which overshot by 16px. One token is now the single source of truth for
  where a header popover begins.

## `16:10` Docs — Carmen Email Automation API spec: DELETE section + accuracy pass

[`docs/CARMEN_API_SPEC.md`](../docs/CARMEN_API_SPEC.md) listed `DELETE /settings/token` in the
endpoint table but never documented it. Added §5 and re-checked every other section against
[`routers/email_automation.py`](../backend/app/routers/email_automation.py),
[`services/email_settings_service.py`](../backend/app/services/email_settings_service.py) and
[`schemas/email_automation.py`](../backend/app/models/schemas/email_automation.py).

- **§5 `DELETE /settings/token`** — query params, `204` with no body (don't `JSON.parse`),
  idempotent on a BU with no token, leaves `enabled`/`tax_ids`/`rules`/`ingest_address` intact,
  curl example. Plus the consequence a UI has to state: documents still extract but **cannot
  post** until a new token arrives; stopping ingest is a separate `enabled: false`.
- **Corrections to what was already there:**
  - `gmail_confirmed_at` was missing from the `GET /settings` body — normally it is the field
    that is set, not `gmail_confirm`.
  - `status.documents_total` / `last_received_at` are **absent** when the blocker is
    `not_configured` (`build_settings_response` returns early), previously shown as always present.
  - `pdf_password` write semantics (omit = keep, `""` = clear) were undocumented, as was the fact
    that `_merge_rule` matches the previous rule by `bank_code` — editing a rule's bank drops its
    stored password.
  - Errors come in **three** shapes, not two: field `errors[]`, FastAPI `detail[]`, and a plain
    `detail` string. Added `invalid_email` and `Malformed Carmen token`, which were missing.
  - `429` carries `Retry-After`; a rejected Carmen token is remembered for 30s, so retrying is
    pointless. `GET /settings/token` on an unconfigured BU is `200`-with-nulls, not `404`.
    `configured: true` + `verified_at: null` = the daily health sweep could not re-prove it.
- Added a TL;DR (3-step enable sequence + a "want to do X → call Y" table), per-field response
  table, and per-blocker remedies, so the reader doesn't have to infer the flow from the endpoint
  list.
- Kept everything v4.0 already said (the `host` → `uri` migration warning, the `sender_not_allowed`
  behaviour of `owner_emails`, case-insensitive `filename_patterns`, the one-shot nature of
  `gmail_confirm`) — the working copy this pass started from had been trimmed, so those were
  merged back against `main` before committing. Doc header now reads **v4.1**.
- Internal only — no release note.

### `16:30` Polish pass — the measurements the first cut got wrong

Six defects, five of them measured rather than eyeballed.

- **The logo was the reported symptom; the asset was the cause.** `logo.png` is a 2250×2250
  canvas whose ink occupies only the **middle 71.6%** (~14% transparent padding per side,
  measured off the alpha channel). Every declared size renders ~40% smaller than it reads on
  paper, and the phantom padding faked a gap the wordmark never asked for. Box is now 40px
  (= 28.6px of visible mark, 1.4× the app header's 20px) with a `-0.35rem` left margin. That
  margin is what fixes the **lockup looking crooked**: under `text-align: center` the browser
  centres the element box, but the box's left edge was transparent padding while its right edge
  was a real glyph, so the ink sat ~2.4px right of true centre.
- **The reveal button jumped on click.** It was centred with `transform: translateY(-50%)`, and
  `base.css:234` has a global `button:active { transform: scale(0.97) }`. Transform is one
  property: the press state replaced the centring and dropped the button 16px. Now centred with
  `top/bottom: 0` + `margin-block: auto`, leaving transform free for the press feedback (whose
  transition also had to be restated, since a bare `transition: color` had dropped it).
- **The background was costing AA.** Two Carmen-blue radial washes, raw-hex, decorative —
  banned outright by DESIGN.md §2 ("do not use Carmen Blue for decorative gradients"). They also
  dragged `--text-3` to **3.20:1**, under the 4.5 floor. Deleted; the page now sits on the app's
  own body surface. Subtitle moved to `--text-2` because even on the plain body bg `--text-3`
  measures 4.29:1 (it passes on a white *card*, which is exactly what DESIGN.md warns about).
- **Caps-lock hint used `--amber` (1.50:1).** `--amber` is a fill/border value; `--amber-text`
  is the AA foreground tier at 5.95:1. The hint also moved onto the label row — under the field
  it shifted the submit button down under the user's cursor mid-keystroke.
- **Two eyes in the password field.** The custom reveal was drawn next to Edge's native
  `::-ms-reveal`. `components.css:2153` already hides it for `.modal-input` — the markup was
  copied from `CustomModal` but not its CSS counterpart. Scoped to `--with-reveal` only: the
  bare password input on the Admin Users page has no custom button, and hiding the native eye
  there would remove its only reveal affordance.
- **Footer deleted.** "Carmen Cloud AI Automation Platform" at `--text-4`/11px measured
  **1.84:1**, and it restated the brand lockup 300px above it in the same column.
- Also: `100vh` → `100dvh` (same mobile-viewport class of bug as the notification panel fix
  earlier today), 44px tap targets below 768px, `alt=""` on the mark (the wordmark beside it
  already announces "Carmen AI"), and the page's `font-family` declaration dropped so it
  inherits the body stack instead of diverging from it.

### `17:10` UX pass — the sign-in form now says what actually went wrong

The backend distinguishes four failure states; the UI flattened all of them into one English
`sonner` toast that then vanished. Worst case: five wrong passwords locks the account for
**15 minutes**, and the only notice was a transient corner toast, in English, telling a Thai
reviewer to "try again in 842s" before disappearing.

- [`adminClient.ts`](../frontend/src/lib/api/adminClient.ts) — `adminLogin` now throws
  `AdminLoginError` carrying the HTTP status (and the lockout seconds parsed out of the 423
  message). The status was previously discarded, which is why every failure looked alike.
- [`AdminLogin.tsx`](../frontend/src/pages/admin/AdminLogin.tsx) — `classify()` maps status to
  one of five localised messages, so the backend's English is never shown. 401/400 → wrong
  credentials, 403 → no access (covers both "disabled" and "no roles": different causes,
  identical remedy), 423 → locked, 5xx → server unreachable. No string-matching on the message.
- **Lockout is now a live countdown** in `m:ss` with the submit button disabled until it lifts,
  then the banner clears itself. Typing does not dismiss a lockout banner (typing cannot fix
  it); typing does dismiss every other error, since editing is an attempt at the fix.
- Errors render **inline above the fields** with `role="alert"`, not as a toast — the message
  belongs where the eyes and the caret already are. Toast removed, so there is one error
  surface rather than two.
- On a failed attempt focus returns to the password field with its value selected, so the next
  keystroke replaces it. Skipped for lockout/no-access, where retyping is pointless.
- The form is wrapped in a `<fieldset disabled>` during submit: one attribute freezes the
  inputs, the reveal button and a second submit. `.admin-form-input` sets its own colour and
  background, which beat the UA's disabled styling, so an explicit dimmed state was needed or
  the frozen form still looked editable.
- Button gets a `Loader2` spinner beside "Signing in…". **Deliberately not a `toast.loading`**:
  the button already carries the state, a second focal point in the screen corner is not an
  improvement, and a loading toast raised on a page that immediately redirects has to be
  dismissed across a hash change and unmount, which is how stuck toasts happen.
- New token **`--rose-text`** in `base.css` (both themes). The system had `--amber-text` as its
  AA red-amber foreground tier but no rose equivalent, so error text had to use bare `--rose` —
  **3.86:1** on `--rose-light`, under the floor. `--rose-text` is 7.3:1 on `--rose-light` and
  7.5:1 on the body background. Missing token, not a one-off patch.
- [`AdminLogin.test.ts`](../frontend/src/pages/admin/AdminLogin.test.ts) — 5 tests pin the
  status→kind mapping, the lockout deadline, the unparseable-duration case (must stay locked
  with no countdown rather than silently clearing), and the `m:ss` padding.

**Two systemic findings, not fixed here** (both are whole-app decisions):

1. `base.css` declares `'Inter'` first on `body` and `button`, but `index.html` loads **DM Sans,
   DM Mono and IBM Plex Sans Thai** — no Inter. The entire app has been rendering Latin text in
   a system fallback. DESIGN.md §3 also still documents Inter + Sarabun.
2. `--text-3` is 4.29:1 on the body background — AA only on white surfaces. Anything using it
   for body text outside a card is sub-AA.

sign-in page with Carmen branding and a show-password toggle.
