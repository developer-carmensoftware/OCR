# 2026-07-21

## `09:00` Production DB brought onto the Supabase-CLI migration lineage

`supabase db push` against production failed on the very first statement
(`ERROR: relation "plans" already exists`). The investigation turned up something
bigger than a missing history row, so this entry is mostly a record of what prod
actually is.

### What was wrong

- Production (`lhlncsjqxttcdegkqvid`) was never on the CLI lineage. It was built by
  the **legacy runner** (`backend/app/migrations.py`, tracked in
  `public.schema_migrations`) and stopped at `217_soft_delete_stray_monthly_quota`
  on 2026-06-29. That runner was deleted in `89a0db9` "migrate to Supabase-native
  stack" without prod ever being cut over.
- `supabase_migrations.schema_migrations` on prod had **0 rows**, so the CLI planned
  to replay all 42 migrations starting from `v1_baseline` — whose own header reads
  `-- Greenfield: no production data`. It was written for the dev project
  (`ycykjisvvrrbgeiirqre`), not for a database with 40 tenants and 279 extractions.
- Blind `migration repair --status applied` would have made this worse: six tables in
  the baseline genuinely did not exist on prod, so the CLI would have been told a
  lie it could never recover from.

### DB — catch-up migration

- `09:00` **`supabase/migrations/20260721000000_legacy_prod_catchup.sql` (new, 1108
  lines).** Generated by diffing the dev project (all 42 migrations applied) against
  prod, not by replaying the lineage — so the enum churn (`on_hold` added in
  `20260622030000`, dropped in `20260623000200`, re-added in `20260701070739`) and
  four rounds of cron-SQL fixes collapse into their end state. Contents:
  - extensions `vector`, `pg_net`
  - enums `billingdocumenttype`, `subscriptionstatus`; `creditorderstatus` swapped
    from `('pending','paid','cancelled')` to the 5-label current set, mapping
    `pending→in_progress`, `cancelled→void`
  - 6 tables added after the legacy cutoff: `billing_documents`,
    `document_sequences`, `tenant_subscriptions`, `ar_customer_profiles`,
    `consent_logs`, `user_notifications`
  - 14 columns added, 9 type fixes (`json`→`jsonb`, `numeric(12,4)`→`numeric(14,6)`),
    83 defaults restored, 35 columns tightened to NOT NULL (backfilled first)
  - 23 indexes, 8 `fn_*` cron functions, 10 cron jobs, RLS deny-all on the new tables
  - reference data resynced from dev: `system_configs` 0→20, `banks` 3→8,
    `credit_packs` 4→10
- `09:00` **`admin_users.email` renamed to `username`**, not added alongside. Dev has
  no `email` column and prod's was `NOT NULL`, so leaving it would have rejected every
  insert the current app code makes. Table was empty, so no data risk.
- `09:00` **Legacy index `uq_credit_orders_one_pending_per_pack` dropped.** Its
  predicate hardcodes `status = 'pending'::creditorderstatus`, which pins the column
  to the old type and blocks the enum swap outright. Dev has no equivalent; it is
  superseded by `uq_credit_orders_one_open_per_tenant`.
- `09:00` **`system_configs['app.base_url']` seeded with the prod backend**
  (`carmen-ocr-backend.onrender.com`), *not* dev's value. Three cron jobs
  (`keep-warm`, `anomaly-detection`, `pricing-sync`) build their target URL from this
  key and carry a bearer from vault — copying dev's value would have pointed prod's
  scheduler at the staging backend holding a production token.

### Deliberately deferred

- **Partitioning of `audit_logs` / `llm_usage_logs` / `outbound_call_logs` /
  `performance_logs`**, plus `pg_partman` and the `partman-maintain` cron job. All
  four hold live rows (667 / 371 / 1980 / 3618); converting a populated table to a
  partitioned one is a copy-and-swap that wants a maintenance window. Prod runs them
  as plain tables until then — correct, just unpartitioned.
- **`public.schema_migrations`** (the legacy tracker) left in place as the record of
  how prod got here. Drop it once the catch-up is confirmed good.

### Verification

Applied inside a transaction against live prod and rolled back — Postgres DDL is
transactional, so this is a real rehearsal, not a simulation. 23 checks pass:
schema shape, enum labels, seed counts, `app.base_url`, and row counts on all nine
business tables unchanged. The same script commits only when every check passes.

### Applied

- `09:35` **Committed to production.** All 23 pre-commit checks passed inside the
  transaction, and all 43 lineage versions are registered in
  `supabase_migrations.schema_migrations` — `supabase db push` now works against prod
  normally. Independent post-apply verification: 18/18.
- Business row counts unchanged across the apply: tenants 40, ocr_tasks 279,
  credit_cards 161, ap_invoices 75, credit_orders 1, llm_usage_logs 371,
  audit_logs 667.
- `ocr_sessions` fell 23 → 5 during the same window. **Not caused by this
  migration**: `pg_stat_statements` attributes it to a query in the *deployed*
  backend — `DELETE FROM ocr_sessions WHERE created_at < $1 OR is_active IS false`,
  1040 calls / 303 rows lifetime — which runs on login. Sessions are ephemeral auth
  state; affected users just re-authenticate through Carmen SSO.

### Side finding — the deployed backend is older than this repo

That purge query does not exist anywhere in the current tree (`retention_service.py`
deletes on `is_active = false AND last_used_at < 30 days`, a different predicate), so
Render is serving an older build. That is why nothing broke when the schema moved
under it. It also means prod is now in a **transitional state**: old code against new
schema. Safe for the endpoints currently in use (auth, quota, Carmen proxy), but a
credit-order write from the old code would try to insert `'pending'`, which the enum
no longer accepts. Deploy the current backend before anyone touches the purchase flow.

## `11:00` Versioning: SemVer, one source of truth

Three schemes disagreed about what was running: `config.py` said `1.0.0` (hardcoded since
day one, surfaced at `/api/version` and `/docs`), `frontend/package.json` said `0.1.0`
(dead — nothing imported it), Home rendered `v2026.07.20` (a *date* dressed as a version),
and `deploy.yml` tagged `v2026.07.21` (a different date). Now: **SemVer in a repo-root
`VERSION` file**, everything else reads it. Dates keep the jobs they were good at —
changelog filenames and release-note identity/seen-key — and stop pretending to be versions.

Bump rule (also in CLAUDE.md): PATCH = fix, MINOR = new user-visible capability, MAJOR =
breaks something outside this repo. Refactors/CI/deps bump nothing.

### Backend

- `11:00` **`VERSION` (new)** — one line, `1.0.0`. Not restarting at 0.x; the product is in pilot.
- `11:00` `config.py` — `_read_version()` reads `parents[2]/VERSION`, falls back to `"dev"` on
  `OSError` so a partial checkout still boots. `app_version` defaults to it; pydantic-settings
  already lets an `APP_VERSION` env var win, so the deploy-time override path stays open for free.
- `11:00` Dropped the stale `APP_VERSION=1.0.0` from `.env`; `.env.example` keeps it commented
  as an override, not the source.

### Frontend

- `11:00` `vite.config.ts` + `vitest.config.js` bake `__APP_VERSION__` from the same file.
  The two configs are separate, so the `define` had to be duplicated — otherwise anything
  rendering the version blows up only under test. Declared in `vite-env.d.ts`.
- `11:00` Removed `"version": "0.1.0"` from `package.json` — a second number that could drift
  and that nothing read. Added `@types/node` (types-only devDep) + `"types": ["node"]` in
  `tsconfig.node.json`; `tsc -b` type-checks `vite.config.ts` and it now imports `node:fs`.
- `11:00` `releaseNotes.ts` — `ReleaseNote` gains `version`. `date` is untouched and still the
  identity/seen-key; the version is display-only and never compared, so the bell's
  lexicographic-date logic needed no changes. Backfilled `2026-07-20` as `1.0.0`.
- `11:00` `Home.tsx` renders `v{__APP_VERSION__}` instead of `LATEST_RELEASE.replace(/-/g,'.')`;
  `WhatsNew.tsx` shows `v{release.version}` beside each date (`.whatsnew-version`, mono, dimmer
  than the date — the date is what you scan for, the version is what you quote back).

### CI/CD

- `11:00` `deploy.yml` tags `v$(cat VERSION)` instead of `v$(date)`. The "tag exists → skip"
  guard now means "VERSION wasn't bumped, so this deploy isn't a release" — the intended path
  for a refactor deploy, not a failure.
- `11:00` Drift guard lives in `releaseNotes.test.ts`, not a CI shell step: `RELEASE_NOTES[0].version`
  must equal `__APP_VERSION__`, plus a SemVer format check. The suite already runs in CI, so a
  separate grep job would have been a second thing to maintain — and this one fails locally
  before the push.

### Verified

- `11:00` `/api/version` returns `1.0.0` from the file; `APP_VERSION=9.9.9` still overrides;
  renaming `VERSION` away leaves the backend booting on `"dev"`.
- `11:00` `npm run build` — bundle contains `System Online — v` + `1.0.0`. `type-check` clean.
  The three version-touching test files pass (23), with the pre-existing `'2026-07-20'` pins
  untouched, which is the proof the seen-logic wasn't disturbed.
