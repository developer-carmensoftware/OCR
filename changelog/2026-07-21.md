## `09:00` Production DB brought onto the Supabase-CLI migration lineage

`supabase db push` against production failed on the very first statement
(`ERROR: relation "plans" already exists`). The investigation turned up something
bigger than a missing history row, so this entry is mostly a record of what prod
actually is.

### What was wrong

- Production (`lhlncsjqxttcdegkqvid`) was never on the CLI lineage. It was built by
  the **legacy runner** (`backend/app/migrations.py`, tracked in
  `public.schema_migrations`) and stopped at `217_soft_delete_stray_monthly_quota`
  on 2026-06-29. That runner was deleted in `89a0db9` "migrate to Supabase-native
  stack" without prod ever being cut over.
- `supabase_migrations.schema_migrations` on prod had **0 rows**, so the CLI planned
  to replay all 42 migrations starting from `v1_baseline` — whose own header reads
  `-- Greenfield: no production data`. It was written for the dev project
  (`ycykjisvvrrbgeiirqre`), not for a database with 40 tenants and 279 extractions.
- Blind `migration repair --status applied` would have made this worse: six tables in
  the baseline genuinely did not exist on prod, so the CLI would have been told a
  lie it could never recover from.

### DB — catch-up migration

- `09:00` **`supabase/migrations/20260721000000_legacy_prod_catchup.sql` (new, 1108
  lines).** Generated by diffing the dev project (all 42 migrations applied) against
  prod, not by replaying the lineage — so the enum churn (`on_hold` added in
  `20260622030000`, dropped in `20260623000200`, re-added in `20260701070739`) and
  four rounds of cron-SQL fixes collapse into their end state. Contents:
  - extensions `vector`, `pg_net`
  - enums `billingdocumenttype`, `subscriptionstatus`; `creditorderstatus` swapped
    from `('pending','paid','cancelled')` to the 5-label current set, mapping
    `pending→in_progress`, `cancelled→void`
  - 6 tables added after the legacy cutoff: `billing_documents`,
    `document_sequences`, `tenant_subscriptions`, `ar_customer_profiles`,
    `consent_logs`, `user_notifications`
  - 14 columns added, 9 type fixes (`json`→`jsonb`, `numeric(12,4)`→`numeric(14,6)`),
    83 defaults restored, 35 columns tightened to NOT NULL (backfilled first)
  - 23 indexes, 8 `fn_*` cron functions, 10 cron jobs, RLS deny-all on the new tables
  - reference data resynced from dev: `system_configs` 0→20, `banks` 3→8,
    `credit_packs` 4→10
- `09:00` **`admin_users.email` renamed to `username`**, not added alongside. Dev has
  no `email` column and prod's was `NOT NULL`, so leaving it would have rejected every
  insert the current app code makes. Table was empty, so no data risk.
- `09:00` **Legacy index `uq_credit_orders_one_pending_per_pack` dropped.** Its
  predicate hardcodes `status = 'pending'::creditorderstatus`, which pins the column
  to the old type and blocks the enum swap outright. Dev has no equivalent; it is
  superseded by `uq_credit_orders_one_open_per_tenant`.
- `09:00` **`system_configs['app.base_url']` seeded with the prod backend**
  (`carmen-ocr-backend.onrender.com`), *not* dev's value. Three cron jobs
  (`keep-warm`, `anomaly-detection`, `pricing-sync`) build their target URL from this
  key and carry a bearer from vault — copying dev's value would have pointed prod's
  scheduler at the staging backend holding a production token.

### Deliberately deferred

- **Partitioning of `audit_logs` / `llm_usage_logs` / `outbound_call_logs` /
  `performance_logs`**, plus `pg_partman` and the `partman-maintain` cron job. All
  four hold live rows (667 / 371 / 1980 / 3618); converting a populated table to a

- **`public.schema_migrations`** (the legacy tracker) left in place as the record of

### Side finding — the deployed backend is older than this repo

That purge query does not exist anywhere in the current tree (`retention_service.py`
deletes on `is_active = false AND last_used_at < 30 days`, a different predicate), so
Render is serving an older build. That is why nothing broke when the schema moved
under it. It also means prod is now in a **transitional state**: old code against new
schema. Safe for the endpoints currently in use (auth, quota, Carmen proxy), but a
credit-order write from the old code would try to insert `'pending'`, which the enum
no longer accepts. Deploy the current backend before anyone touches the purchase flow.

## `16:30` AP Invoice — discount column was flipping the document's VAT reading

> **Release note + version bump deliberately NOT done in this change.** User-visible, so it
> needs both before it ships — but batched with whatever else goes out in that release,
> rather than one note per PR. `VERSION` stays at `1.0.1`. **Pending:** a `fixes` entry in
> `frontend/src/content/releaseNotes.ts` (EN+TH) covering the two user-visible items flagged
> below, plus the matching `version:`.

### The bug

Reference document: B 47 Service invoice `66-0023` (`20260408_164331.jpg`) — six rows with a
printed `ส่วนลด %` column, footers `17,691.10` + 7% `1,238.38` = `18,929.48`. A plain
**Exclude** document that is internally consistent.

`discountPct` was extracted but never converted into `discountAmt` (`ap_invoice.py:45` asks
for it; the backend only ever derived the *reverse*). So `_detect_tax_type` summed
`qty × unitPrice` with zero discount — `20,607.00` instead of `17,691.10` — and compared:

- Include: `|20,607.00 − 18,929.48| = 1,677.52`
- Exclude: `|20,607.00 − 17,691.10| = 2,915.90`

Include won **by being less wrong**. Every line was then divided by 1.07 and the shortfall
plugged onto the last row, which posted `2,524.19` against a printed `1,462.50`. The header
grand total was correct, so nothing looked wrong in any screen or summary. Every
percent-discount invoice has been posting this way.

### Backend — `services/ap_invoice_postprocess_service.py`

- `16:30` **`_resolve_line_discount()` (new), called first in `postprocess()`.** Normalises
  every row's discount to a whole-line `discountAmt` from the printed Amount column: whatever
  `lineAmt` falls short of `qty × unitPrice` IS the discount, however the document expressed
  it (% column, per-unit, per-line). `discountPct` is the fallback when there is no Amount
  column. An Amount *above* gross clamps to 0 — that is a surcharge or a misread, never a
  negative discount. The ordering is the fix: this must run before any sum is taken.
- `16:30` **`_net_item_sum()` (new)** — one definition of "what the rows actually bill", used
  by both `_deposit_applies` and `_detect_tax_type`, subtracting the row discount *and* the
  footer share. Previously each inlined its own sum and neither saw `_footerDisc`.
- `16:30` `_distribute_footer_discount()` records shares on **`_footerDisc`**, not folded into
  `discountAmt`. Keeping them apart is what stops a document carrying *both* a discount column
  and a footer discount from deducting the row's own discount twice. Also: falls back to
  `lineAmt` when a row has no qty/unitPrice (the whole footer discount used to vanish when the
  `qty × unitPrice` base summed to 0); prorates over **positive bases only** (a `-190` credit
  row was taking a negative share, growing itself and shrinking everyone else's base); and
  absorbs the rounding remainder on the largest row rather than blindly the last.
- `16:30` `_compute_line_totals()` — `has_footer_disc` parameter **removed**. That
  document-wide flag was the double-deduct. Amount-column semantics are no longer guessed:
  `lineAmt` is already net of the row's own discount, so only the footer share is deducted.
  Restates `discountAmt` to `qty × unitPrice − after_disc`, establishing the invariant the
  frontend relies on. Stale docstring corrected — it claimed `unitPrice` is normalised to a
  net per-unit price, which was never true (that happens at payload-build time).
- `16:30` `_detect_tax_type()` now returns `(tax_type, misfit)`. It is a nearest-match vote
  with no absolute floor — it always returns *something*. When the winner still misses the
  footer by more than 1% (`_TAX_FIT_TOLERANCE`), `postprocess` appends to a new **`warnings`**
  output key. This is the guard that would have caught 66-0023 on day one.
- `16:30` Zero-`lineTotal` rows are no longer dropped if they carry a discount — a
  100%-discounted free line was losing both the row and its discount from `totalDiscount`.
- `16:30` **Pre-existing bug found via the reference document:** the penny reconciliation
  shifted the header tax by `diff` *after* it had already been snapped to `doc_tax`,
  correcting twice and landing `sub + tax` a satang below `grand` — which trips the
  frontend's "document figures don't add up" banner on a document that adds up fine. Now
  re-summed from the items instead of shifted.

### Frontend

- `16:30` `lib/apInvoicePayload.ts` — **`InvdPrice` is now derived from the line amount**
  (`NetAmt`, or `TotalPrice` for Include rows), not rebuilt from `unitPrice − discountAmt`.
  Those were two independent sources and nothing forced them to agree, so Carmen's AP screen
  showed `Qty 6 × Price 781.00` against a `Net Amount` of `4,379.44` — arithmetic a customer
  cannot check by hand. `discountAmt` leaves the payload entirely. Kills three defects at
  once: the `Math.max(0, …)` clamp that posted `0.00` for every negative credit/deposit row
  is **deleted, not patched**; the `grossLine <= 0` branch that silently dropped the discount
  is gone; and the discount Adjust button can no longer reach the posted price.
