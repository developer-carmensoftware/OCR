`09:37` **Email review: one document, one JV — approve takes a real claim, and stamps only this
BU's own card.** *(shipped as PR #251 — `10b91cd`)*

Fixes DEF-1 and DEF-2 from the multi-BU QA run
([`docs/email-automation/qa/2026-09-24-multi-bu-report.md`](../docs/email-automation/qa/2026-09-24-multi-bu-report.md)).

- **DEF-1 (HIGH) — two approvals of one document both posted a JV.** `_claim_for_review` took
  `SELECT … FOR UPDATE` in a session that closed before `post_gljv` was awaited, so the lock was
  gone when it mattered; two reviewers in one BU (the bell notifies everyone) could both post.
  Now a compare-and-set on a new column, `email_documents.posting_started_at`
  (`20260925000000_email_documents_posting_claim.sql`): `UPDATE … WHERE status='pending_review'
  AND (unclaimed OR claim older than POSTING_CLAIM_TTL) RETURNING`. The second click gets 409
  "Another reviewer is posting this document right now". `approve_document` gives the claim back
  on every exit before Carmen accepts (no credential, duplicate, Carmen unreachable, Carmen
  rejected) and keeps it after; `reject_document` takes the same claim, so a reject racing an
  approve is refused rather than marking rejected a JV that is going into Carmen; `_finish`
  clears it. A timestamp rather than a status on purpose — no tab or count changes, and a claim
  left by a dead process expires (5 min, ≥ two Carmen posts at the 30 s timeout) instead of
  stranding the document. Holding the row lock across the Carmen call (the wizard's approach) was
  rejected: it pins a pooled connection for up to a minute against a pool of 10.
- **DEF-2 (MEDIUM) — approve stamped another BU's card.** `_mark_submitted` took the
  client-supplied `extracted.id` and loaded it with no tenant filter. Now
  `_mark_submitted(tenant_id, task_id)` finds the card by the ledger row's own `task_id`
  (`uq_credit_cards_task`) with the tenant in the WHERE clause — the wizard's `proxy_gljv` pattern.
  Both call sites (auto-post in `_run_document`, and approve) use it; `extracted.id` is no longer
  read anywhere on this path.
- **Tests:** `tests/tenancy/test_email_approve_integrity.py` — the two `xfail(strict=True)`
  reproductions now pass on the real dev DB, plus five new ones (reject racing approve, Carmen
  rejection releases the claim, expired claim retaken, live claim refuses a second approve, own
  card still stamped). `tests/unit/test_email_ingest_pipeline.py` — `_ReviewDB` fake now plays the
  compare-and-set; four new unit tests; `_mark_submitted` assertion pinned to (tenant, task).
- **DB:** migration applied to the dev project by direct SQL (additive, `if not exists`) because
  `supabase db push` from this branch is blocked by five migrations other unmerged branches applied
  to dev (`LegacyDbPushMissingLocalError`); the normal `db push` after merge re-runs it as a no-op.
  **Not yet applied to prod.**

Stacked on `test/email-automation-multi-bu` (it needs that branch's test file). Release note

`09:55` **Email routing: the `+tag` must be on our exact address — lookalike domains no longer
route.** *(PR #252 — `456b94d`)*

Fixes F-3 from the multi-BU QA run
([`docs/email-automation/qa/2026-09-24-multi-bu-report.md`](../docs/email-automation/qa/2026-09-24-multi-bu-report.md)).

- **F-3 (HIGH):** `email_imap.tag_from_recipients` built its regex as `user\+(tag)@domain` with no
  edges, so it was a substring search. `aragent+<tag>@carmensoftware.com.evil.test` was routed
  live, during the QA run, to the BU owning `<tag>`; `xaragent+<tag>@…` would have matched too.
  Now bounded on both sides: no local-part character before `user`, and no label continuing the
  domain after it (`-x`, `.x`) — while `>`, `;`, a comma, a space, or a sentence-ending dot still
  end the address, because candidates can be free text like `for <…>; date`. One function, so the
  document poll, the confirmation sweep and the confirmation branch of `_process_message` are all
  fixed at once.
- **Tests:** `tests/unit/test_email_ingest_routing.py` +11 — six lookalikes (domain suffix, bare and
  inside a `for <…>` line, hyphenated suffix, three prefixed local parts) must yield no tag; five
  real header punctuation shapes must still yield it.

No release note: a routing hardening with no visible behaviour for correctly addressed mail.

`10:12` **Email ingest: the mailbox queue is our own `$OcrDone` flag, not `\Seen` — opening
the mailbox no longer loses mail.** *(PR #253 — `b6a5888`)*

Fixes F-1 and F-4 from the multi-BU QA run
([`docs/email-automation/qa/2026-09-24-multi-bu-report.md`](../docs/email-automation/qa/2026-09-24-multi-bu-report.md)).

- **F-1 (HIGH):** the poll's queue was `SEARCH UNSEEN`, and `\Seen` is something anyone can
  set. During the QA run 39 appended mails were marked read by a reader outside the poller and
  never produced a row. In production, support opening `AIAGENT@` to look into a complaint would
  have erased exactly the document in question. `email_imap.fetch_unseen` → `fetch_pending`
  (`UID SEARCH NOT KEYWORD $OcrDone …`, all three searches incl. the `SMALLER` fallback and the
  beyond-window count); `mark_seen` → `mark_done` stores `(\Seen $OcrDone)` — `\Seen` kept only
  so the label reads as handled to a person. Deleting a mail or removing its label still loses it.
- **F-4 (LOW):** `fetch_confirmations` fetched `(RFC822)`, which on Gmail sets `\Seen`, so a
  confirmation for a tag nobody was waiting on was consumed instead of left for the document poll
  (its docstring promised the opposite). Now `BODY.PEEK[]`, same `$OcrDone` queue.
- An odd `FETCH` response shape was skipped with no trace; it now logs a warning naming the UID
  (the mail stays pending, as before).
- **Transition:** new `scripts/imap_mark_done_backfill.py` (dry run by default) flags mail older
  than the hold window done, so the first poll does not raise `email_ingest_beyond_window` for
  the mailbox's whole history. In-window mail is left pending on purpose: already-decided mail
  dedupes on `email_documents` for free, and whatever F-1 hid is found and processed. Dev dry run:
  209 → done, 86 in-window left for the poll. **Run it against prod before this deploys** —
  see [`05-operations.md`](../docs/email-automation/05-operations.md).
- `scripts/reset_email_test.py --unread`, `reset_tenant_email.py`, `email_ingest_e2e.py` now
  clear/check `$OcrDone`; clearing only `\Seen` would replay nothing.
- **Tests:** unit — the queue never mentions `UNSEEN`, `mark_done` sets both flags, the
  confirmation sweep peeks, the odd-FETCH skip is logged.

No release note: no customer-visible behaviour change.
