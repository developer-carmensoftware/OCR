## `14:20` Email Automation — route on a per-BU address, not on the document's contents

Spec bumped to **v3.0**: `ingest_address` becomes per-BU and nullable, and
`filename_pattern` becomes the required list `filename_patterns`. Breaking for Carmen's
settings screen, and deliberately taken now — no customer is live on this feature and
nothing has been handed to the Carmen team, so the contract change costs nothing today
and costs a partner integration later.

### Why

Reviewing the implementation ahead of launch turned up five defects. Two of them could
move money into the wrong company's books:

| | Finding |
|---|---|
| A | A document was routed to a BU on **one signal only** — a tax ID an OCR model read off the page. `resolve_by_tax_ids` returned the first match with no ambiguity check, and no second factor could contradict a wrong first one. |
| B | Nothing stopped a BU registering **a bank's own tax ID**. The bank's TIN is printed on the same invoice the user reads to find theirs; one copy-paste captured every document that bank issues, for every customer. |
| C | Every attachment was sent to the vision LLM **before anyone was known to own it** — no size cap on the ingest path, no magic-byte check, and a non-matching `filename_pattern` was not a stop. Every signature logo in a forwarded chain was its own LLM call. |
| D | That spend was **invisible**. `llm_usage_logs.tenant_id` is NOT NULL, so tenant-less calls were parked in a ContextVar buffer and flushed only on the fully successful path — five exits discarded it. `run_ingest` also wrote no `job_runs` row at all. |
| E | `CARMEN_INTEGRATION.md` §0.1 told Carmen we verify the bank's DKIM signature. We never did. |

The root cause of A, C and D is one decision: routing on the tax ID means reading the
document to find out whose it is. `20260805000000_email_drop_ingest_tag.sql` dropped the
per-BU `+tag` on the reasoning that a manual forward "comes from an employee's own client,
which rewrites the recipient". **That premise is wrong** — on a manual forward the employee
*types* the destination, so the recipient is whatever Carmen's screen told them to send to.
The tag survives a manual forward exactly as it survives an auto-forward.

### Backend

- **Migration [`20260806000000_email_ingest_tag.sql`](../supabase/migrations/20260806000000_email_ingest_tag.sql)** —
  `email_ingest_settings.ingest_tag` is back, with two deliberate differences from the
  original: **nullable** (a BU that signs in once and never buys anything must not consume
  a tag — that is most tenants) and covered by a *partial* unique index. Allocated on the
  first successful enable, behind the existing `is_entitled()` gate, and **never reissued**
  — the customer's mailbox rule points at it, so a new one makes their documents vanish
  with no error anywhere.
- `email_settings_service` — `ingest_address(tag)` builds `<user>+<tag>@<domain>` and
  returns `None` until a tag exists, so **nobody is ever shown the bare address**. New
  `resolve_by_tag()` (envelope → tenant, one indexed SELECT) and `foreign_tax_id()`
  (post-extraction verification). `_fresh_tag()` is `secrets.token_hex(4)` — random, not
  derived from `bu_code`, which is not unique across hosts, is guessable, and drifts when
  Carmen renames a BU. `resolve_by_tax_ids` and `ingest_pool` deleted.
- **The pipeline is inverted** ([`email_ingest_service.py`](../backend/app/services/email_ingest_service.py)):
  tag → tenant → entitled → claim the ledger row → bank rule → open the file → charge →
  extract → verify the tax ID → post. Four problems dissolved rather than needing separate
  fixes:
  - `_already_seen`'s full-table scan is gone. With the tenant known up front, `_claim`
    alone is the dedupe and it uses `uq_email_documents_message` directly.
  - `_open_or_fail` no longer tries **every customer's** PDF passwords — only the owner's.
  - `pending_llm_usage` **deleted** (`context.py`, `llm_usage_logger.flush_pending_usage`).
    Extraction now runs with `current_tenant_id` *and* a `task_id` already set, so the
    usage row inserts normally and all five lossy exits stop being lossy. This is the fix
    for D, not a workaround for it.
  - `ingest_pool` (rules pooled across every enabled BU) became a per-tenant read.
- **`filename_patterns` is a required list and a hard gate.** A non-match ends the
  attachment with no LLM call — previously it merely meant "no bank hint" and the file was
  extracted with the generic prompt. `match_rule` → `match_rules`, returning every match:
  sender now **narrows** instead of short-circuiting (a sender hit that matched no filename
  pattern used to walk straight past the gate), and overlapping patterns leave `bank_code`
  as `None` for `detect_bank_code` rather than guessing the prompt. Per-pattern semantics
  unchanged — `%pattern%`, case-insensitive, pinned by test so a refactor cannot tighten it
  to equality. `bank_sender_email` stays a single optional value: a bank uses one sending
  system, and leaving it empty is the escape hatch that keeps manual forwarding working.
- **The tax ID became verification.** `tax_id_mismatch` is back as a reason code, and parks
  **only on positive evidence of conflict** — a number registered to a *different* BU. Not
  parking merely because nothing matched: some fee invoices never print the buyer's TIN.
- **Caps the tag does not provide** — `_fetch_unseen` now filters at the IMAP server with
  `SEARCH … SMALLER <max_file_size_mb>` (RFC 3501, falling back to plain `UNSEEN` if a
  server refuses it rather than silently reporting an empty mailbox), so `FETCH (RFC822)`
  stops pulling oversized mail into memory. `MAX_ATTACHMENTS_PER_MESSAGE = 10`.
  `_open_or_fail` now calls `validate_magic_bytes` — `ensure_pdf_openable` is a no-op for
  non-PDFs, so a `.jpg` that was really a text file used to reach the model and be paid for.
- **The spend is visible** — `run_ingest` writes a `job_runs` row (`job_name`
  `email-ingest`), so the job finally appears on `#/admin/jobs`, and raises one
  `email_ingest_unrouted` anomaly alert when a poll is mostly unattributable mail. The
  threshold is **per poll, not per day**, so daily-commission volume does not trip it.
- **Phase 4** — registering a bank's own TIN is `422 reserved_tax_id`, checked against
  `banks.tax_id` (the column already seeded for the ACTX record, so "adding a bank is an
  INSERT" stays true). This is a prerequisite for the conflict check above: a BU holding a
  bank's TIN would trip it on every document that bank issues.

### Tests

`test_email_ingest_routing.py` rewritten, `test_email_ingest_pipeline.py` and
`test_email_settings_service.py` reworked — **842 backend tests green**. The load-bearing
ones:

- an unknown tag, and the bare address, both return `unrouted` **with the extractor
  asserted never called** — the assertion the whole change exists for.
- `To:` is pinned *out* of the delivery headers. Reading it fails open in testing and
  closed in production: a hand-sent test passes while every real auto-forward routes
  nowhere.
- a sender hit does **not** buy a filename miss an LLM call; a sender matching no rule
  leaves every rule eligible.
- **forward-as-attachment** — a `message/rfc822` part yields the inner PDF under its
  original name. Load-bearing for manual forwarding and previously only an assumption.
- a document whose tax ID belongs to another BU parks as `tax_id_mismatch` and refunds;
  one printing no TIN at all still posts.

### `14:35` Tested against the live mailbox — and the core assumption was half wrong

Ran the plan's §6 verification against the dev mailbox. **Four findings** — two would have
shipped broken, and one (finding 4) took two wrong turns before landing back on exactly
what the plan said to do in the first place.

**1. The 29 messages sitting in the `ocr-test` folder are fabricated.** No `Received`
chain, no `Authentication-Results`, no `Return-Path`, `Message-ID` domain `test.local`,
and a spoofed `From: no-reply@bay.co.th`. An earlier session built them with a script and
IMAP-APPENDed them, writing the `Delivered-To` header itself. They prove that our parser
reads a header we planted — nothing about Gmail. This is the plan's own "fails open in
testing" trap, one level deeper than it anticipated: **do not treat that folder as
evidence of anything.**

**2. `Delivered-To` is not guaranteed.** A real SMTP send to `<user>+<tag>@gmail.com`
arrived with **no `Delivered-To` header at all** — so `tag_from_recipients` returned
`None` and the mail would have been dropped as `unrouted`. Cause: sender and recipient
were the same account, so the mail was accepted at submission (`ESMTPSA`) and never
traversed the inbound MX hop that stamps `Delivered-To`. Measured, both shapes:

| Delivery path | `Delivered-To` | `Received … for <…>` |
|---|---|---|
| self-send → tagged address | **absent** | tagged address, verbatim |
| genuine external inbound | present (bare) | bare address |

**3. The poll would have seen nothing anyway.** `_fetch_unseen` selects
`IMAP_FOLDER` (`ocr-test`) only, and both probe mails landed in **INBOX without that
label** — so `SEARCH UNSEEN SMALLER` over `ocr-test` returned **0**. Tag parsing is
irrelevant if the mail never reaches the folder the poll reads. The reason the earlier
session's tests appeared to work is the same reason finding 1 exists: the fabricated
messages were APPENDed straight into `ocr-test`, bypassing both the delivery path *and*
the filter.

**4. Was wrong twice on the same point before landing where the plan started.** §6 step 1
already said to build the Gmail filter on **`deliveredto:`, not `to:`**. Tested that
against the self-send probes with `X-GM-RAW` (Gmail's own search engine, the same matcher
filters use) and got:

| Filter condition (against the self-send probes) | matched? |
|---|---|
| `to:AIAGENT@carmensoftware.com` | yes |
| `deliveredto:AIAGENT@carmensoftware.com` | **no** |

— and concluded the plan's instruction was wrong. It wasn't. Those probes have **no
`Delivered-To` header at all** (finding 2), so `deliveredto:` had nothing to match; the
test was incapable of confirming or denying the operator either way. This is finding 1's
trap again, from the other direction: a test that returns a clean result on data that
cannot exercise the thing being tested.

Step 3 of §6 (§ live run: 15:10) — real external sender → real Gmail auto-forward →
tagged delivery — settled it against a message that actually carries `Delivered-To`:

| Filter condition (against the real forward) | matched? |
|---|---|
| `to:AIAGENT+<tag>@carmensoftware.com` | **no** |
| `deliveredto:AIAGENT+<tag>@carmensoftware.com` | **yes** |
| plain text, no operator, same address | no |

The visible `To:` header on a real forward stays the original recipient (the customer's
own address) — the tag only ever appears in `Delivered-To`. **The plan's original
instruction was correct throughout: filter on `deliveredto:AIAGENT@carmensoftware.com`
(bare — Gmail's `+` folding still applies), not `to:`.** The Gmail UI has no dedicated
field for it; it goes in **"Has the words"**, typed as `deliveredto:<address>` — the
Advanced Search dialog's **To** field only ever builds a `to:` query.

**Fix:** `_recipients()` now also reads the envelope recipient from the `for <…>` clause
of the `Received` chain, after the delivery headers. Still envelope-only — both sources
are written by a mail server, whereas `To:` is written by whoever composed the message,
which is the distinction that keeps `To:` out. Forgeability is unchanged in substance: an
upstream sender can fabricate either header and gains nothing by it, since the tag is the
capability, so anyone who knows one can simply address the mail to it.

Re-ran the probe after the fix: **PASS**, tag recovered from the `Received` clause.

Tests (+4, 846 total green) pin both measured shapes verbatim, including the
no-`Delivered-To` one that failed. The `To:`-is-never-a-source test was rewritten to
assert behaviour — a tagged `To:` with no delivery header and no `Received` chain must
still resolve to nothing — rather than asserting the contents of a constant.

### `15:10` Step 3 of §6 run — real external sender → real Gmail auto-forward → tagged delivery

The one thing left untested. Set up: mailbox 3 (a real university address, standing in
for "the bank") → sends to mailbox 2 → mailbox 2 has a Gmail filter (`From: mailbox-3`,
action "Forward it to") pointing at `<ingest-user>+extfwd01@gmail.com` — filter-based
forward, not the blanket "forward every incoming mail" toggle, because a real customer
forwards only their bank's mail, not their whole inbox.

**Result: PASS.** The forwarded copy arrived carrying
`Delivered-To: <ingest-user>+extfwd01@gmail.com` (Gmail's own `caf_=` bounce-address
marker confirms it went through Gmail's native forward mechanism, not a script).
`tag_from_recipients()` read `extfwd01` correctly on both attempts.

It did **not** land in the `ocr-test` label on first arrival — that surfaced finding 4
above (the label filter was still on `to:`, which a real forward's visible `To:` header
never carries). After correcting the filter to `deliveredto:` and manually moving the two
already-arrived messages, both are confirmed sitting in `ocr-test` with the tag intact.

All ten items in the verification plan are now run. `UNSEEN` on those two messages is 0
because they were opened by hand during triage, not because of a code path — a real poll
never opens mail in the Gmail UI, so this has no bearing on production behaviour.

**The two probe-arm findings from `14:35` are superseded, not just supplemented**: finding
4 originally said the plan's `deliveredto:` instruction was wrong (based on a self-send
test that had no `Delivered-To` header to test against at all). It was right. Filter on
`deliveredto:AIAGENT@carmensoftware.com`, entered into the **"Has the words"** field —
Gmail's filter-builder **To** field only ever composes a `to:` query, so it cannot express
this condition itself.
