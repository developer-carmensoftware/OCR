### Admin — filtering, sorting, and the 30-day walls

`09:30` **The complaint:** filtering and sorting across `#/admin/*` were hard to use, and
most tables refused to look further back than 30 days even though the data behind them is
retained for 12–24 months. An audit of all 18 pages found two root causes.

**1. The time walls were arbitrary, and several were narrower than the API allowed.**

| Wall | Was | Now |
| --- | --- | --- |
| `period_hours` on `/tenant-ranking`, `/error-breakdown` | `le=720` (30 days, hard) | `le=8760` (a year) |
| Errors page period dropdown | 1h / 24h / **7d** — narrower than the 30 the API already allowed | shared picker, up to 12 months |
| `_MAX_DATE_RANGE_DAYS` (extraction-failures, quotas/overview) | 92, answered with a red toast | 366 — both are bounded by their own row `limit`, so the cap only ever belonged to `/usage-summary` |
| LLM Logs, Performance, Jobs, Anomalies, Sessions, Credits, Overview | no time control at all | period picker |
| Credit ledger | flat newest-100, no dates, no note — entry #101 was unreachable | paged, searchable, date-filtered |

- **`/usage-summary` + `/usage-summary/totals` gain `granularity=day|month`.** `day` keeps
  the 92-day guard (that query has no row limit at all, so the range is the only thing
  bounding it). `month` reads `monthly_usage_summary` — the nightly rollup that has existed
  since `fn_build_monthly_summary`, is kept indefinitely, and which no admin page had ever
  read. That is what makes a year of history answerable instead of a validation error.
  New `get_monthly_usage_summary()` / `get_monthly_usage_totals()`. `extract_calls` /
  `suggest_calls` are **null**, not 0, at monthly granularity: the rollup never captured
  the split, and a zero there would read as "nobody ran an extraction that month". The
  totals' latency is weighted by call count, not a mean of means.
- The frontend picks the granularity itself (`granularityFor()` in `PeriodPicker`) and says
  so in a note, so nobody has to know 92 is a number.

**2. Three sorting systems that contradicted each other.**

- **Sorting moved to the database.** New `app/utils/list_query.py` (`ListQuery`,
  `apply_list_query()`) + `routers/admin/_query.py` (the `?q=&sort=&dir=&limit=&offset=`
  dependency). `DataTable` only ever sorted the rows already fetched, so on a capped
  endpoint "highest cost" silently meant *highest cost among the last 200 by time* — and
  only 3 of 18 pages admitted they had been truncated. Converted: `/llm-usage`,
  `/performance-logs`, `/jobs`, `/alerts`, `/sessions`, credit ledger, `/user-usage`.
  - `sortable` is a whitelist; an unknown `sort` is a 400, never a silent fallback to an
    arbitrary order.
  - Every sort carries a **tiebreak** column. Under offset paging, rows equal on the sort
    column have no defined order, so a page boundary could repeat one row and skip another.
  - Nulls sort last in both directions; `%` and `_` in a search term are escaped.
- **Two controls answering one question, differently.** LLM Logs and User Usage each had a
  server-side `order_by` `<select>` *and* clickable column headers. The dropdowns are gone;
  the headers drive the server sort, which now covers all five columns instead of three.
- **Four columns sorted by a field they did not display** — `key: 'tenant_id'` while the
  cell rendered `tenant_name` (LLM Logs, Performance, Usage), and `key: 'host'` while
  showing `name` (Quota). Clicking "Tenant" ordered by UUID. Fixed; on the two partitioned
  log tables the column is now display-only, because the name is not a column there and the
  tenant dropdown above already answers "just this BU".
- **First click follows the column's grain.** `Column.defaultDesc`, plus the rule that a
  right-aligned column opens descending. Every date column used to open on the oldest row
  in the range and every amount on the smallest.
- **Unsorted columns show a dimmed `⇅`.** The slot rendered empty, so the only clue a
  column could sort at all was a hover state — which a tablet never produces. `--text-4`
  with no `opacity`: an opacity would composite it under the 3:1 floor, and `npm run
  contrast` reads tokens, so it could never have caught that. Added a row to the audit.

**Search, where there was none.** Only Credit Orders had a search box, and it matched the
company name only. `DataTable` grows an optional toolbar: server-side (`q`) on the paged
tables, client-side over the visible columns on the small complete ones. Debounced, and
rendered outside the loading branch so the input does not lose focus mid-fetch. Credit
Orders now also matches proforma number and pack code.

**Filters live in the URL.** New `hooks/admin/useTableQuery.ts` syncs filters, sort, and
page to the hash query string (`AdminLayout` already routed on `hash.split('?')[0]`).
Defaults are omitted, so an untouched page keeps a clean URL. Leaving a page and coming
back no longer resets everything, and a view can be handed to a colleague as a link.

**Deliberately left on client-side sort** — `/usage-summary`, `/quotas/overview`,
`/tenant-ranking`, `/error-breakdown`. They return small complete result sets, so sorting
in the browser is truthful there; the bug was only ever sorting a truncated window.
Extractions likewise stays unpaged: the page groups failures by cause client-side, and
grouping one page would report cause counts that are simply wrong. What it gained instead
is a real `total`, so it can now say *"showing 500 of 843 — the cause counts are a sample"*
where `len(data)` could never have revealed the cap had bitten.

**Other fixes found on the way:**

- **Overview described two different periods at once.** The KPI cards called

  the last 30 days — so on the 2nd of the month the cards described one day and the charts

- **Tenant Ranking silently stopped at 20.** The endpoint defaults to `limit=20` and the
  page never passed one, so "rank every tenant" showed the first twenty with nothing saying

- **`TenantSelector` capped at 200 tenants** (the endpoint's default) — BU #201 was simply
  not in the list. Raised to 500, and it is now a native `<datalist>` type-ahead instead of
  a scroll-hunt through a plain `<select>`.
- **`/alerts`, `/jobs`, `/performance-logs`, `/sessions` reported `total` as `len(rows)`**,
  i.e. capped at `limit`, which is the bug class `count_rows()` was written for. Counted off
  the unlimited statement now.
- **Errors and Sessions were hand-rolled `<table>`s** with no sorting, paging, or search.
  Both moved onto `DataTable`; net line reduction. Email Automation's nine columns had zero
  sortable ones and now sort.

**A bug the new tests caught before it shipped:** `PeriodPicker`'s widest preset sends
"365 days ago 00:00 → today 23:59", which is **366** days of hours — but `period_hours`
was capped at a bare `8760`. So picking *Last 12 months* on Errors or Tenant Ranking would
have 422'd on the page's own dropdown, i.e. exactly the option this whole change existed to
add. The ceiling is now `_MAX_PERIOD_HOURS = _MAX_DATE_RANGE_DAYS * 24`, derived from the
day ceiling instead of written out, and asserted from both sides so the two cannot drift.

`10:50` **The suite pinned no timezone, so date tests meant different things in CI.**
`PeriodPicker`'s `today()` test asserted an ICT date, passed on a laptop, and failed on
the PR — CI runs in UTC, where the local date for that instant genuinely *is* the previous
day. The helper was right; the test had baked in the runner's timezone, and nothing in the
config said which timezone a test should assume.

`process.env.TZ = 'Asia/Bangkok'` in `vitest.config.js`, set before anything constructs a
Date. Bangkok rather than UTC because that is the offset the product runs at: every user is
Thai, and a helper that reads the *local* date is only meaningfully exercised where local
and UTC disagree — under UTC the whole class of bug (`toISOString().slice(0, 10)` quietly
asking the API for yesterday) is untestable. Verified both ways: `TZ=UTC npx vitest run`
and the ambient ICT run are both 500 green.

**Unrelated pre-existing flake, fixed because it made the suite unusable for verification:**
`useFileUpload` / `useAPExtraction` raised their `waitFor` budget to 10s on 2026-08-21, but
vitest's own per-test timeout is 5s — so the test was killed before `waitFor` could spend
that budget and the fix never took effect in a full-suite run. Both now pass the timeout to
`it()` as well.

`09:45` **Fix: every server-mode admin page fetched forever.** Caught in the uvicorn log
within minutes of the above landing — a steady stream of the same request alternating
`limit=15` and `limit=17`, on every page using the new server mode.

`useFitRows` derives the page size from the space left *below* the table, and server mode
fed that size back into the fetch. So 15 rows left room that measured as 17, 17 rows left
room that measured as 15, and the two chased each other until the tab was closed. Client
mode never had this: `perPage` only sliced rows already in hand, so nothing refetched.

The page size follows the **viewport**, not the data, so `DataTable` now keeps a
high-water mark per viewport size and only ever reports a *larger* measurement. A shrink
caused by its own rows is ignored, which makes the sequence monotonic and therefore
terminating; a real window resize clears the mark and it re-measures from scratch.

Tests: `DataTable.test.tsx` gains the invariant directly ("never reports a page size
smaller than the one it already asked for"), and a new
`DataTable.fetchloop.test.tsx` reproduces the reported symptom end-to-end —
`useTableQuery` + `DataTable` with the measurement mocked to flip 15↔17 — and asserts the
fetching settles. Reverting the fix makes that test hang, which is the bug.

## `22:30` Frontend — fix the measured-page-size fetch loop (429s on Order History)

- Symptom: `/credits/orders` hammered until rate-limited, `limit` alternating 8 / 7 / 4,
  taking `/notifications`, `/maintenance/status` and `/credits/payment-info` down with it
  (shared limiter).
- Root cause is the one `DataTable` already carried a local guard for: `useFitRows` derives
  the row count from the space left **below** the list, and where that count feeds a fetch,
  the rows it asks for change that space — n rows leave room measuring n±1, forever.
  `useOrderHistory` rebuilds `load` on every `limit` change, so each flip fired both the
  history request and the `open_only=true` one.
- Fixed in `hooks/useFitRows.ts` instead of per caller: the count is monotonic per viewport
  (a real resize clears the mark). Covers Order History, the notification bell and the admin
  `OrderTable` in one place; `DataTable`'s own guard stays (its regression test mocks the
  hook).
- `hooks/useFitRows.test.tsx` reproduces the flip-flop with a faked measurement — reverting
  the guard makes it fail.
