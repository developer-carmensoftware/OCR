the light background — the two converge to near-identical lightness in dark mode.

## `21:15` CA-34 Admin User Management (list/create/edit/deactivate + role assignment)

Jira CA-34, child of epic CA-21. Backend RBAC schema (`admin_users`/`roles`/
`role_permissions`/`admin_user_roles`) and permission seed rows already existed but had
no CRUD surface — this closes that gap. `super_admin`-only (the seeded `admin`/`viewer`
roles are deliberately excluded from `admin_users`/`roles` permissions). v1 writes only
global role grants (`tenant_id=""`); per-role tenant scoping is supported by the schema
but not exposed in the UI. Deactivation is not instant — it blocks future logins only;
an already-issued admin JWT (8h TTL) has no revocation path and stays valid until it
expires (known/accepted limitation, no revocation list built).

### Backend

- `21:15` `models/schemas/admin_users.py` (new): `AdminUserCreateRequest`,
  `AdminUserUpdateRequest`, `PasswordResetRequest`, `RoleAssignmentRequest`; exported via
  `schemas/__init__.py`.
- `21:15` `services/admin_user_service.py` (new): list/get/create/update admin users,
  password reset, full-replace role assignment, list roles. Reuses `hash_password`/
  `verify_password` from `admin_auth_service.py` rather than duplicating bcrypt logic.
  Guards: an admin cannot deactivate their own account; the last active `super_admin`
  cannot have their `super_admin` role stripped (would lock everyone out with no
  recovery path short of direct DB access).
- `21:15` `routers/admin/admin_users.py` (new): `GET/POST /admin/admin-users`,
  `GET/PUT /admin/admin-users/{id}`, `POST /admin/admin-users/{id}/password-reset`,
  `PUT /admin/admin-users/{id}/roles`, `GET /admin/roles` — all gated by
  `require_permission("admin_users"|"roles", "read"|"write")`. Registered in
  `routers/admin/__init__.py`.
- `21:15` `services/audit_service.py`: added `ADMIN_USER_CREATE/UPDATE/PASSWORD_RESET/
  ROLES_REPLACE` to `AuditAction`; every mutation writes an audit_logs row (password
  reset logs the action only, never the password value).

### Frontend

- `21:15` `lib/api/endpoints.ts` + `adminClient.ts`: new `admin.adminUsers`/`adminUser`/

Follow-up to the `18:40` badge/toast fix — an `/impeccable` audit of every `:hover`

instead of a token, so it didn't flip with `[data-theme='dark']`.

- `22:45` `styles/pages/ap-invoice.css`: `[data-theme='dark'] .ttd-trigger:hover` — added
  `box-shadow: none` to clear the light-mode black shadow the base rule still applied.

Verified: reviewed each selector's resting-state token to pick a matching hover token
(no new colors invented); no component logic touched, CSS-only.

## `23:40` Dark mode fix: square seam on step-wizard "done" checkmark

Reported bug: the completed-step checkmark circle in `StepWizard.tsx` (AP Invoice /
Credit Card wizards) showed a stray rectangular seam overlapping the icon, only in
dark mode. Isolated via one-change-at-a-time testing (box-shadow removal did not fix
it; ruled out).

### Frontend

- `23:40` `styles/components.css`: `.step.done .step-num` — `border-color: transparent`
  → `border: none`. Root cause: a transparent border on a `border-radius` element with
  a gradient background is a known Chromium/Windows rendering bug that paints a visible
  seam along the border track; removing the border entirely (rather than making it
  transparent) avoids the seam.
