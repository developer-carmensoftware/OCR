# PMS Integration — Carmen → AI (CA-93)

**Audience:** the Carmen developers wiring PMS data into the AI module.
**Status:** phase 2 (CA-119). We accept the hook and process the day it names:
1. read it from Carmen's Data Bank;
2. find the rows the BU's mapping in Carmen has no account for, and suggest them;
3. have **Carmen's own PMS engine** post it (`interfacePostGL`), or park it for the BU to
   review.

Debit, credit and the counter line are Carmen's config, never ours (decision-log #43). What we
still need from Carmen is in §7.

When a day of PMS data lands in Carmen's Data Bank, Carmen sends us a short hook that names
that day. It carries no PMS data: we read the day back from the Data Bank ourselves
(`GET /api/interface/PMS/{InterfaceName}/{DocType}/Date/{DocDate}`). That is the whole
integration for now: one URL for the hook, and a key per BU and PMS that your PMS setting
screen generates through our Settings API (§2, §6).

---

## 1. Endpoint

```text
POST {base}/api/v1/pms/events
```

| Environment | `{base}` |
|---|---|
| QA / dev | `https://carmen-ocr-backend-xntb.onrender.com` |
| Production | sent together with the production keys |

The URL is the same for every BU. The key tells us which BU an event belongs to; the body
never names one.

## 2. Authentication — one key per BU and PMS, generated by your PMS setting

```text
Authorization: Bearer cpk_…
```

Your PMS setting screen (one per BU and PMS) generates the key by calling our Settings API
(§6), stores what we return, and sends it on every hook of that PMS. Nobody copies or pastes a
key, and nobody hand-picks the BU: the call is proven with the user's Carmen token, and the key
belongs to exactly that (host, BU) and PMS (decision-log #44).

**Rules:**

- A key is returned once, by `POST …/carmen/pms/keys`, and we keep only a hash. If it is lost,
  generate a new one.
- **One live key per BU and PMS.** Generating a new one revokes the old one at once, so store
  the new key before you send the next hook. A hook in flight with the old key gets `401`;
  resend it with the new key.
- **A key is for one PMS.** A hook whose `InterfaceName` names another PMS gets `403`, compared
  without case (`Comanche` = `comanche`).
- `Bearer ` is optional. A bare `Authorization: cpk_…` works too.
- Keys do not expire. **Revocation** (`DELETE …/carmen/pms/keys`) is immediate and is how a
  PMS is switched off. A revoked key gets `401`.
- Server-to-server only, over HTTPS. Never put the key in a browser or a URL.
- Our admins can also see and revoke any BU's keys (`#/admin/api-keys`), for support. They
  cannot generate one: your screen is the only place a key comes from.

## 3. Request body

```json
{
  "InterfaceType": "PMS",
  "InterfaceName": "Comanche",
  "DocType": "Daily",
  "DocDate": "2026-10-07"
}
```

| Field | Type | Rule |
|---|---|---|
| `InterfaceType` | string | `PMS` on this endpoint (`pms` also works). |
| `InterfaceName` | string, 1–40 chars, no `/` | The PMS, as in the Data Bank (e.g. `Comanche`). |
| `DocType` | string, 1–30 chars, no `/` | As in the Data Bank (e.g. `Daily`). |
| `DocDate` | **ISO date string** | `"2026-10-07"`. A datetime such as `"2026-10-07T00:00:00"`, `…+07:00` or `…Z` also works; we take the date part. |

**What we accept, so your client's defaults do not matter:**
- field names in any case: `InterfaceType`, `interfaceType` (.NET `PostAsJsonAsync`), `interfacetype`;
- extra fields, which we ignore;
- any `Content-Type`, since we parse the body as JSON regardless, with or without a UTF-8 BOM;
- `Authorization: Bearer …`, `bearer …` or the bare key.

**What we refuse with `422`, because a guess could record the wrong day:**
- **`DocDate` that is not an ISO date string.** A number such as `20261007`, `"07/10/2026"` and
  `"2026-10-7"` are all refused: they are ambiguous, or would be read as a timestamp.
- **Invalid JSON.** That includes a trailing comma, as in the first sample we were sent.
- **An array.** Send one hook per day.
- **An `InterfaceType` other than `PMS`, or a `/` in `InterfaceName`/`DocType`.**

The hook carries no PMS data, so no guest data travels through it; the figures stay in the
Data Bank until we read them. The maximum body size is 16 KB.

**Send `InterfaceName` in one casing.** The key accepts it in any case, but the day's row is
keyed by the name as sent, so `Comanche` and `COMANCHE` would make two rows for one day.

**One BU, one day, one row.** The four fields identify a Data Bank day. A second hook for the
same BU and day lands on the same row: we answer `200` and record when we last heard of it.

## 4. Responses

| Status | Body | Meaning | What Carmen should do |
|---|---|---|---|
| `202` | `{"id": "<uuid>", "duplicate": false}` | A new day for this BU, recorded | Done |
| `200` | `{"id": "<uuid>", "duplicate": true}` | This BU and day were already recorded; we noted the repeat | Done |
| `401` | `{"detail": "Invalid API key"}` | Key missing, unknown or revoked, or the BU is disabled | Do not retry. Check the key. |
| `403` | `{"detail": "This key is for PMS 'comanche'"}` | The key belongs to another PMS than the body's `InterfaceName` | Do not retry. Send this PMS's own key. |
| `413` | `{"detail": "..."}` | Body over 16 KB | Do not retry as is |
| `422` | `{"detail": [...]}` | Body invalid: not JSON, a field missing or misnamed, `DocDate` not a date, `InterfaceType` not `PMS` | Do not retry. Fix the body. |
| `429` | `{"detail": "Too many requests — please slow down."}` + `Retry-After: 60` | More than 120 requests a minute from one source IP | Wait `Retry-After` seconds, then resend the same body |
| `5xx` / timeout | — | Our side failed | **Retry with backoff, same body** |

Any `2xx` means "we have it". A retry of the same body is answered `200` with the same id, so
retrying is always safe.

**Pacing.** The limit is 120 requests per minute per source IP, shared by every BU your server
sends for. For a backfill (many days or many BUs at once), stay under 2 requests a second.

**A `422` names the field.** Real bodies:

```json
{"detail":[{"type":"missing","loc":["DocDate"],"msg":"Field required", ...}]}
{"detail":[{"type":"value_error","loc":["DocDate"],"msg":"Value error, DocDate must be an ISO date string, e.g. \"2026-10-07\"","input":20261021, ...}]}
{"detail":[{"type":"literal_error","loc":["InterfaceType"],"msg":"Input should be 'PMS'","input":"POS", ...}]}
{"detail":[{"type":"json_invalid","loc":[],"msg":"Invalid JSON: trailing comma at line 1 column 97", ...}]}
```

## 5. Test checklist: run these before going live

These use the QA URL and a key your PMS setting generated for Comanche (§6). Replace `cpk_…`,
and use a **`DocDate` you have not used before** for step 1. Every step must give exactly the
status shown.

```bash
URL=https://carmen-ocr-backend-xntb.onrender.com/api/v1/pms/events
KEY=cpk_…
BODY='{"InterfaceType":"PMS","InterfaceName":"Comanche","DocType":"Daily","DocDate":"2026-10-07"}'

# 1. A new day                       → 202 {"id":"<uuid>","duplicate":false}
curl -s -w ' %{http_code}\n' -X POST $URL -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d "$BODY"
# 2. The same day again              → 200 {"id":"<same uuid>","duplicate":true}
curl -s -w ' %{http_code}\n' -X POST $URL -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d "$BODY"
# 3. A wrong key (yours + one char)  → 401 {"detail":"Invalid API key"}
curl -s -w ' %{http_code}\n' -X POST $URL -H "Authorization: Bearer ${KEY}x" -H "Content-Type: application/json" -d "$BODY"
# 4. DocDate missing                 → 422 … "loc":["DocDate"] …
curl -s -w ' %{http_code}\n' -X POST $URL -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"InterfaceType":"PMS","InterfaceName":"Comanche","DocType":"Daily"}'
# 5. Another PMS with this key       → 403 {"detail":"This key is for PMS 'comanche'"}
curl -s -w ' %{http_code}\n' -X POST $URL -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"InterfaceType":"PMS","InterfaceName":"Opera","DocType":"Daily","DocDate":"2026-10-07"}'
# 6. After DELETE …/carmen/pms/keys (or a new key), step 1 with a new day → 401
```

Then send from **your own code** (not curl) for one real day, and check step 1 and step 2 give
202 and 200. Your HTTP client's defaults (content type, name casing, BOM) are covered by §3.

## 6. Settings API — your PMS setting screen

Your PMS setting screen sets two things for one BU and one PMS: **auto-post** and the **hook
key**. There is no settings page of ours to link to (decision-log #44).

```text
{base}/api/v1/carmen/pms
Authorization: <the user's Carmen token>
```

**Call it from your server, not from the browser.** Our CORS policy admits only our own app's
origin, so a request from a page on your Carmen host is refused by the browser. From your
server, mind the limit: **20 requests a minute per source IP** (300 a minute overall), shared by
every BU that server handles; a 21st answers `429` with `Retry-After: 60`. One screen visit is
a GET, and a save is one PUT or POST, so this is room for about 20 screen actions a minute.

The token is sent the way every Carmen call sends it, with no scheme. Send the **non-expiring**
token, the same kind as in the menu link: every write stores it as the BU's credential, which
is what we read the Data Bank and post with (decision-log #42: one per BU, shared with email
automation). We prove it against `uri` on every call. Show the screen only to users your own
permission model allows; we check no roles of our own.

| Method | Path | Body or query | Answer |
|---|---|---|---|
| `GET` | `/settings` | `?uri=&bu=&pms=` | `200` the settings below |
| `PUT` | `/settings` | `{"uri", "bu", "pms", "auto_post": true}` | `200` the settings below |
| `POST` | `/keys` | `{"uri", "bu", "pms"}` | `201` the settings below, plus `"api_key": "cpk_…"` **once** |
| `DELETE` | `/keys` | `?uri=&bu=&pms=` | `204`, or `404` when this PMS has no live key |

- `uri` is your Carmen origin (`https://hotel.carmen4.com`), as sent to `/auth/exchange`.
- `pms` is exactly the `InterfaceName` your hook sends (1–40 characters, no `/`). We compare
  it without case.
- **Auto-post** defaults to off: every day waits for a person in AI JV Automation. On, a day
  whose rows your mapping already covers posts by itself; a day with a new row still waits.
- **Please tell your users, on this screen,** that the AI reads the day's figures (rows by code
  and amount, no guest data) to suggest accounts. A BU that uses only PMS never opens our app,
  so it never sees our AI consent notice.

```jsonc
// the settings
{
  "pms": "comanche",
  "auto_post": false,
  "key": {"prefix": "cpk_Ab12Cd34", "created_at": "…", "last_used_at": "…"},  // null when none
  "has_credential": true   // false: nothing can be read or posted until a write stores a token
}
```

`key.last_used_at` answers "is my hook arriving?". A BU that never opened the AI app is
registered by its first write (`PUT /settings` or `POST /keys`); before that, `GET /settings`
answers the defaults above with `has_credential: false`. Errors use the email Settings API's shapes: `401` with "please
re-login to Carmen" for a token your Carmen refuses, `502` when we cannot reach it, `422`
naming the field, `429` with `Retry-After`.

## 7. Open questions for Carmen

Tracked in CA-116, with what we found on the dev Data Bank:

1. **Settled (2026-10-14):** the AI maps, Carmen posts. The day goes through
   `interfacePostGL/REVENUE`, by the BU's PMS setting and its mapping table in Carmen.
2. **A GET for the setting and the mapping on `/api/interface`** (blocker). The menu's token
   opens only `/api/interface/*`, and `interfacePost/Setting` and `interfacePost/mapping`
   have no GET there. Without one, an unattended day cannot know what to map or which
   setting posts it.
3. **The token we use to read the Data Bank and post,** per BU, with no user session. It
   needs to last longer than a few hours, and to hold `Inf.PMS.DataBank` View (a menu user
   without it gets 403).
4. **The JV number** in `interfacePostGL`'s answer. Today it says "Posting complete." without
   it.
5. **What a repeat hook means.** Is the hook sent on Add *and* on AddOrUpdate? Is a second
   hook for the same day a changed day that we should process again?
6. **Is the gross Summary line intended?** For Comanche it is 2 × Guest Ledger to the
   counter account, against the Guest Ledger row's credit.

generated through `routers/pms_carmen.py` (one live key per tenant and PMS,

`pms_events`, unique on `(tenant_id, event_id)`. There `event_id` holds the day's key

`updated_at`. Code:
`backend/app/routers/pms.py`, `routers/pms_carmen.py`, `services/shared/api_keys.py`.
Processing (CA-119) lives in
`services/pms/`:
- `carmen_config` reads Carmen's PMS setting (the INI in `ConfigBase64`, the mapping key, the
  file layout);
- `mapping` holds the AI's picks for rows Carmen's table cannot place;
- `process` is the job, and posts through Carmen's engine;
- `review` handles approve/reject. Approve writes the mapping table back whole, because
  Carmen's PUT replaces it.

The Carmen calls are in `services/shared/carmen.py` (`get_pms_settings`, `get_pms_mapping`,
`put_pms_mapping`, `post_pms_gl`). Every call uses the BU's stored Carmen credential (#42),
stored by the Settings API's writes (#44). Decisions:
[email-automation decision log #39 to #44](email-automation/06-decision-log.md). Our side in full:
[`pms-interface/`](pms-interface/README.md).
